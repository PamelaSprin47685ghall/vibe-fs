# context-compression — WHY

总流程里“把一件事真正做完”的那朵浪花：长任务的过程性输出会不断堆积，模型需要一条由自己掌握的清理边界，同时不能被系统猜测的容量数字牵着走。

模型能容纳多少历史并不可靠可知。禁止宿主推导窗口与剩余预算、禁止请求前预测溢出，只披露已发生的计量和 provider 声明的常量，是为了让容量猜测不变成新的控制权；真实的 provider attempt 失败是唯一的恢复触发信号，恢复因此有界、可解释。

`resetScope` 把长程任务组织成显式的工作闭环：模型自己判断当前目标是否已完成、下一阶段需要什么，因此重锚由模型发起。最新一次 reset 之前的普通工具过程与旧 Scope 思考退场，真人操作员消息、assistant 正文与关键咨询调用按原序保留，形成明确的因果脉络；旧 Scope 里下一阶段仍需的关键事实（函数签名、报错堆栈、精确行号）由模型逐字抄进 `oldScopeVerboseVerbatimExperience`，保证认知连续而不必靠重抄历史。

计费回合估计是模型求助的通道：如实报数，数字降不下来时系统安排 Advisor 专席；报 0 才持续催重锚。没有已确认估计时只催首次报告，不伪造余额、不催重置，因此冷恢复不会把编造的数字变成控制权。

重锚前必须先落盘不可变的出站档案，再原子提交 `ScopeReanchored`：回问前任 Scope 要靠这份档案真实重构旧模型的上下文，无档案的成功重置会造出无法回答的问题。宿主自动 compaction 允许存在但只记 `ContextReanchored`，因为它改写的是传输视图，不代表工作阶段结束。
