# participant-identity — WHY

模型和会话都是执行手段，不能回答这段工作由谁承担、继承了谁的身份。把身份锚定在 logical participant run 上，才能在重试、恢复和更换物理执行时保持同一责任关系，也能在旧工作结束后让同一容器承接真正的新身份。

Role、Persona 和来源版本共同解释一个参与者。若由不同模块分别保存，恢复就可能拼出一份从未存在过的身份；若身份先于 root 接受独立持久化，崩溃又会留下没有权威来源的身份。因此，解析由身份所有者承担，安装与接受同一项工作共享原子事实。

派生工作的身份需要可核对的 owner 证据。物理父节点只能说明 Host 如何组织容器，模型目标只能说明谁执行计算，两者都不能证明人格继承或授权关系。显式证据使错误 owner、过期 run 和缺失来源可以被拒绝，而不靠缓存补齐。

历史身份用于解释过去，活跃身份用于决定今天能做什么。两条路径混用会使旧记录在重放时悄悄获得新权限。稳定的角色标签和版本化来源让恢复保留原事实，不把实现重命名误当成身份变更。

内部机制也有自己的身份与生命周期，但它们的存在不等于增加公开角色或扩大调度权限。将内部身份、公开身份和物理资源分开，才能让 system prompt 表达真实参与者，而不是当前模型配置。
