# change-integration — WHY

## 领域价值与核心矛盾

在多任务并发执行中，多个独立的 Manager 工作在各自的 worktree 中独立成熟，最终必须将成果合入同一个共享的目标分支（如 `master`）。

核心矛盾在于：**如何既保证并发分支进入共享目标时的原子性与因果一致性，又不通过粗暴的全局长事务锁破坏多任务的并行演进**。若全局加锁，长 review 与冲突修复将迫使所有任务完全串行化；若缺乏原子发布门禁，并发提交将相互覆盖，破坏共享代码库的稳定性。

## 核心不变量

1. **发布生命周期完整性**：变更进入目标 ref 必须经历 candidate 产生、变基（rebase）、变基后双重验证（post-rebase review）、短锁检查并交换（CAS）与快进发布的完整链条。
2. **唯一短临界区（Integration Gate）**：全局门禁仅在向目标 ref 推进指针的原子操作窗口内持有，严格禁止在 review 或冲突修复等长耗时阶段持有门禁。
3. **干净工作区准入（Clean Gate）**：编排器受理请求前工作区必须处于 clean 状态，严禁隐式 stash 或猜测用户意图。
4. **门外冲突解决与身份连续**：冲突检测后在原有 worktree 中由原 Manager 解决，完成后重新进入发布循环，不重置执行主体。
5. **基于事实的重放恢复**：崩溃恢复仅依赖不可变的持久化事实与目标分支的当前现实，严禁依赖文件系统残留推测进度。

## 破坏后果

- **并发提交覆盖**：多个任务并发推送共享分支导致提交丢失或快进历史断裂。
- **并发性能雪崩**：长时间审查与冲突排查持有全局排他锁，导致所有独立道路被动串行化。
- **不可判定与幽灵状态**：恢复时根据磁盘未追踪文件猜测状态，导致未经验证的代码意外合入主干。
