# verification-system — WHY

## 不可替代的存在理由

「测试通过」是最容易被伪造的信号。一个损坏的系统可以通过多种虚假方式呈现为「绿灯」：
- 静态门禁扫描了不存在的路径或空目录，造成恒真假象。
- 测试套件入口未正确接线或产物陈旧未更新，实际并未执行。
- 断言仅验证真值（truthy），字段重命名或缺失返回 `undefined` 时静默通过。
- 看门狗计时器被底层的传输噪声或背景无关事件持续续期，挂死时无法触发。
- 盲目调大超时阈值或采用重试直至通过（repeat-until-pass），掩盖了并发竞态与死锁。
- process-isolated runner 把叶子测试预算施加到整份测试文件，使健康断言因模块加载与调度竞争被误杀。
- release sink 与 integration orchestrator 重复调度同一 package suite 或物理 warmup，使一次验收执行两遍同一昂贵步骤并产生两个 owner。
- 测试直接断言内部实现细节或模拟桩迎合错误实现，失去了对真实契约的证明力。
- interleaving helper 在进入 production 前按测试自建 prerequisite graph 拒绝输入，再把该 helper rejection 冒充 production fail-closed。
- 验收标准事后缩水，在未达成既定目标时单方面放宽通过条件。
- 设立机械行数上限或空心扫描器门禁，将伴生表象误作缺陷根因，诱导代码恶意碎片化以迎合检查。
- 日志观察器发生多字节截断、提前消费未换行残片、误将散文关键字识别为领域事实，或在多写者交错、文件替换与前缀截断时静默吞没异常。
- 验证调度器在长时序阶梯推进中未锁定输入基线，使得执行期间并发改动或环境污染悄然混入，产出虚假的有效性报告。

`verification-system` 的核心存在理由是：**把「什么构成有效证明」本身变成被严格检验和证明的元规则。** 证据必须分层，验证必须真正具备失败能力（可红性），时序推进必须确定且可重放，并在遇到未知或损坏状态时严格 fail-closed。

### 关键机制的存在理由

- **禁止机械行数检查（[012]）**：代码行数只是演进过程中的伴生表象，绝非缺陷根因。门禁系统一旦设立机械的行数硬门禁或 advisory 扫描器，不仅无法识别真实架构腐蚀，反而会逼迫工程人员通过伪拆分将原本高内聚的业务语义切碎为无意义的胶水文件与脆弱间接层，严重增加系统的偶然复杂度。验证系统必须通过明确的架构命名约束与语义边界守卫代码质量，坚决禁止设立任何基于行数指标的形式主义门禁。
- **日志观察器因果消费与完整性（[015]）**：测试与运行期的时序推进和挂死判定，必须完全建立在底层不可变事件流（Journal）的保真观察之上。若日志观察器在监听事件流时未严格进行行缓冲、因多字节 UTF-8 编码切割而提前提交残片、把散文描述中偶然出现的关键字误判为领域 Fact，或在遭遇多写入者交错、底层文件替换与前缀截断时未抛出异常，整个验证体系就会建立在被污染或不完整的时序证据之上。日志观察器必须作为不可妥协的因果消费看门人，确保每一条被消费的事实具备绝对的完整性、唯一性与确定性。
- **验证输入快照与运行时扰动拦截（[016]）**：证明的有效性完全取决于「被验证的对象在整个多阶段验证生命周期内保持物理不可变」。如果在 format、check、build、unit、integration 直至 e2e 的漫长验证阶梯推进期间，源码、脚本、规范、资源或配置在后台被并发任务或脏环境悄悄篡改、新增或删除，即便后续测试全绿，所证明的也是一个现实中从未完整存在过的虚幻混合状态。构建与验证调度器必须在执行前捕获完整的输入快照与内容摘要，并在执行全过程中对任何外部扰动进行实时拦截与安全失败（fail-closed），彻底封死虚假有效性报告的出笼通道。

## 核心张力与分层治理

各业务产品包拥有其特定领域事实的证明义务，但它们不应自行发明独立的证据评级与门禁机制。`verification-system` 集中管理通用的验证法域与证据阶梯：
- **纯逻辑命题**使用确定性的纯函数与代数属性在毫秒级内完成证明；
- **组合输入空间**可用属性生成扩大搜索域，但 generator 不拥有 oracle；命题关系必须独立给出，断言必须消费注册 production Surface；
- **时序与交互命题**通过虚拟时钟与确定性调度在 Temporal 层完成验证，禁止依赖真实环境墙钟的偶然性；
- **物理世界契约**严格限制在单一真实适配器与恰好一个 Long Stroke 验收入口中，杜绝使用昂贵且脆弱的端到端测试替代本应在底层证明的语义分支。

这种分层治理确保了验证体系在保持极高运行效率的同时，提供坚不可摧的正确性背书。

## 依赖关系

**DEPENDS ON** `requirement-system`

证明体系必须建立在明确的规范所有权之上：只有当每个断言有唯一 owner、每个命题有唯一规范合同时，系统的证明资格与证据满足性判定才具有确定性语义。

## 核心不变量与违约状态（RED）

仓库处于 RED 状态，当且仅当出现以下任一破坏证明有效性的违约：
1. 证据金字塔层序在配置或运行器中被随意颠倒或跳过。
2. 静态门禁指向不存在的文件路径，或门禁执行失败时未将非零退出码向上传播。
3. 看门狗由非因果的底层传输噪声或背景进展续期，或依赖单一的绝对墙钟超时作为挂死判据。
4. 单元与集成测试直接依赖真实墙钟进行时序推导或竞态验证。
5. 门禁或测试断言在重构中被实质性弱化，或测试覆盖率分母因未加载模块而失真。
6. 测试越过公开语义契约面，直接侵入底层实现内部。
7. 同一 release leaf step 被顶层 sink 与子 orchestrator 重复调度，或没有唯一父级负责其失败传播。
8. 门禁系统设立基于物理行数、文件长度或代码体积的机械硬门禁或 advisory 警告，或仅为展示政策存在而设立无真实语义判定能力的机械扫描器。
9. 日志观察器未按完整行结束符提交位点（如截断多字节 UTF-8 或未闭合行）、将散文正文字符串误识为领域 Fact、在遭遇格式损坏、标识冲突、底层文件标识替换或消费前缀被截断时未严格抛出异常中止（fail-closed），或破坏多写入者交错下的单调位点前进语义。
10. 构建与验证调度器未在执行前捕获完整输入快照与哈希摘要，或在验证推进全过程中对源码、脚本、规范或配置等输入的运行时改写、新增或删除未能即刻拦截并以非零状态中断退出（fail-closed），产出输入不一致的虚假通过报告。
