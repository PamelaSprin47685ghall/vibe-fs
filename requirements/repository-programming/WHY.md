# repository-programming — WHY

仓库修改要同时照顾表达力与保守性。局部小改若必须重建整份文件，模型就要承担不必要的定位与保全文本责任；`cat` + `where`/`whereAll` + `slice` + 一次 `write` 的组合让常见改动保持精确，快照与整文件重写为结构重排和计算变换保留完整表达力。

可见成员与实际权限一致，执行者才能按工具面工作，不必猜哪些示例能跑。所有角色共用同一套文件原语与事务边界，换角色或换入口不改变授权与文件保护。

一个程序可能同时影响多个文件。逐笔原子落盘让失败有明确后果：已发生的写是事实，未发生的不存在；冲突时保留第三方修改并报 `FILE_CHANGED`，比自动重读重跑更尊重真实的并发工作。崩溃留下的无 Committed 配对 Prepared 只说明中断，不能代替用户再次授权操作。

近似诊断（`nearest`）能减少恢复成本，但相似文本不能确定要改哪里。诊断可以宽容，写入仍依据精确、唯一或明确声明的全部匹配；诊断本身有界，避免一个小错误制造大段噪音。

事务为检测冲突会读许多执行者并未实质使用的文件。若把这些读取全部写进案例关联，后续复用会被搜索噪音污染。快照、显式访问与已提交效果分开记录，才能说清一次工作实际依赖和改变了什么。

物理终止必须让事务先完成必要结算，否则还原依据可能丢失，第三方修改也可能被覆盖。同一故障只有一条终止责任链，避免重复退出与相互掩盖的诊断。

命名程序与 park/unpark/abandon 把长命令、用户往返与多步派工从单次工具调用里解放出来：等待是真实暂停，恢复回到原现场，交付前未结清的程序按名字暴露给 Work 终局。
