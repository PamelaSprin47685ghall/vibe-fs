# repository-programming — WHY

## 不可替代的存在理由

可编程 repository 变换若拆解为多套独立 RPC（如独立的 read、edit、write、glob、grep 接口），路径边界检查、文件系统沙箱、结果渲染、权限控制、状态快照与事务语义将被重复实现并不可避免地发生语义漂移。

`repository-programming` 将一次模型调用定义为一个受 capability 约束的完整程序：批量读取、批量内存变换与批量写入在单个事务边界内完成。模型可见的编程 surface 必须与运行时实际执行能力严格同构：

```text
If a method is present, the capability exists.
If a method is absent, it does not.
```

模型无需解析复杂的权限矩阵或记忆“文档存在但运行时不可用”的隐式规则，工具面本身即为能力的直接投影。

但“可编程”本身不能成为把机械负担重新甩给模型的借口。若一次单行修改仍要求模型手算
offset、拼接整文件、处理重复片段并自行发明失败恢复协议，那么强模型虽能完成，较弱模型却
会把大量智力浪费在本应由 Host 拥有的确定性工作上。这个包因此同时维护两条不可互换的路：

- **常见修改走窄而安全的高层路**：模型只声明当前文本 `find` 与目标文本 `put`，Host/SDK
  负责唯一性、重叠、快照与单次 staging；
- **复杂变换保留无上限的低层路**：模型仍可用 `file(matches)`、anchor slice、任意 JavaScript
  与 `rewrite` 构造完整目标文件。

前者让 easy things easy；后者确保 hard things remain possible。高层路绝不能靠静默模糊匹配
换取表面成功：不确定时必须拒绝写入，并把当前证据与可直接修正的下一步交还给模型。

## 核心不变量

1. **能力即投影**：编程 SDK 基类、工具描述与示例代码由当前 Attempt 的 `ToolCapabilitySet` 机械投影生成，不存在第二份 role→permission 权限矩阵。
2. **沙箱无 Ambient OS 权限**：用户程序运行于隔离环境中，无法直接访问底层 OS 文件系统句柄、网络、进程或环境变量，所有 I/O 必须通过显式注入的数据与受控原语完成，且受硬性超时与输出尺寸约束。
3. **All-or-Nothing 事务语义**：所有写入操作先进入内存 staging；成功前真实文件系统保持不变。多文件修改在单个原子事务中提交，任一文件校验或写入失败导致全局零提交。
4. **单一 EventStore 事实源**：事务的持久化 Prepare 与 Commit 事实严格经由统一 EventStore 提交，禁止任何专有的 feature-level 存储或旁路状态。
5. **确定性串行化与冲突检测**：单次模型消息中的并行工具调用在 Host 侧按确定性顺序逐个执行，每次调用基于最新提交快照验证。若读取快照后目标文件被外部修改，立即判定冲突并 fail closed，绝不执行隐式重试。
6. **渐进式编辑能力**：普通替换、插入、删除与全匹配修改不要求模型重建整文件；结构重排与算法化变换仍可下沉到 anchor + `rewrite`，两层共享同一事务与权限边界。
7. **宽容输入、保守落盘**：可恢复的常见调用形态错误可以规范化；近似文本只用于生成诊断，绝不自动成为写入目标。

## 违背边界的破坏形态 (RED)

- **能力脱钩**：生成的 SDK 出现当前 Attempt 未被授予的方法（如无 Edit 权限却生成 `rewrite`），或通过手写变体绕过权限门禁。
- **沙箱逃逸**：模型程序获取宿主环境权限（如直接 `require('fs')` 或发起外部网络请求），或因死循环/超大输出导致宿主挂起。
- **事务撕裂**：多文件编辑中途出错导致部分文件已写入磁盘而部分失败，留下不一致的工作区，或在崩溃后无法通过 EventStore 正确审计恢复。
- **静默覆盖 (Lost Update)**：外部并发修改被基于旧快照的提交无感知覆盖。
- **低层回退**：工具描述未能有效传达高级原语的不可替代性，导致模型退化为手工字符串切片、正则猜测与多轮修补。
- **易事过度编程**：已知旧文本与新文本的一次局部修改仍被迫通过整文件拼接完成，导致缩进、换行、重复片段或遗漏上下文错误。
- **模糊成功**：工具把“看起来相近”的文本当成真实目标并静默写入，或失败只返回“not found”而不给当前片段、候选位置与原子性后果。
