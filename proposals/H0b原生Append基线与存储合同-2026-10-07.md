# H0b-C0：原生 Append 基线与后续存储合同

## 认领与范围

从 `4c251754b` 接续08卡。本包只补原能力的正式前提证明，并重写H0b后续分包；不修改生产Store、HostAdapter或017，不新增无人消费的fresh API。依据 sphinx-v2[010,019,034]、durable-events[013,017,019,020,024]、durable-convergence[004,010,011]。完整H0b、034和真实首答案继续开放。

原生 Append 在 native lease 内验证本实例 Current，再追加、提交 Current、释放锁；它没有在每次取锁后刷新其他 handle/process 的事实。`Ok + Cuts=[]` 同时可能表示新增事实和 exact replay。持锁与 raw Append 成功本身不能证明首次接纳。

正式010沿原 seed 建 inquiry/round/work/预留/lease：两个实际handle先读同base、seal同intent不同command，依次原Append；另用两个自有OS子进程和IPC固定双方seal完成后才go。独立cold运行原Canonical Integrator，保合法双头DomainConflict，不挑最后写者。exact同event重复追加核零新字节；changed-same-id负控复用既有正式019，不复制一套oracle。

本包已有限验收。gen267完整Sphinx＋convergence004＋durable017＋JS002＋requirement017，**29/29文件、308 pass、0 fail、0 skip、14 TODO**，2.94s wall/15.42s test；退出1仅pending，group34224 accepted=true/15.621ms。Fable、完整check、前后freshness通过。生产已有行为直接满足基线，无虚假业务红，不声称尚不存在的guarded入口已重复发送Host。

正式runner不输出成功leaf的diagnostic正文，另定向原生运行两叶补收实际身份：2 pass、0 fail、0 skip、0 TODO、exit0。parent34402；双handle cold34404；双进程coordinator34407、writer34408/34409、cold34412，原IPC轨迹sealed/sealed/go/go/appended/appended。此次仅为保存身份收据，不作为碰运气重跑。完整raw bytes由正式断言逐writer核验，完整事件id/轨迹见[证据目录](archive/2026-10-07/h0b-c0/)，SHA256绑定原件。H0b-C0只有限完成，完整010/034及后续许可能力未销项。

## 必须保持的合同

| 边界 | 已有事实与约束 | 不能据此推出 |
| --- | --- | --- |
| 原 Append | native lock、单实例gate、原PrepareLive/物理追加/CurrentCommit/typed Release | 旧Current在另一writer推进后仍fresh，或成功必然新增 |
| ReloadLocal | 原canonical reader/validator/replay替换唯一Current | 与下一次admission同lease，或返回可复用read-set证书 |
| stat/fingerprint/cache | 可提示部分Changed，供同步缓存使用 | 内容等价、变化完备、Unchanged授权 |
| Current reference | 可防本engine的旧prepare提交 | 跨process真实输入未变 |
| 原24小时retention | 整writer按统一cut保留；等于expiry仍retained | 相关证据退出窗口后永久去重 |

fresh read-set必须由原EventStore/Integrator owner从真实canonical read产生。至少绑定同一Current身份、真实store、完整writer发现边界、已验证内容及所需payload closure、同次统一retention cut和下一expiry。被排除writer的再次活跃、新writer、替换/删除及时间回退均不能漏掉。物理部分留原runtime私有，不让Sphinx读文件或另fold，不造第二Current、registry或durable generation。

只允许本次原锁下真正新增、原Current完整接纳、无相关cut/fork且Release成功的结果授本地one-use许可。existing exact只返回原binding或Pending，receipt丢失零重发；changed full request拒绝。Unknown、未写、无新写Release失败、cut、StorageInvalid及freshness不可证均零许可，复用U0既有类型和mandatory owner。Host effect在释放原锁后执行，claim后取消/异常/Unconfirmed不能恢复许可，冷启动不能从Pending重铸。

## 下一包C1：同lease首次激活的有限正控

先确认有真实有限消费者。若当前只能造无人消费的API，就只保合同和前提测试，先做C2能力调查。工程签名可以按现规范决定；涉及改变corruption检测或工作寿命时先由owning requirement定合同。

1. 在原owner内把首次实际业务激活的canonical read、唯一Current发布、同步纯准入、原append/commit放进同一native lease。禁止锁外Reload后重新取锁，禁止外层持锁递归Append。
2. supplied callback只见本次readonly Current和原完整request，不取得Append、payload写入、Host、网络或异步能力。复用原Sphinx admission与Codec.seal，不能提前seal旧head后盲用。
3. 在原owner复用appendValidated/Prepared/settleReleased；先定bounded契约，再串行迁移factory与deferred装配。旧Reload若仍可换Current，必须同时让任何新witness失效，不加第二semaphore掩盖所有权。
4. positive必须实际新增指定primary fact、完整cold Current一致、真实Host Create/Send非零。两个OS child同intent竞争只一份fresh许可，loser exact Pending零Host。
5. exactduplicate、changed request、旧handle、Unknown、cut、cold Pending、重复claim全部拒绝新许可。Host pending期间第三writer仍可Append，证明锁已释放。
6. 显式统一cut覆盖等于expiry、越界、excluded writer重新活跃及Journal ObservedAt/cut-tail活动语义。缺work或相关fork不能猜成可派发。
7. 首次激活的真实历史读取作为020成本单列；完整调用成本也列出，不能每dispatch重建handle伪装一次性activation。原activated Append的017-I0回归保留。

验收至少按实际改动覆盖010、durable006/013/017/019/020/024、convergence007/011。如需改旧ReloadLocal形状门禁，同包用原cold Current/注册必要性/late insertion/expiry/cut行为对照替代，不能单删门禁。此包完成只称同lease首次激活的有限接纳，热H0b、第二binding gate和installed Host仍开放。

## 下一包C2：跨lease热freshness的能力裁决

当前缺的是可证明的变化完备性，不能只把stat装进opaque type后改名authority。调查结果允许是能力仍未取得；此时入口保持拒绝，不实现假的Unchanged。

1. 对Linux/macOS分别列具体native primitive、建立时点、内容/名字/替换/删除覆盖与跨process同步fence。overflow、丢事件、重建、路径替换或通知无法fence时明确Unavailable。普通fs.watch/FSEvents安静不是正控。
2. 若改用封闭append-only mutation假设，逐项核原Store/Hook如何维持它、外部非法前缀改写如何拒绝；对照StorageInvalid及cache非权威条款。需要缩窄规范时先改owning requirement，不由实现默许。
3. 在原lease内正规refresh实际read/validate/publish并产生内部witness；caller固定原完整request。再次取锁仍核那枚witness和实际输入，期间变化即拒绝，不重新绑定当前command/work，不fallback raw Append，先不加自动retry。
4. 正式矩阵覆盖refresh后另一writer推进、新writer/替换/删除/追加、excluded reactivation、payload closure损坏、retention越界/时钟回退和Unavailable。只证明Changed负例不足以证明Unchanged；必须有独立可信正控。
5. 若选择增量canonical refresh，先证明原ordered prefix稳定。late insertion、ready key变化、整writer expiry/external parent、identity/cycle/cut必须与原唯一Integrator对照。当前KWayMerge无续接frontier，不能suffix直接PrepareLive或另写业务fold。
6. 用017原meter核完整调用的旧bytes/decode/fold、新fact/payload与Git，不能清零昂贵阶段后报告合计，也不以walltime或扩大预算证明。

完成标准：选定且证明真实authority后，才认领生产热路径；否则交付具体缺失能力、可继续调查的原语和有限C0/C1结论。跨retention永久去重若确需，先定工作/权限寿命或合法持久证据合同，不能偷加永不清理表。
