## 结论与第一步

现有 `PromptPhysicalAcceptance` 已是这项物理观察资源的唯一模块，能够在原模块内加入 opaque registration lease，不需要另一张全局 registry、另一套 journal/fold、业务阶段或新的 durable fact。

但是现有 `cancel key` 不是退订：它同时删除当前 callback 和确认 waiter，并把 waiter 结算为 `Rejected "Cancelled"`。call 结束时不能调用它来解除本地 observer，更不能调用 Dispatcher.Abandon。最小退订操作必须只 compare-remove 自己那次注册，不改变 durable Pending/Submitted/PhysicalAccepted，也不结算其它 owner 的 waiter。

下一包先冻结“注册资源”和“确认等待”的各自所有权，再做 effect-before-registration-handoff 接线。只改 register 的返回值而在 Send 内丢掉 lease，不能完成 call 资源闭环；在 Sender 内 `use` 到 Detached 返回即释放，同样不合法。

## 应冻结的最窄 registration 合同

建议公开 `register : PromptKey -> (PhysicalUserMessageId -> unit) -> opaque IDisposable`。该 lease 只表示一次真实进程注册，不是流程 continuation 或 claim 生命周期。

1. 每次 register 创建不同 registration token，即使 key 和 callback function instance 都相同也必须不同。
2. registry 在原模块中保存 `{ token; callback }`；现有“一 key 当前一个 callback”行为不在本包扩成 multicast。
3. Dispose 幂等、同步、无 durable effect。只有 map 中仍是自己那个 token 时才移除 callback；否则 noop。
4. Dispose 不触碰 confirmation waiter，不调用 cancel/rejected/Abandon，不写 journal，不重发 Host。
5. accepted 按原 owner 原子取出当时的 callback registration 和 waiter；通知一次。后续旧 lease Dispose 不能删除同 key 的新注册。
6. 不用 callback 引用相等作为 token。相同闭包重注册仍是新资源世代。
7. lease Dispose 与 accepted 的取出有明确线性化点。accepted 已取出资源时，简单 unregister 无法撤回已在执行的 callback；A2 的 callback 必须捕获具体 call 并检查其本地存活/所属资源，不能再查询 session 的当前 call。不能承诺“Dispose 返回后全无在途 callback”而没有相应同步证明。
8. 旧 registration 被新 registration 替换，旧 lease 的释放必须 noop。这个保护解决清理跨世代；它不自动证明两个 owner 都收到了通知。需要同时观察的场景另有合同，不能在本包暗造多订阅。

## sender → call 的 handoff

call 必须在 Host effect 前拥有真实 register 返回的 lease。可冻结一个窄的 acceptance observation 参数，包含实际 physical callback 和同步接收 lease 的 capability；sender 注册后立刻把 lease 交给该具体 call 的资源作用域，再调用 Host。

不要在 `onSendObserved(Sending key)` 再建第二份注册，它会覆盖 sender 本来的 callback。不要在 Detached 结果返回后才补 registration；fast ingress 会丢通知。不要将 typed lease/native registration identity 改成 callback 函数地址、字符串编号或 mutable current-session lookup。

接收 lease 的 call scope 必须处理“已结束后才 Attach”：立即 Dispose 这份 lease；Attach 与 Close 由同一物理资源 owner 排序。资源作用域可以保存当前 call 拥有的有限 observer handles，但不保存执行阶段、重试程序计数器或新的 durable authority。具体 callback 捕获具体 call，对 accepted successor 做本地归属登记；call 结束只释放自己的 handles。

不能仅更新 Send 两处而留下 Fork reattach 按全 key cancel。register 返回类型变化影响这三个实际 owner；需一次改完所有消费者并证明 Pending reattach 不会被函数返回释放。

## confirmation waiter 的独立问题

当前 `awaitConfirmation` 按 key 共用 TCS，但每个 caller 有自己的 timeout。任一 timeout 会调用全 key cancel，从而删除当前 callback，并将其它 caller 共用的 waiter 结算为 Cancelled。该源码事实已确认，本轮没有执行反例。

不能给 observer lease 增加一个“Dispose 顺便 cancel waiter”的捷径。确认等待是不同的资源，必须有自己的 invocation 身份：

- 一个 caller timeout 只返回自己的 unknown，不把 timeout 变成拒绝/Abandoned，不否认实际 accepted truth。
- timeout 的 cleanup 只能释放该次等待的订阅，不能移除后来创建的 waiter 或 callback。
- 若保留共享 per-key TCS，需要区分每个 waiter invocation 的存活；一个 invocation timeout 不拒绝其它 invocation。
- 接收 actual accepted/rejected 仍由原 key-resolution owner 广播给当时尚存的等待者。
- 最后一个确认等待结束时，可归还进程 waiter 资源；不能连带释放还在等待真实物理 ingress 的 Detached/call observer。
- 没有等待者时 actual ingress 仍正常 persist/accept，resource absence 不应改变业务结果。

这项与 callback lease 不同，建议独立正式小包；如果 A2 接线仍沿用旧 timeout cleanup，不能宣称 observer lifetime 全闭合。

## callback throw 的明确剩余边界

当前 accepted 在锁内删除 callback 和 waiter，锁外先调用 callback，再 SetResult waiter。callback 抛异常会使已删除的 waiter 永不结算；durable accepted 已发生，不能造 Refused/Abandoned 来掩盖。

最小 owner-safe 方向是保证原 waiter 无论 callback 是否抛错都按 actual accepted 结算（例如 owner 内 `try/finally`），同时按明确异常政策保留/传播原 callback 异常。不能由 Surface facade catch 后伪造成功；也不能移动 accepted 的持久化时点。是否向注入 incident/report capability 报错须依现有 owner 合同，不在本卡新造政策。

D0 只证明 nonthrowing observer。本项需要正式反例与 owner 修复，作为 A2 完整接线前的前置或独立包；不以本文记录冒称关闭。

## 正式 red / positive 矩阵

使用已有真实 DispatchSurface send + `acceptManagedPromptClaim`，callback 内读取 `Execution/Session/ChatExecution/StatusSurface.query`，journal snapshot/bytes 来证明 truth。thin fixture 只暴露 opaque lease 与真实模块调用，不读 private dictionaries，不直接调用假的 accepted writer。

| 场景 | 必须证明的公开结果 | 证明边界 |
|---|---|---|
| effect 前 register；真实 managed ingress | exact native physical 一次回调；callback 内 accepted=true；Host 一次 | 复用 D0 正控，保持原兑现时点 |
| Unknown 后结束 call / Dispose observer | journal bytes 不变；仍原 key Pending；后续真实 ingress accepted，已结束本地 call 无通知或结果改变；不重发 | Dispose 是资源退订，不是 Abandon |
| Dispose observer，另 owner 正在 awaitConfirmation | 实际 ingress 仍结算确认为 exact Accepted physical | 不误清其它 waiter |
| 同 key L1 → L2；Dispose L1 | L2 在实际 ingress 得通知 | compare-token，旧 lease 不能清新 registration |
| 同 key、相同 callback instance L1 → L2 | Dispose L1 后仍通知一次 | 防 callback-reference 身份替代资源世代 |
| accepted 后建新 registration，释放旧 L1 | 新 registration 不被旧释放清掉 | 不将已经 consumed 的 lease 再解释为 key owner |
| Dispose 同一 lease 两次 | 两次均无 journal effect、无其它资源清理 | 幂等 |
| 两个 confirmation invocation，一短一长 | 短的 unknown；同 key observer 与长的 waiter 仍能被真实 ingress accepted | 现有公开 API 可执行的主要 business red；不用缺新 API 充红 |
| 旧确认 timeout cleanup 与新 register | 新 registration 和新 confirmation 不被旧 invocation 清理 | 需要受控任务结算/确定 timer；不能碰运气重跑 |
| callback 抛异常，另 owner waiter 存在 | actual durable accepted 不倒退；waiter仍 exact Accepted 结算；原异常按 owner 政策处理 | 现有 callback/Await API 可写 business red；不是 facade swallow |
| 当前明确 Refused | actual Abandoned；晚 actual ingress 按现行协议拒绝，不通知 | 保留 D0 现有 Refused 正控；不扩称整个 WHAT009/GAP137 late-fatal 已闭合 |
| call A 结束，same child call B 开始，旧 A successor 晚到 | B 不被旧 callback/terminal 结算；合法 B successor 能结算 B | A2 producer causality 主包，不由 lease 单包关闭 |

### 现有能力能构造的精确首个反例

已有 F# public contract 是 `PromptPhysicalAcceptance.awaitConfirmation : PromptKey -> int option -> Task<PromptPhysicalOutcome option>`；当前编译导出为 `dist/Interaction/Dispatch/PhysicalAcceptance.js` 的 `PromptPhysicalAcceptance_awaitConfirmation`。typed key 可用 `Foundation/Identity` 已公开的 `PromptKey.create(sent.key)` 构造；当前 JS 导出 `PromptKeyModule_create`。不是猜 DU 字段或伪造 acceptance evidence。

测试薄夹具只需把实际 awaitConfirmation 的 typed Accepted/Rejected/None 显式编码为 plain DTO，不能改变任务或 settlement：

1. 复用 D0 `prepareAcceptanceObserver`，真实 Detached send + Some observer，取得实际 sent.key，Host SDK task 保持 unresolved。
2. 对这个同 key 启动两个实际 awaitConfirmation，显式短/长资源 timeout，例如 100ms 与 2000ms。等待短的返回 Unknown；这不是时间充当身份，测试正是在证明 timeout 不能修改其它资源/事实。
3. 立刻核对 durable claim 仍 Pending、journal bytes 未改变，seen 仍空。
4. 用原 key 经 `acceptManagedPromptClaim` 提交真实 physical；StatusSurface accepted 必须为 true。
5. 长 waiter 应为该 exact physical 的 Accepted，原 observer 应通知一次；旧实现实际会为 Cancelled 且 observer 被清掉。这是现有行为主红，不能以扩大资源 timeout 绕过。
6. actual ingress 后 SDK task 以 receipt 释放，不再产生新的 accepted writer。每个 key 必须最终 actual accepted 或 definite refused。

callback-throw 首红也可用现有 `sendAgentOwnerRootWithAcceptance(..., "Await", throwingCallback)`：Host 返回 receipt，实际 managed ingress 在 durable accepted 后触发该 callback；原确认 waiter 不应因 callback 异常悬空/再给 AcceptanceUnknown。正式夹具须对已拥有的 waiter 做 plain outcome 映射，并保留 callback 原异常政策；不要把“provider send task 抛错”偷换成这条反例。

## 规范依据与不能混淆的边界

- dispatch-protocol-003/004：receipt 不等于 physical，兑现必须来自真实物理证据。
- dispatch-protocol-007/008：Unknown 保持 Pending 原 key，不自动重发；不以时间替代身份。
- dispatch-protocol-009：Detached 不等待 physical/provider；解除资源不能把返回改成等待。
- dispatch-protocol-013：wall clock 不推进事实。
- delegation-025：具体 call 的因果身份；到达时序不代身份。
- delegation-026：Unknown/confirmation timeout 保留 Pending；不得伪造失败或发布 join ghost task。
- structured-workflow-001/003/005/008/009/013：原生资源作用域、真实资源世代、局部同步、透明作用域、取消不伪造业务终态、窄 capability 边界。

本卡不要求新增全局 registry，不要求 schema/Journal 改动，不恢复第二套 fold，不借 resource lease 修三类 producer 的来源丢失。producer effect 前绑定与 actual successor 归属仍按 `/private/tmp/vibe-fs-n06-b1-a2-handoff.md` 及 transport 的穿透卡另行施工。
