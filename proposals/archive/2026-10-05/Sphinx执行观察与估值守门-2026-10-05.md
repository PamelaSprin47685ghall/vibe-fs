## 生产行为与边界

B1-A在原 SyncDelegateRuntime 上增加 typed Admission/Completion。原 dispatcher 在真实 SendPrompt 前记录 Sending，在原生任务返回后记录 Answered，保留实际 PromptKey 与 SendOutcome。NotDispatched、Refused、Unconfirmed、Accepted 分开；同样的错误文案不能替代原生 verdict。只有原发送 owner 成功且有已持久化的 exact physical/root 才发布 Accepted；形似 message id 的 receipt 仍等待真正 PhysicalAccepted。正式响应保存实际 session、physical、root、provider run 与本次正式文本，排除 reasoning/tool 材料，并在原工作流及 checkpoint 完成后交付。没有新 listener owner、timer、执行 registry 或持久程序状态。

原字符串接口仍从同一次 terminal capture 投影文本。新观察接口的 preparation 异常直接拒绝，不把原 charge 当备用 prompt 发出；旧普通接口的既有 fallback 保留。Host Promise 真正抛错时保留 Sending 的实际 key，发布 Unconfirmed/无原生 outcome，不伪造 Fatal 或“确定未发送”。Dispose 测项只证明已接纳后本地等待失败与订阅释放，不证明物理 abort/drain。

SettleCompletedFromTurn 原来按 session peek 任意 call，能接受错误 root、旧 physical，并重复覆写响应。现在先核已接受 root 与现有 belongsToCall，再同步 pop 该 call、结算一次。普通旧 physical、错 root 与重复 fallback 的正式红绿已建立；恢复 continuation 的完整归属另见下段。

**B1-A2仍未修。** belongsToCall的同root+continuation-kind分支只有分类，没有当前assignment来源；child复用同root时，旧retry/guard/repair仍具备被新call认领的条件。现retry fixture只更新readiness，尚不能提供真正canonical successor的业务红灯。本批不以观察API或普通physical反例关闭025/T111/GAP-153。下一步在effect前绑定具体call，沿三个producer传回真正PhysicalAccepted；晚acceptance也不能转移到复用后的call。[活动接手卡](../../TODO施工分册-2026-10-03/07-Sphinx恢复因果.md)列出具体签名、Detached/AlreadyAdmitted前提和正反例。Sphinx实际Host接线须在A2后进行。

## 014成本oracle与真实退化变异

旧gen149并行墙钟973.2ms>500ms与隔离绿色原样保留。本批没有放大500ms、总预算或静默预算；改为证明WHAT014要求的实际算法工作量，墙钟继续作为诊断。

同一原生merge owner、同一ready heap，在每次真实ready-cursor pair比较时加一，返回decimal string诊断。旧merge/mergeRetained结果形状不变，没有第二算法或按N/K伪造计数。正式fixture仍512 writers×16 events=8192，先深比较完整native envelopes、数量与唯一性，再查比较次数。每次push至多H次、pop至多2H次，H=ceil(log2 512)=9，界为3NH+2K=222208。

真实变异只将生产heapPop改为对现有ready entries用同一计数比较器Sort、取首项；push/readiness/身份/DTO完全保留。gen153全部8192事件正确，actual comparisons=3605957，只有复杂度断言红；整叶234.281ms仍低于历史500ms，说明墙钟不能独立证明复杂度。源码patch、原函数与恢复patch均归档，随后手工恢复原heapPop，gen154宽选集通过。正常紧凑reporter没有打印成功diagnostic，不捏造normal精确计数。
