# K1 路径别名与 finally 只读审计

日期：2026-10-08。读取时 HEAD 为 b85533202，工作区干净。本记录只读源码、WHAT 和现有正式测试；未改仓库、构建、运行测试、暂存或提交。下述“预计红/预计绿”都是待执行判断，不是验证结果。

## 结论

1. Fetch single-flight 的 workspace 身份目前没有路径归一。相同实际目录通过不同字符串绑定时，可能各建一个 flight；Store 的引用检查无法跨两个 key 生效。这是明确源码线索，正式业务红尚未取得。
2. Git common-dir 的成功路径有 realpath，但它只用于取得 Store，并不归一传给 Fetch 的 workspaceRoot。不能把“同 Store”推成“同 flight”。
3. finally 的 Remove 已存在，原 callback 返回、抛错、普通 Unknown 的对外结算均有独立正式证明；这些证明都未覆盖相同 key 在该结算后的重新准入。普通成功路径已有弱的顺序执行证明，不能称所有 finally 组合均未证明，也不能称已完整证明。
4. 建议下一包先做 K1-A：相同实际 Store、两个 required owner、真实目录别名的 single-flight 正式回归及局部归一。它与 finally 的 K1-F 组合分开交付，避免借测试补证暗改更多生命周期。

## 原调用链与身份

- `src/Wanxiangshu/OpenCode/Host/PluginHost.fs:41–51`：input.directory 只做非空检查，原字符串成为 workspaceDirectory。
- `OpenCode/Plugin/PluginBoot.fs:73,128`：保存该 workspaceDirectory；`PluginHooks.fs:187–190` 将同一字符串传给 CasebookTools.buildSpecs。
- `Repository/Knowledge/Casebook/OpenCode/Tools.fs:23–25`：分别执行 `WorkspaceEventStore.acquire(RuntimePath.gitCommonDir workspaceRoot)`，以及 `FetchTool.spec factory workspaceRoot store owner`。前一个 commonDir 结果没有成为后一个 workspaceRoot。
- `Persistence/Journal/RuntimePath.fs:47–53`：Git 答案缓存也以输入 workspace 字符串为键。`gitCommonDir:72–77` 成功时执行 Git common-dir → 相对路径 resolve → realpathSync；Git/resolve 故障则直接返回 workspace，realpathSync 失败则 canonicalPath 保留已有 path。这是既有容错，不能描述成所有输入必然 canonical。
- `OpenCode/Host/WorkspaceEventStore.fs:65–83`：registry 直接按 commonDir 字符串查找，返回同一个 entry.Store；registry 自身不做 realpath。共享引用成立的前提是上游真的给到相同 commonDir 字符串且 entry 尚在。
- `OpenCode/Tools/FetchTool.fs:38–39,129–139`：全局 flight 字典键为 `string * string`，内容为实际 `IEventStore * Task<string>`。键严格是 `(workspaceRoot,shelfmark)`；同键且 `ReferenceEquals(boundStore,store)` 才 join；同键异 Store 拒绝。owner 不入键，保首执行者的 owner/Task。
- `Repository/Knowledge/Casebook/FetchSurface.fs:12–20`：只从 opaque EventStoreHandle 取 `.Store` 并转发；Surface 不归一、不做另一 flight。把同一 handle 交两次确实取得同一底层 Store。两个分别创建的 writer/port 即使指同一目录，也不是同 Store。
- `CasebookFeature.isEnabled`（Workflow.fs:19–23）只 pathJoin marker；文件读取沿 Capture 的 workspaceRoot。marker 存在不等于 workspace 身份归一。

因此：真实 Git checkout 的 canonical root、symlink root、相对 root 可以取得相同 commonDir/同 registry Store，但 Fetch 仍按三串不同键执行。非 Git 临时 fixture 的 commonDir fallback 还可能产生不同 Store；若测试要专验 Fetch alias，必须显式共用同一个 actual Store，不能先创建两 writer 再声称它们相同。

commonDir 不能直接替换 Fetch workspace key：两个真实 Git linked worktree 共享 commonDir，却有不同的物理工作文件状态。Fetch 的 diff 必须仍归本工作区。Store 身份和 workspace 身份是两件事。

## 下一最小工作包 K1-A：相同 Store 的工作区别名

预计 35–50 分钟（含 root 按原流程构建/正式验证），先取业务红，再改生产。最小源码范围为 FetchTool.fs 及正式 011.test.mjs，施工卡/总计划由 root 更新；若保同签名，无需新 Surface/领域 owner/state 或工程依赖。扫描器仅按真正新增调用登记，不能给路径豁免。

正式回归优先从 011:48 双 required owner leaf 复用小型 helper，保所有原 leaf 断言，不全量重写：

1. 创建一个实际临时目录、marker、实际 Store、Case 和 baseline；只创建一次合法 `createAppendPayloadStore(base,false,observer)`，两工具传同一个 shared handle（严格同引用）。两个 required owner 保持不同实例。
2. 单独生成别名，不预先归一要交给 Fetch 的字符串。三叶可为 physical absolute vs literal `${directory}/.`、physical absolute vs `relative(process.cwd(), directory)`、physical absolute vs 实际 symlink。`path.join(directory,'.')` 会先归一，不能用它假装别名反例。relative 不需要全局 chdir；symlink 位于本 fixture 自己的 temp 父目录内。
3. 前提先 assert 两输入字符串不同且 `realpathSync(alias) === realpathSync(directory)`；marker 两边可见；同一 subject.txt 读取完全相同。保同 Store handle，不额外打开第二 Store。
4. 写 version-C，首工具进入原 Bookkeeper SendPrompt barrier；先核 create1/program0/append0，再启动别名工具，立即给两个调用装 Promise.allSettled，随后放行同一 barrier。不用 sleep，不等待旧实现不一定能给出的第二 barrier。
5. 对外必须两个结果相等且是实际维护答案，Bookkeeper create/program 各1，实际 Refresh1、Access1，零 incident；检查精确原请求/durable facts、completion baseline不变/maintenance更新。别名在旧实现分 key，预计会出现第二 Bookkeeper/差异结果或额外 append；以实际首红为准，不预填具体失败次数/原因。
6. finally 无条件 release → await allSettled 两工作 → reset runtime → dispose shared/base → 删除自己创建的 symlink/目录。不处理未知路径。
7. 修复只在 Fetch spec 绑定边界捕获一次物理 workspace root（既有 node:fs realpathSync 足够）。该绑定应同时用于 flight key、marker 和后续 diff 文件读取，避免 canonical key 与 raw symlink I/O 指向分裂。不用 Git commonDir 当工作区 key、不把 owner 加 key、不把不同 Store 放并行 key，也不新增 global fallback。relative 在构造时绑定，不能随以后 cwd 改变。
8. 先明确 realpath 失败行为，沿当前 constructor/装配异常合同处理；不要 catch 后静默退回原字符串，再宣称 alias 已闭合。当前产品入口本来只应绑定真实存在目录；本有限包不擅自改全仓 PluginHost 输入合同。
9. 重建只用 `node scripts/build.mjs`；正式完整 011/013 加相关 005/015、JS002/requirement017 和仓库要求的边界门禁。保所有 skip/TODO；预算不变。直接绿的控制不是业务红。

边界：本包证明 Fetch 同物理工作区的三种别名；不证明任意 Git commonDir fallback、case-insensitive filesystem、symlink 运行中 retarget、工作目录移动、跨 linked worktree 合流、跨进程 Store registry 或 installed Host。真实 linked worktree“commonDir相同但根不同”宜保为后续显式负控，不能借 commonDir 修复误合流。

## 后续独立有限包 K1-F：原结算后的相同 key 再次准入

这包预计已有保护直接绿，不能用无测试 API/编译失败或主动抛错冒充旧产品业务红。先补正式回归，若直接绿便如实登记已有保护；如需证明 oracle，可由 root 独立精确移除 finally 的 Remove，取变异红，再逐字节恢复重建，变异红与原业务红分开。

最窄两叶：committed malformed Access 首次 cut × required owner 返回/throw。没有 Refresh/异步 Bookkeeper也能证明 owner异常之后 finally；若希望共享 waiter组合，应另用原 SendPrompt barrier 的 Refresh叶，不把单 waiter 扩称双 waiter。

可直接借既有 `EventStore.Surface.createAppendPayloadStoreAt(base,1,observe)`（Surface.fs:393–399）：只第一 append坏payload，后续同一个 Store对象恢复原合法请求。该能力已有正式 durable024用途，不需要新 API。

1. 原 Case/version-B不变化，单一 shared handle、同 workspace/shelfmark，两次 Fetch传完全相同实际 Store引用。首 Access实际 committed cut，先保存旧Case/baseline/index及canonical前像；callback返回拒绝原incident，callback抛错拒绝原sentinel。首坏fact/cut-tail/原incident前提逐项先核。
2. 首 Fetch 已结算后才启动第二 Fetch，同 key、同 shared Store，可用新 explicit owner以避免误把曾经认领事件与新工作混为一谈；两 owner须保不同引用。第二调用应真正执行一条合法 Access、零 Bookkeeper/Refresh，返回原答案fresh。observer必须增加一次且新eventId不同于首坏eventId，payload合法/零Cuts；首incident callback仍一次，second owner零 callback。这证明没有返回首Task缓存/首拒绝，也没有重投旧cut。
3. Casebook IntegrationRules.ApplyCut（:27）保 last-good projection，故合法 Access跟在已结算 cut后是明确可执行保护前提；它不是重新Refresh/重发旧坏fact。第二条合法Access允许推进accessOrder，不能要求整Case所有字段不变。首Capture/completion/maintenance/Q&A与前像前缀保留，原cut内容不变，index行为按实际Access合同核，不乱加“所有文件字节不变”。
4. 若改用首 Refresh cut，第二次前须把 subject 恢复到旧baseline，使第二工作仅合法Access；不要让同一个未变化 malformed=true wrapper再产生另一个cut，或把反复刷新作为finally证明。
5. Unknown emptyCuts 再入单列一叶：原 fault handle 的 Commit fault是每次PrepareLive都注入（Surface.fs:195–207），不是 fail-once。首Refresh实际Unknown后恢复subject到旧baseline，第二同key/同Store实际Access也可能再次Unknown emptyCuts；正常fresh与第二真实Access事实可以证明再次准入，但不得宣称第二次提交成功/Current推进。cold应沿真实durable Refresh＋Access重放，不能沿旧V单Refresh oracle原样套。为控制范围，优先交两条committed cut的finally保护，Unknown矩阵后包。
6. 双 waiter throwing callback 是另一个真实欠组合：W/U已有双 waiter returning callback，013有单 waiter throwing callback，尚未共同证明同一个callback sentinel被两个waiter收到。可以随后给 W/U helper显式callbackThrows参数补两叶，仍保真实settlement/cold并严格同sentinel；不能靠分层证据直接销项。

K1-F 不需要第二 Store。若为验证“旧entry已释放后可以重新绑定不同Store”另外创建合法新 capability，必须明确它是顺序新binding，不能称同Store重入；当前建议完全不做这项。也不把 finally 清理与能力物理 dispose、owner 全生命周期、资源泄漏或 full013混在一起。
