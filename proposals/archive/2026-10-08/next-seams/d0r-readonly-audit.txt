# D0-R 原 shared Store 接缝审计

2026-10-07。只读源码与既有证据；未修改仓库、运行构建/测试或执行故障注入。本卡是下一包方案，不是已取得的运行证据。

## 结论

现有公开能力不能直接完成「原 SessionDeleted → 原 shared Store 的本次 Capture 产生真实 cut → 同 Scope Dispose 拒绝」。缺的不是第二个 runtime 或另一套结算算法，而是 **WorkspaceEventStore 首次登记唯一 entry 时的受控 append 端口装配**。物理 Release 的原生故障接缝已经存在，可以复用；语义坏输入必须进入真实 `ICanonicalIntegrator.PrepareLive` 之前。

仅在 fs.writeFileSync、appendFileSync 或 Release 上做 ordinal 故障，最多证明实际 I/O 失败/Unknown，不能保证本次 `Prepared.Cuts` 非空。合法 Casebook producer 的 Capture payload 当前不会自然触发 Casebook decoder cut。不得改写磁盘后让下一次 reload 发现坏事实，冒充本次 live settlement 的 cut。

建议先做一个受限的共享 entry 装配能力，再执行 committed-cut / actual-Release-Unknown-cut 两叶，带合法和合法-Release-Unknown 控制；不改 HostSessionDeletion、Casebook、Store 或 fatal 决策算法。预计默认原链已有 typed throw 和 owned-work drain 保护，应先实测，不预设业务红。

## 当前真实调用链与所有权

1. `OpenCode/Plugin/SpikePlugin.fs:createRuntime` 只装配一个 `PluginBoot.Boot` 和 `PluginRuntimeScope`；`PluginLifecycleSurface.create` 借用的就是它。
2. `PluginBoot.create → PluginHost.createJournal → acquireWorkspaceJournal → WorkspaceEventStore.bootPort`。`WorkspaceEventStore.acquire` 按 git common-dir 在唯一 `shared` 字典创建 `SharedEntry { Store:IEventStore; RefCount }`。
3. `WorkspaceEventStore.deferredStore` 只有一个 lazy `EventStore.createLocal`，一个随机 writer 和一个 `CanonicalIntegrator.createWithRules hostProgram`。hostProgram 包含原 Journal、Strength、Sphinx、Casebook、JS 规则。
4. Journal boot 持有 entry.Store；`PluginHostWiring.tryFinalize → acquireFinalizationStore → WorkspaceEventStore.acquire` 再取得同一个 entry.Store。它不是另开 writer，也不是重建 Current。
5. 原 child/owner `hooks.event(session.deleted)` 经 `HostSignalBootstrap.onSignal` 同步 `HostSessionDeletion.prepare`，然后同 scope `RunBackground` 依次等待 `finalizePreparedDelegate → tryFinalizeWithin → CasebookLifecycle.tryFinalizeDraft`。
6. Lifecycle 原 `tryTake` draft、Drain observations、原 Bookkeeper active-owner 准入、CreateSibling/SendPrompt/Completion、`freezeCompletionState → archiveCase → Workflow.finalizeCase → CasebookStore.appendCaptured`，最后才调用上述 Store.Append。
7. `Store.appendOwned` 是 acquire gate → validate → `PrepareLive` → physical append/fsync/close → Commit Current → Release → typed settlement。Release forward 后抛原 Error 时，fresh write 得到 `CommitUnknown { Prepared; Primary.Phase=StoreRelease; Cause=原Error }`。
8. `CasebookStore.appendEvent` 保原 EventId/AppendError；`Lifecycle.archiveCase` 交 `PersistenceFailed`；`PluginHostWiring.tryFinalizeWithin` 在 ordinary catch 之外调用原 Boot 的 `CasebookSettlementOwner.Observe`。
9. 原 owner 只从 matching Casebook cut 构造 `CasebookSemanticCutIncident`，先调用 mandatory `bindCasebookSemanticCut`，回调返回后仍抛 incident。同 Scope `CaptureBackgroundFailure` 留原异常；`DisposeAsync` 等 owned drain 并在安全 cleanup 后拒绝。本包只用一个业务失败，不把已登记的多失败优先级缺口扩成 first-cause 保证。

## 现有接缝能做什么、不能做什么

| 现有能力 | 能证明 | 不能冒充 |
| --- | --- | --- |
| EventStore Surface `createAppendPayloadStore` / `At` | 包装同一底层 IEventStore，改真实请求 payload，原 Integrator 生成真实 bad fact/cut-tail；保原请求和原 Error observer | 返回的新 wrapper 不会替换 WorkspaceEventStore 已登记/已借出的 Store；手传它给 finalize helper 不是 SessionDeleted 链 |
| `WorkspaceEventStoreSurface.acquire` | 获得原共享 IEventStore 的不透明观察入口 | 当前并非 EventStoreHandle，也无合法原位改 Append 的 API；不可在 JS 读取或替换编译对象字段 |
| 原 fs + syncBuiltinESMExports 的 scoped Release 注入 | 只对实际 common-dir 的 lock、实际 Capture append/fsync/close 后 Release forward-then-throw，保原 Error | `WritePayload` 也持同锁，不能凭 lock-release ordinal 猜它是 Capture；不能坏 RuntimeStarted 或其它 Journal append |
| `createWithCurrentCommitFault` | 独立 store 的真 pre-Current Unknown | 新建 writer/integrator，不能借来当原 workspace entry |
| D0-G helper + 原 plugin fixture | 真实工作、删除、Bookkeeper、Capture 与 Dispose 等待；gen306 已有去 owned await 的精确变异红 | 不证明 physical fatal、last writer ref、private Bookkeeper physical retire、exact identity closure |

源码没有名为 `AppendPayloadWrite` 的生产符号。需区分 `IEventStore.WritePayload`、`IEventStore.Append` 的 event.Payload，以及 `ProcessEventLog.AppendAllText`，三者的失败意义不同。

## 最小可手工实现的接缝

### A. 唯一 entry 的首次装配，由原 WorkspaceEventStore owner 执行

在 `OpenCode/Host/WorkspaceEventStore.fs/.fsi` 提取 private entry 创建共用体：默认 acquire 原样使用 identity decorator。新增仅供本程序集 Semantic Surface 使用的内部首次登记函数，类型边界可为：

```fsharp
val internal acquireInitialAppendPort:
    commonDir:string -> decorate:(IEventStore -> IEventStore) -> IEventStore
```

要求在同一个原 gate 内检查 `shared` 尚无 entry；已有 entry 必须拒绝，不能覆盖或局部换指针。函数自身调用原 `deferredStore commonDir` 恰好一次，将 `decorate` 返回的端口作为唯一 `SharedEntry.Store` 登记。不给调用方传入任意 store/factory，不新增第二 registry，不改公开 plugin input/default 行为。该 internal 函数由同程序集 `WorkspaceEventStoreSurface.fs/.fsi` 组合，JS 只收到 opaque probe handle，不接触 IEventStore 或字典。

与整个 Boot 增加可选 Store 参数相比，这个接缝更小：D0-G 已有 `beforeCreate`，在真实 decoy 写完后、原 plugin create 之前准备唯一 entry 即可；随后 `SpikePlugin.createRuntime`、Journal、Strength、Casebook 的 acquire 都沿原 registry 获得同一端口。不得在 plugin 已 boot 后替换 entry。

### B. 复用原 payload decorator 共用体，按真实请求选中 Capture

现 `EventStoreSurface.createAppendPayloadStoreWhen` 的 selector 只看到全局 ordinal，不能识别原请求。D0 原 shared store 会有 RuntimeStarted、admission、terminal、cleanup 等 append，不应硬编码“全局第 N 次就是 Capture”。

最窄扩展是把这一个共用体的选择器改为接收 `(ordinal, 原 EventEnvelope list)`，旧 bool/At 公共 API 继续包原选择规则；增加一个 Surface 窄入口供 workspace probe 复用。probe 只计实际 `EngineerCaseCaptured` 的 matching ordinal，选择第 1 个 singleton Capture（decoy 已在 probe 安装前完成）。其它 batch 原样转发，mixed batch 不得被笼统改坏。onAppend 必须记录原全局 ordinal、matching ordinal、原 DTO、实际 settlement；父测试再核 selected case identity/EventId 恰为 D0 原 Engineer。没有假 Prepared、假 Cut、第二 settlement 算法或 mirror Current。

建议 JS 面是 `prepareAppendPayloadProbe(commonDir, eventType, matchingOrdinal, malformed, onAppend)` 及只读 `isCurrent(probe)`/`disposeProbe(probe)`；只有有限的首次登记/观察职责。若工程希望更窄，可固定该新入口为 Capture，而不要发展为通用故障框架。matching ordinal 与实际全局 ordinal分开命名，不把前者谎称第 N 次全 Store append。

probe 的 lease 只释放自己一次 acquired reference；不得循环调用原 release 清空他人引用。当前生产 grep 中 WorkspaceEventStore.release 仅由其 Surface 调用，不能借本测试补造 last-reference 关闭证书或顺手改 refcount 生命周期。独立子进程结束可隔离该测试期 registry，物理 Store 每次操作的 lock/FD 仍须真实排空。

现 owner 工程：`Wanxiangshu.Owner.host-boundary.opencode-host-workspaceeventstore.fsproj`；原 EventStore Surface 在 `Wanxiangshu.Owner.durable-events.runtime.fsproj`。前者新增 Surface 调用后需要显式 project reference，落地前核实际 DAG 和架构门禁；不可把 Workspace/OpenCode 依赖倒灌进 EventStore core。默认生产 WorkspaceEventStore 无需引用 JS Surface，只有同 owner 的 probe Surface 组合它。

### C. 原物理 Release，按真实 append 因果武装

沿既有 native fixture：patch 自己进程的原 fs，forward `appendFileSync` 后只认自己 common-dir 下 writer NDJSON 中的 selected original Capture EventId（cut模式同时实际有 cut-tail），记录其真实writer路径；随后实际 open/fsync/close与owner.json.pid/锁路径正控通过，才在紧接的该 owned Release 完成 `rmSync` 后抛同一 Error。不能从第几个 fs.rmSync 猜归属，不能在此前 WritePayload release 注入。

onAppend 在消费者拿到 settlement 之前只记录/核物理事实，不抛 fixture assertion去遮产品结果。正式父测试应先完成物理与独立 cold 前提，再断言 typed结果。Error identity与 Prepared identity必须在同一进程检查，跨进程只传明确 boolean收据与完整可序列化 DTO。

## 正式最小矩阵与 oracle

复用原022 D0-G完整前提，不调用 stage/notePrompt/noteAnswer，不手工设置 owner/profile。切勿把同目录另一个 EventStoreHandle传给finalize。

1. 合法正常：一次原Capture，Dispose fulfilled，index推进，hot/cold合法新案；原decoy、terminal、旧bytes保持。
2. 合法真实Release Unknown：Prepared.Cuts=[]，原cause/StoreRelease/事件身份保留，零casebook-semantic-cut报告，不能自动重投Capture。**此故障发生在Current已经commit之后，hot可能已出现新案，cold也应重放新案；不能沿用CurrentCommit-before失败的hot旧案oracle。** index不因failed settlement被当作成功归档推进。
3. 坏payload committed cut：真实目标bad fact+Casebook cut-tail，旧Case与原Journal已接纳/terminal事实保持，新目标不进入Case Current/index；原owner报告一次，同scope Dispose拒绝原typedincident，重复同dispose Task给出同异常且零新append。
4. 坏payload真实Release Unknown cut：同上，incident.failure保原CommitUnknown、exactevent/Prepared/Cuts/cause；不得降为普通Unknown结算或普通成功，不自动发第二次Bookkeeper/Capture。

每叶原SDK barrier和owned等待仍使用D0-G已证策略；formal必须记录已进入目标Append、实际writer/lock/FD结算，普通控制不能仅检查字符串。cold用原Canonical replay，核整个canonical字节映射、两Case、相应head/heads、旧非空payload、目标bad/cut原fact。Casebook `ApplyCut=current`，不得清空Journal或删旧case。

## Fatal 与身份边界

原 `PluginBoot.bindCasebookSemanticCut → Diagnostic.fatal → FatalProcess.kill` 会在 Observe 中执行物理退出，然后才有 owner 的 raise。当前原 plugin fixture 明确设置 `WANXIANGSHU_NO_FATAL_EXIT=1`。D0-R可以沿这一既有明确抑制证明“原report + 原typed throw → RunBackground → Dispose拒绝”，不需要新callback或重绑owner；必须标明 **不证明物理kill，也不证明kill等待完整Scope drain**。要做无抑制的physicalfatal应另立native child包，不能把两种生命周期的证据相加。

knowledge013要求有committed/unknown cut evidence、mandatory capability和单次incident。EFP006要求fatal遵守对应phase结算依赖，EFP007禁止Unknown当未发生或自动重投；managed021还要求对应exact settlement/child drain/durableclosure。上述抑制fixture只补拒绝传播，不能授予所有phase/fatal资源顺序。

managed022仍写exact Inspector及Finalized/NothingToFinalize释放、其它状态保留；现生产按Engineer draft归档并新增PersistenceFailed，`DropSessionIdentity`本身no-op。现有卡已明确这是条款/取证carrier边界，不能从这次caseIdentity或子sessionid推导durable exact closure，不能恢复ActiveLogicalRun、重建Inspector或另造registry。

## 文件范围与停止条件

预计源码限 WorkspaceEventStore.fs/.fsi、其Surface.fs/.fsi与owner project；EventStore Surface.fs/.fsi只复用原decorator selector，不改算法；正式022/D0 support、native/cold helper、Surface laws与本卡状态文档。PluginBoot/HostSessionDeletion/Casebook/Store/Integrator/Scope默认算法不在本方案修改范围。

若必须修改已活跃entry、把另一Store注入原finalize、用物理字节损坏冒充live Prepared.Cuts、重绑Boot owner、按clock等待arm、或无法保证选中真实Capture，应停在前提失败，不调预算、不改期望取绿。若项目DAG要求复制整套Store装配或协议，先缩小方案，不引入泛框架。
