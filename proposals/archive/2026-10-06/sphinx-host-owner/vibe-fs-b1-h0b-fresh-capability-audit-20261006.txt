B1-H0b：跨 writer/process 的首次接纳能力前提
2026-10-06，只读审计；没有修改仓库、需求、计划，没有运行构建或测试。

一、结论与本包边界

本包不能从 IEventStore.Append 的 Ok 或 Cuts=[] 构造 Host 发送许可。
首次派发必须由拥有 native store lock、canonical Integrator 和物理 append 的
EventStore owner，证明“锁内 fresh Current 中尚无此 intent，完整事件首次提交，
唯一 canonical Current 已真正接纳该 intent”。Sphinx composition 负责读取其
唯一业务 Current、构造合法完整请求和消费一次本地发送能力；Adapter 只消费
已经交接的实际 owner/request，不自行推断首次性。

同进程 Semaphore 不是跨 writer/process 证明。先 ReloadLocal 再 Append 也不是：
两次调用间有竞争窗口。跨进程物理锁必须覆盖 fresh read/业务准入/prepare/
完整落盘/Current commit，且在能力返回和任何 Host 创建/发送前释放。
不能外层 withStoreLock 再调用现 Append：现 Append 会再次取得同一非重入锁。

当前唯一可用的 authoritative refresh 是全量 canonical replay。成本矛盾必须
先明确：WHAT durable-events-017 不允许每次 append 成本随历史字节增长。
不能把全量 ReloadLocal 藏入 Append，也不能把全量刷新改个函数名后声称整个
事务是 O(new bytes)。本卡给出原子合同和验收；生产实施先冻结 fresh-read 与
append 的成本边界。若要求整个 guarded admission 都具备严格新字节成本，
现存 API 不够，需先完成基础设施 checkpoint/增量刷新合同，H0b 保持关闭。

本包只闭首次正常派发与 conservative zero-resend。没有 send 前 actual
child/PromptKey 持久关联，不能关闭完整 receipt-loss recovery、cancel、usage，
更不能宣称公开 work_next/work_submit 或首个答案已完成。

二、已核实的源码证据

1. Persistence/EventStore/Store.fs:79-92,174-219
   observeStoreOrFresh 从当前 integrator.TryEvent 去重；相同 EventId+字节从
   fresh 列表移除。fresh=[] 返回 AppendReceipt.empty。重复成功不是首次成功。
   StoreTypes.fsi:24：AppendReceipt 只有 Cuts，没有 Fresh/Replayed/CommitUnknown
   区分。不能在 domain 中自行补 boolean 然后把它当 owner 证明。

2. Store.fs:222-241,261-266
   createLocal 启动一次 ReloadLocal；Append 在 withStoreLock 内直接执行
   appendValidated，完全没有重新读取其他 writer 已提交的事实。
   公开 ReloadLocal 独立于 append。两个 store 实例有各自 integrator 和 gate。

3. EventStore/ProcessEventLog.fs:213-254
   withStoreLock 复用 proper-lockfile 的跨进程排他门禁，明确只保护物理
   bytes/snapshot，不携带 domain truth。returned Task 包含 Release 完成。
   异常路径也释放；无需另建 Sphinx 锁文件、日志、registry。

4. ProcessEventLog.fs:289-298
   append 只 encode incoming events、AppendAllText、fsync，不读或覆盖旧字节。
   保持这一物理 primitive 和当前事件 vocabulary，不增加 durable generation。

5. IntegratorEngine.fs:474-507
   ReloadLocal -> ProcessEventLog.readStreams -> validateLocalHistory -> replay。
   readStreamsAt 在 ProcessEventLog.fs:703-721 对每个 retained writer decodeFile。
   replay 在 IntegratorEngine.fs:250-270 从 initialState 遍历全部 canonical 序列。
   没有热 suffix refresh/checkpoint API。physicalFingerprint:609-613 是文件 stat
   辅助键，不被 ReloadLocal 使用；它还枚举全部 writer 与 payload，不能冒充
   O(current event) 原子 fresh 证明。
   PrepareLive 在同一 Integrator 中调用 integrateOne，Commit 只核本实例
   expectedState reference，不核另一个实例或另一个 process 的新 writer 字节。

6. Sphinx/V2/Persistence/Integrator.fs:53-65,74-104
   已 accepted ancestor 可以作另一个合法 child 的 base。不同 commandId 从
   同一 prior head seal 请求时，结构事实可以成为两个合法 heads。这个设计
   必须保留；不能为了 Host 至多一次而把普通 Append 的合法 fork 判坏。
   Bind.tryInquiry/tryTrace 只读该唯一 Current；H0b 不能自行扫描历史或第二 fold。

7. Sphinx/V2/Composition/Commands.fs:192-201
   当前 read 会先 ReloadLocal，但没有原子跨 writer 的 business transaction。
   当前 H0a Adapter 消费实际 SessionId 和 DispatchRequestedBody，不提供
   fresh-store permission。新能力要在 composition/store 交接，不能由 Adapter
   自己把这些参数命名为“已准入”。

三、必须先冻结的最小合同

建议增加独立的 store-owned guarded admission capability，保留原 Append。
名称和具体类型由 owner 最终确定；以下是行为合同，不是已实现 API。

1. 唯一 checkpoint 来源
   - 只能由 EventStore owner 在同一 native exclusive lock 下捕获。
   - checkpoint 绑定该 store identity、唯一 canonical Current、统一 retention
     cutoff/有效 writer 集合和已验证的实际物理输入；domain 只看 typed Current。
   - obj reference、revision、最大 EventId、writer mtime、文件尾长度、进程退出码
     都不能单独代表该输入完整性。
   - token opaque、不可由调用方反序列化/伪造，不增加任何 NDJSON version 或
     generation 事实，不把 Git/file types 引进 domain contract。

2. 没有可逃逸的锁内 callback/effect
   - 锁内 composition callback 是同步纯计算，只读取 supplied canonical Current、
     校验 exact request/command fingerprint、计算合法 sealed envelope。
   - 不访问 Host、network、model、clock、另一 journal writer；不递归调用 Append。
   - 该回调可以调用既有纯 Codec.seal/Reducer transition preparation，不能新增
     history fold；真正接纳仍由唯一 registered Integrator 的 PrepareLive 完成。
   - 工厂保有 physical primitive，门禁和异常/release owner 不交给 JS。

3. 读与提交的原子关系（两种合法方案，实施前明确选一）
   A. fresh canonical read 与纯 plan/append 在同一次锁 lease 内顺序完成；
      canonical Current/物理输入期间不能被其他 append/sync 改变，随后释放。
      这不需要持久 checkpoint，也不需要额外 registry；但现 full refresh 总成本
      随历史增长，必须显式计作 arbitration read，不得宣称 whole operation O(new)。
   B. 分阶段 prepare checkpoint，然后重新取得 native lock compare-and-commit；
      必须由 store owner 证明 Current 和物理输入在两阶段间未变。发现任何无法
      证明的变化先返回 FreshnessLost（零 append/零 Host），经 canonical refresh
      重新判定。物理 stat/fingerprint只是检测辅助，不能省略 canonical validation。
      当前缺少既正确又满足严格成本的 revalidation/change-notification 接缝，不能
      用全文件 fingerprint 或本地 sequence 假装这个方案已可用。
   A 最小且可证；B 不应为了表面减少锁持有而先造空证明。

4. 结果应明确分型，而非一枚 ok
   - FreshAccepted：指定主 envelope 首次进入 durable bytes，所有依赖 closure
     已验证；Commit 已执行；Sphinx 唯一 Current 没有 cut/fork，exact request 在
     预期 head 中可读。仅此 case 可以产生本地发送能力。
   - ExistingExact：相同 canonical event，或该 intent 已有完全相同 request。
     返回已有 binding/pending 分类，绝不产生发送能力。
   - AdmissionRefused/FreshnessLost：本次还未写入；返回 closed reason，零 Host。
   - CommitUnknown：可能已经写入，或 append/commit/release 结算不明；零 Host，
     对账原 exact identity，不能把错误当“未发生”然后重试 send。
   - SemanticCut：保留现坏 fact+ProjectionCutTail settlement 与 mandatory fatal
     owner。不得为了取得 fresh result 删除坏事实、吞 cut、跳过 integration。

5. exact lookup 次序
   - full request / command fingerprint mismatch 应具体拒绝；先比较完整 contents，
     不能只比较 intentId/workId，也不能先返回旧 receipt 遮住 changed request。
   - exact existing intent lookup 先于一般 stale head/revision gate；exact accepted
     replay仍不产生新 permission。若两阶段 old checkpoint 只能证 stale，先返回
     FreshnessLost 再 refresh 判 exact；不能未经事实直接造 ExistingExact。
   - 已有 receipt：返回 stored actual binding，零 Invoke。
   - 已有 request、receipt=None：返回 RecoveryIncomplete/Pending，零 Invoke。
   - 不同 commandId 携同一 exact intent：也不派发；不得为它 append第二预留或
     第二 intent。不同 identity/内容冲突不得选择某一 branch 继续 Host。

6. capability 的所有权
   - Store owner 是 fresh durable commit witness 的唯一构造者；composition 把
     witness 与 exact inquiry/work/attempt/fence/intent/public/private contents 绑定。
   - dispatch effect owner 通过一个本地一次消费资源执行原 Runtime。单纯 immutable
     record 或公共 bool 可被重复调用，并不保证一次；opaque witness 不暴露 JS。
   - 不保存在另一全局 map，不产生另一 durable truth；本地资源关闭/进程重启后
     不从 intent 重建 permission。durable Current 的 existing request 负责阻断
     冷启动、另 writer、reentry；receipt负责后续已知事实读取。
   - 原 native lock 在 Host get/create/send 之前释放。可在真实 Host callback 中
     让另一个 writer 完成无关合法 append，证明锁没有横跨 Host/network等待。

四、budget/状态合同，避免在加 gate 时回归 B0

从 fresh 唯一 Current 得到合法 Spec/attempt/fence、依赖 actual success、合法
Round、Ready/matching Leased、自己的足额 reservation。若需首次 reserve，
BudgetReserved + DispatchRequested 用现同一 Sphinx transition envelope 同 batch
提交；后半拒绝不得发布前半。已有 own reserve 时只提交 Request，不再扣。
existing intent replay先 lookup，不能再写 BudgetReserved；Core 已有重复预留拒绝。
Receipt 不自动生成 Running；Running 仍是独立正式事实。Unconfirmed/Unknown
不能包装 Failed、physical 或零 usage；无实证时保留 reservation。

五、最小正式回归矩阵与真正业务红

主位置 requirements/sphinx-v2/tests/010.test.mjs，唯一 WHAT[sphinx-v2-010]。
薄原 Surface 只装配真实 EventStore/canonical rules/原 observed Runtime+Host
recording port，不复制 gate、dedup、Current、seal 或 permission 算法。
新 API missing/import failure只记新能力缺失，不称 production business red。
现 raw Append 的两成功/合法 fork可先经已存在 public persistence surface证实
原子前提不足；不能冒称当前尚未实现的 H0b 已经重复发送。

A. same intent，两 owner 的确定 barrier（必需主红）
   1. Seed 一个真实 inquiry、round/work/Ready/自己的足额 reserve 与实际 nested
      Host owner active profile。ownerSessionId 故意不同于 InquiryId。
   2. 两个不同 writer/独立 store owner；至少一个变体在不同真实 OS 子进程。
      两方先完成同一 canonical base 读取并通过 IPC报 ready，再同时放行调用。
      barrier 在尝试 gate 之前，不能在拿着锁的纯 callback 中 await另一 owner。
   3. 相同 exact intent/request，使用两个不同 commandId（避免仅靠 eventId去重）。
      primary intent batch只含 Request，避免重复 BudgetReserved 的 semanticcut
      遮蔽真实 first-admission 竞争。
   4. 父进程记录 original Host actual Create/Send，首次正常 sender保未决可控。
      最终仅一个 owner 获得 FreshAccepted、仅一条 accepted intent、一个 unique
      Sphinx head、一次 reserve、一次实际 child/send。另一方明确 ExistingPending/
      RecoveryIncomplete，不能以 generic Ok 自证成功。
   5. 对赢家实际 managed acceptance/exact completion做正控；cold新writer读取
      同 intent/receipt与原 trace。两方退出须结算所有 controlled Task/资源。
   6. 临时变异去掉 gate 内 refresh/比较、或把 ExistingExact 变 FreshAccepted，
      此正式例必须失败；不靠重复运行、sleep、增大测试预算发现竞争。

B. exact event duplicate（与A分开）
   - 同 commandId/相同全部字节：只一个 new event，原 writer bytes不变，第二
     结果为 ExistingExact、零 Host、原 receipt unchanged。
   - 第二实例在第一次提交前启动并保持旧 Current，是 stale-writer主变体。
   - 相同 EventId不同字节：保持 StorageInvalid.IdentityCollision，零 Host。
   - same intent改 public/private/schema/spec：具体 admission conflict，零 append/
     零 Host，不能只读旧 receipt返回成功。

C. failure与commit边界
   - fresh正常 positive使 Host计数非零；真实写入拒绝使 Create/Send=0，所有
     journal原字节及 canonical Current未变化。
   - whole batch第二body非法，prefix不发布；不绕过现 Core严格验收。
   - semantic cut/坏seal：现 badfact+cutsettled保留，派发0，按既有 fatal owner；
     不能把新 gate 的业务拒绝都写坏事件以借 fatal当普通分支。
   - durable已append但Current commit/writerrelease出现Unknown：不发；fresh
     reader/cold reader查 exact canonical原事实，reentry也不发。不得false fresh。
   - 在 Host仍未决时无关 writer可以正常 append，证native store lock已释放。

D. 冷 Pending 与 receipt后只读
   - 人为在“真实 fresh intent durable，Host effect前”结束生产owner。新进程看到
     request无receipt：RecoveryIncomplete零Host；不能因测试知道nevercalled而
     让生产恢复器猜nevercalled。
   - Host确实调用但尚未receipt也同样zero-resend；Submitted仅transportreceipt。
   - Unknown保原 actual key/Pending不造failure/usage；重新调用不再创建/发送。
   - receipt已durable：exactrequest返回同 actual child/PromptKey/physical/root;
     changedrequest拒绝；status/export原字节不变且没有Host/model/lease调用。

E. 存储法律回归（各NNN只对应自己的WHAT）
   durable-events/004：能力返回前真实 native lock release；新路径也必须同义。
   /006：exact canonical bytes idempotence，changed sameid collision，Unknown
     依事实存在性判定；新receipt能力不改旧raw Append receipt语义。
   /008：普通 Append 仍接受合法双head，cold Current仍DomainConflict，不挑winner。
   /013、/019：仅canonical commit后Current更新，注册删除变异仍破坏实际Current。
   /017：追加成本独立history证据，不由少量source token测试代替。
   /021、/024：semantic cut 与既有settlement/fatalcapability保持。
   这些是原相关验收，不把同一测试title挂多个WHAT。

六、017成本与checkpoint的真实未完成前提

现 /017 正式测试主要验证无Git capability、字节前缀不变、cold/corrupttail。
没有测“增加旧历史而append成本不变”。生产新增guarded路径前应新增真正
physical recording fixture，装配原 ProcessEventLog和 canonical engine，记录
event/payload bytes read、decoded envelopes、oracle integrate次数及写字节；
仅test port记录实际I/O，不能用手写估算函数或 walltime阈值作证明。

两个seed histories（相同writer数量/相同valid当前head，旧历史长度明显不同）
在activation/fresh arbitration read完成后清零记录，追加相同尺寸event/payload：
原 append必须旧history read/decode/fold=0、写字节相同、Git操作=0。另将整个
guarded dispatch成本单列，不能只清零其中昂贵阶段而称总成本符合017。

如果checkpoint方案最终采用增量：仅读取suffix仍不能直接把delta追加fold。
EventKWayMerge.compareReadyCursor 按EventId/WriterId的readyfrontier排序；新独立
writer的较小event可能插到既有canonical序列之前，retention移除整writer也会
改变输入。必须证明 incremental Current == canonical cold replay；统一cutoff、
late insertion、payloadclosure、missingparent/cycle、identitycollision、semanticcut
都由现 engine owner处理。不能在Sphinx再写suffixreader或第二fold。

最低checkpoint合同至少要：validated writer-input identity/retention boundary、
唯一 engine state与该输入绑定、跨process变动发现、无法证明prefix稳定时的
closed FreshnessLost或正规replay路线、commit按同一输入原子确认。物理缓存
不是权威，miss必须回到canonical验证，绝不能fallback “assume current”。
当前没有现成 constant-time跨process change witness；新 writer文件可加入，
旧writer content append不会更新events目录mtime。proper-lockfile owner.json、
heartbeat/Date.now也不是commit sequence。不得另加durable store generation来
绕开 WHAT002/009，更不能说一个无约束stat token已经证明完整history未变。

七、具体施工/停点

1. Parent与durable owner先冻结 fresh arbitration/append成本边界、原子API和
   Unknown/fatal结果合同。若严格whole-operation017仍无可用checkpoint方案，
   停在本只读结论，H0a可独立结算，H0b不开公开入口。
2. 单editor先补 store-owned capability+thin fixture签名、正式A/B失败例；旧API
   能跑的前提反例先保原raw证据，新API缺失不能代替业务red。
3. 修改 EventStore/Store fs/fsi、Port/StoreTypes必要有限contract；native锁和
   canonical规则保持原owner。若需checkpoint涉及 IntegratorEngine/Kernel，
   作为前置独立包，不将缓存framework顺手塞进H0b。
4. 然后串行修改 Sphinx Composition/Commands或一个真实effect-owner模块、
   Hosts/OpenCode Adapter构造注入；root拥有公共边界，原Runtime不增加第二owner。
5. 正式010目标green，再跑上述最小相关storage NNN；使用冻结源码和正式runner。
   若成本或冷恢复矩阵未证，记有限accepted-normal/zero-blind-resend，不写全闭合。
6. Docs由parent在验收后同步08/04/总计划。下一首答案链仍需真实profile/schema/
   claim+submit/interpretation/renderer，不能由这枚发送capability冒充完成。
