1. 真正的调用链与缺口

Persistence/EventStore/Store.fs 的 commitPrepared 当前固定顺序：
  ProcessEventLog.append(log, prepared.DurableEvents)
  prepared.Commit()
  return {Cuts=prepared.Cuts}
appendFresh 保存 prepared 仅在局部，最终 Store.Append 的 inner catch 只返回
Error(AppendFailed ex.Message)。因此 physical append/open/fsync/close 或
Current commit 抛错都丢失原 Error 身份、request、prepared 列表与具体阶段。

ProcessEventLog.fs:289 的 append 先 encode，再 ensureDirectory，才执行真正的
appendFileSync，随后 openSync(r+) -> fsyncSync -> finally closeSync。不能把
“进入 ProcessEventLog.append”当作物理写已开始：原013的 events 路径是普通
文件时，ensureDirectory 已失败，实际 appendFileSync 尚未调用。

withStoreLock(fs:243) 在 inner catch 外：acquire -> work -> await Release ->
return result；catch work/release 时再 await Release 后 rethrow。StoreFileGate
在调用实际 release 前已置 released=true(fs:27)，所以成功 work 后的 Release
异常会进入 catch，但第二次 Release 是 no-op；最终 Task 直接抛原 release
异常，不是任何 AppendError。inner catch 覆盖完整 append Task 的建议必须
保留 physical 阶段，不能只把这个异常追加成另一个 AppendFailed 字符串。

另有两个需独立证实的复合错误：work 抛错且 Release 再抛会覆盖 work cause；
durabilityBarrier 的 fsync 与 finally close 双错会覆盖 fsync cause。单错绿
不证明这两项已经关闭。不要为修 single case 另造复杂通用错误层；保原 primary
cause 与实际 cleanup cause 的有限表示需先冻结，再补两个独立正式反例。

generic withStoreLock 还有实际 WritePayload 与 Git/Hook/Sync.convergeUnderLock
消费者。不可把 generic 锁 helper 的所有异常改称 EventStore CommitUnknown。
Git sync 的既有错误/释放行为和 payload 的独立写入结果需保留。

2. 最小类型信息，先冻结含义再定确切名称

稳定 request 是 IEventStore.Append 收到的完整 EventEnvelope list（包含原 EventId、
stream/type、parents、payload、refs）；Prepared 是原 canonical PrepareLive 产生
的完整 DurableEvents/Cuts。两者不可互换：dedup 可排除已存在事实，语义拒绝
还会追加实际 ProjectionCutTail。Unknown 不能只保一个 request eventId。

建议在既有 eventstore-port-contract/StoreTypes.fs/.fsi 冻结有限 carrier：
  Requested: EventEnvelope list
  Prepared: {DurableEvents: EventEnvelope list; Cuts: SemanticCut list} option
  Phase: 具有确定含义的有限 union
  Cause: 原 native/F# exn（保持对象身份，不用 ex.Message 代替）
不携带 commonDir、文件路径、Git oid/ref、锁对象或 CanonicalIntegrator；不能
让 pure contract 反依赖物理 runtime。StoreTypes 所在 shard 已依赖 model 与
foundation-outcome，可容纳这些稳定领域字段，无需新 registry。

Phase 至少区分 PrePhysical、PhysicalAppend、DurabilityBarrier、CurrentCommit、
StoreRelease；PrePhysical 内可按实际需要区分 gate/validation/preparation，
不为日志造无消费者的状态。PhysicalAppend 的边界须由真正 appendFileSync
owner 标记（调用前即表示可能部分写入），不能由上层函数进入时猜测。
DurabilityBarrier 包含实际 open/fsync/close；不能把 fsync 未跑当成成功。

Unknown 至少是 AppendError 的独立 case，因而不能与 StorageInvalid、durable
SemanticCut 或已证明未尝试的拒绝混为一谈。是否将现 AppendFailed 改为带
同样 context 的已知失败，或新增明确未尝试 case，需要同步冻结。只新增
Unknown 但让所有 pre-physical native cause 继续字符串化，不能称完整 cause
保留。Prepared=None 与 Some empty 也不可互相猜：准备尚未发生和合法 dedup
是不同事实。

原 Error 在同进程 native Surface 上应能严格相等比较。MCP/Wire JSON 无法
传递 Error 对象身份，内部仍必须保留 typed carrier；对外另给明确 Unknown
语义、稳定原因/阶段及必要请求身份，不泄漏 private payload/ticket。不能
把 carrier 用 sprintf %A 直接外发。外部 outcome/code 的确切合同另行冻结。

3. 分类矩阵与必须裁决的窄边界

- 格式/身份/父边/payload/vocabulary 校验拒绝：StorageInvalid，零物理追加。
- PrepareLive 返回 Error：零物理追加；保持它的真实 reason，不能编造 native
  exception 或 CommitUnknown。
- ensureDirectory/gate 获取在 actual append syscall 前真实失败：已知未尝试
  该 append，但门禁/启动拒绝与业务事件已存在性是两回事。
- appendFileSync 已调用后抛错：可能部分/完整写入，CommitUnknown；不能以
  ex.code、exit code、live Current 缺事件证明未写入。
- 完整行写出后 open/fsync/close 异常：CommitUnknown；保 prepared 与原 cause。
- 已物理落盘，Commit 之前或之后异常：CommitUnknown。若原 Commit 已执行，
  live Current 可以已包含事实，不能为了“Error”回滚它或篡改历史。
- 已物理落盘/Current commit，native Release 失败：CommitUnknown，完整锁
  Task 必须结算成此 case，且不能谎报释放已完成。
- exact duplicate/no-op 尚未做新写，Release 失败：不能机械声称物理写未知，
  也不能声称原 event 未提交（它本来就可能存在）。必须保 no-new-write 与
  release-failed 两个事实；成功要求 release 完成，因此也不能硬返回 Ok。
  这一 case 的公开错误名称/是否携带已有 receipt 是需要先裁决的最小问题。
- batch 的部分完整行与尾部半行：Unknown，不能因某一个 eventId 存在就把
  整批判 Committed。现007遇非法尾行整体 fail-closed；U0 不授权截断修复、
  忽略尾行或自动补交。对此最低限度保完整 prepared，后续恢复另包。

WHAT013“失败保持前 Current”用于物理未成功或 Commit 未执行的边界；post-Commit
Unknown 已发生的 Current 不能倒退。若外部仍把一切 Error 都理解为未写入，
必须修明确规范/结果合同，不能让实现伪造旧态来迎合旧断言。

4. 原生正式 red 的最窄入口（两个无需生产 seam，Commit 需窄能力）

统一真实 Node child，在任何 dist import 前给原 node:fs default method 作
单次 exact-owned-target forwarding wrapper，并 syncBuiltinESMExports；仍只
动态导入正式登记 EventStore/Surface、CodecSurface。运行由原
runVerificationToolProbe(process.execPath,...,{signal:test.signal}) 收取 PID
与 monitor 生命周期，不裸 spawn，不改预算。每例有独立真实 temp/commonDir/
WriterId 与 finally；注错仅自身资源，original native method 必须真实执行。

A. PhysicalAppend：目标 writer 的原 appendFileSync 成功返回后抛唯一原 Error。
   断言实际全 canonical bytes/LF，live event/head 仍原态（Commit未执行），
   原 lock 真实消失，独立 cold 新 writer 恢复完整请求事实，然后才断言
   typed CommitUnknown/Phase/Requested/Prepared/Cause===原 Error。
B. DurabilityBarrier：real open 得到 fd，核 fd 真指向该 writer；原 fsyncSync
   返回后抛原 Error，真实 finally close 与 lock Release 仍执行。物理/cold
   正控同 A。不得拿 fake fd、计数或假 fsync 成功代替实际同步。
C. StoreRelease：仅对 exact commonDir/wanxiang.lock 的 fs.rmSync 作原调用
   完成后 throw。production processAwareFs.rmdir 会把真实 Error 交原 callback。
   当前 proper-lockfile/lib/lockfile.js:288--292 已先停止自身 update timer、
   标 released、删除自身 lock registry，再走 removeLock；该 fixture 同时
   证明真实锁目录已消失、Current/bytes 已提交、cold 合法。它证明的是
   “成功 native Release 后的响应异常”，不证明真实 remove 失败时的锁回收。
D. CurrentCommit：现 opaque JS Surface 没有直接操纵 Prepared.Commit 的能力。
   不 import generated IntegratorEngine/私有 closure，也不以 ControlledEventStore
   返回 Unknown 当 actual commit proof。可在既有 F# verification owner 构造
   原 CanonicalIntegrator，所有成员原样转发；PrepareLive 只包装其真实返回
   Commit，执行 original Commit 后调用受控 throw，DurableEvents/Cuts 原样保留。
   通过一个登记 native scenario entry 驱动原 EventStore.createLocal；没有第二
   fold/假 Current。若需主 Surface 完整 production program，先把当前组装点
   用同一 private factory供普通 create/scenario复用，不能复制第二组规则。
   正控先证明 actual disk、原 Current、cold；再断言 Unknown/cause。此 seam
   要先冻结编译闭包/所有权，不能在 JS 直接挖出不透明 handle。

每例先检查实际写盘/合法 cold/锁状态，再检查错误分类，避免旧版第一条红
之后真正物理事实从未被断言。旧版预期 A/B 是 AppendFailed string，C 是
Task rejection，D 是 AppendFailed string；应分别取得行为红，不能把新增
scenario API-missing red 当作旧业务缺陷已复现。

原正常公开正控可以复用 durable-events004 完成后 lock 不存在、006 返回后
Current 已积分、013 pre-write failure 不推进 Current、017 exact bytes/cold、
019 registration 及021实际 cut-tail。现 006 的 duplicate/collision 不证明
post-write Unknown；013 的 EEXIST 不证明物理已尝试；Verification.EventStoreWriter
的 ControlledEventStore “disk exploded”只证 journal 分支，不证本地 syscall。

再补 original work error+Release error、fsync error+close error，以及某个真正
registered business cut 产生的 Prepared 扩展列表。不能造假 cut record；用
021/025已有原 business fault fixture。若本轮只单错，对复合错/坏尾行保留
明确未证，不能称全部 Unknown/cleanup 义务关闭。

5. 必须手工迁移的实际消费者（穷举新 case不足，wildcard也需读）

EventStore/Surface.fs appendErrorToJs：稳定 native CommitUnknown/context/cause，
不能退回 AppendFailed；其同进程原 Error identity可作正式断言。

Journal/EventStoreJournalWriter.fs：formatAppendError；RuntimeStarted 与 business
分别看。当前 business Error 一律 CommitUnknown(eventId,WriteFailed string)，
失去 phase/cause/prepared，并把已知 pre-write StorageInvalid 也当 uncertain。

6. 建议切包/验收停止线

U0-T0：只冻结上述 pure carrier、实际phase边界、post-Commit Current、duplicate
Release错误和wire/Journal降型政策；落实最窄actual Commit scenario能力。

U0-I0：原 Store/ProcessEventLog + native EventStore Surface 的单错正式红→绿：
真实 append、fsync、Commit、Release，完整 request/prepared/cause，原 bytes/
Current/cold/lock正控；保无新 history read/Git及正常cut/idempotence。新union
consumer必须至少明确fail-closed并保carrier，不允许旧wildcard误称Rejected。
可在一个原子提交闭合，但不叫首次派发、完整恢复或全消费者策略闭合。

U0-C0：Journal、Strength、Casebook、Js、Sphinx各原owner分别冻结typed传递与
canonical事实查询政策，补其最窄真实held/error/unknown正反例；不得以仅
更新error formatter算接续完成。若目前生命周期/外部Result无对应case，
该consumer contract是I0全面宣布闭合的前提，不能藏到future TODO。

U0-E0：复合异常保双cause、native release实际失败后的resource ownership、
partial-tail/batchUnknown读证与冲突；分别取得真实正式反例后施工。

Known absent/known present只能由合法canonical事实证据判定，保exact identity
及完整byte equivalence；本卡不授予对损坏尾行的修复、不修改retention、不
新增history cache/read-set witness，不在append catch里全扫历史，不引入
Sphinx-private log、第二fold/registry或Host fresh-dispatch permission。
