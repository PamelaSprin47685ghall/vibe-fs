一、可实施结论与停点

1. 原 Append 可以证明本实例已准备的事件经过物理 append 与 Commit；它
   不能证明“这个 intent 在跨 handle/process 的 fresh canonical Current 中
   从未接纳过”。Cuts=[]、Ok、new eventId 都不足以成为首次 Host 许可。
2. 可以先原子施工 typed commit settlement 前置包 U0：把物理追加开始后、
   Current commit 后及 native release 失败的完整未知结算保留下来，正常
   append/duplicate/cut/Current 语义保持。U0 不需要刷新历史，不触及017，
   也不提供首次派发能力。见第七节的实际 red/green 卡。
3. “changed/unknown 在锁内拒绝零 effects，锁外 cold refresh 后重试”比每
   call锁内全量 replay 更窄，应当优先考虑。它需要 store owner 已持有
   与唯一 Current 和确切 physical read-set/retention cut 绑定的有效 witness。
   现源码没有这枚 witness。只有同步 Git snapshot 的 stat cache，没有
   canonical Current checkpoint，也没有可靠 native change-completeness 证据。
4. 因而不能安全 small 实现完整 H0b。可以做 U0 或017实际成本观察前置，
   然后以正式反例建立 fresh-witness 合同。不能拿“声明 GuardedAppend API”
   当施工完成，更不能为了正控通过就把 stat equality 当真实权限。

二、这次深入审计得到的新事实

Store.fs:189–219、233–241 的真实执行链是：
native lock -> 本实例 gate -> validateForAppend -> PrepareLive ->
ProcessEventLog.append(prepared.DurableEvents) -> prepared.Commit -> receipt ->
退出本实例 gate -> native release。
观察到的关键边界：
- newEventsAgainstCurrent 只看本实例 integrator.TryEvent；另 writer 的已落盘
  事实不自动进入这个实例。不同 commandId产生不同 eventId不能靠此去重。
- 原 Append 没有 ReloadLocal。createLocal:226/228 只在 boot reload一次。
- Store.ReloadLocal:266 既不取 native lock，也不取 Store 的本实例 gate。
  Integrator 自己的 gate只分别保护 Reload/Prepare/Commit，各阶段之间仍可
  被本实例 Reload 插入。不能把这条公开方法当“锁内 fresh 事务”。
- Prepared.Commit 的 expectedState reference只证本实例准备后的 Current
  未被替换。它不代表另一实例或另 process 的文件集没有改变。
- reference检测失败发生在物理 append之后；Store catch将它压成普通
  AppendFailed。因此 AppendFailed目前混合了确实未写、可能部分写、已完整
  落盘但Current未commit的情形，绝不能供H0b推断not-written。
- ProcessEventLog.withStoreLock:243–254 的 returned Task包括 Release。
  Release错误在Store.Append内部try之外，可能在返回receipt之前直接reject。
  因此只匹配 Result.Error仍漏一个after-commit Unknown入口。
- StoreFileGate.Release先置本地released=true，再await native release。
  不应给caller“再调用Release就证明释放”的假恢复路线。
- Journal CommitBusinessEnvelopeLocked:343–354 将普通 Append Error保守映射
  为CommitUnknown并poison，但原cause只剩reasonstring；Task级reject不经过
  该Result分支。它不是H0b可复用的完整store-owned未知结算。
- Sphinx Commands.appendRefusal:257–264 把AppendFailed统一包装为
  PERSISTENCE_REJECTED。这条当前start/cancel分类不适合作为dispatch结算，
  新effect路径不得复用它来丢失unknown/request identity。

三、native锁内现在究竟能取得什么 durable witness

能取得的是：
A. 在同一次exclusive native lease内，通过原readStreamsAt捕获统一now/cut，
   validateLocalHistory与canonical replay全部成功，publish同一个Integrator
   Current后，owner知道该Current对应这次实际读取的retained canonical输入。
B. 在该lease仍有效、没有同实例reload/其他commit插入时，prepare并追加
   完整prepared.DurableEvents、fsync、Commit成功，owner知道这些完整事实
   已写入且唯一Current接纳。这是一段锁内操作的实际见证。
C. Release正常完成后，才能向外返回这次新接纳的本地一次能力。

目前A的实现是全量read/replay，且现Reload API并不返回一个可跨lease重用的
read-set证书。最大eventId、head/revision、Current reference、writer尾长、
readLastCompleteLine、owner.json(pid/time)均不能从A推导“后来全部输入未变”。
owner.json是proper-lockfile存活提示；每次release移除，并不是commit sequence。
锁只排除遵守同一锁的实际writer/sync操作，不自动使旧Current成为fresh。

全量A+B在同lease内能保证原子首次性，但将A塞进每次Append会让实际成本
随旧历史增长，违反WHAT017。不能只把A改名arbitration便宣称整条派发是
O(current bytes)。成本报告必须同时保留read arbitration和append两部分。

四、安全拒绝stale方案：可复用部分与准确缺失

理想最窄算法（尚未实现）：
1. Store owner先拥有已验证checkpoint，内部绑定自己的唯一Integrator状态，
   全部retained writer/payload实际输入、统一cutoff以及下一expiry。
2. 调用者只提交完整业务request；不提交Current、physicalfingerprint或token字串。
3. 取得native lock，核checkpoint仍属于本owner、Current未被替换、retention
   未越界，且可靠的physical freshness证据明确无变化。
4. mismatch或无法证明：FreshnessLost/Unavailable；零append、零Host。释放锁。
5. Caller可在正规owner边界做实际cold refresh，取得新checkpoint，再用原
   exactrequest重新判定。刷新途中若又有writer推进，下次gate仍拒绝；不把
   无限retry、sleep、增预算当正确性。先不设自动重试，显式closed结果即可。
6. 只有确知unchanged才在同lease内执行纯业务准入/Prepare/append/Commit。
   native release成功后再交付一次能力；Host pending不占磁盘锁。

现存可复用primitive：
- ProcessEventLog原native lock及唯一append/fsync primitive。
- canonical engine的single-event integrateOne、PrepareLive、cold replay。
- writerPhysicalStats/payloadPhysicalStats/fingerprint作为cheap mismatch观察。
- canonical codec的完整identity check与Sphinx accepted-state/trace查询。

缺失的真正authority：
- 唯一Current没有绑定validated physical read-set或retention-cut checkpoint。
- 没有证明cross-process全部变化已经被观察到的native通道。
- physicalFingerprint仅hash dev/ino/mode/size/mtimeMs/ctimeMs字符串，并枚举
  全writer/payload名字。它可帮助拒绝明显变化；相同metadata不是canonical
  bytes相同的证明，文件系统也未承诺每次内容变化都有唯一statidentity。
- 现cached materialization只保存Git Root/OID/stat/expiry；不能读它再造
  domain Current；也不能把Git cacheversion转成durable store generation。
- 即使将stat快照与Current一起存成本地owned closure，所欠的“物理内容没有
  变化”的信息也不会凭封装出现。新globalregistry同样无助crossprocess。
- writerPhysicalMetadata会读取durableTailActivity，必要时反向寻找活动事实；
  它不是常数当前事件操作，也没有完成canonical input validation。

一个可诚实实现但不够开H0b的tiny阶段是：把known stat mismatch/expiry变成
FreshnessLost，其余未证情况也closed。此阶段没有fresh正控，不能宣布首次
能力完成。给缺能力返回Unknown而不派发是安全停点，不是完整交付。

五、incremental/replay能否现成复用

IntegratorState私有字段只有Currents/Events/Faults；没有writeroffset、input
certificate、canonical frontier checkpoint或retention expiry。ReloadLocal
每次从initialState经整个mergeRetained -> integrateOne重新求值。
EventKWayMerge每次从完整writer arrays重建knownIds、cursors、readyheap、waiters；
其现API不返回可继续的frontier。不能把某writer新增suffix直接PrepareLive：
新writer或新tail的ready key可能插到旧canonical序列中间，retention整体
删除writer还可能改变parent boundary及业务cut顺序。

因此未来增量实现必须在canonical owner内部证明prefix稳定；无法证明则
正规cold replay或安全拒绝，绝不在Sphinx加第二fold。正确性oracle应比较
所有注册production Current/heads/accepted trace，不只是events数组或空state。
Sphinx自己的Accepted Map可做exact查询/trace，不能反向成为跨writerfreshness。
fullReplayUsed只限制semantic cut推断失败的紧急fallback一次；它不限制普通
ReloadLocal，也不是热刷新预算或缓存。

七、U0独立下一施工卡：typed commit/release Unknown

Why：现AppendFailed/Taskreject会遗失真实written/commit/release边界，后续
first-admission owner无从保守传播完整Unknown。
What：同一真实append算法返回可辨known-not-attempted vsCommitUnknown，后者
保原request identity、实际prepared durable envelopes（包括cut-tail）、失败
阶段与原cause；不得变Failed、零usage、可再次发送。U0不提供first-intent许可。

最窄production范围：
- EventStore/StoreTypes.fs/fsi：新增typed unknown settlement/evidence。
- EventStore/Store.fs：记录append尝试阶段，catch包住完整native-lock Task，
  包括Release。physical开始后任何不确定都不得转known-not-written。
- ProcessEventLog只在需要准确区分append/fsync阶段时增加owned观测接缝，
  保原complete canonicalappend primitive，不重复encode/write，不加日志代次。
- 所有实际AppendError consumer必须保留新增case；不是只增加DU标签。
  已定位：EventStore/Surface、Journal/EventStoreJournalWriter、Strength/Surface、
  Strength/Persistence/Store、Sphinx/Composition/Commands、Sphinx/Hosts/Mcp/Server；
  Strength/Persistence/Durability还须核Error fallback怎样保Unknown。
- 如新增IEventStore方法，需同步两真实factory与两个controlled-fixture owner：
  Store、WorkspaceEventStore.deferredStore、Verification/EventStoreWriterSurface、
  Verification/JournalPortObservationSurface；不可靠全量编译掩盖遗漏。

结果最低法律：
Known refusal：尚未调用physical append，零durableeffect。
CommitUnknown：physical append已尝试（包括partial/full/flush/Currentcommit），
或commit成功后Release失败；向调用者传完整attempt/context，零新Host许可。
Already exact/no-write结果在Release失败时同样不能交许可；须保已有事实及
gate结算失败，而不能捏造本次有新append。相关error不能只剩一条generic文字。
Cut：实际badfact+cut-tail正常settled后走mandatoryfatal owner；Unknown带
prepared Cuts和事实身份，不能把cut-settlement误包装正常Fresh。

先写正式red的最窄真实fixture：
1. 用实际EventStore+实际canonical engine；物理append失败正控，cold无fact、
   localCurrent/head无变化，known refusal零Host。
2. native filesystem recording port执行原append/fsync，然后在fsync返回边界
   抛指定Error。cold确认实际完整canonicalfact存在，调用者必须Unknown，
   exactrequest保留，localCurrent不得被提前发布，不能收到fresh许可。
3. wrapping实际PrepareLive返回的实际Commit：原Commit真实执行后再抛原Error；
   不伪造Current、不fakefold。cold/current事实存在，但对外Unknown，零Host。
   另变体在commit前使同实例Reload替换state，触发原真实reference拒绝，
   证明“物理已append但Current未commit”也Unknown。
4. actual native Release执行之后注入其ack错误，测试原Task级异常不能逃逸
   typed settlement。真实append/current/cold仍有fact，对外Unknown零Host。
5. 原sameevent+samebytes exactdup、changedsameid collision、cut/fatal法律回归。
   不能用一个fakeAppend永远Error证明2–4，所有fault都需真实physicalpositive。

这些fault接缝只装配原effect/engine的controlled边界；不另写存储或积分算法。
若需先加新fixtureAPI，missingAPI红只叫能力缺失；真正red必须原生产调用
完成到实际append/commit/release阶段后分类错误。由root统一冻结build/formal。

八、017实际成本前置卡（不以wall阈值或源码token代替）

现017只有无Git源码token与append字节prefix/cold/corrupt-tail两例，没有
增加旧history时成本不变的behavior proof。因此先增加一条真正native I/O
recording回归可以独立完成，不必先开放H0b。

转发原readFileSync/readSync/appendFileSync/writeFileSync/fsync；只统计本fixture
实际event/payload读写，禁止从N/K估算counts。封装既有production rule的

固定writer数量，两组不同旧历史长度；相同目标stream合法head、相同尺寸
new event/current payload。在正规activation完毕后清零只测原rawAppend：

这证明的是可观测正常append成本，不冒充所有数据结构基本操作的全复杂度。

九、完整first-admission合同（fresh前提未完成前不开入口）

Store-only工作：native lock -> 验真实freshwitness -> supplied只读Current的
同步纯准入 -> validate/seal/PrepareLive -> completeappend/fsync -> Commit ->
确认该primaryenvelope被唯一Current接纳且无cut/fork -> Release -> returncap。
不能outerwithStoreLock后递归Append；原锁非重入。回调无Task/Host/模型/网络
能力，不能await另owner。只读view不暴露Append/WritePayload或Integrator。

Typed结果至少分：FreshCommitted(one-usecap)、ExistingExact(storedbinding)、
FreshnessLost、AdmissionRefused、CommitUnknown(fullattempt)、CutSettled。
FreshCommitted只允许主intent原先不存在且本次确实新增完整fact；emptybatch/
duplicate receipt不能产生它。不同commandId的同exactintent归ExistingExact，
不写第二intent/reservation；changedpublic/private/schema/spec必须先比较完整
内容再拒绝，不让旧receipt遮住changedrequest。Existing Pending保原binding
与unknown，无新的Create/Send；Receipt已知返回原binding，仍不再发送。

一次能力是每新调用的owned opaque资源，不是bool/immutablepermission DTO。
Store是durablefreshwitness唯一构造者；Sphinx composition将其绑定完整request
与真实owner，effectowner同步claim一次再启动Host。claim后throw/Unknown也不
恢复可用，冷启动或重复request不能重新mint。cap不经JS反序列化、不放global
map，不新建另一durabletruth；原Current既有intent负责跨owner/cold零resend。
Host callback pending时必须已完成nativeRelease。
