## 2. 逐项核算：只在自己的时钟域相减

worker 的 CPU 字段是 `process.cpuUsage()` 的累计微秒，单调时间为该 worker 的 `performance.now()`。pre-import 由真实 Node `--import` hook 在测试入口前采样；exit 是该进程实际 exit hook，运输尽力而为。两点 pid、parentPid、entryFile一致，序号0→1，计数不倒退；collector 的 interval 与下面独立减法完全相同。

| 原生字段 | gen179，PID2659 | gen180，PID6714 |
| --- | ---: | ---: |
| pre-import monotonicMs | 18.357584 | 19.554584 |
| exit monotonicMs | 17403.668000 | 17051.283209 |
| 差值 wallMs | 17385.310416 | 17031.728625 |
| pre-import user µs | 23149 | 25195 |
| exit user µs | 385690 | 391429 |
| 差值 user µs | 362541 | 366234 |
| pre-import system µs | 4927 | 4482 |
| exit system µs | 103330 | 92050 |
| 差值 system µs | 98403 | 87568 |
| 差值总 CPU 秒 | 0.460944 | 0.453802 |
| 自身 CPU 秒 / 自身窗口秒 | 2.6513% | 2.6645% |

最后一行只是这个进程的 CPU 时间与窗口时间的比值，不是 host 总 CPU 利用率，也不是所有工具的 CPU 利用率。pre-import 以前已有的 CPU 被减去；这不是从 OS fork 起算的进程全成本。

parent 文件生命周期的 `elapsedMs` 是 supervisor 收到 IPC 时自身的 `performance.now() - startedAt`。`runner:file-start` 的 pid是inner，不是实际 worker；实际 worker PID须从原生样本取得并核对 parentPid。

| supervisor 自己的时间字段 | gen179 | gen180 |
| --- | ---: | ---: |
| 收到 file-start 的 elapsedMs | 41.850208 | 38.327583 |
| 收到 file-drained 的 elapsedMs | 17460.293333 | 17105.426958 |
| 两点差值 ms | 17418.443125 | 17067.099375 |
| 上述差值减 worker 自身窗口 ms | 33.132709 | 35.370750 |

不能把 worker 的绝对 `monotonicMs` 从 parent 的绝对 `elapsedMs` 中相减。后面两项可以比较各自的时间跨度，但33/35ms不是一份精确的 fork/IPC/cleanup 分摊：parent 记的是收到消息的时刻，worker 记的是采样时刻。现有记录没有逐项交付延迟或同域 fork→sample 映射。

gen180比gen179的 worker 窗口短353.581791ms（约2.03%），自身 CPU少7142µs（约1.55%）；这是两次观测差异。输入、并发 scope、相邻负例均不同，无重复对照，不能认定是任何修复带来的性能收益。

## 3. 现在能回答的事与仍未观测的事

已经能回答：真实 entry/PID 归属；pre-import和exit是否收到；同 PID窗口和CPU差值；parent 的文件准入/排空时序；已排空文件的窗口排名；截止时哪些文件 active/queued；authoritative summary及整组回收是否完成。缺 exit时必须保持missing，不能用0CPU、默认exit或完整窗口填空。disabled和invalid也是独立状态。

当前不能回答：

- import完成到第一条 body 的耗时。50条body记录带实际PID和名称，但没有原生时间/CPU；它们不是 first-leaf 计时证据。
- 17秒中测试本体、等待真实probe、子工具CPU、休眠、OS调度、磁盘、网络分别占多少。父进程自身CPU不能替代子进程CPU，更不能用wall减CPU宣称“空等时间”。
- stdout/stderr/diagnostic实际事件数、UTF-8字节数和排队峰值；raw日志文件大小不是每个worker实际输出量。
- IPC或reporter callback背压耗时。`run-inner`确实等待每次 `PassThrough.output.write` callback，但没有成本记录；compact reporter的stdout/stderr写入也没有独立bytes/return-false/drain/callback计时。源码上的可能路径不等于本轮实际背压。没有同时间的CPU配额、throttling/pressure观测，也不能仅凭worker自身CPU低推断host争用。
- 最新1eb Linux CI在300秒时793/821排空、2active、26queued的原因。该旧CI先于新M1运行，没有这组同PID成本证据，不能把本地006约17秒直接移植到该CI。

现workflow仅在failure时上传verify日志。若下一轮完整通过而没有可下载的原阶段artifact，不能假称拥有其全部worker样本；是否需要保留成功运行的诊断收据应另作为artifact留存合同，不与预算修补混在一起。

第一次只需完整保留已有字段：

1. run/job/head、实际 merge checkout及parents/tree、verify输入fingerprint、编译generation/digests、artifact SHA；Node/npm/Fable/.NET的实际版本，runner image/OS、host身份和实际并发配置。host可用并行度若要新增，须来自真实 `availableParallelism()`，不能用runner营销核数代替。
2. 每个正式entry完整file-start/file-drained的supervisor elapsedMs，及每个worker完整原始pre-import/exit/status/reason/interval。保存disabled/missing/invalid，不只保最慢几个或只保有exit的样本。由此离线算准入、文件窗口与自身CPU排名，并保留 active/queued 截止快照。
3. 原authoritative summary、退出/pending policy、物理backstop是否触发，以及原进程组回收证书。timeout无summary时明确缺失，不能从最后的叶子输出拼一个总数。
4. 016已经主动开启的真实tool阶段；无需再造一套tool生命周期。现有 `monitor-spawned` 的worker PID→monitorPid，与monitor发布的 `tool-spawned/tool-exited/group-drained` 的monitor PID→toolPid，可沿实际父子链归到worker。所有实际启动的工具是否排空以真实事件计数为准，不照搬旧输入的201计数；未启动016时不能写0工具成本或“工具清理已证”。
