结论：存在必须修正的确定缺陷。scripts/build.mjs:420–422 用 dist 非空推断前次提交成功，并永久删除唯一 last-known-good backup；非空不是 commit 证据。未运行任何测试、编译、信号探针或 Git 写操作。下述判断来自当前已合并源码与现行规范，不是执行所得的红证据。

1. 合同与权威

requirements/distribution/WHAT.md [005] 要求测试消费同一份 dist，并以 manifest 摘要拒绝陈旧构建。requirements/structured-workflow/WHAT.md [012] 明确增量选择/编译责任，但正文没有逐字规定 crash rollback 协议；不要把新增注释“fail-safe structured-workflow-012”说成规范原文。既有 structured-workflow/tests/012:2963、3047 已有失败保留 prior manifest/dist 的正式合同样本。该新 staged swap 也以保留失败前 dist 为明确行为承诺（build.mjs:385–407）。恢复把未提交输出当成功提交，违反这一承诺并让 [005] 摘要验证之后无法恢复既有成功产物。

唯一现有持久 commit 证据是 .fable-build/build-manifest.json 的原子替换：build.mjs:595 调用 writeManifest，随后才设置进程内 buildCommitted=true。build-state.mjs:265–276 先写临时文件、rename 到正式 manifest。输出含 path→[SHA256,size,mtime]；checkOutputsValid:219–232 已用非空、完整路径集合和每文件 SHA256 证明实际 bytes 与记录相同。mtime 不是 production bytes 身份，不能要求编译重做后的 mtime 与旧 manifest 相同。进程内布尔变量不是重启后可用事实。compileIncremental 的 success marker 只表示编译阶段，不代表 artifacts/input 检查和 runBuild manifest 已提交（owner-compile:1698 明确 compile-only 不跟踪 manifest）。

2. 实际因果链与可达中断点

a. runBuild 持锁，recover 先运行，再读 manifest（build.mjs:438–450）。进入 full 分支时把已有 dist rename 到 .fable-build/dist.staged-backup，创建空 dist（389–398、510）。
b. Fable 实际先编译到 scratch staging（owner-compile:1773–1789）。因此“Fable 编译途中任意中断必然造成 target partial”不准确：那时 target 通常仍空，旧恢复分支可正确回滚。
c. 成功编译后 fs.cpSync(stagingOutputDir,resolvedOutputDir) 逐项写 target（owner-compile:1790–1799）。SIGKILL/进程崩溃可发生在拷贝若干文件后；随后还有 verifyArtifacts（build.mjs:543）、三类输入重新计算、collectOutputs，最后才 writeManifest:595。即使 copy 全部完成，manifest 未提交的 dist 仍未证明通过后置验证。
d. CLI SIGINT/SIGTERM handler 只删 lock 并 process.exit（build.mjs:735–757），不会执行 async runBuild 的 finally；SIGKILL 同样不执行 finally。因此 backup+非空未提交 dist 是真实可达磁盘状态。
e. 下次 recover 仅检查 readdir.length>0，删除 backup，保留未提交 dist。旧 manifest 仍在。determineBuildDecision:263–278 会识别 output-hash-mismatch 并返回 full，但无法复活已经删除的旧 bytes。
f. 下一 full rebuild 再把 partial dist 当成 backup。若第二次构建失败，finally 的 restoreStagedDist 只能恢复 partial；若 collectCompilerInputs 在重新 stage 前就失败（例如未归属源），partial 原样留下且 backup 已没有。摘要门禁仍会拒绝陈旧状态，但“下一次会 full”不能补偿数据保护已经失去。

3. 当前测试为何未抓到

distribution/tests/005:180–187 只向新 dist 写 Fresh.js，没有 writeManifest，却称它 committed 并要求删除 backup。此正例编码的是错误推断，应改成通过真实 writeManifest 提交实际 collectOutputs 之后的正例，不能为了保它而放宽恢复判定。
005:198–224 的真实 runBuild 接线只覆盖空 dist，旧逻辑本来就能正确恢复。
structured-workflow/012 的 compiler-failure 样本由异常走 finally；它证明正常失败回滚，不证明进程退出后 residue 恢复。

4. 最窄修复建议（仅建议，未编辑）

在持有同一 build mutex 的 recover 中读取 sibling .fable-build/build-manifest.json；仅合法 schema 且 checkOutputsValid(manifest,targetDist) 的完整输出路径/bytes 比对通过，才允许删 backup。缺 manifest、解析失败、不支持 schema、输出集合为空、缺/多文件或 hash 不符，均恢复 backup。readManifest 本身 JSON.parse 可抛异常，恢复判定必须把不可用证据视为“不能确认 commit”；不应在删 backup 后才处理解析错误。
runBuild 后续仍读/验证当前 manifest；恢复不得重写/伪造 manifest 或把它升级 generation。恢复旧 bytes 并不宣称这些 bytes 对当前源码 fresh。若当前 inputs 已变化，正常 decision 可继续 focused/full。
无需用 assertBuildFresh 代替输出匹配：它会结合当前源码摘要，可能把“已经提交但其后源码又修改”误当未提交；恢复判定只确认已提交输出身份，输入更新由正常 decision 负责。
路径/大小/hash 可沿用当前 checkOutputsValid；至少要求 manifest.schema 正确与完整输出 bytes 匹配。生产 manifest 还有 rootIdentity/outputDir，可校验显式不一致，但既有合法旧测试 manifest 缺这些字段，不能未经讨论新增 schema 迁移。mtime 不参与 commit 确认。

5. 最窄回归夹具与独立 oracle

该夹具证明真实子进程退出后的恢复 API，不宣称启动过 Fable，也不称真实 copy 中途 SIGKILL 证明；没有 sleep、随机时序或 mock recovery。它可迁到 distribution/005 作为最小正式回归。下一轮可用 012 既有真实 Fable fixture 补 copy/verify 切点的 OS 中断集成证明，但这不是发现当前确定缺陷的前提。

必要配对正例：完整新 dist + writeManifest(actual outputs) + 遗留旧 backup，恢复保留新 bytes、删除 backup、manifest 原 bytes 不变。
最小反例矩阵建议：缺/损坏 manifest；旧 manifest 与非空 partial；路径数量相同但单文件 bytes 不同；少/多输出；仅空目录。后三类能阻止把修复退化为“manifest 存在”或“文件数量相同”。
再复用现 005 runBuild no-op 接线样本，把 staging 后 dist 改成非空未提交值；仅恢复成功才能在无编译情况下 no-op。另以 012 未归属生产源作下一 build 的前置拒绝，断言 prior manifest/bytes 仍存，可直接证明后续失败不会丢 last-known-good。

范围边界：未审计 symlink/权限/磁盘满/掉电 fsync 可靠性，也不宣称解决 clean 模式或 focused copy 的所有崩溃事务性。当前修复应只关闭新增 full staged recovery 错把非空当 commit 的漏洞。
