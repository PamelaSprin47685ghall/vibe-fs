三、四例共有的 foreign、launcher、HOME 与 tempdir 证据

1. launcher
四例均失败于 support252，因此 support248–251 的 launcher close 已 fulfilled，且 {code:1,signal:null} 精确断言已通过。caller launcher 本体的关闭有测试控制流证明。

2. foreign
生成的 foreign 先写 foreign-ownership.json，再输出实际 {pid,pgid}；launcher await 此 ready 成功后才调用 superviseNodeTest（support80–86、179–196）。所以 foreign 准备成功，不是 Foreign group exited before ready。
生成 launcher 的 finally 无论 marker/caught 记录是否失败，都向自身 foreign 发送清理信号并 await foreignSettled，再执行真实 processRows 记录 foreign-cleanup.json（support219–230）。raw AggregateError 的 errors 只有 supervisor 错误和 marker ENOENT，没有 foreign close 或 native cleanup-query 错误。
外层 finally 又依据存在的 foreign marker 做 reclaimCapturedGroup 和真实 exact PGID empty 断言（support314–320）。最后没有 support334 的 cleanup AggregateError；因此按此未修改源码的控制流，可重建 foreign 的该最终判据没有失败。
但 foreign-cleanup.json 的 live 数组在 support299 的业务断言没有触达；所有实际 foreign 数字及 marker/receipt 被最后目录删除，raw log 未输出。故本报告只能注明“foreign close/最终 cleanup 路径完成且没有报告清理错误”，不能伪造一张保留了具体 PID/PGID/原始 native rows 的独立证书。更不能声称失败被 caller 捕获时 foreign 仍活着：该 caught.json 断言完全未执行。

四、能否漏掉尚未登记的 monitor：存在明确的证据/清理覆盖缺口

tool marker 是晚写入：probe 先 spawn detached monitor，monitor 再 spawn detached tool，tool 再 spawn child；等待 child ready 并完成三次 native metadata 查询后，才原子提交 tool-ownership.json（support68–77；verification-owned-tool46–49；verification-tool-monitor105–109）。因此“不存在 marker”不是“尚无 monitor/tool”的判据。
外层 finally 对缺失 marker 直接 continue（support315）；若 tool marker 始终未出现，既不会执行 exact tool/monitor 清理，也不会把该 inventory 缺口记入 cleanupErrors。然后它仍可删除目录和 foreign/suite 记录（support325–327）。
三个人为 fault 场景的 inspectProcessTree 又在返回真实 native snapshot 前依赖这个晚 marker（support128–129），所以此次 initial-capture 将全部已取得但未返回的实际 ps 输出丢弃。supervisor 无法得到候选 group，更不能凭空补猜 PID。
normal 没用这条 fixture seam，实际 capture 非空，但 drain ps 超时；组号只在局部 Set，没有进入失败收据。原 cause 得到保留，具体资源 identity 仍丢失。
生产 monitor 的 lifeline 在父 worker 死亡后预期触发 reclaimTool，尝试 kill exact tool group 并有界观察，然后退出（verification-tool-monitor58–98）。这是可能完成回收的实际机制，却不是此次运行已完整回收的证据。不能从 launcher close 或最外层 group99289 accepted=true 推断 detached monitor/tool 完成。

因此，这轮既不能补“所有已创建 monitor/tool 排空”的证书，也不能通过猜测组号或事后扫杀来修饰结果。没有保留精确 detached identity，当前不执行 ps；即使只查已知 inner/launcher PID，也无法填补 detached inventory 缺口。
