1. 每次注册独立身份

PhysicalAcceptance.fs:51 的 register 每次分配新的 CallbackRegistration record，dictionary 保存 record；Dispose 比较当前 record 与本次 record 的 ReferenceEquals 后才 remove。比较对象不是 callback function。
所以：同一个 callback instance 再注册两次，得到两个不同 registration/lease；释放旧 token 或重复释放旧 token不会删掉较新 token。没有 token 来源字符串猜测、全 key disposal 或 second registry。
现有正式证明：dispatch-protocol/007 的 root/continuation same-callback independent leases、different later observer、old release twice 三类行为。

2. Accepted snapshot、旧 lease cleanup 与 callback 重入

PhysicalAcceptance.accepted 先在 gate 内移除当前 callback、取出并移除同 key 的旧 waiter array，再在 gate 外通知被取出的 callback；finally 无论 callback 是否抛错，都结算旧 waiter snapshot 为实际 Accepted physical。
若 callback 重入 register/await：它们进入新 record/list；旧 lease Dispose 的 identity 比较失败，旧 confirmation 的 releaseWaiter 在新 list 找不到旧 TCS，不能删除新注册或新 waiter。若旧 waiter snapshot 已被 accepted 取出，subscription.Dispose 不会把它改判为 released/Unknown；实际 Accepted 的 finally 仍负责结算它。
这是一条源码上的顺序证明，不等于新跑了“callback 重入”的正式 case。当前 root/continuation callback throw 与两个独立 waiter 的 Accepted 保真有正式覆盖；accepted 后旧 lease 释放不会产生额外 Notify，因为 lease 只有 remove 操作。

3. waiter 的 timeout/release 只拥有本 invocation

beginConfirmation 每次有独立 TCS + released TCS。releaseWaiter 按 ReferenceEquals 移除自己，只有成功移除且 list 真空才删 key。timeout finally 调自己的 subscription.Dispose，既不调用 cancel，也不删 callback。raceTimeout 的 finally 清 timer。
accepted/rejected/explicit cancel 仍按 exact PromptKey 取 snapshot 广播，保留原 key-wide verdict 行为。timeout 先完成则自己的 outcome 为 Unknown；随后实际 Accepted 可以结算其它仍活跃 waiter 并通知 callback。Accepted 先取 snapshot则旧 cleanup 不能伤到后代注册。
现有正式证明：007 的单个 timeout 保留另一个 waiter/callback、两个 waiter 都 timeout 后仍可观察 physical，以及 callback 抛错仍使独立 waiter Accepted。
gen182 的 native timer 尾巴已定位为测试在创建原生 10000ms timer 后才切 mock API；007 现在在 Host effect 前启用 mock，原 50ms independent waiter 与断言保留。不是生产 timeout 增预算修补。

5. Unknown 与 Closed

Send 的 Await Unknown 只 releaseRegistration 本次 callback，并在 finally 释放本次 confirmation；不调用全 key cancel，不改另一 caller waiter或 durable Pending。Detached OutcomeUnknown 仅记录诊断，保留 Pending 与 owner 持有的观察；确定 native Refused/明确 Abandon 才走原 exact key verdict/cancel路径。全源码的 PromptPhysicalAcceptance.cancel 生产调用只在 Dispatcher.Abandon，不在 Unknown 或 local scope Dispose。
SyncDelegateCallAcceptance.Close 原子 Closed 后才取资源数组；AttachDisposable 在 Closed 时立即 Dispose，Accept/Owns 在 Closed 时分别 no-op/false。BindContinuationAcceptance 捕获具体 call 的 acceptance owner，要求原 accepted root + accepted physical，后续 Notify 不再查 latest child/call。exact pop、fail、invocation cleanup、ClearAll 都关闭该 call 的 acceptance，旧 continuation 的晚 Notify 无法转给新 call。
Fork PromptAcceptanceScope 同样 Closed 即拒收、迟 Attach 即 Dispose；notifyAndClose 保留 finally dispose/onClosed。Runtime 的 registry 在 observer shutdown 时置 None；原来捕获的 sender仍经 ObservePromptSend 检查该 actual registry，Closed 不进入 send，因此不写新 claim或调用 Host。Unknown scope保留到实际接受/本地 detach；Rejected/throw 释放自己的 scope。detach 不调用 whole-key acceptance cancel，也不改 Unknown claim truth。
