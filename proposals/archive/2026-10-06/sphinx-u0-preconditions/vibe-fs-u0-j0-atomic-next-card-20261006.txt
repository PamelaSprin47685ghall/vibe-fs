五、U0-A0 最小 Store settlement 状态机（先冻结再改）

IEventStore.Append 总签名仍 Task<Result<AppendReceipt,AppendError>>。
Requested：本次完整 typed event list；Prepared：唯一 Integrator.PrepareLive 原成功结果中的
DurableEvents/Cuts 数据，不能含 Commit closure，不用 request 代替 cut-tail-expanded list。
Prepared=None 在 exact duplicate/no-op 原路径是真实的（原代码根本不调用 PrepareLive）。
Cause 是 native exn/JS Error 原对象；Phase 有限表。无 string/obj global lookup，无重新读 history。

建议阶段：GateAcquire、Preparation、BeforePhysicalAppend、PhysicalAppend、DurabilityBarrier、
CurrentCommit、StoreRelease。内部状态只服务本次 await：Received→GateHeld→Validated→
Prepared→PhysicalAttempted→BarrierDone→CurrentCommitStarted→CurrentCommitDone→Released。
重复/no-op：Validated→NoFreshEvents→Released，不进 PrepareLive/append/fsync/Commit。
原纯 refusal 仍是 StorageInvalid 或 preparation refusal，不发明原 native cause。

关键界线是 ProcessEventLog 真 AppendAllText/appendFileSync 调用之前一刻；进入 append 函数
不等于开始写，encode/ensureDirectory 仍可能 prewrite 错。物理 owner 必须暴露有类型的
阶段失败结果或一个严格本次调用的 phase seam；选择须 root 冻结，不能改所有 withStoreLock
调用成事件 Unknown（它还服务 payload/Git）。更不能用 Error.code/message 猜已写。

归类：
* 原 known validation refusal且Release正常：保原拒绝，零新写、Current不变。
* native prewrite失败：AppendNotAttempted，原 cause/phase 与 request，无新 syscall。
* physical syscall尝试后 append/fsync/close失败：CommitUnknown，保存 prepared；不执行
  Current Commit。cold可能有新行，不把 live旧当未写证明。
* 原 Commit 完成再抛：CommitUnknown，live可已新；禁止回滚或称未执行。
* fresh成功且Release失败：CommitUnknown + StoreRelease；真实 bytes/live/cold仍新。
* duplicate/[]成功路径Release失败：NoNewWriteReleaseFailed，Prepared=None、零新追加，
  既有 canonical 事实保持；不是 Unknown，也不是那个旧事件 NotCommitted/不存在。
* 原 validation refusal后Release再失败：保 typed prior rejection与真实 release cause，
  不能统一 Unknown，不能 native异常遮掉 IdentityCollision/MissingParent。
* physical主错+Release错、fsync错+close错：primary Cause/Phase不换，cleanup failures显式
  保存第二个真实对象；单错绿不证明双错。每个实际 native Release 至多执行一次。

carrier 至少 Requested/Prepared/Phase/Cause；双错需 finite PriorPreWriteRejection 与
CleanupFailures，后者只装这一次调用的真实错误，不递归复制 AppendError 不造万能error bag。
正常 append只有完全落盘、原Current Commit、原Release完成才返回Ok；unknown不publish。
durable-events 004/006/013/017/019/021/024是不同义务，历史NDJSON不变，不改retention/seal。
