1. 最窄 Store 合同

原 IEventStore.Append : EventEnvelope list -> Task<Result<AppendReceipt,AppendError>> 保留。
新增有限数据，不传 physical lock/路径/Git/Integrator/Commit closure：

  PreparedAppend = { DurableEvents:EventEnvelope list; Cuts:SemanticCut list }
  AppendPhase = GateAcquire | Preparation | BeforePhysicalAppend
              | PhysicalAppend | DurabilityBarrier | CurrentCommit | StoreRelease
  AppendFailureEvidence = {
      Requested:EventEnvelope list
      Prepared:PreparedAppend option
      Phase:AppendPhase
      Cause:exn
  }

AppendError 原 StorageInvalid/SemanticCut 保持原法律含义。PrepareLive 正常 Error(reason)
也仍是纯准入拒绝，不能伪造 exn 或标 Unknown。现 AppendFailed(reason) 若保留，应仅
用于这一已有纯 preparation refusal；真实 exception 分支不再塞进它。

建议增加三个明确分支（名字可由主 owner 冻结）：
  AppendNotAttempted of AppendFailureEvidence
  CommitUnknown of AppendFailureEvidence
  NoNewWriteReleaseFailed of AppendFailureEvidence

最后一支不是 Unknown 也不是“旧 event 未提交”。它表示本次没有任何 fresh event
syscall，但 successful return 所需 native Release 失败；exact duplicate 的旧 canonical
事实仍存在。empty request 的相同 Release 边界也归此类，不硬返回 Ok。

实际原代码 fresh=[] 直接 AppendReceipt.empty，未调用 PrepareLive。因此 duplicate
的 Prepared=None 必須诚实保留，不能为方便把它编造成 Some {Events=[];Cuts=[]}。
更不能从 Prepared.IsNone 推断完全重复：acquire/prepare 尚未发生也可能 None。
它由独立 error case NoNewWriteReleaseFailed 明确说明，免添“prepared empty”等假状态。

Requested 是本 Append 收到的完整原 list；Prepared 是唯一 oracle 真 PrepareLive 的
原 DurableEvents/Cuts 数据，保 actual ProjectionCutTail，不能用 request 替代。
Cause 原 native Error/F# exn 对象保持引用。Phase 指原 owner 的正在执行边界。

物理尝试边界在 ProcessEventLog.append 的真正 AppendAllText/appendFileSync 调用前，
不在进入 append 函数时：encode/ensureDirectory 都可能在 syscall 之前失败。
DurabilityBarrier 包含 open/fsync/close；CurrentCommit 在实际 prepared.Commit 调用前。
StoreRelease 在真实 await gate.Release 前。局部 scratch 只负责本次调用，不是 registry。
完整 catch 必须覆盖 acquire/work/release Task。generic withStoreLock 同时被 payload、Git
sync 使用，不能全局把其所有失败改称事件 CommitUnknown。

2. 对当前 Current/提交法的有限分类

预写 native 失败 -> AppendNotAttempted；零新行，Current/head 不推进。
append syscall 已调用 -> CommitUnknown，不能凭 error.code、Current 缺失判未写入。
append/open/fsync/close 抛错 -> prepared 未 Commit，live Current 仍旧；cold 可有新事实。
原 Commit 完成后再抛 -> CommitUnknown；live Current 已新，不准回滚。
fresh append/Commit 成功，Release 抛 -> CommitUnknown；Current/bytes 已新，不准称未写。
duplicate/empty no-op，Release 抛 -> NoNewWriteReleaseFailed；零新写，旧事实/Current 保持。

WHAT004 要真实 physical settle + release 后才可成功；WHAT006 不许从内存/退出码反推
commit；WHAT013 对“未成功 append/未执行 Commit”要求原 Current 不变；它不授权 post-
Commit 异常时伪造旧 Current。WHAT017 禁止为分类扫 history；WHAT019 禁止第二 fold；
WHAT022 规定 pure contract 到 physical runtime 单向。

3. Foundation/Journal 的真实 DAG；S0 与 J0 必须分开设计

现在：eventstore-model-contract -> foundation-outcome；port-contract -> model + outcome；
StoreTypes 所在 port-contract 还包含 Port 与 EventStoreHandle。Outcome 再直接引用
StoreTypes 当前会成环。

逐文件核实：Model/StoreTypes/Port/EventStoreHandle 的 fs/fsi 都没有使用 Outcome，但
删除无用依赖仅解决 graph cycle，不解决领域归属。scripts/checks/subsystems.mjs:62--65
禁止 runtime-platform 的 Outcome 依 persistence 的 Model/Port/result；两种 Outcome->
port/result 方案都不合法。root已明确拒绝此方向以及 obj/string carrier绕门禁。

U0-S0 可把 StoreTypes.fs/.fsi 原样归到新 eventstore-append-result-contract locality，
依 model/identity；原 port locality保 Port/EventStoreHandle并依result，Model删除未用
Outcome边。Foundation Outcome 暂不反依赖任何 persistence capability或模型。
这种提取让请求/结果/错误属于durable-events的pure contract，不移动到 Foundation。

U0-J0 应将 JournalFailure/JournalUnavailable/CommitResult/JournalAppendFailure 与其
renderer真正迁归独立 durable journal-result contract（namespace Persistence.Journal；
不要试图跨两个文件拼一个 Foundation.Outcome module）。FoldRejection可暂留Foundation，
其 neutral fold拒绝语义不因Journal迁走改变。新journal-result依identity、Foundation
残余pure结果、append-result；IJournalWriter/AgentJournal及各领域journal port依它。
不得 Foundation->Journal。全部实际fs/fsi调用方与locality必须人工迁移，旧namespace
不留facade/re-export以回避清理。现 direct/transitive compile成本由ci_audit独立量算。

S0可以先取得原API红，但不能在S0生产提交中让Journal遇到新case立刻再stringify：
Store、native、必须迁移的直接结果consumer需一个原子闭环，或S0暂止于测试/contract
准备。J0完整消费者证据未取得时，不称整个U0已完成，也不开Host首次派发。

Journal 需无损承载新 typed carrier，不在 EventStoreJournalWriter.formatAppendError
提前 render。实际下层 cause 保同对象；最小 poison record 应含 FailedAppendEventId +
原 AppendError，字段不要叫 AttemptedEventId（预写错误未尝试）。firstFailure 不再只有
string。describe 是最后的人读 renderer；native Surface 必须传原 cause 引用供 strictEqual。

RuntimeStarted 的 store append 与业务 store append 是两次不同调用：
 - lazy init fsync/release Unknown，可有 RuntimeStarted 行；该次 business 尚未构造或发送。
 - 返回该 business EventId 的 NotAttempted/WriterPoisoned，poison 指 init 的原 EventId与
   carrier；不能因 init Unknown 返回 business CommitUnknown。
 - 后续 business 也 NotAttempted，保首个 carrier，同 cause，零新增 store/syscall。
 - 已成功 init 后 business 真 Unknown，才返回该 business CommitUnknown。
 - 已知 StorageInvalid/纯 PrepareLive refusal 不能再按 writer 当前 blanket Error
   分支变成 CommitUnknown；是否沿用现 writer poison政策与是否 attempted 是两个问题。

旧 JournalUnavailable 注释把 NotAttempted 等同“known-not-committed”；这不适用 general
Store duplicate/no-op（事实本来已存在）。新 NoNewWriteReleaseFailed 不得硬映成这个
NotAttempted 或 Unknown。实际 Journal 随机产生新 EventId，正常路径不产生 exact
duplicate，但 adapter exhaustiveness 仍需明确该独立 operational failure，不能 wildcard
吞。若本包不迁移它，只能结算 Store boundary，不宣布所有 Journal/consumer 已闭。

5. Release 前已有原业务拒绝与复合异常

原 work 返回 StorageInvalid 后 Release 也可抛。这里零append，不可统一 Unknown；也
不可只留下 release Error 而丢原 IdentityCollision/MissingParent等typed拒绝。
最小补充建议：
  AppendPreWriteRejection = StorageInvalid of StorageInvalid | PreparationRejected of string
  AppendCleanupFailure = { Phase:AppendPhase; Cause:exn }
  carrier增加 PriorRejection:AppendPreWriteRejection option、CleanupFailures:list。
仅原 Store实际的 pre-write拒绝属于这个subset，不把已durable的SemanticCut假称pre-write。
原正常拒绝仍保 AppendError.StorageInvalid/AppendFailed；Release发生native异常时
AppendNotAttempted carrier保存原typed拒绝、Phase=StoreRelease、Cause=原release对象。

若物理/Commit主异常之后Release再错，primary Phase/Cause保持原异常，cleanup表另添
StoreRelease原对象；fsync+close两个native错同理。列表只装本次真实cleanup，不递归
AppendError链、不aggregate覆盖原cause、不靠旧Error.message解析原validation类别。
若本包不做复合cleanup，必须保留未证停止线；不能称“完整cause保留”。

需要正式额外正反例：正常collision保原拒绝且零write；collision+forwardRelease错
保typedcollision和exactrelease Error，前后字节/live/cold原事实不变；prepare拒绝+release
同理（prepare原能力seam，不造假businessfold）；physical主错+Release错保两个真实对象。
