B4-O0a 原状态账的验收不由本卡重开。H0b 的跨 process 首次接纳/物理 effect 许可由原存储 owner 另包解决。

一、结论

目前没有一个可直接装配的真实 executable inquiry profile。原 GoalSpec 已持久保存用户正文，但它没有进入 PluginContext；MaterialRefs 是经校验的身份字符串，不是材料读取证据；Registry 与 Plan/Observe/Render 也没有生产装配调用链。继续在现 Driver 的 empty envelope 之后调用 Host，会把这些缺前提洗成“已派发”，不可采用。

可以独立在约一小时内结算的纯前置是 P0a：修唯一 Registry 的 executable/manifest 一致性及 DAG 每插件只返回一次。它有可用旧函数的真实行为反例，不依赖 H0b，不开放 Host。完整 profile、schema 文档、实际 Goal/material、公有 prompt 与 durable plugin lock 仍须另包施工；本调查不能标 B2 完成。

三、建议先做 P0a：唯一 Registry 的真实纯行为边界

生产 owner：Runtime/Registry.fs/.fsi；测试薄桥：现有 registered Runtime/Surface.fs/.fsi（只调用 Registry）；正式新 requirements/sphinx-v2/tests/009.test.mjs，标题唯一 WHAT[sphinx-v2-009]。旧 [020] 的保留依据记 README/验收，不另放第二 WHAT 锚点。

先定合同：
- bind 成功的每个 LockedPlugin，其外层 Manifest 必须完整等于 Execute.Manifest（包括 ImplementationHash、ABI、Capabilities、Dependencies、SchemaRef）。不一致具名拒绝，不能选外层或内层来洗成一致。
- 完成集与当前递归栈分开：完成的依赖不再执行排序；递归栈仍负责 cycle。每个 admitted ID 在输出只出现一次，依赖在 consumer 前。输出按原确定顺序，不能随机或按 arrival。
- 对同 ID 的列表输入，明确“完全相同 manifest 的重复注册是幂等去重还是具名拒绝”。不同 release/hash/ABI/schema 至少具名冲突；不能 Map.ofList 静默选择。相同声明不是两个不同 callable 身份已验证，真实 artifact binding 是后续 P0c 的义务，不用 function.ToString 比较。
- ordered/lockOf/compatible 的信任前提要明示；不能让公开兼容路径绕过 bind 后只验外层。此处不需要顺手扩大所有 manifest 字段格式政策。

最小正式矩阵：
1. A、B(dep A)：旧函数的 native 输出恰为 [A,B]；应先得到重复 A 的 business red。输入顺序交换仍相同。
2. diamond A→B/C→D：每 ID 一次、所有 dependency before consumer；重复初始化/规划不能发生。fixture 的可调用体仅为测试插件，不称实际 inquiry renderer。
3. outer ImplementationHash 与 Execute.Manifest 不同：bind 具名拒；ABI/schema mismatch 同类覆盖。先用旧 bind 得到实际 Accepted 的 business red，不用缺新 API/import 作为失败证据。
4. matching actual plugin 正控、missing dependency/cycle/multiple release 旧拒绝保持；compatible 对已定 lock 变 schema/hash/ABI 继续拒。

范围/停止：不改 Core/Driver/Commands/Host、没有 I/O/Current/cache、没有 fake plan score/cost、没有新 executable default。薄桥返回 native DTO，只调用真实 Registry，不复制 topo 算法。若 duplicate exact-registration 政策未冻结，先结 DAG once + outer/inner mismatch，不在一小时包凭猜测处理该政策。只标 Registry 前置有限完成。

四、完整有限 profile 的最短分包与冻结契约

P0b：纯输入/compiler（H0b 可并行，Host 保零）
- root 先冻结 PluginContext 的 Goal snapshot 与材料内容类型；建议传完整只读 GoalSpec 作为唯一目标，MaterialSnapshot 独立含 typed ArtifactRef、Revision、ContentHash、实际内容/可见内容与 selection/exclusion provenance。不要只添 GoalText 却丢目标 revision/约束；不要让 plugin 自行文件读取。
- composition/material owner 显式读授权材料，核 ref/revision/content bytes；插件接已取得快照。已有 Sphinx 内没有 material reader，必须先选实际 Host/workspace 可授权读取口并明确 ref→来源映射；MaterialRefs 不是文件路径许可。最窄初版可显式支持无附件（[]），并对任何 unresolved ref 具体拒绝，不把附件静默忽略。包含实际材料的有限 profile 则至少一件可真实读取并校验 hash 的附件作为正控。
- 纯 compiler 接 Current.Goal、已验证 snapshots、已绑定 schema documents、authorized resources/tools/model reference。合成 PublicEnvelope 与 PrivateTicket 时仅 public 有 Goal/material/question/response schema/work limits；private 承 label→实际映射。最终可见字节 hash 来自真正编译输出，不能用 source hash/template hash替代。
- Prompts.goalPrefix/render 可复用文字，不能直接传 worker 的“目标理解”替换 Current.Goal。普通零材料 inquiry 合法；Context.tryValidate currently rejects empty Included，要明确是否包含原 Goal 自身的 included artifact，而非虚造材料来满足。
- 正式 001：两个不同原目标、CRLF/空白精确保留；用户 amendment 改 revision/prompt，语义 proposal 不改 Goal。007：缺 material/content mismatch 具体拒、零工作/零效果。023：相同 source 不同实际可见字节 hash 不同、private mapping 不进入 public；没有真实 prompt bytes 时不标完成。

P0c：真实 schema/executable/ABI lock（先纯准备，再同 Current 持久接纳）
- profile owner 供应固定有限 canonical schema 文档（至少 planning response、render response、public envelope、private ticket/interpretation delta 的实际使用者所需）；SchemaRef.Hash=SHA256(canonical schema document UTF-8)，使用现 Foundation.CanonicalJson + 注入 sha256/Host.HostDigest。同 ID 两不同内容必须不同 hash；不用 schema 名、release label 或 empty。Core 仍只 opaque identity/hash；具体结果校验在 runtime/schema owner。
- ImplementationHash 的输入必须冻结真实“可执行 artifact”边界，不 hash源码标签/function.ToString。不把 build compiler/generated digest直接改名为 plugin hash。可定义 artifact closure 原字节证据（模块及依赖的内容索引与 digest）或整个已验证部署产物的真实 identity，但 root 必须先定其范围/变更意义。现 build-state 有 generation/输入/产物证据，没有已接 runtime 的 per-plugin artifact binding。
- ABI canonical descriptor 应覆盖实际 Initialize/Observe/Propose/Refine/context/delta contract，变 ABI 必改变 hash；ABI 变更要在 context契约确定后封存。schema refs/能力/依赖都是 manifest lock 的内容。
- Registry.bind(实际 ExecutablePlugin)→lockOf；creation 同一 canonical batch 写真实 lock，Current 冷恢复必须能拒同release不同实现/schema/ABI。无 lock 的历史只允许读取/已有合法回放，不据 ProfileRef 猜执行许可。具体新事实/版本及 seal compatibility由 parent 先冻结；不新 registry或 history fold。
- 正式 015 新测试文件：独立 canonicalJSON/SHA oracle核 schema、改内容/字段顺序正反；009：声明一致实际 executable正控与漂移拒；019：真实旧 @2 sealed历史保留或具名cut，不能手算旧seal。持久锁证明要独立新 process，而纯准备前置不能代替它。

P0d：一个有限 inquiry executable（仍不开放 Host）
- 只启用实际实现的 planning/rendering capability，不将 Catalog.all的17个空 schema probe作为 enabled。
- Initialize/Propose 产生实际规划 work 输入及 schema；Observe 从原 ResultAccepted canonical bytes严格 decode、验证目标/refs/schema/permission，返回真实 Graph/Work proposals 与 full delta。失败按 B4 outcome facts处理，修代码需新 hash +显式派生 inquiry，不同 inquiry 内 failed→pending→applied 重试。
- answer.now 作为实际同集合候选与真实 render 工单，成本来自明确授权 cost/model 配置，不从 empty map/默认0/方法名推导；模型/provider/tool permission 由 Host owner显式供应。没有 authority/真实成本则具体拒绝/排除，不填默认值。Unestimated没有估值即不可选，无固定“先规划”收益表。
- 002/029/018/032 各按唯一编号正式测试：无default gain、真实 answer.now/cost/insufficient reserve、 worker提议不扩大工具、动态问题仍原schema/lock。先有限 planning→render profile，全部 probes/questions另留E。

五、与 H0b 的关系和验收截止

P0a/P0b/P0c 的纯准备可与原 Store fresh admission 合同独立并行；持久 profile lock/public start 改动与 Commands/Core 的共享契约串行 owner。真正 Host execution 必须 H0b 首次接受 witness + effect-before intent门 + actual owner/profile/compiler 全齐，且原锁在 Host I/O 前释放。

P0 有 green 只表示真实输入/锁/编译/插件有限能力，不能宣称公开首个持久答案。B3 claim/submit及ticketHash/scope，B4 real HostSnapshot + accepted Observe，B5 accepted renderer→AnswerCommitted，installed SDK/cancel/receipt-loss/usage 等仍未闭合。此卡无构建、formal business red 或性能证明，只有源码与规范审计；后续必须 fixture-first red→实现→正式green→更新计划。
