2026-10-06。审查 gen180 冻结输入；没有修改仓库，没有运行构建、测试或新物理探针。以下是源码可达性与正式测试建议，**不是新故障的红绿证据**。

## 结论

旧 A 与当前 B 共用 child、Authority Root，旧 A 的 successor physical 已不属于 B 的 invocation acceptance 集时，`SyncDelegateRuntime.HandleTurn` 返回 `false`。`TurnWorkflow.observe` 把这个 `false` 与没有 SyncDelegate owner 的 turn 走同一 ordinary fan-out，因此旧 completed turn 可继续进入 `TerminalReporter`。现恢复矩阵只直接调用 Runtime 的 terminal helper，不能证明完整 Application pipeline 无副作用。

这条 completed ordinary 路径可达 XTrace capture、共享 terminal bus/sticky 更新，以及 provider-success ledger。没有找到它直接关闭 child authority 的调用。当前 B 是 `ExistingAuthorityContinuation` 时，B 的 SyncDelegate terminal subscription 忽略 `Completed`，也不会用 coarse `Failed`/`Aborted` 结算 B。因此本次未证明 B 被误结算或 authority 被旧 terminal 关闭。

## 规范约束

- `requirements/delegation/WHAT.md:97`，WHAT[DELEGATION-025]：completion 只能由本 work unit 实际接受的因果 terminal 单次认领；旧 run/sticky 不得结算新 work unit；晚到 terminal 幂等忽略。
- `requirements/interaction-authority/WHAT.md:78`，WHAT[INTERACTION-AUTHORITY-018]：authority closure 必须来自 exact typed durable lifecycle witness；Host observation 不能自行推断 closure。
- 不能仅从“Runtime 返回 false”推导所有真实旧 attempt 的审计材料都禁止落盘。旧 attempt 的物理证据、B 的 completion、共享 budget 与 authority lifecycle 是不同所有权；下一包必须先明确欲禁止的具体后果，不改大范围 policy。

## 为什么不能直接宣称真实 Host 故障

`Composition/Turn/TurnReconcile.fs:72` 只取当前 bound physical 之后的 assistant，不回退 root 后旧 assistant。`Scheduler.fs:470` 的 projection wake 要匹配当前 physical。`ReconcilePass.fs:108` 调 onTurn 后才记录 publish maps；`Program.fs:237` 的 token 包含 session/physical/provider run。它们排除了“从包含历史消息的普通新 snapshot 随意取旧 A”这种虚构前提。

publish map 按 session 只存最近 token，不等于永久历史集合；HostTurnObserver 在 Application 前还有真实 awaited interrupt/pre-turn/primary/XWire/preparation/fission 步骤（`OpenCode/Host/HostTurnObserver.fs:162,224`）。这只提示一个可能的在途旧 context 与新 assignment 的交错窗口，尚没有可执行证据。不能把人为 new `ReconciledTurn` 注入完整 pipeline 的结果，改称 scheduler/Host 的真实晚到故障。

## 最窄下一正式入口

建议先做 **Application owner 的有限边界覆盖**，沿现有真实 fixture 扩一个 terminal entry，不另建 runner、registry、fake event port 或 second lifecycle owner：

1. 复用 `SyncDelegate/Surface.fs:1355` 的 exact terminal turn 构造与 `:1409` 的 `observeRecoveryTurn`（它已调用真正 `TurnWorkflow.observe`）。新增 fixture operation 接受 actual A 的 session、physical、root、provider run 和原 terminal parts，返回 Task；构造 Observation context 后按 `:1426` 相同方式调用真正 `HostTurnObserver.observe`。**不要先调用 Runtime helper 再调用 Application**，否则同一 terminal 被人为重复处理。
2. A/B 均沿现有生产创建、managed ingress、真实 guard/retry/repair producer acceptance 建立；旧 A identities 从它们各自 actual receipt/turn 保留。B 完全 admitted 后，把 A 的已存在 terminal context 交给入口；不从 latest projection 拼 source。
3. 两个独立 case：已完成 A 的完全相同 terminal 重放；尚未完成 A 的 late terminal 首次到达。两者都先记录 B accepted physical、invocation acceptance frontier、live completion、active authority logical run/root，以及实际 XTrace/provider failure projection。
4. 使用现有真实 EventPort 的受控 observer 收集 root/provider run/outcome，`finally` Dispose 自己 registration；读 sticky 需真实 bus read/replay，不能另造队列充当生产 cache。只把得到的 shared-bus 变化记为观察，不预先猜它必然属于 B。
5. 检查 B 仍未完成、其 frontier 未吸收 A physical、authority 未关闭/更换；最后以 B 自己实际 producer successor terminal 正控完成 B，证明 owner 仍可用。完整 await 原 fixture close，消费者/listener 清理仍按现有 owner。
6. 若要检验 budget 分支，必须用实际 current authorized failure 写入建立非零 budget，再用真实 projection 读前后值；零 budget 下没有 append，不能声称证明清除防护。先核该 budget 是 logical-run 还是 work-unit 边界，明确预期后才能写拒绝断言。

这一步能取得 actual HostTurnObserver→Application fallback 后果，仍不证明 scheduler 真的会送出旧 context。若覆盖暴露需要所有权分型，再冻结最窄的 handled/ignored/unowned 契约及真实错误反例；不提前把整个 Host preprocessing 全部跳过，旧 attempt 的合法清理仍有自己的 owner。

## 完整 Host 在途交错的后续前提

要把上述线索升级为 Host fault proof，另需沿原 Scheduler/ReconcilePass 和 production onTurn callback，利用已有真实 awaited owner 的受控 ready/release 点，使 A context 已被原 source 选中而尚未进入 Application，期间实际 admit B，然后释放 A。不得替换 assistant selector、回退 binding、直接调用 fakeSource，或将 ordinary snapshot 中不可能被选中的历史 assistant 标成新 observation。此测试须保留正确 physical wake/consume token 的正控，证据不足时继续标“在途交错待证”。
