## 为什么改

原 Store 在通用 `withStoreLock` 的 work 内将物理异常压成 `AppendFailed(ex.Message)`，Release 又在 catch 之外。实际落盘后 fsync 抛错会被说成普通拒绝；新写、重复请求、空请求的 Release 异常都直接拒绝 Task。writer 把所有 Error 字符串化后归为业务 Unknown，初始化失败又丢失 `RuntimeStarted` 自己的身份。

先补正式 durable-events006，再构建旧产品。gen222 的 compiler digest 仍为 `3b68852916378431cd6e2b63b81a00708dd7a2ac04464ba2900a99512e6d37b2`，generated digest 为 `1a6a2f33f8d45040fdc559e572c3905980110e105fa92021d0591c87f9d72381`。正式 1/1 排空、3 pass/4 fail：normal 与两既有用例通过；fresh/duplicate/empty Release 拒绝 Task，fsync 被压成 `AppendFailed`。每个反例均先完成真实字节、live Current/head、实际 owned lock 释放与独立进程 cold reopen 的前提，再在结果分类处失败。outer74563 accepted=true/18.100ms。原始日志不能由后续绿替换。

## 有限合同

- `IEventStore.Append` 签名不变。原 `StorageInvalid`、`SemanticCut`、pure preparation `AppendFailed` 保留原含义。
- 新 `AppendNotAttempted`、`CommitUnknown`、`NoNewWriteReleaseFailed` 分别承接真正进入追加前的失败、进入物理追加后的不确定、明确没有新写入但释放失败。不是“Prepared 存在就 Unknown”。
- 保存原 Requested、实际 Prepared/DurableEvents/Cuts、九个阶段、原 primary cause 和按发生顺序保留的 cleanup cause。副故障不覆盖主故障，既有事实不会因重复请求释放失败而消失。
- Store 拥有 append 的 acquire/work/一次 release/settle；通用 `withStoreLock`、payload 和 Git 路径不作这次错误分类迁移。append 专用 durability helper 与原 unit/throw helper 分开。
- Journal poison 保存失败的原 eventId 和 AppendError。lazy RuntimeStarted 的 Unknown 属于初始化，当前业务为 NotAttempted；后续业务不再访问存储。业务 Unknown 不发布 committed revision/waiter，不声称真实 Current 回滚。
- Casebook、JS、Strength 保存自己的 operation/transaction/event 身份及原 AppendError，最后在 native 或工具边界渲染。Prepared JS 失败不执行文件修改；Committed JS 失败保留已经发生的真实效果，不自动重投或虚构恢复。
- 没有新追加的释放失败独立进入 execution policy 的 `NoNewWrite`：保事实及 exact fence，不授权 provider retry，不把资源释放说成成功；fatal 仍受实际结算前提约束。
- 只有实际 Unknown.Prepared.Cuts 才交 semantic-cut owner；未尝试的计划 cuts 不冒充已结算。Sphinx Runtime 构造必须显式提供 typed fatal capability，mapper 不直接调用 physical FatalProcess。
