## P2：公开重交 Surface 可以把同一个原 incident 交给第二个 owner，再次执行 callback

具体调用链：`SettlementSurface.fs:46-48` 的 `observeIncident(ownerB, incidentA)` 只以 `incidentOf` 验证 A 是真正的 typed incident，随后把原 `incidentA.Failure` 交给 B 的 `Observe`。`SettlementOwner.fs:32-35` 为该 Failure 构造一个新 candidate；B 的字典尚无该 EventId，`claim` 会登记并在 27-28 行再次调用 B 的 capability。

这不需要伪造 descriptor、F# runtime fields 或假的 AppendError：从一个真实 bad-payload Append 所产生的 callback 取得原 opaque incident A，再使用公开 API 即可到达。现有 descriptor 负控只拒绝普通对象，现有重复正控始终使用同一 owner，因此没有覆盖此路径。

范围说明：正确的生产 Fetch single-flight 只会把一次执行交给首 owner，没有证据表明正常 Fetch 会主动跨 owner 重交。漏洞位于本次新登记的公开 semantic Surface，它所表达的“原 owner 重交 / 同一 incident 一次”没有由 owner 归属验证守住；不要将它描述为已观察到的 installed Host 双 kill。

最小修法：保留 `Observe(failure)` 作为生产首次结算入口；为原 incident 重交提供 owner 方法，只在既有字典中找到相同 EventId 且值与入参是同一 incident 引用时，抛回该缓存 incident。未知或来自另一 owner 的 incident 明确拒绝，不构造新 candidate、不调用 capability。Surface 转发此方法。复用现有实例 latch，不加全局 registry 或第二份 owner 真相。

最小正式负控：复用 013 已产生的真实 incident A，建立第二个必需 owner B；交 A 给 B，断言明确归属拒绝、B callbacks 仍为空、A callbacks 仍为 1、原 append 数与 canonical bytes/index 不变。随后继续原 A→A 两次重交及原对象 identity 断言。

## 已核对通过的新增边界

- Access 的普通异常 catch 只位于 `Lifecycle.fs:283-293`，包住原 workflow/index；`Result.Error` 在 `refreshWhenTouched` 原样返回。Fetch 在该 Task 返回后才执行 owner，因而 callback 的原异常和返回后抛出的 typed incident 不在这个 catch 内。普通 observer 抛错仍按原 best-effort 保留；013 已有相应阳性控制。
- Refresh 从原 `CasebookBookkeeper.refreshStale` 的 Result.Error 进入 `observeMutationFailure`，之后才可能返回 stale；owner 拒绝未被外层 catch 转成普通答案。
- `CasebookStore.appendEvent` 保存实际构造的 EventId 与原 AppendError；Workflow 只包入 AppendFailure，incident 保存该 Failure。Unknown 的 Prepared 与 primary/cleanup Cause 不通过文本重建。新 Surface 的两个引用检查分别覆盖原 Error 与 Prepared，cause 则直接投影原对象。
- incident 只认 `AppendError.semanticCuts` 中本 EventId 且 Rule=Casebook 的 settled cut。NotAttempted / NoNewWrite 不因有 prepared 数据而升级成 fatal；普通 Unknown 空 Cuts 无 incident。
- 必需 owner 已从 Boot record → Hooks → CasebookTools → FetchTool 贯穿，Tools/Fetch 的 null 检查位于实际构造入口。没有 optional/default/global fallback。唯一新物理调用位于命名 composition binding `PluginBoot.bindCasebookSemanticCut`，F44 与 C02 也区分了这条绑定和 store 无物理 fatal。
- 同一 owner 的 claim 在 callback 前登记、callback 在锁外；callback 返回后抛原 incident，callback 抛错直接离开，重复交付不再次 callback。普通 native descriptor 被类型检查拒绝，没有从 descriptor 反向重建领域 incident。
- 013 的四个 cut 用例先核真实 malformed request、bad fact/cut-tail、旧 capture/payload、Case 双基线及独立 OS cold，再断言拒绝普通答案；新 `isIncident + strictSame callback incident` 比 native Error 构造器判断更贴近公开合同。
