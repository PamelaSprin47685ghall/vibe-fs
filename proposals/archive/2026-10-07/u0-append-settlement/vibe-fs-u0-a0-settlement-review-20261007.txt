1. Actual path and current failures

IEventStore.Append -> Store.createLocal -> ProcessEventLog.withStoreLock ->
validateForAppend (vocabulary, normalized identity/fresh subset, parents/payload)
-> integrator.PrepareLive -> PreparedIntegration.DurableEvents ->
ProcessEventLog.append (encode, ensure directory, appendFileSync, open/fsync/close)
-> prepared.Commit -> AppendReceipt -> native gate.Release -> returned Task.

Store.fs catches only inside the withStoreLock work closure. It turns native
exceptions, including CurrentCommit, into AppendFailed ex.Message. Gate acquire
and Release are outside that catch, so Release rejects the Task rather than
returning a typed result. WithStoreLock's catch attempts Release again, but its
released latch is already set, so this is not a second actual release attempt.
If work returned StorageInvalid and release throws, the original typed rejection
is simply lost. durabilityBarrier's finally-close can also replace an fsync error.

Fresh=[] returns AppendReceipt.empty without PrepareLive or physical append.
That is a different state from successful fresh append followed by Release error.
Prepared=None cannot itself identify a duplicate: acquire/validation/preparation
may also fail before any prepared result exists.

EventStoreJournalWriter.commitEnvelope encodes exactly one journal envelope and
calls Store.Append. On the first business call it first makes a separate lazy
RuntimeStarted append. Current error handling is lossy:
- formatAppendError reduces Store errors to strings;
- a business Error of any kind becomes CommitUnknown(eventId, WriteFailed text);
- RuntimeStarted Error becomes a string poison and business NotAttempted;
- a rejected Store Task bypasses these branches, poisoning neither firstFailure
  nor serial in the intended typed way; later accepted work/release can inherit
  the rejected serial task instead of a typed settlement.
AgentJournal publishes revision/waiter notifications only for Committed, which
must remain true. It currently routes CommitUnknown directly to WriteUnknown;
semantic-cut fatal handling exists only in Rejected. New Unknown-with-Cuts must
not bypass the actual fatal owner merely because its physical outcome is unknown.

2. Minimal contract proposal — names remain a proposal, not approved API

Keep IEventStore.Append's Task<Result<AppendReceipt, AppendError>> shape and
canonical event/receipt success vocabulary. No lock, fd, Git identity, physical
path, mutable integrator, or executable Commit closure belongs in its pure result.

Use the bounded fields already identified by U0's contract card:
  PreparedAppend = { DurableEvents: EventEnvelope list; Cuts: SemanticCut list }
  AppendFault = { Phase: AppendPhase; Cause: exn }
  AppendPreWriteRejection = StorageInvalid of StorageInvalid
                         | PreparationRejected of string

Three different error outcomes are required:
- AppendNotAttempted: exact Requested; Prepared only if actual preparation had
  completed; optional original typed pre-write rejection; primary native fault;
  actual secondary cleanup faults.
- CommitUnknown: exact Requested, REQUIRED actual PreparedAppend, primary native
  fault and actual secondary cleanup faults. The prepared data must include real
  appended cut-tail envelopes and cuts, not just the original request.
- NoNewWriteReleaseFailed: exact Requested and original Release cause. It carries
  no invented prepared result. Existing canonical duplicate facts stay committed;
  [] has no event whose existence can be inferred. Neither is a fresh write.

The first two can share a small native fault record, but do not use optional
Prepared/booleans to infer which outcome occurred. Requiring prepared data in the
Unknown case prevents an acquire failure accidentally becoming write uncertainty.
Ordinary StorageInvalid and pure PrepareLive refusal remain typed ordinary errors;
they do not acquire a fabricated exception or become Unknown. AppendFailed string
must no longer be the exception escape route; if retained, restrict it to the
existing pure preparation refusal, or rename that one case in the same migration.

Finite phases must describe actual boundaries: gate acquisition, preparation /
pre-physical work, physical append invocation, durability barrier, CurrentCommit,
StoreRelease. For fsync+close dual failure, label Close separately from the primary
barrier failure (a bounded extra phase, not an arbitrary string phase). Do not mark
physical append as begun at function entry: encoding/ensureDirectory happen first.
Conservative uncertainty starts immediately at the actual appendFileSync boundary;
do not infer no bytes from error.code. Full canonical bytes, not Current/exit code,
are the eventual commit oracle. No recovery scan belongs on the append hot path.

Reference identity is part of this carrier:
- Requested is the original F# list received by IEventStore.Append, before fresh
  filtering/normalization. Do not rebuild it from prepared or copy it for errors.
- PreparedAppend retains the actual PreparedIntegration DurableEvents and Cuts
  lists; it excludes the executable Commit closure. A mixed duplicate+fresh case
  and a real semantic cut prove request and prepared are not interchangeable.
- Primary and cleanup exn objects are the actual native/F# objects, not Message,
  sprintf, newly constructed Error, or a JSON round-trip copy.
- Surface.append currently parses JS into a new F# request. A strict JS input-array
  identity check would be false ownership. A thin F# verification owner must retain
  that real list/prepared data and expose referenceEqual observations, or forward
  those exact objects within the same process. Cross-process JSON can carry the
  boolean result of strict identity assertions, not the Error identity itself.

3. Small ownership algorithm, not a generic transaction framework

Append owns acquire/work/release settlement locally. Acquire failure has no gate
to release. Once acquired, work yields its original typed result/evidence; release
is attempted once regardless of work result; settlement then combines both facts.
- fresh success + release fault -> Unknown at StoreRelease with actual prepared;
- fresh primary failure + release fault -> primary Unknown phase/cause unchanged,
  append StoreRelease to secondary cleanup; never replace the primary;
- StorageInvalid/preparation refusal + release fault -> NotAttempted with original
  typed rejection plus exact release fault, zero new physical append;
- duplicate/[] success + release fault -> NoNewWriteReleaseFailed;
- successful release -> preserve the work result exactly.
ProcessEventLog's append boundary must supply truthful phase/fault evidence for
its own append/fsync/close operations; a narrow typed physical result or internal
phase handoff is sufficient. Do not put a generic injected transaction registry,
global phase state, or history-based commit inference around it.
Generic withStoreLock is also used by WritePayload and Git/Hook/Sync. Its consumers
must not inherit event-specific CommitUnknown. Keep append settlement local; any
generic primary+cleanup preservation change requires its own consumer evidence.

4. Journal's distinct init and business identities

Poison must retain { FailedAppendEventId; original AppendError }, not a string.
Use FailedAppendEventId, not AttemptedEventId: the failure may be pre-write.
Only the final human-readable describe function renders this typed carrier.

Business fresh Unknown -> business CommitUnknown/WriteUnknown with original
underlying uncertainty; no AgentJournal PublishCommitted/revision/waiter wake.
Business known pre-write refusal -> NotAttempted with its own exact original
failure, even if the existing poison policy is retained. Poison policy and
whether a write was attempted are different questions.

Lazy init Unknown -> the current BUSINESS EventId is NotAttempted. Poison names
the actual RuntimeStarted EventId and its exact original carrier. Business
envelope construction/Store.Append must not occur. Next business calls remain
NotAttempted and reuse the same first evidence/cause, with no extra Store calls.
Do not report init uncertainty as uncertainty of the caller's unattempted fact;
do not fabricate a business prepared envelope which was never created.

NoNewWriteReleaseFailed needs an explicit Journal/AgentJournal operational case,
not CommitUnknown and not WriterUnavailable's old 'known-not-committed' claim.
Although normal Journal assigns fresh GUIDs, its IEventStore result contract must
be exhaustive; a wildcard or failwith-unreachable discards a legal Store result.
Unknown carrying real Cuts still reaches the existing semantic-cut fatal owner
after settlement; a plain unknown renderer must not erase this obligation.

5. Atomic migration frontier

Current C0 source has StoreTypes only in eventstore-append-result-contract, with
Model/Identity dependencies. Journal Outcome currently depends on Identity and
neutral Foundation Outcome. It can depend on the pure append-result contract;
Foundation must not depend on Journal/EventStore, and Journal result must not
depend on Port/Core/Integrator/Host. This review did not validate a build or closure.

An atomic production change must include these actual loss points and their fsi:
- StoreTypes, ProcessEventLog, Store, EventStore Surface native error view;
- Journal Outcome, EventStoreJournalWriter, AgentJournal, Writer/observation
  surfaces and controlled IEventStore fixtures; keep accepted-prefix drain typed;
- Strength Store.appendToPublish and Durability wildcard mappings, PublishError
  and DurabilityPort result types, then their composition effect/fatal owners;
- Casebook Store.appendEvent's Result<EventId,string>, Workflow/Bookkeeper to the
  actual tool owner. Keep generated event identity; separate domain not-found
  errors from storage evidence; no new random-id retry after Unknown;
- Js TransactionStore's two Result<EventId,string> methods and ToolWorkflow's
  mapPrepareFailure/mapCommitFailure, which currently discard the entire error.
  Prepared Unknown permits no file effects; Committed Unknown follows existing
  transaction recovery with exact transaction/event identity, not 'not written';
- Sphinx Commands.appendRefusal and Mcp.Server.appendRefusal currently map all
  failures to PERSISTENCE_REJECTED. Use an explicit unknown/no-new-write vocabulary
  with exact command/inquiry identity; no replacement command or child dispatch;
- Journal semantic decision sites including ChatExecution.Acceptance and plugin
  Todo terminal checkpoint settlement. Current WriterUnavailable releases retry
  markers while WriteUnknown/FactRejected keep them. A no-new-write operational
  error must not accidentally enter the former branch and grant a fresh retry.
  Pure pass-through journal adapters can retain the carrier without new policy.

Exhaustive compilation is necessary but insufficient: wildcard/string renderers
are precisely where the compiler will not reveal lost semantics. Callback test
surfaces and public renderers require explicit new-case observations. A smaller
Store-only production commit that immediately stringifies new cases downstream
does not complete U0-A0; a contract/test-only preparatory commit is the safe cut.

6. Minimal native/controlled cases and independent oracles

A. Fresh native Release forward-then-throw. Existing original native red can be
registered as formal durable-events/006. Only the actual owned lock path is
patched, native rm succeeds first, then the same Error travels via its original
callback. Prove canonical full bytes + live event/head/Current + actual lock gone
+ independent cold read first; then assert Unknown/StoreRelease/actual prepared
and original cause. Keep zero Git calls. Original red is a Task rejection, not a
missing API. It proves post-removal error, not recovery of a lock never removed.

B. Duplicate and [] Release fault. Seed real normal canonical fact, snapshot full
file bytes, replay exact request with native release fault. Assert zero NEW append
/fsync, unchanged complete bytes/live head/cold fact, NoNewWriteReleaseFailed and
no prepared result. Separate [] case with no old fact inference. Normal duplicate
/[] release succeeds as a positive control. Counters alone do not prove durability.

C. CurrentCommit forward-then-throw. A registered F# verification owner creates
the real CanonicalIntegrator and forwards every method. Only its real successful
PrepareLive Commit is wrapped: originalCommit(); throw originalError. Use actual
Store.createLocal. Prove full bytes/live Current already advanced/cold matches,
then Unknown(CurrentCommit), exact request/prepared/cause. Do not mutate a private
generated object or reproduce the fold. A pre-Commit throw variant has old live
Current but the same actual disk fact/Unknown; these are distinct observations.

D. Physical append and fsync faults. Forward original own-file append or own-fd
fsync, then throw. Full bytes/cold witness must be nonzero; Current remains old
because Commit did not execute. Preserve primary phase/cause and perform actual
close/release. Add fsync+native-close and primary+Release dual faults to prove both
original Error objects survive. Non-target writer positive control stays normal.

E. StorageInvalid + Release. First persist a valid event; submit same id/different
canonical payload. Without fault expect original typed IdentityCollision and no
new bytes. With actual native Release fault, expect NotAttempted, SAME original
typed collision detail, exact release Error, zero append/fsync and unchanged full
bytes/current/cold. This is not duplicate and must never become Unknown. A real
PrepareLive refusal + release error is a separate typed-preparation case.

F. Lazy RuntimeStarted Unknown. Real Journal writer/AgentJournal, first business
fact and a second queued/follow-up fact. Fault the actual FIRST init append's
fsync or Release only. Disk/cold may contain RuntimeStarted but zero business
events; both business results are NotAttempted, first poison names init and
reuses the same carrier/cause, no business revision or wait-notification publish,
no second storage call, ReleaseAsync drains. After successful init, a BUSINESS
fault is the contrasting CommitUnknown case. Do not reuse a sealed WriterId in
the independent cold process; open with a fresh writer identity.

G. Real semantic cut with release/fsync Unknown. Reuse the actual bad-fact/cut
fixture from durable-events/021 (not a fabricated prepared.Cuts field). Prove the
prepared and actual canonical bytes carry bad fact+ProjectionCutTail and that the
existing fatal owner receives settlement evidence. Unknown must not grant effect
or merely return ordinary WriteUnknown. Full WHAT024 mandatory-capability/crash
closure remains its own TODO unless actually exercised; do not claim it by type.

H. Consumer mapping negative controls. At their real public entry, feed a legal
controlled new typed settlement and prove original identity/evidence still reaches
the owner and effect count is zero (with a nonzero committed positive control).
This proves mapping, not native I/O. Native A-F remain required separately.

7. Stop conditions / unclosed boundaries

- Freeze names/Journal cases before implementation; no string/object catch-all
  to avoid project dependencies or consumer migration.
- Real CurrentCommit seam and reference-identity observation must exist before
  calling their absence a business red. Controlled results cannot stand for I/O.
- No all-history read or automatic resend/truncate/rollback after Unknown. Partial
  lines, partial multi-event writes, actual native release unable to remove lock,
  process death and recovery remain unproved by forward-then-throw full-write cases.
- AppendUnknown does not provide Sphinx first-intent fresh admission, and releasing
  the storage gate must precede any Host/network effect. This package adds no Host
  dispatch permission and cannot close H0b.
- Original native Release reds are scoped evidence; normal controls, cold reads,
  old 007/008 classifications, 017 no-history cost and locality gates must remain.
  No test/build was run in this review, and no proposed API is marked implemented.
