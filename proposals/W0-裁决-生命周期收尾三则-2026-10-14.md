## 裁决一：early closure 写入点固定在 `Persistence/Journal/Surface.fs` 的 `appendAuthorityLogicalRunClosed` 窄端

### context / constraints

- `AuthorityLogicalRunClosed` durable 事实链（fact → fold → PromptAuthoritySet）是 activeLogicalRun 归零的唯一有证据 writer，见 [interaction-authority-018](../requirements/interaction-authority/WHAT.md) 与 [participant-identity-009](../requirements/participant-identity/WHAT.md)。每个 AuthorityRoot lifecycle 必须收敛为 exact durable closure，witness 必须来自 durable terminal，而非时间、信号或 Host 观察。
- 写入必须同时满足：有 exact witness；不创造第二个 writer；失败 fail-loud；重复 transform 幂等。
- 调用时机在 Manager deliver 落盘之后的同栈路径内，而不是异步兜底链。

### chosen path

- 窄端写入点：`src/Wanxiangshu/Persistence/Journal/Surface.fs:461` 的 `appendAuthorityLogicalRunClosed`；公开签名在 `Persistence/Journal/Surface.fsi:24`。注释明确契约：经 process-local shared journal owner 写入、缺失共享条目时拒绝而非创建第二 writer、已关闭投影为 no-op 以保证重复 transform 幂等。
- 拒绝型 acquire：`SharedAgentJournal.acquire` 传入 `refuseMissingEntry`（`Surface.fs:471-483`），缺失 shared entry 时 `failwith`（fail-loud），不新建 runtime。
- 单写者守卫：只复用既有 shared journal entry；acquire 失败即拒绝。
- 过滤：仅 Manager × HumanRoot 的 active profile 才发 closure fact（`Surface.fs:494-505`），`ClosureWitness = retirementId`。
- 幂等双保证：写入侧「已关闭 no-op」+ fold 侧幂等（`Interaction/Authority/Fold.fs:114-138`：run 匹配才 close、active 为空返回 `Ok []`、冲突 fail-closed）；同事实重放按 [durable-events](../requirements/durable-events/WHAT.md) 的追加语义幂等。
- 调用点（seed 交付链同栈）：`src/Wanxiangshu/Mission/Lifecycle/Surface.fs:948-951`——receipt 为 Committed/Replayed/Observed 且 `completedManagerDelivery` 取到 retirementId 时 `do! JournalSurface.appendAuthorityLogicalRunClosed dir workId retirementId`。

### alternatives 及拒绝原因

- **异步 provider transform 兜底链**：保留为后备路径，但不作为主写入点——其时机与因果弱于「交付落盘后的同栈调用」，且把 closure 与交付事实的时序关系交给调度偶然性。
- **Workflow 直写**：拒绝——跨层双写。Workflow 已有自己的 `appendManagerAuthorityClosure`（`Mission/Manager/Workflow.fs:215-233`）；在 Journal owner 之外再落一份 closure 会形成第二个 writer，违背单一 writer 纪律。

### consequences

- 缺失共享 runtime 时 closure 写入 fail-loud，不会静默制造第二 writer；写入失败不降级。
- 边界清晰：事实编码、shared acquire 语义、过滤留在 Journal owner 内部；Lifecycle 调用方只传 `commonDir / sessionId / retirementId`。
- 验证状态：实现与调用点按最新快照只读取证，**未验证/待运行**（构建与测试由 DevOps 执行）。

### 什么会触发 revisit

- `appendAuthorityLogicalRunClosed` 的 Manager × HumanRoot 过滤与 [interaction-authority-018](../requirements/interaction-authority/WHAT.md) 声明的五类 `ExpectedClosureKind` 出现需要对齐的扩展；
- shared journal acquire 需要支持非共享 runtime（当前无此消费者，出现即重新裁决）；
- GAP-123 的 durable 链测试落地后发现幂等双保证有缺口。

## 裁决二：RequestIdConflict 结构化返回（库侧 `Work.fs` 重放分支）

### context / constraints

- 同一 requestId 搭配不同载荷是可预见的冲突，不是意外异常；宿主需要可分类、可决策的结果面。
- 库侧 `Work.execute` 是重放/冲突判定的唯一 owner；冲突必须零写。

### chosen path

- `wanxiangli/src/lifecycle/Work.fs:203-209`：`TryReceipt requestId` 命中且 hash 一致时返回 `Replayed`；hash 不一致时返回结构化结果 `{ status: "Conflict", revision, result: null, record: "RequestIdConflict" }`——不写、不抛。同一来源见 `wanxiangli/src/eventstore/SqliteJournal.fs:123` 的冲突命名。
- 该分支与 `Commands.decide` 的 `Refuse reason`（同样以 `Conflict` 形态返回 reason）保持同一结果家族。

### alternatives 及拒绝原因

- **异常传播**：拒绝——宿主无法分类（异常文本不构成决策依据），调用方不可决策；与 [execution-failure-policy-001](../requirements/execution-failure-policy/WHAT.md)（自由文本只作诊断，不决定类别与后果）及 dispatch-protocol 的 typed 结果面要求相悖。

### consequences

- 上层可把 `RequestIdConflict` 当作 typed 冲突消费；不需要以字符串匹配捕获异常。
- 验证状态：行号经 grep 与库文档交叉确认（`Work.fs:209`）；**未验证/待运行**（库侧测试未运行）。

### 什么会触发 revisit

- 出现需要区分「同载荷的独立 logical act」与「异载荷冲突」的新语义（[dispatch-protocol-006](../requirements/dispatch-protocol/WHAT.md) 已有 ClaimSequence 方案，若覆盖不足再裁决）；
- 宿主需要更细的冲突分类（如 hash mismatch 与其他 refusal 分离）。

## 裁决三：旧直清出口收束两步走

### context / constraints

- 旧出口 `closeCompletedHumanRootManager`（无 witness 直清：仅 HumanRoot × Manager active 时调 `closeActiveRun`）经 `DispatchSurface` 暴露，并被 `dispatch-protocol/tests/007.test.mjs` 第三用例固化为纯层合同；而生产 writer 已唯一（裁决一的事实链）。
- `Verification/TemporalSurface.fs:883` 仍依赖该纯函数作为「先关闭再接受」的验证构造辅助；GAP-123 的 durable 链测试尚未落地。两条依赖未切断前不能一步删除。

### chosen path（第一步，已落盘实施）

- 摘除 JS 暴露：删除 `DispatchSurface.fs` 的 `closeCompletedHumanRootManager` 包装与 `DispatchSurface.fsi` 的签名（落盘时 fsi 存在并行状态漂移，按最新快照删除；最终以「.fs 无实现、.fsi 无签名」为一致判据）。
- 007 迁移（`requirements/dispatch-protocol/tests/007.test.mjs:162,213-234`）：第三用例改用 `RuntimeSurface.closeAuthority` 的 exact-run 语义——匹配 active → `Ok(closed)`；已关闭且 `LastAuthorityProfile` 匹配 → `Ok` 原样（幂等）；否则 Error。旧「非 Manager/非 HumanRoot 原样返回」断言删除：exact-run close 无过滤，过滤属于 writer 侧决策（`activeHumanRootManager + appendManagerAuthorityClosure`），纯层不可表达（测试内注释已写明）。
- 018 新增真测试（`requirements/interaction-authority/tests/018.test.mjs:80-120`）：exact-run close 的保留/清零/幂等（unlanded root claim 保留、run-scoped continuation 资源清零、`LastAuthorityProfile` 匹配后幂等）。
- 第二步（留 GAP-123 落地后）：删除 `PromptAuthorityLedger.closeCompletedHumanRootManager`（`Ledger.fs:48`、`Ledger.fsi:18`），并把 `TemporalSurface.fs:883` 改调 `PromptAuthorityRun.closeAuthority` 并内联所需过滤。

### alternatives 及拒绝原因

- **一步删（同时删 Ledger 函数与 TemporalSurface 依赖）**：拒绝——`TemporalSurface.fs:883` 依赖未切断（会直接编译红），且 GAP-123 未落地时删除会让 Manager 特化测试空洞化。
- **保留并改名/加注释为「纯转换」**：不作为终点——没有减少任何 live surface，只是给旧世界续命；不满足「收束为一个 writer」的目标。

### consequences

- JS 侧不再存在「无 witness 直清」的入口；纯层测试改测 exact-run close 的真实语义。
- 本会话确认的未落地事实（决定第二步形态）：closure 的 JS append 入口当前不存在——`JournalSurface.appendAgent` 的 fact 解码器只支持 Companion/Execution 子集（`Persistence/Journal/Surface.fs:118-159`，未知 family 直接 failwith），`appendManagerLifecycle` 是 Companion 专用封装；writer 过滤（`activeHumanRootManager`）无 Surface。因此 018 的「append → 读回」durable 链测试不可表达，GAP-123 的两个 todo 锚点保留（`018.test.mjs:122-123`）。
- 验证状态：007/018 修改与 DispatchSurface 摘除均只读复核过，**未验证/待运行**。

### 什么会触发 revisit

- GAP-123 落地（durable 链测试 + 是否新增 closure 的窄 Surface 写入入口）→ 立即触发第二步；
- 出现可替代 `TemporalSurface.closeFirst` 构造依赖的新方式（可提前切依赖、提前删 Ledger 函数）；
- 若再发现 Ledger 纯函数的其它消费者（当前全仓仅剩 Ledger.fs/fsi 与 TemporalSurface.fs 三处）。
