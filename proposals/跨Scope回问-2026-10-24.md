# 跨 Scope 回问：每次 reset 后自动向过去的自己请教

状态：PROPOSED（修订于 2026-10-24）；尚未实施，也没有真实模型 canary。本文是设计稿，不取代 WHAT。
依据：AGENTS.md §6.6–6.7、requirements/context-compression/WHAT.md [017][033]–[041]、requirements/delegation/WHAT.md [034] 与 wanxiangli/src/pair-hint/AGENTS.md。

## 1. 用户承诺

每次 resetScope 成功，不再只向新 Scope 留一段“可以问过去”的提示。系统**必须自动触发一次额外的旧 Scope 模型询问**：新 Scope 自然开始工作，旧 Scope 在其冻结上下文中回答“对新目标有哪些重要的遗留事实、依据、未决问题或需逐字保留的原文”，答复稍后作为真正的 agent steer 送达。

这与 negotiate 一样是异步问答，不阻塞正在进行的工作，不等待模型回答后才让 resetScope 返回。之后如仍有不明之处，可随时手动调用 askPreviousScope(questions: string) 追问。一次 reset 的自动首问不能依赖新模型再次自发调用工具；否则并不能兑现“每次都额外调用”。

“旧自己”并非恢复先前模型的隐藏思考，而是用旧 Scope **真实出站的上下文快照**再做一次新推理。未出现在快照中的事实不能凭空恢复，回答不是完成证明或新的权威。

## 2. 自动首问：时序和问题

成功 reset 的事件流：

1. 在旧 Scope 的 Provider 出站处，确认本次 reset 调用所属的真实、完整、只读请求快照；不得从当下已清理的消息重建。
2. 在一个 durable 原子提交中，同时确立 ScopeReanchored(e → e+1)、旧 Scope 的 archiveRef 和本次自动首问 AutoConsultRequested（身份由 session、源/目标 epoch 和 resetToolCallId 决定）。先写入并校验 archive blob，才能提交事实。
3. 提交成功后更新 PairHint 的新 Scope / turnBudget。resetScope 返回原始成功文本 Scope reset. Objective: <newScopeObjective>；它不等待自动首问完成。
4. 组合者从持久请求认领唯一一次 AutoConsult，使用旧 Scope 冻结上下文发起一条额外的模型请求；这是用户明确接受的每次 reset 固定附加成本。自动首问默认**只发起一次 provider 请求**，不做无限补发或失败重试。
5. 答案经现有 PromptDispatcher 的 Detached/observed 路径投递为当前新 Scope 的真实 steer。即使模型回答晚到，当前新 Scope 仍可继续工作。

自动首问使用本次 reset 参数中的 newScopeObjective，并把 oldScopeVerboseVerbatimExperience 作为模型当时已提交的交接说明（可能为 null），向旧模型问：

> 我刚刚结束了当前 Scope，即将以目标“<newScopeObjective>”进入新 Scope。请根据你刚才确实看见的历史，指出对这个目标仍重要、但可能没有写进交接说明的决定、确切资料、失败反例、未收尾事项与风险；需要引用原文时准确给出。不要机械复述全文，不要臆测你不知道的内容。如无补充，请明确回答“没有可确认的补充”。

“可能遗漏哪些信息”的语义判断由临时旧模型完成，宿主不得审查或裁减答复；只有身份、来源、形状、重复性、可逆性等防呆。问题与 resetToolCallId 固定绑定，重放必须保持相同问题原文和回执。

成功 reset 的工具结果原始字节不变。新 Scope 首次请求可以在其结果的**请求副本**上附一条 frozen 状态提醒：“上一 Scope 的自动回问已受理；答复将以 steer 到达，可继续工作。需要细节再用 askPreviousScope(questions)。”该提醒不是再启动第二次回问，也不追加到 durable 工具结果，不能反复重写同 epoch 的已呈现字节。

## 3. 自动首问的“一次”与实际失败语义

每次成功重锚必须恰有一个**持久 AutoConsultRequested 意图**，且同一 resetToolCallId 的重放返回同一意图，绝不再次启动。这是可证明的逻辑一次，而非依赖运行时 Task 恰好只创建一次。

真正向 Provider 发出请求是外部效果，没有 Provider 级幂等回执就不能宣称强杀、网络断开后严格 exactly-once：

- 外部请求已明确 NotStarted，可以由同一意图恢复首次发送；不另建新意图。
- 已明确 Started / 完成 / 答复已记录，不得重新请求同一自动首问。
- 已尝试调用但结果 Unknown（包括崩溃窗口），保存 Unknown 并停止自动重发；不能为凑齐“每次一调用”而冒险产生第二次模型调用。模型仍可以选择明确发起一次新的手动追问。
- 自动询问缺快照、Provider 不可用、输出空白、拒绝或网络错误，都必须留有可见、可查询的失败结论，不能静默跳过、伪造一条成功 steer，或据此撤销已提交的 reset。

这是“每次成功 reset 自动安排并尽力启动**一条**额外模型请求”，不是保证任何网络故障后仍能无重无漏地收到一次 Provider 答复。物理 canary 必须证实正常路径的一次真实计费请求，不把持久意图冒充已经调用了模型。

## 4. 如何取得旧 Scope

在 resetScope 执行之前，从与 resetToolCallId 因果匹配的最后一次**完整实际 Provider 请求**捕获 system、messages、真实 model/variant、实际工具定义及其来源身份。快照的 session、epoch、provider run/attempt 必须一致；不能把 rememberSystem、rememberMessages、rememberModel 中不同请求的最新值拼成“一份真实请求”。

冻结旧消息的字节和顺序。不重算旧预算、elapsed、Pair Hint、注入提示或模型路由，不写回真实 Host 历史。档案 blob 按内容地址写入主工作树的 .Herdchestra/，不进 .git；同笔 ScopeReanchored durable 事实关联 archiveRef/digest 与自动意图。旧数据只能在短命问答的 Provider 请求副本中借用，绝不自动进入新 Scope 正常请求。

写 blob 失败、因果身份缺失、存储内容校验失败或提交 Unknown 时，resetScope **不能返回成功并推进 epoch**；先查询精确事实恢复，无法判定就显式报告未知。重复 reset toolCallId 不重复创建档案或意图。旧日志没有 archiveRef 时，不能伪造历史快照；兼容处置须在实施时按事实格式裁决。

## 5. 与 negotiate 的 DRY：共用机制，不共用错误的权威

不为“过去自己”复制第二套 BTW 管线。将现有 negotiate 的可复用物理部分抽成一个真实的、单一所有者的只读咨询执行单元；两个功能只是不同的来源决议与任务领域。

| 协作步骤 | negotiate | reset 自动首问 / askPreviousScope | 共用实现 |
| --- | --- | --- | --- |
| 确定被问上下文 | 实见委托者最新完整 Provider wire | 按 archiveRef 读取旧 epoch 冻结 wire | 一致的 WireSnapshot 数据与校验 |
| 受理身份 | delegator + recipient + delegation generation + receipt | session + old/new epoch + reset/toolCallId + receipt | 一套 Consultation receipt / 效果状态协议 |
| 暂时会话 | OpenCode 创建单问题短命孙会话 | 同一创建 API，绑定旧 Scope 只读快照 | 一份 create/prompt/delete 生命周期 |
| 模型调用 | 借委托者 system/messages/model 并追加问题 | 借旧 Scope system/messages/model 并追加问题 | 一份 provider transform 热替换逻辑及模型选择 |
| 工具安全 | 全部副作用工具在 tool.execute.before 拒绝 | 完全相同，含 resetScope 和 askPreviousScope | 一个 ephemeral-readonly 标记和一个前置硬门禁 |
| 结果 | 取普通文本；空答/异常保留故障 | 同一分类；自动首问不盲目重试 | 一个结果解码器、可观测失败和确认收尾 |
| 送达 | PromptDispatcher Detached/observed steer | 同一个 Dispatcher 路径 | 一份真实 user-carrier steer 投递和 PhysicalAccepted 观察 |
| 特有规则 | 首次委托问答的 PhysicalAccepted 解锁 reset 门禁 | auto 首问由 reset durable 意图触发，迟到回答要核对目标 epoch | 领域判定由各自 owner 保留 |

建议共用的调用形状为 ConsultationJob(sourceRef, recipient, question, identity, targetEpoch?)。组合者分别向源快照 owner、ReadonlyConsultationExecutor 和 PromptDispatcher 发出消息，不把 Journal、Session SDK 或同胞对象的回调注入领域对象。库的泛用部分负责 receipt 状态、一次性认领、重复、Unknown 和终结；PairHint 只保留首次 negotiate 门禁、ScopeSession 预算、上下文过滤及提示冻结；scope archive 自己持有 durable 引用与 epoch 身份。**不得产生两本可互相覆盖的会话历史/预算账本。**

当前源码在 PluginHooks.fs 使用 negotiationSdk/createTemporarySession/runTemporaryQuestion/deleteTemporarySession，PluginTransforms.fs 使用 negotiationStartTemporary/negotiationProjectMessages 与 tool.execute.before，ToolRuntimeScope.fs 使用 sendNegotiationSteer。实施时把这一条**已存在的机制改为来源无关的共用实现**，由 negotiate 与旧 Scope 回问共同调用；不要原样复制一套并换前缀命名。

还须处理当前 runTemporaryQuestion 遇工具违规或空答可能无界自调用的问题：引入两类咨询共用的明确有界恢复与真实失败结算。旧 Prefix 的完整性、模型的真实 Provider identity 和不执行工具是同一组测试合同；不能靠改一个工具名称视为 DRY。

## 6. 手动追问仍然存在

保留 askPreviousScope(questions: string)：参数是非空字符串，可集中询问多个疑问。第一版仅查询当前 Scope 紧邻的上一份封存 Scope；第一次 reset 之前明确返回 NoPreviousScope。

**自动首问不需要模型调用 askPreviousScope**，因为它是 reset 提交事实直接触发的固定协作。手动追问是后续额外查询，每次调用是新 requestId / receipt；同一工具调用幂等重放，不会影响本次 reset 已登记的自动首问。不能拿“已经自动问过”拒绝模型按真实需要继续追问。

两种旧 Scope 问答都使用同一个共享物理模型执行器和同一条投递通道，不另建手动调用专用 runner。初次自动回答不是解锁 delegated negotiate 的首轮答复；两个协议回执和确认身份不能混用。

## 7. 回答 steer、时序与用户消息真实性

回答要附可见来源：“这是前一 Scope 的自动回问/手动追问答复，源 epoch e，目标 epoch e+1”；回答仍是模型建议，不是用户真正说的话，不转移任务权威或权限。

PhysicalAccepted 必须同时验证 receipt、session、source/destination epoch 以及目标物理消息身份。Queued、Answered、PhysicalAccepted 和模型已实际消费不是同一个事实。重复送达最多确认一条；同一时间可以运行多个不同手动询问，结果无需按提出顺序到达。

若回答生成时目标 Scope 已再次 reset、session 已删除或权限已关闭，本次 answer 标为 Stale，绝不偷渡到新 epoch。下一次 reset 自行创建它的那一笔自动首问；保留在途旧档案直至其 lease 安全收尾，不默默重新指向“当前最新 Scope”。

answer steer 走真实 Host 用户载体但 attribution 必须为 agent，不伪装为 operator 新输入；不能因此归零 turnBudget 或触发用户原文初始化提醒。旧的用户消息始终原样保留；需要来源归属证据，不只依赖可伪造的 part.metadata。

## 8. 成本、保留与恢复

用户明确接受每次成功 reset 的额外一次模型请求及相应可计费成本。工具文案和 reset 后提醒需明示此后果；运行日志须将自动咨询与普通任务 Provider 调用分开观测，不据 token 数值推算模型剩余容量。

v1 只开放“紧邻上一 Scope”查询；历史归档数据能不能删除取决于 in-flight query 是否仍在使用、用户数据保留策略及 durable 关闭事实，而不是只看一个缓存指针。session.deleted 停止新问答准入，实际结束时才释放旧档案资源。进程重启后必须通过已提交 archiveRef 和请求状态恢复，不用 process-local rememberMessages 猜测。

真实 Host SDK 若不能观测本次 reset 所属请求的完整快照，先停在捕获能力的 canary；不能退而求其次，让旧模型借用不确定的最新前缀。

## 9. 验收与反例

1. 连续两次真实 reset，观察到恰好两个不同的 AutoConsultRequested，正常路径每次各引起**一次额外真实 Provider 请求**；旧任务历史没有回填新 Scope，而两次答案分别送回各自的目标 epoch。
2. 第一次 reset 不需要调用 askPreviousScope，也不需要新模型“决定先问”；相反，对同一 resetToolCallId 的回放不得增加一次请求。
3. 故障矩阵：档案缺失、blob 写失败、Journal Unknown、提交后强杀、Provider 请求 Unknown、空答案、工具违规、Provider 取消、session.deleted、迟到答复。报告的状态与真实外部效果一致。
4. fast-check 交错自动 reset、手动 ask、委托 negotiate、重复调用、回答、PhysicalAccepted、后续 reset 与 crash/restart：恰一持久自动意图，同 receipt 至多一次有效 steer，旧回复不跨 session/epoch。
5. negotiate 和旧我咨询通过**同一物理短命会话、同一读取上下文的 provider transform、同一 tool.execute.before 门禁、同一 PromptDispatcher** 测试，不允许复制的第二实现；移除任一上层源策略不破坏共用执行器。
6. 原始工具结果、用户原文、同 epoch 冻结尾巴及 system/messages/model/variant 无回写；每个短命问答无工具外部效果，失败后资源完成收尾。
7. 库独立 Fable 构建、实际 npm tarball 在 Node/Bun 安装、主仓 provider-prefix/prefix-stability/context-compression/delegation-negotiation 回归、OpenCode/OMP 实际注册 hooks 和真实 Provider canary **分别**取证。未验证不能称全绿。

## 10. 施工顺序

A. 先修订正式 WHAT：每次 reset 自动额外调用的承诺、附加成本、自动问句、异步时序、归档、失败边界；消除 context-compression [036][037] 与更近的“委派只传当前指令”规定之间的叙述冲突。先写失败反例。

B. 把当前 negotiate 的临时问答、只读工具门禁、Provider 前缀借用和物理送达链抽为共用执行单元；原有 negotiate 先在重构前后完全等价通过，不能先复制一条新链。

C. 独立实现可持久旧 Scope archive + 自动咨询意图与幂等 receipt；Fable、独立消费者、随机状态机测试通过。

D. 将一次性 archiveRef + AutoConsultRequested 与 ScopeReanchored 原子绑定，提交后自动异步调度。完成问答才通过 Dispatcher steer 投递，继续开放 askPreviousScope 手动追问；处理所有迟到和并发场景。

E. 删除旧重复 owner，验证真实 OpenCode/OMP 物理生命周期与 Provider 请求数，再分别精确提交两仓；不得拿日志或 mock 代替真实模型调用。

## 11. 核心不变量

- CommittedReset(session,e→e+1,callId) ⇒ 存在恰好一份可验证 Archive(session,e) 以及恰好一条 AutoConsultRequested(callId)。档案不可用时不能提交成功 reset。
- 每份 AutoConsultRequested 只有**一次可确认的物理启动**；启动结果 Unknown 不盲目再次调用。正常路径每次 reset 实际消耗一条额外 Provider 请求。
- AutoConsult(source=e,target=e+1) 只从冻结旧请求获得历史；其结果只可能进入对应目标 epoch，且同一 receipt 至多一条 PhysicalAccepted steer。
- AutoConsult 不经过新 Scope 的 askPreviousScope 调用；手动问答与委托 negotiate 复用同一无副作用临时咨询机制，而各自的来源权限和代际约束保持独立。
- Answered 或 Queued 不推出 PhysicalAccepted；PhysicalAccepted 不推出新 Scope 已消费。模型隐藏思考和 Provider 的真实缓存率不由本协议保证。
