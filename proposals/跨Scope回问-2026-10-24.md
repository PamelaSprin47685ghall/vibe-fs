# 跨 Scope 回问：向 reset 之前的自己发问

状态：PROPOSED，设计稿；尚未实施，也没有真实模型 canary。
依据：AGENTS.md §6.6–6.7、requirements/context-compression/WHAT.md [017][033]–[041]、wanxiangli/src/pair-hint/AGENTS.md。本文不取代 WHAT。

## 1. 目的

新 Scope 仍应彻底失去旧 Scope 的过程上下文。oldScopeVerboseVerbatimExperience 用于主动传承已知重要原文，但模型在清空时无法预知未来所有问题。应允许新 Scope 在真正遇到歧义时，向封存的旧 Scope 提问，只把回答以 agent steer 带回。

“旧自己”不是仍存在的脑内运行状态，而是用上次 reset 前实际出站的 system、messages、model/variant 重建的一次只读模型请求。没有记录的隐含思考无法恢复，也不保证旧 provider 永远可用。

## 2. 新接口及 reset 回执

新增 askPreviousScope(questions: string)。参数仅一个非空字符串，允许一次提出多个相关问题；第一版只能寻址当前 Scope 紧邻的前一个 Scope，没有任意历史选择或跨会话能力。已有上一 Scope 时平时也可调用；第一次 reset 前必须明确返回 NoPreviousScope。

调用只返回带精确身份的 Accepted 受理回执，不同步等待模型；旧 Scope 的回答通过已证明物理接纳的 user steer 送达，与 negotiate 一样，既不阻碍当前工作，也不把受理误认作答案。

resetScope 的三参数签名与原始成功结果 Scope reset. Objective: <newScopeObjective> 不改；当且仅当旧上下文确已封存且本次 ScopeReanchored 已提交，在第一次发往新 Scope 的请求副本中，紧挨该工具结果写入一次冻结的提醒：

    # 前一 Scope 的可见上下文已经封存。如果遇到说不清的旧决定、
    # 原文、依据或未收尾事项，请调用 askPreviousScope(questions)，
    # 可以一次提出多个问题；该调用不必等待，答案随后以 steer 送回。

提示只写请求副本，不能修改原始工具回执、持久化历史或历史前缀；按新 epoch 一次生成并原字节重放。它是有疑问时必须询问，不是每次 reset 无条件额外调用模型。

## 3. 封存内容与身份

在 resetScope 执行之前，从与该工具调用因果匹配的最近一次真实 provider 出站请求捕获完整只读前缀：system、messages、实际模型及 variant、可观察的工具定义及必要 provider 身份。和 session、源 epoch、provider run、toolCallId 必须精确匹配；不按 session 的“最近记录”猜测来源，不拿重新编码的宿主历史冒充真实出站内容。

复制过去已呈现的原字节和顺序，不重算旧预算、elapsed、Pair Hint，不原地改写缓存。只读快照存于主工作树共用的 .Herdchestra/ 内容地址存储，不进 .git；Journal 持久化该引用与摘要。该视图只在旧 Scope 临时询问时借出，新 Scope 从不直接接收旧材料。真实 provider cache 命中必须靠真实计费观察，不能只凭前缀字节相等宣称。

## 4. reset 提交必须原子

1. 校验精确 toolCallId、session、源 epoch、出站请求与 provider run 的关联。
2. 写入并读回校验不可变 blob，取得内容摘要和引用。
3. 使 ScopeReanchored 的同一个 durable 事实原子携带该存档引用；不得用两个独立的成功追加造成一个 epoch 已清空而档案不存在。变更 codec/旧日志的兼容方式另行裁决。
4. 持久提交成功后才更新内存 ScopeSession 的预算与初始化状态，并返回原有 reset 成功文案。
5. 任何身份、快照、存储或提交不确定时，本次 reset 不成功、旧 Scope 不清理；孤儿 blob 仅在证明无引用后 GC。重复 toolCallId 只能重放同一提交，不重复重置。

这样保证“成功重置必有可验证旧视图”，不让成功 reset 与无法询问过去同时成立。若未来允许无档案的显式重置，必须另外经产品契约决定；本稿不悄然降级。

## 5. 询问协议

1. askPreviousScope 验证当前正式 session 的 epoch e+1 与存档的源 epoch e，登记含 session、源/目标 epoch、toolCallId、receipt 的查询。重复工具调用幂等返回同一 receipt。
2. 以封存的真实 model/variant 创建短命旧 Scope 临时会话；真实 Host 会话只包含唯一问题，在 provider 出站副本中借用旧 system/messages 并追加问题。绝不写回当前会话历史。
3. 临时会话不得执行任何工具。所有真实 tool.execute.before，包括 resetScope、negotiate、本工具和未知工具，均在副作用前拒绝。可以有界重问以争取纯文本答案，但不得让被拒绝的工具体运行。
4. 模型回答只代表旧视图中的建议与可核查证据；遇到不知道的事情应答不知道。不能用答案直接形成权限、完成或持久状态事实。
5. 使用现有 PromptDispatcher 的 Detached/observed 通路将带来源的 answer steer 物理送回。Answered、Queued、PhysicalAccepted、已进入模型可见历史各有独立记录；只有真实落地才能称为已送达。
6. 答案必须恰好送至提问时的 session 与目标 epoch。若期间又 reset、用户取消或 session 删除，则迟到响应为 Stale，绝不可进入更新的 Scope；失败、空答与失效都须收尾临时会话。
7. answer steer 的归属为 agent，绝不混成新的 operator 用户消息，不能错误作废 turnBudget 或触发未初始化 reset 指令。

该协议不改变已有 negotiate 的首次必问与首次回复解锁 reset 的门禁；两套 receipt 不可混用。

## 6. 状态归属

- 新的 wanxiangli/scope-consultation 自治对象拥有上一 Scope 的存档引用、epoch lineage、查询 receipt、迟到/重复处置及查询生命周期；不识别 OpenCode/OMP raw envelope。
- 现有 wanxiangli/pair-hint 仍只拥有 ScopeSession 的预算、过滤和字节冻结；不要再设第二本 Scope 账。
- 内容地址 blob 与 Journal 由持久层各自拥有，组合者安排“保存→重锚”和“询问→临时运行→物理交付”的合作；不得把宿主服务作为回调塞进库对象。
- OpenCode/OMP 只负责真实物理 envelope 的捕获、临时 SDK 会话、工具前置拒绝与被接纳的 steer。借用现有 BTW 的物理机制，但借出的必须是过去 epoch 的存档，不是当前委托者前缀。

## 7. 保留、恢复与边界

第一版只保留当前 Scope 的直接前一份存档。下一次 reset 成功后才替换引用；仍被在途查询读取的旧 blob 按资源租约完成收尾才释放，旧查询回复不穿过新 epoch。session.deleted 要先停止准入、处理在途查询，再释放存档。

重启依赖真实已提交的存档引用和查询状态；未知是否发生过模型副作用时不得默默重试支付第二次调用。没有完整出站证据、源模型不可用、上下文已满、归档数据损坏、旧模型输出空白或伪工具调用时都返回明确的 Unavailable / Unknown 结果，不用当前 Scope 的摘要伪装旧自己的答复。模型的隐含思考和 provider 的真实缓存命中率不在此合同保证范围内。

## 8. 反例与验收

- fast-check 随机交错 reset、ask、retry、重复调用、答复、PhysicalAccepted、下一次 reset、delete、crash/restart；只有来源和目标 session/epoch/receipt 全匹配才能交付，其他均为零效果。
- reset 的 blob 写入失败、Journal 拒绝、提交后立刻崩溃、重复 toolCallId 均不能出现“新 epoch 已生效但无可验证旧视图”。
- 同 epoch 已呈现前缀字节不变、旧 system/messages/model 原样借用、仅追加一条问题；源对象和用户原文不被改写，旧 Scope 原文不得直接进入新 Scope。
- 所有临时旧会话的工具尝试零副作用；临时会话失败或终止确认关闭，不滞留权限。
- 真实 OpenCode 注册 hooks 与 SDK 的物理 canary 必须区分排队、PhysicalAccepted 与回答实际可见；覆盖忙碌/空闲/删除及迟到。
- Fable 独立模块、实际 npm tarball 安装 Node/Bun 消费、Host 消息物理测试、prefix-stability 相关套件必须分别通过。缺一层不能记全部完成。

## 9. 施工顺序

先修改 WHAT 对 reset 成功、存档、answer steer 和 prefix 冻结的合同，并处理 context-compression [036][037] 与 AGENTS.md §6.7 的历史语义冲突；然后造独立自治核心及反例；再建立真实旧请求捕获与原子持久化；复用 BTW 物理临时会话和 PromptDispatcher；最后删旧状态、测真 Host/Provider 与安装包，逐阶提交。整个过程中不能因“设计已定”关闭 TODO 或 GAP。

## 10. 核心不变量

ScopeReanchored(session, e→e+1) 成功 ⇒ Archive(session, e) 已提交、存在、可校验且身份精确。

Ask(session, source=e, destination=e+1, receipt=r) ⇒ 只能在 epoch e 的旧视图回答，且只向同一 session 的 epoch e+1 投递。

Answered(r) 或 Queued(r) 不推出 PhysicalAccepted(r)，PhysicalAccepted(r) 也不推出模型已消费。

旧 Scope 临时模型的工具外部副作用始终为零。任何重复、迟到、损坏或未证明的来源都不能改变当前 Scope 的权限、epoch 或已经呈现的前缀。
