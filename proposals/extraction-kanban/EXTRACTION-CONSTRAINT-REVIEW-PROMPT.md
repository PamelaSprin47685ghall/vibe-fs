# 后续模块拆分、交接与并行修复方法 Prompt

更新：2026-10-19。

请将以下方法最小化纳入现有施工指南、交付清单和计划，用于后续每个新模块的拆分、交接、修复和验收。原有自治职责、显式组合、可拆增强与小步交付原则继续适用；已有规则和检查能够覆盖的，直接复用。

本方法从前四模块的真实教训中提炼，后续分工由本次讨论确定。历史案例说明为什么需要这些方法，不是本次待修任务；新模块也不必先发生同类缺陷才适用。具体反例和验证范围由新模块自身的契约决定，不照搬旧模块的故障场景，不增加没有依据的通用门禁。

## 1. 从真实消费者确定本轮职责

每次拆分先明确：真实消费者需要什么结果，本轮迁出什么职责，新模块保证什么，主仓或组合层还负责什么。

将消费者要求与拟议公共契约逐项对照。基础库提供较小完整能力是允许的；消费者需要的其余能力应归入明确的组合或后续工作包，保留在迁移范围中。库测试通过，只说明库契约已经取得相应证据。

用现有卡片写清完成后可观察到的变化及本轮排除项，直接引用适用的 SPEC、WHAT 和已有证明。

## 2. 按职责承接划边界、排步骤

说明本轮职责现在由谁承担、将交给谁、哪些旧实现会退出、哪些仍因其他职责保留。若涉及事实保存、外部效果或资源寿命，还要明确由谁确认完成；发出请求与结果成立分别判断。

按原设计规则确定公共契约及必要协作，再安排实现、接线和旧职责退出。选取与本轮职责相关的实际消费入口和关键反例，在对应阶段验证。代码搬迁、增加导入或接入一个索引，都不能单独证明职责已经迁移。

后续模块使用自己的输入、边界和观察点。纯规则模块按规则结果验收；涉及实际效果的承诺，需要对应效果的观察，受控替身只证明其覆盖的范围。

## 3. 区分需要先定的边界与可以后移的缺陷

按修复是否会改变已约定的职责、公共契约或协作关系判断分工：

- 尚需裁决这些边界的问题，继续作为拆分或共同设计工作处理，先明确后续各包的范围。
- 边界已经确定、能够在该范围内修正的实现缺陷或补充验证，可以移交独立修复包。拆分者不必亲自修完全部局部问题。

交接沿用现有记录，留下候选版本、已验证范围、剩余问题、修复范围、负责人或待认领状态、关键反例及验收条件。已有记录直接引用。

拆分者完成约定阶段并交接后，可以继续下一项拆分。移交不会使缺陷自动通过验收，也不等于受影响路径已经可以启用；合入与发布仍遵循原有规则。

## 4. 分阶段验收，保留最终承诺

| 结论 | 判断依据 |
|---|---|
| 拆分已交接 | 本阶段职责、契约和必要协作已确定，候选、已证范围及剩余修复范围可交给接手者 |
| 修复包完成 | 本包行为、关键反例、正常正控及相关消费者验证通过，剩余边界明确 |
| 完整迁移通过 | 本轮承诺全部兑现，实际消费者由预期实现承接，约定退出的旧职责已退出，适用验证通过 |

沿用现有卡片与状态含义，不另建状态系统。有已知库契约缺陷的候选可以交接修复，但不能因此标为 LIB_READY；子包完成不关闭尚有承诺的迁移父项。

每个结论只覆盖实际取得的证据。分别说明库测试、受控端口、真实效果和主仓接线证明了什么；相关失败、未运行、TODO 或 skip 保留为未通过，不能被总通过数覆盖。

最终迁移标准保持完整，但不把所有最终验证都要求在拆分交接前完成。已有有效证明直接复用；只按本模块承诺安排相关验证。

## 5. 按依赖组织后续修复并行

修复方接手后，沿用计划中的范围、依赖、文件边界、关键反例和验收条件分包。契约稳定、能够独立修改和验证的工作包可以并行；共享接口或重叠文件的修改按实际依赖安排顺序，明确后续集成责任。

先少量试行，例如两个具备条件的模块，再根据修复、复核与集成的实际耗时调整。并行是本次选择的分工方式，尚未验证提速幅度，不承诺线性收益。

## 6. 将方法落入后续任务

对照现有施工入口，只补尚未表达清楚的方法和阶段边界，并用同样的方法组织下一批任务说明。无需重开已完成的历史模块，也不为本方法增加重复表格、阅读回执或审批轮次。

专项方法放在施工文档和交付清单，不加入根 AGENTS.md。保留他人的未提交工作，不顺带切换依赖、迁移数据，不合并、变基或挑取 upstream。实际拆分与修复按已授权的工作范围进行。

交付更新后的方法入口及下一批工作包说明：每包要迁出的职责、交接范围、关键反例、验收条件、负责人或待认领状态，以及并行或串行依据。说明哪些规则直接复用、哪些补充源于下列教训；没有实际执行的验证或试行，不写成已经通过。
