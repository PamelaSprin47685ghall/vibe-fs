# 拆分交付与并行修复审查执行 Prompt

更新：2026-10-19。

请审查并改进 vibe-fs 与 wanxiangli 的拆分交付、后续修复和验收分工，在符合原设计原则及维护权限的范围内落实最小必要修改。优先把职责边界、公共契约和必要协作确定下来，让后续修复能按模块独立推进。可以后移的局部问题不必全部由拆分者解决；尚未修复或验证的义务仍如实保留，不能计作最终迁移完成。

本次采用的工作假设是：职责划分和共享协议决策较难并行，而边界稳定后的局部修复更容易并行。请用实际依赖和一次小批次验证这个假设，不把所有拆分强制串行，也不假定所有修复互不影响。并行主要缩短日历时间，不自动减少总投入；复核、共享接线和集成仍可能限制整体交付速度。

已有复核发现过“库测试通过被扩大解释为主仓迁移完成”等问题，但原要求已经规定真实组合、旧职责退出和分阶段验收。请区分规则含混、任务没有带入适用规则、实现未执行规则、证据被扩大解释及复核遗漏；没有记录支持的原因标为待核实，不预设责任，也不把增加“必须、严禁”等措辞当作改进完成。

## 分阶段判断完成

请在现有任务记录中区分以下结论，并据此审查施工文档、交付清单和检查入口。不必为此另建看板或增加一套状态系统。

| 阶段 | 本阶段必须交出的结果 | 仍可留给后续的工作 |
|---|---|---|
| 拆分可交接 | 职责、状态归属、公开契约与协作边界已确定；候选可复取、能独立构建，最小实际消费链可运行；足以推翻边界的关键反例已检查，剩余问题能归到明确修复范围 | 不改变既定边界的局部缺陷、补充验证和后续增强，可交给独立修复包 |
| 修复包完成 | 本包行为、反例、正常正控与相关消费者验证通过；修改及剩余边界清楚，可进入集成复核 | 其他独立修复包或尚未完成的主仓迁移，不阻止本包交付 |
| 最终迁移验收 | 当前候选满足全部已承诺范围，真实消费者、公开产物、关键反例、旧职责退出及适用风险验证通过 | 未完成承诺继续保留，不能用若干修复包完成代替父项完成 |

拆分者完成并交接已约定范围后，可以结束本阶段、继续下一项拆分；后续修复由对应负责人接手，父卡仍保留修复和最终验收义务。不能因为父卡尚未 DONE，就要求拆分者包办所有后续工作。

“拆分可交接”不是空目录、接口草稿或替身演示，也不等于独立库全部契约已经通过。存在已知契约缺陷的候选可以在明确限制下移交修复，但不能直接标 LIB_READY、完整迁移 DONE 或发行验收通过；这些状态仍按其实际含义判断。预先明确各阶段范围，不能在失败后改名销掉原承诺。

交付清单的四类证据继续约束最终迁移验收，拆分阶段按当前真实闭环取得必要证据，不把所有消费者、平台和故障矩阵一律前移。独立库已兑现较小完整契约时，仍可独立验收和交付。

## 决定哪些问题可以后移

判断依据是问题是否破坏交接边界、是否会迫使其他模块返工，以及是否会进入实际使用路径；不能只按缺陷大小或严重程度分类。

| 问题 | 处理方式 |
|---|---|
| 状态 owner 不清、公共协议仍需裁决、声明独立的模块互相调度，或最小真实链无法运行 | 先解决相关边界或做有限原型，不能把它当作已经独立的普通修复任务派发 |
| 行为已裁决，修正只影响一个模块内部；例如参数保真算法、既定 API 的声明修正、局部错误处理 | 可移交修复。记录反例和影响，不要求拆分者亲自完成全部修正；不得把仍有缺陷的产物宣称为契约已通过 |
| 补充平台或故障验证、独立性能改进、未纳入本轮承诺的增强、未被本次拆分恶化的历史缺陷 | 按风险归入后续包；本轮已承诺的支持范围仍须在最终验收前取得证据 |
| 会进入使用路径的新增数据丢失、重复外部效果、权限扩大、资源提前释放等回退 | 阻止启用或相应集成交付；可以把隔离候选交给修复方，不能以“以后修”授权暴露已知回退 |

每个后移问题在现有卡片中留下：固定候选与复现、受影响保证、已确定的契约、修复负责人或明确待认领状态、依赖和编辑面、验收条件及启用限制。未知负责人不算已承接；在已有修复能力不足时调整接收量，不把问题无限转入队列。沿用原证据和例外记录，不另建重复台账。

可移交修复与可合入、可发布分别判断。隔离分支或未启用候选可以先交接；是否合入仍按现行净改进与集成要求判断，尤其不能把新增回退混作原有欠账。涉及旧职责尚未退出时，明确当前实际 owner 和下一步，不能同时维护两份可写权威。

## 组织模块修复并行

先固定共享契约与候选，再按能够独立验证的行为分包。不同模块只有在不争用同一事实 owner、公共接口或编辑面时才适合并行；一项修复需要改变共享协议时，先形成该协议的独立前置工作，再让调用方接续。

每个修复包写明范围、依赖、唯一负责人、文件边界、关键反例和验收条件，使用隔离工作树、固定库产物和各自的测试资源。不要同时修改共享类型、Host 组装、根锁文件或同一发布产物；这些改动由明确的集成负责人串行处理。工作树隔离不等于数据库、Git common-dir 或外部进程资源已经隔离。

先从少量已具备交接条件的独立模块试行，例如同时处理两个模块，再按结果调整并行度。记录修复、复核、等待和集成各自耗时、返工原因及未完成队列的变化；若共同返工或待复核积压增加，应先修正分包和共享边界，必要时减少新拆分的在制量。比较最终验收通过的交付周期，不以同时启动的 agent 数或标记完成的模块数作为收益。

本次先审查并落实分工、规则和必要检查。生产修复的并行试行只使用已授权工作包，不因修改本 prompt 自动启动其他模块修复。

## 审查与修改

1. **找出约束在哪一步失效。** 选择已有错判案例，追踪“适用条款 → 本卡承诺 → 当时实现与证据 → 完成判定”。区分事实和推测，逐项说明已有要求是否足够、缺的是文字还是执行连接。已有准确条款尽量保留，通过引用和检查落实，不另抄一套规范。

2. **把必要条款写成分阶段的可判定条件。** 在对应 SPEC 或专项验收规则中明确适用阶段与范围、必须观察到的行为、有效证据、不能替代它的观察，以及不满足时保留的状态。区分拆分者必须完成的边界工作与可交接的局部修复，避免用最终验收标准阻塞所有移交。保留自治职责、显式组合、可拆增强与最简完整契约；不要为验证强造 C、包装层或无实际需要的第二种合作方式。

   例如：Process 的有界留尾库可以独立验收；主仓迁移完成前，必须从真实执行入口证明完整输出仍可取回，且这项职责只有一个负责者。缺少该证明时，主仓迁移卡不得 DONE。不要要求基础 Process 库独自承担主仓全部保证。

3. **将阶段结论与实际证据绑定。** 复用现有卡片、验证结果和检查入口，把本卡承诺关联到被测候选及对应结果。审查是否需要在已有脚本或 CI 中补最小检查：拒绝缺失、失败、未运行、失效或范围不符的证据被用于相应完成声明，同时允许问题已明确归属的受控交接。检查实际测试结果与输入身份，不以文件存在、勾选框、总通过数或作者文字作为充分条件。职责归属、真实消费者覆盖等语义判断仍由非作者复核；已完成子范围与待修复移交分别记录，不因父卡未完阻止独立工作。

4. **限制历史证明的适用范围。** 将长期有效的要求与某次验证记录区分开，保留历史记录中的版本、支持环境、实际观察和未证范围。新候选只能复用未受变化影响且能说明适用依据的证据；受影响部分重新验证。禁止把库独立通过写成宿主通过，也不能用后续新绿抹去未定因的旧失败。

5. **明确联合使用和冲突处理。** 在现有拆分任务入口同时链接原要求与交付清单，并写明本卡适用范围。无需新增阅读回执或重复表格。遇到冲突列出版本、原文、影响和修订建议，由对应维护者明确处理；不能自行取较新或较宽松的一份。已知例子是上游 `705e1ea3b` 的项目规则改用 submodule/`file:wanxiangli` 并禁止 tgz 入 Git，旧 distribution WHAT [011] 与施工 §8 却仍要求跟踪 tgz。请核实接手版本是否已统一；源码接入和临时发行包验收应分别证明。

使用隔离案例或既有证据验证以下判断，不在真实看板上制造虚假完成记录。对新增自动检查运行有效候选正控和无效候选负控；尚需人工判定的部分明确说明。

## 修改范围与交付

优先修改局部 SPEC、专项施工文档、交付清单、修复计划和现有验证入口，使阶段边界与后移条件一致。不要把项目专项流程堆入根 AGENTS.md；如确需修改通用规则，说明原规则为什么不足，按该仓维护流程提交审查。保留他人的未提交工作，不顺带重构生产模块、切依赖或迁移运行数据，不合并、变基或挑取 upstream。

完成后交付：各阶段的最低要求与可后移事项、后续修复包及其并行或串行依据、约束失效的证据与未决原因、实际修改位置、反例与正控结果，以及仍需维护者裁决的冲突。试行后的效率结论同时列出总投入、日历时间、排队和集成成本；未试行时只给方案，不承诺线性提速。区分文档修订完成、自动检查已接入并验证、仍依赖人工复核；新增一个未接入的脚本不能称为约束已生效。提交、推送与部署分别报告。
