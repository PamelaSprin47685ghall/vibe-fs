## 分阶段判断完成

请在现有任务记录中区分以下结论，并据此审查施工文档、交付清单和检查入口。不必为此另建看板或增加一套状态系统。

| 阶段 | 本阶段必须交出的结果 | 仍可留给后续的工作 |
|---|---|---|
| 拆分可交接 | 按原规则确定职责、契约及协作；交出可复取的候选、已验证范围和剩余修复范围 | 不改变既定边界的局部缺陷和补充验证，可交给独立修复包 |
| 修复包完成 | 本包行为、反例、正常正控与相关消费者验证通过；修改及剩余边界清楚，可进入集成复核 | 其他独立修复包或尚未完成的主仓迁移，不阻止本包交付 |
| 最终迁移验收 | 当前候选满足全部已承诺范围，真实消费者、公开产物、关键反例、旧职责退出及适用风险验证通过 | 未完成承诺继续保留，不能用若干修复包完成代替父项完成 |

拆分者完成并交接已约定范围后，可以结束本阶段、继续下一项拆分；后续修复由对应负责人接手，父卡仍保留修复和最终验收义务。不能因为父卡尚未 DONE，就要求拆分者包办所有后续工作。

存在已知契约缺陷的候选可以在明确限制下移交修复，但不能直接标 LIB_READY、完整迁移 DONE 或发行验收通过；这些状态仍按其原有含义判断。已完成的库契约、未完成的主仓接线和局部缺陷分别记录。

交付清单的四类证据继续约束最终迁移验收，拆分阶段按当前真实闭环取得必要证据，不把所有消费者、平台和故障矩阵一律前移。独立库已兑现较小完整契约时，仍可独立验收和交付。

## 决定哪些问题可以后移

按实际修复需要决定：Journal 的资源释放缺陷没有推翻原职责划分，可以交给后续修复者；Process 的基础留尾库也可以独立交付，但主仓完整输出由谁承接、怎样接回实际执行链，须明确留在对应工作包中。Trace 尚未完成的原件迁移同样不能从父卡承诺中消失。

每个后移问题在现有卡片中留下固定候选、已有反例、修复范围、负责人或待认领状态，以及验收条件。原记录已包含时直接引用，不另建表格。拆分者不必亲自完成所有后续修复；移交后由修复包负责人接续。

移交修复与启用生产路径分别判断。已经复现的完整输出丢失、未见证退出就清账等问题，不能因交给后续修复便宣称相关路径可用；可以先移交隔离候选。是否合入和发布仍按已有规则处理，不新增一套通用风险清单。

## 组织模块修复并行

这是经本次讨论选择的后续方案，不是新增的拆分质量指控。沿用现有计划中的范围、依赖、文件边界、关键反例和验收条件，按实际依赖选择可并行的修复包；共享接口或同一文件的修改仍按原工具调用纪律安排顺序。

先少量试行，例如两个已具备交接条件的模块，再根据修复、复核与集成的实际耗时调整。暂未试行，不要求另建效率报表或承诺线性提速。

本次先审查并落实分工、规则和必要检查。生产修复的并行试行只使用已授权工作包，不因修改本 prompt 自动启动其他模块修复。

## 审查与修改

1. **只追踪已发生的遗漏。** 对照上表，追踪“适用条款 → 本卡承诺 → 当时实现与证据 → 完成判定”，再核对当前是否已经修正。没有记录支持的原因保留未知，不能据此加规则；已经有效的检查不重复建设。

2. **只补案例暴露的验收遗漏。** 在原 SPEC、测试或卡片的对应位置，补齐缺少的实际行为与完成边界。原设计规则继续适用，不全文重写，也不增列没有实例依据的错误清单。区分拆分交接和最终迁移，局部修复不必全部前移。

   例如：Process 的有界留尾库可以独立验收；主仓迁移完成前，必须从真实执行入口证明完整输出仍可取回，且这项职责只有一个负责者。缺少该证明时，主仓迁移卡不得 DONE。不要要求基础 Process 库独自承担主仓全部保证。

3. **使完成结论对应实际结果。** 重点纠正 E-02 所示的 TODO 被写成通过，以及基础库通过被用于证明主仓更强承诺。复用现有卡片、结果和检查入口；只有确认现有入口仍会放过同类错判时，才补最小检查。不能仅凭历史问题要求新建 CI 门禁或增加审批轮次。

4. **保留原要求的入口。** 继续使用已经建立的原规则与清单链接，不增加阅读回执。本次未证明 agent 漏读规则，也不据此要求新的传达流程。若案例涉及的现行条款确有歧义，指出具体原文与影响，请维护者作最小修订；其他历史文档冲突不扩入本任务。
