# 拆分约束改进审查与执行 Prompt

请审查并改进 vibe-fs 与 wanxiangli 拆分工作的约束方式，在确认符合原设计原则及维护权限后，落实最小必要修改。目标是让不充分的证据无法被计作完整迁移完成，同时保留独立库、小范围净改进和分阶段交付的能力。

已有复核发现过“库测试通过被扩大解释为主仓迁移完成”等问题，但原要求已经规定真实组合、旧职责退出和分阶段验收。请区分规则含混、任务没有带入适用规则、实现未执行规则、证据被扩大解释及复核遗漏；没有记录支持的原因标为待核实，不预设责任，也不把增加“必须、严禁”等措辞当作改进完成。

## 审查与修改

1. **找出约束在哪一步失效。** 选择已有错判案例，追踪“适用条款 → 本卡承诺 → 当时实现与证据 → 完成判定”。区分事实和推测，逐项说明已有要求是否足够、缺的是文字还是执行连接。已有准确条款尽量保留，通过引用和检查落实，不另抄一套规范。

2. **把必要条款写成可判定条件。** 在对应 SPEC 或专项验收规则中明确适用范围、必须观察到的行为、有效证据、不能替代它的观察，以及不满足时保留的状态。保留自治职责、显式组合、可拆增强与最简完整契约；不要为验证强造 C、包装层或无实际需要的第二种合作方式。原要求中的正确设计推理仍独立有效。

   例如：Process 的有界留尾库可以独立验收；主仓迁移完成前，必须从真实执行入口证明完整输出仍可取回，且这项职责只有一个负责者。缺少该证明时，主仓迁移卡不得 DONE。不要要求基础 Process 库独自承担主仓全部保证。

3. **将完成状态与实际证据绑定。** 复用现有卡片、验证结果和检查入口，把本卡承诺关联到被测候选及对应结果。审查是否需要在已有脚本或 CI 中补最小检查：拒绝缺失、失败、未运行、失效或范围不符的证据被用于完整完成声明。检查实际测试结果与输入身份，不以文件存在、勾选框、总通过数或作者文字作为充分条件。职责归属、真实消费者覆盖等语义判断仍由非作者复核；已经标明范围的部分交付不因父卡未完而被阻止。

4. **限制历史证明的适用范围。** 将长期有效的要求与某次验证记录区分开，保留历史记录中的版本、支持环境、实际观察和未证范围。新候选只能复用未受变化影响且能说明适用依据的证据；受影响部分重新验证。禁止把库独立通过写成宿主通过，也不能用后续新绿抹去未定因的旧失败。

5. **明确联合使用和冲突处理。** 在现有拆分任务入口同时链接原要求与交付清单，并写明本卡适用范围。无需新增阅读回执或重复表格。遇到冲突列出版本、原文、影响和修订建议，由对应维护者明确处理；不能自行取较新或较宽松的一份。已知例子是上游 `705e1ea3b` 的项目规则改用 submodule/`file:wanxiangli` 并禁止 tgz 入 Git，旧 distribution WHAT [011] 与施工 §8 却仍要求跟踪 tgz。请核实接手版本是否已统一；源码接入和临时发行包验收应分别证明。

## 用反例验收这次改进

使用隔离案例或既有证据验证以下判断，不在真实看板上制造虚假完成记录。对新增自动检查运行有效候选正控和无效候选负控；尚需人工判定的部分明确说明。

| 案例 | 应有判断 |
|---|---|
| 基础 Process 库兑现有界留尾契约，主仓完整输出尚未证明 | 允许库独立验收；主仓迁移不得 DONE |
| TypeScript 按公开声明编译通过，运行时缺少声明的方法或返回值不符 | 公开产物不通过，不能用编译绿色代证 |
| 实际入口仍走旧实现，或双方继续维护同一业务事实 | 完整迁移不通过，即使库测试全部通过 |
| 引用旧包的通过记录，但新候选已改变相关代码或产物且未补验 | 相关完成声明不通过；记录未证范围 |
| 纯模块在声明范围内完成相关验证，没有持久化或增强承诺 | 不强加冷恢复或增强栈；按其实际范围验收 |
| 本卡完整承诺及适用原规则均有当前有效证据，已完成非作者复核 | 允许按现有流程完成，避免新增检查误拦正常交付 |

## 修改范围与交付

优先修改局部 SPEC、专项施工文档和现有验证入口。不要把项目专项流程堆入根 AGENTS.md；如确需修改通用规则，说明原规则为什么不足，按该仓维护流程提交审查。保留他人的未提交工作，不顺带重构生产模块、切依赖或迁移运行数据，不合并、变基或挑取 upstream。

完成后交付：约束失效的证据与未决原因、采纳或不采纳各项建议的理由、实际修改位置、反例与正控的命令及结果，以及仍需维护者裁决的冲突。区分文档修订完成、自动检查已接入并验证、仍依赖人工复核；新增一个未接入的脚本不能称为约束已生效。提交、推送与部署分别报告。
