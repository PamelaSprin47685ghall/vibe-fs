# CUT-00-R1 ended allowance / next begin transport race

Independent read-only review, d1_review_git, 2026-10-19. No shared source edits or execution. This issue was observed by root during B1 acceptance; this document is source reasoning, not independent reproduction.

The original control guard refused every new begin while entry.allowance existed, even after the exact previous end ACK. Native node:test events and the private control socket use distinct transports. A real next leaf can therefore send a valid begin before the previous native complete reaches the supervisor. This is an R1 supervision regression; it is not a B1 product regression.

The two-line change is reasonable: permit one pending request while the prior allowance is ended, but bindPending returns no reply while any allowance exists. This admits a request, not a physical-wait grant. The previous occurrence and absolute deadline remain active until its exact native complete. The complete removes the old occurrence and then tries binding; a next occurrence still needs a real dequeue. usedTokens, one pending request, unended refusal, spent occurrence and matching run/file continue to apply. Native dequeue during any allowance remains rejected; no relaxation of this guard is needed because run-inner forwards native events in one sequenced IPC stream.

Same-name next occurrences are the necessary counterexample for bindPending's new guard. At review time, both new model tests used different names ('probe' then 'next probe'). Without the new bindPending guard these still wait because the names do not match, so they do not falsify premature binding to an old same-name occurrence. Root was asked to use the same name/fullName and a fresh token for at least one case: next begin before old complete must return [], keep the old deadline, old complete must clear without granting, and the next same-name dequeue alone must grant. Removing the bind guard would bind against the old spent occurrence, clear pending and wrongly reject, so that fixture distinguishes the two implementations.

Additional retained boundaries: another pending token is refused, the old spent token remains spent, unended old allowance still refuses, reaching the old deadline before native complete fails closed even with pending, and new pending creates no provisional deadline. Late begin/end/verdict continue to pass through check(now) first.
