## 工作生命周期与原子日志

CUT-01 先完成实际工作路径切换，退出旧生命周期内核。随后复核没有推翻 Work、Journal、DurableWork 的职责划分，主要发现了日志原生资源寿命及验证方法的问题。

已完成的修正包括：

- Bun 在 COMMIT 入口发生异常后，未释放的原生 statement 会让旧连接继续持写锁。现在每次操作释放自己创建的 statement；Unknown 仍封存业务实例，不重发未知提交或外部命令。实际消费者保留原生引用且不调用 GC，重开后可以立即追加。
- 将业务封存与物理关闭确认分开。首次原生 close 失败后，允许显式重试 close；封存实例不能恢复 read 或 append。
- 双写者竞争夹具先等待双方初始化完成，再同时追加，检验真实 CAS 竞争。另保留初始化持锁反例，没有靠串行化追加或调大等待消除冲突。
- Bun 的 statement.get/all 在部分关闭情形下仍可能执行，旧断言不足以证明 finalize。改用保存的原生 get 观察释放，并用去掉 finalize 的突变检验断言能否发现问题。

0.6.2 交付轮的 Journal 独立复验为 30/30，双写者连续竞争 25/25，Bun 七种去 finalize 突变均被拒绝。同一精确安装包的 Node、Bun 消费者各 7/7，并通过严格 TypeScript 检查。后续 0.6.8 的库完整套件继续覆盖原有模块。

## 进程执行与完整输出

首次接线把基础库的有界留尾能力用于主仓完整输出和强取消。实际后果是大输出丢失、目标退出后的 Draining 阶段失去控制，以及相对 PATH 与目标 cwd 不一致。后续修复围绕这些真实反例逐项展开。

### 采集与物理监管

主仓已退出有损尾部轮询，改用显式 Capture 单消费者读取，完整字节流交给 Spool。采集或落盘失败进入明确失败，清理部分文件，迟到输出不能重新创建已放弃的 Spool。首次创建后写入失败留下路径的问题也已补上反例并修复。

基础 ProcessSession 继续拒绝对已经失效的旧 PGID 发信号。需要更强控制的路径由 SupervisedProcess 保持实际监管实例，分别观察目标退出、输出结束和监管范围结束。取消与硬期限因此能处理目标先退、同组后代仍活着的情况；没有目标退出证据时保留 Unknown，不从信号请求成功推断命令结束。

### 契约与运行时

CUT-02-R6-A 将 ProcessRequest、PtyTypes 的 fs/fsi 四个文件收敛为无工程依赖的纯契约闭包，物理实现进入独立 runtime 工程。实际 run、Git 和 PTY 消费者显式取得 RunProcess、RecoverPty 或端口；旧默认工厂和隐藏物理入口退出。无 durable workspace 的生产入口仍在预留或启动前拒绝。

这次边界变化经过真实 Fable 独立正反编译和实际消费者检验，不能只归为目录整理。独立复审的编译验证 2/2，实际 Node/Bun 冷接管及无 owner 拒绝 3/3。详见 [纯契约报告](PROCESS-CONTRACT-2026-10-18.md)。

运行时修复统一了环境、参数和 stdin 的承诺：库接收完整环境快照，主仓负责显式增量合并；合法特殊键按字面传递，真实监管目标的第二跳也保留这些值。stdin 的 Written 只确认约定的管道写入边界，不等于目标已经消费；实际断管后的 Unknown 不自动补写。相关 Node/Bun 和安装包消费者已有验证，但 R6-C 整体验收仍保留 REVIEW。详见 [运行时报告](PROCESS-RUNTIME-2026-10-18.md)。

### 输出结束与 Bun 背压

R7-A 发现旧清组许可可能早于 Bun 写出缓冲真正交付。现在两路输出分别冻结最终 extent，外侧实际观察到的字节数与其完全一致后才允许自然清组，再等待 EOF。短数、超数、主动中断和显式放弃各有明确结果。0.6.7 的 Node/Bun 物理套件各 82/82，精确包双路 128 MiB 矩阵 12/12。

R7-B 再处理另一项独立缺口：旧 Bun Capture 在消费者尚未读取时，写者仍可完成至少 64 MiB 输出。最终 Bun 物理适配使用 POSIX FIFO 和按需求读取，Worker 出口取得完整 write/flush 回执；Node 继续使用原生 child_process。逐路 extent 屏障保留。

0.6.8 已验证暂停消费会阻塞真实写者，以及空闲、取消、fd 复用和大输出完整性。读队列及 scratch 的边界有具体定义，但它们不等于整个 Bun 进程的 RSS 上限。macOS 和 Linux 的所列物理场景已取得独立证据，不能延伸成所有平台和规模的承诺。详见 [extent 报告](PROCESS-OUTPUT-EXTENT-2026-10-18.md) 与 [背压报告](PROCESS-BACKPRESSURE-2026-10-18.md)。

### 对拆分质量与速度的判断

按完整职责迁移的交付标准，**已检查的职责迁移与完成判定偏粗，尤其是 DONE 判得过早。部分交付速度来自把消费者验证、产物核对和旧职责退出留到了接收阶段。** 这是前四模块记录与两个新增样本共同支持的判断，不能外推为全部上游模块都需要重做，也不表示原拆分方法或要求本身粗糙。原规则已经要求独立职责、真实组合与分阶段验收，主要问题是落实不足。Process 只提供有界留尾可以是合法的小契约；错误在于未补齐主仓的完整输出义务，就把它计作完整迁移。

| 证据 | 缺少的交付检查 | 接收阶段承担的额外工作 |

| resources 替换后 Trim 裁掉注入参数首尾字符，实际 horizon 资源可复现 | 等价迁移的字面量反例及真实资源消费 | 重新比较新旧语义，定位裁剪，补产品入口回归 |

前四模块的依据见上节；新增样本的固定版本、命令和限制见[只读评估](UPSTREAM-INTAKE-ASSESSMENT-2026-10-18.md)。把这些检查推迟后，修复者还要重建上下文，区分拆分回退、原有缺陷和新增需求；接口已经被依赖时，改动与复核范围也更大。这可以解释部分修复成本，不能免除下节所列的本地修复回退、夹具错误和流程干扰。

改进应把上述证据前移到拆分交付，而非让接收方无限增加复查轮数。[交付检查清单](UPSTREAM-DELIVERY-CHECKLIST.md#done-gate)作为原规则的证据补充提案：主仓迁移卡的真实消费者、公开产物、关键反例、旧职责退出四类证据齐备并通过，满足相应风险门禁、非作者复核及最终集成核验，才能标 DONE。独立库仍按自身契约验收，迁移卡可记 LIB_READY，完整子范围可以先提交；相关缺口不能改名、挂子卡后从父项完成条件中消失。工作量校准分别记录库就绪和完整接收的范围与投入，不把包数、测试数或提前标 DONE 当产出。

## 持续接收上游拆分

上游继续拆出新模块，本地将持续承担接收评估和必要修复。前四模块的遗留计划只能安排当前存量，不能回答后续每批的成本。每个候选都要验收，是否需要大修则应由反例和实际调用链决定。不能把前四模块的平均耗时乘以剩余模块数，也不能将“模块变多”解释成同一批修复范围不断扩大。

### 两个样本带来的修正

|---|---|---|

| CUT-21 time/wait | 库原有 67 项测试通过；公开声明与产物不符、向 deadline 写测试计数；主仓仍保留部分算法，纯契约引入合并的 Time 导出 | 契约、实际包、真实消费者及旧实现退出分别取证；先修能力边界再接线 |

以上套件在 Node/Bun 均通过，但安装包补充观察各有 5 组失败，其中两组属于同一资源裁剪问题。库测试绿色不足以证明主仓职责已迁完。另一方面，resources 的问题有明确局部修正范围，也没有证据要求它重做进程、存储或恢复验证。完整证据与限制见[接收评估](UPSTREAM-INTAKE-ASSESSMENT-2026-10-18.md)。

### 拆分方法

1. **按完整职责拆分。** 先列事实、效果、完成确认和收尾分别由谁负责，再确定库边界。选一条真实调用链完成迁移，并盘点该职责的全部消费者；不能用“已经导入新库”代替职责转移。
2. **契约先经过反例检查。** 拆分前用本地有效保证、现行 WHAT 和实际消费者确定可观察结果。等价迁移做新旧对照；有意改变行为则明确裁决。旧实现和新实现同错，不算通过。
3. **内部步骤可以细分，交付责任保持完整。** 公共类型确定后再改调用者和删除旧路径；不为每个步骤新增转发层或兼容账本。库先完成可记 LIB_READY，主仓链和旧 owner 未退出时不能记为完整迁移。
4. **把已有修复变成可复用的反例。** 完整输出、原件不变、未知结果不重发、范围完成冻结、持久确认后清账等保证，随相关上游候选重新验证。调整测试入口以适配新合同，不强行恢复上游已经退役的工具。
5. **固定批次接收。** 针对一个明确的上游 SHA 和库产物列接收范围，先评估再施工。公共协议未稳定时，依赖它的候选先停在评估阶段；上游下一批不会改变本批已冻结的完成定义。

### 验收标准

所有候选均需契约与关键反例、实际安装产物、明确的旧职责去向。公开 API 必须同时通过类型消费和运行时消费；两套各自绿色仍需确认测试的是同一合同。涉及真实接线时，再验证对应的注册入口和效果，不能只测手工构造的库对象。

额外证据按风险选择：纯规则和资源定位不强加冷恢复；Host/多消费者增加真实调用链；持久化、并发和外部效果增加提交失败、重复、乱序及独立进程恢复；物理进程增加真实退出、背压、崩溃和声明平台。原工作包已经明确的门禁继续有效，分级不用于免除尚未兑现的保证。

基础层通过、真实链通过、独立复核、提交推送和部署分别记录。复核优先检查跨边界反例和完整候选，不以增加测试数或反复全量重跑作为质量指标。具体证据和不得标 DONE 的情形以[交付清单](UPSTREAM-DELIVERY-CHECKLIST.md)为准；接收标准与候选工作范围已写入[现行计划](REMAINING-REPAIRS-2026-10-16.md#upstream-intake)。

### 投入与校准

若后续启动这两个候选，按已见范围暂留 resources **4–8 小时**、time/wait **12–24 小时**，合计 **16–32 有效工程小时**，包含修正、接线验证和复核；不含整批上游合并、其他产品变化和公共接口等待。它们是排期预算，不是实测修复工时。time/wait 在契约确定后先重新估算。
