# 上游拆分交付检查清单（证据补充提案）

制定：2026-10-18；同日按[原要求对照](LOCAL-FIRST-FOUR-MODULES-REPORT-2026-10-18.md#original-requirements-alignment)修订。问题依据见[四模块复盘](LOCAL-FIRST-FOUR-MODULES-REPORT-2026-10-18.md#delivery-quality-judgment)及 [resources、time/wait 接收评估](UPSTREAM-INTAKE-ASSESSMENT-2026-10-18.md)。本轮只更新文档，未修改或合并上游。

**依据与采纳：** 原独立库根规则的 SPEC 2—6 及本计划 A—H 已要求自治个体、显式组合、可拆增强和真实交付。本清单补充这些要求的证据检查，不是完整设计规范，也不替代原规则。具体补充作为本地接收标准向上游提案，是否采纳由维护者在 PR 审查中决定；不自行设立全仓 agent 规则。上游源码接入规则与旧 distribution 条款的矛盾仍待其维护者统一，不能用本清单默默裁决。

**阅读与交接入口：** [施工指南](README.md#delivery-handoff) → [职责卡首页](CARDS.md) → 本清单。上游采纳后，在现有任务说明或[交接单](TEMPLATES.md#handoff)附上适用规则、清单的固定版本、本卡范围及验收责任，不另设阅读回执。文件已合并不等于正在运行的 agent 已经读到，跨仓工作也不能依赖自动继承。

<a id="done-gate"></a>
## DONE 的必要条件

**主仓职责迁移卡在冻结范围内，真实消费者、公开产物、关键反例、旧职责退出四类证据必须齐备且通过。** 再满足该范围的风险门禁、非作者复核及最终主仓集成候选核验，才能标 DONE。库内测试通过、包已发布、文件已移动、净改进获准合入，均不能单独代替完整迁移证据。

独立库或增强按原 SPEC 验收其最简完整契约，不以主仓接线或全系统加固为前提；对应迁移卡可记 LIB_READY。较小但完整的库契约本身不是缺陷，主仓的其余必要保证仍须有 owner。事先独立定义的调查、取证或可行性子卡按其研究结果验收；子卡 DONE 不关闭产品父卡，不能事后改称“原型”销掉生产承诺。

完整迁移的四类证据不得整类填“不适用”。某个细项确实无关时，按原规则说明依据，例如纯资源定位无需跨进程恢复、没有增强就不造增强栈；已经承诺的行为不能借风险分级免验。涉及本卡承诺的失败、未运行、TODO、skip、未知结果或失效候选，均保留为未通过。非作者复核不能代替缺失的运行证据。

- **库已完成，主仓未接完：** 保留 LIB_READY；开始实际接线后进入 INTEGRATING。
- **实际链或旧职责尚未收口：** 保留 INTEGRATING；协议本身不成立则回到 DOING。
- **候选证据齐备：** 进入 REVIEW；复核发现缺口则补证或退回相应施工列，不能带着相关缺口进入 DONE。
- **部分交付：** 可以先提交完整子范围，父卡未完成义务仍保留。不能在失败后自行缩小承诺、另挂子卡就关闭父卡；必要范围变更须遵守现有产品裁决规则并重定验收范围。
- **历史 DONE 出现反例：** 保留原始记录并关联修复卡，注明被推翻或未证的承诺；依赖方不能再引用该历史 DONE 证明当前完整职责成立。

状态只在 [BOARD](BOARD.md) 维护，清单与收据不另设第二份进度表。

<a id="delivery-scope"></a>
## 开工前固定交付范围

- [ ] 用一句话写明完成后真实消费者能做什么、旧系统少负责什么；关联原局部 SPEC、适用的主仓 WHAT 与卡号。
- [ ] 列明输入、输出、事实 owner、外部效果、完成确认和收尾；盘点全部受影响消费者、旧实现与在途义务。
- [ ] 区分等价迁移、批准的行为变化、旧缺陷、新能力和证据不足；固定排除项、支持环境、关键反例和各检查项的预期结果。
- [ ] 固定上游/本地基线、库候选、主仓候选和包标识。后续源码、锁、资源或生成物变化须记录新输入，并重验受影响证据；不把旧验证的 SHA 改成新 SHA。

按原 LEMMA 2—7，先核对自治职责、状态归属、真实合作与反例，再定公共接口、改调用者、删旧路径。C 可以有自己的协作状态；纯函数不强造 A/B/C，不为验收增加包装层。内部步骤可以细分，不能把必需的产品保证留在没有 owner 的“后续工作”里。

<a id="real-consumers"></a>
## 1. 真实消费者

- [ ] **调用链清单：** 每个受影响入口写到具体文件、注册/组装点、调用者、公开库入口及结果/效果观察点；列出各链的事实与清理 owner。源码中出现 import 不算接线证据。
- [ ] **真实入口运行：** 从生产实际使用的注册、Host、工具、Join 或资源入口触发，使用本卡真实适配器与被测包；至少验证正常结果和该链关键失败/取消的可观察后果。纯模块验证其实际调用者，不强加无关 Host。
- [ ] **真实组合：** 涉及独立 A/B 的合作时，C 使用公开能力安排顺序、关联和结束，不复制业务账本；按根 SPEC 4，改变一种实际需要的合法合作方式而不改 A/B 内部。仅替换同接口实例不算证明，不为填表虚构第二种需求。
- [ ] **确认走了新路径：** 收据能够把入口、被加载产物和结果关联起来；在隔离测试中移除旧实现或使目标新路径故障时，观察应按预期变化。不能只手工创建库对象，也不能由旧 fallback 悄悄完成任务。
- [ ] **消费者覆盖：** 全部受影响消费者逐项映射到验证。共享同一语义路径的用例可以复用，但须说明等价依据，并核对各入口确实接到该路径；不同能力、错误处理、状态归属或效果不能借一条链代证。

**交付证据：** 调用链表、入口与测试位置、输入、预期与实际结果、实际副作用或零副作用观察、精确包标识、命令与收据。mock 可用于边界反例，不能替代已承诺的真实接线。新旧对照只在隔离夹具运行，不重复执行用户真实外部效果。

<a id="public-artifact"></a>
## 2. 公开产物

- [ ] **输入可追溯：** 分别记录开发接线和发行验收。开发接线按宿主现行规则固定主仓候选、库 commit/gitlink、锁及构建输入；发行验收另记同一库候选的临时 tarball、SHA-256 与包内容。证据注明实际消费方式，不强令源码依赖具有 tarball integrity，不沿用已变更输入的成绩。
- [ ] **独立构建与消费：** 按根 SPEC 2 移除兄弟职责和 C 的源码、实例、服务回调后，仅靠本库与声明依赖仍能构建和验证；实际安装包中移除声明独立的其他职责产物后仍可消费。必要基础依赖如实保留，不能靠模拟兄弟工作流的替身补洞。
- [ ] **发行包完整：** 在不含库源码与源码编译器的干净目录安装实际 pack，从公开 exports 核对 ESM、声明、资源与包外 cwd，不借源码回退。上游允许开发期 submodule/`file:wanxiangli`，但不以开发接线代替此项；临时 `.tgz` 不进入上游 Git，本提案不要求上游恢复本地现用的 vendor 流程。
- [ ] **类型与运行时一致：** 同一个公开消费程序先按声明编译，再运行其产物，核对值、方法、构造方式和失败语义；必要非法调用有编译负控。覆盖本卡涉及的公开入口与契约，而非只检验接口形状。
- [ ] **能力边界成立：** 实际 npm 产物的依赖闭包符合声明；纯入口不能暗带物理或诊断权威。用实际消费正反例核对，源码工程图不能代替打包后闭包；不得向外部注入对象写测试状态。
- [ ] **支持范围有证据：** 在预先声明的运行时与平台组合消费同一包；Node/Bun 各自记录结果，不能相加成双倍覆盖。未覆盖的承诺须保留未通过，不能用另一运行时成绩代证。

**交付证据：** 源码候选与实际消费方式、临时发行包摘要与内容、独立构建和干净消费、声明与运行结果、闭包反例。开发接线与发行验证分别下结论；发布成功只能证明发布动作。

<a id="counterexamples"></a>
## 3. 关键反例

- [ ] **条款对应：** 每个强制保证有能推翻错误实现的用例和正常正控，写明输入、预期与观察点。库内沿用局部 SPEC 与同模块编号测试；主仓沿用 `NNN.test.mjs` 和 `WHAT[PREFIX-NNN]`，不替独立库另建 WHAT 需求树。
- [ ] **先证明反例有效：** 在固定基线重现缺陷；原实现已正确时，用隔离变异或负控证明断言有效，不伪造业务失败。导入错误、夹具漏收尾、超时或环境错误必须单独归因，不能冒充目标反例命中。
- [ ] **保留原保证：** 等价迁移对照新旧可观察行为，同时按适用 SPEC/WHAT 独立裁决；两边同错不能算通过。已有完整输出、原件不变、未知不重发等有效反例随相关候选复用。声明可拆增强时，按根 SPEC 5 让基础单独、加入增强、移除增强均兑现基础契约；增强特有保证另验，不把新契约说成透明替换。
- [ ] **按风险补齐：** 只对本卡承诺增加拒绝、取消、重复、未知、乱序、提交失败、恢复或物理观察；清楚区分请求停止、真实退出和持久确认。详见[风险分级](REMAINING-REPAIRS-2026-10-16.md#acceptance-levels)。
- [ ] **如实记录结果：** 关键反例、相关 requirement 及必要实际链在固定候选通过；列出 fail/skip/TODO/cancelled 与未完成文件。exit 0 或总通过数不能覆盖相关缺证，后续新绿不能自动冲销旧的未定因失败。

**交付证据：** 原 SPEC/WHAT—用例—消费者映射、基线失败或负控、修正后结果、正常正控、原始日志与因果说明。先窄反例、再相关套件与风险验证；仅在有新修改、新失败或未解风险时重复或扩大，不以全量重跑次数作为质量指标。

<a id="old-responsibility"></a>
## 4. 旧职责退出

- [ ] **逐项交账：** 建立“旧文件/符号/状态/调用者 → 新 owner → 删除或保留依据 → 验证证据”表，包含项目引用、公开别名、资源定位、持久 writer 和恢复入口；不能只给删除行数。
- [ ] **实际删除：** 被替代实现、废弃引用、旧解码/回退和重复账本在交付候选退出。结合 diff、引用/依赖检查及旧路径不可用时的实际入口验证，证明旧职责已不再承担承诺；单纯搜索不到旧名字不足为证。
- [ ] **唯一事实来源：** 新旧实现不并行维护同一业务事实，不以永久转发层隐藏未迁移的算法。保留的适配只承担明确的 Host 或组合职责，不复制库内决策、状态或资源所有权。
- [ ] **保留项有边界：** 写明旧路径的消费者、owner、保留理由和可验证的退出条件；独立库的临时兼容、废弃接口或未解耦关系只在其根《例外清单》登记，本卡引用，不另设例外账。本卡承诺迁出的职责仍留在旧侧时不能 DONE；明确排除的独立职责不必一并删除。
- [ ] **数据和在途效果不失主：** 按该候选已批准的数据政策，给出仍受支持的数据和活动资源的切换、未决效果与清理处置及适用恢复证据；不猜事实、不抹账、不因结果未知重发。读取或迁移旧数据不是默认要求，尤其不能借此恢复上游已明确退役的 `.git/wanxiang*` 路径。

**交付证据：** 迁移与删除对照表、实际代码 diff、引用与包闭包检查、旧路径退出后的消费者运行、适用的数据/在途义务处置记录。旧文件保留并不必然失败，但其保留职责必须与本卡完成声明一致。

<a id="delivery-receipt"></a>
## 交付收据与最终判定

证明优先填回原局部 SPEC、测试及现有单卡记录；主仓命令可复用[实际验证收据](TEMPLATES.md#verification-receipt)。已有记录包含相同信息时只作链接，不另填一套表。下面仅为可选索引，不能代替证明。测试与消费程序应可复取；原始日志及必要产物留可复取位置和摘要，不要求把临时包提交到 Git。

| 检查项 | 结果（通过 / 未通过 / 未取得） | 证据链接、候选和观察结论 | 未完成承诺、owner 与下一步 |
|---|---|---|---|
| 真实消费者 | 待填写 | 调用链、真实入口、效果与新路径证明 | 待填写 |
| 公开产物 | 待填写 | 源码与发行输入、独立构建、干净消费、类型及运行 | 待填写 |
| 关键反例 | 待填写 | SPEC/WHAT 映射、有效负控、适用增强拆除与相关结果 | 待填写 |
| 旧职责退出 | 待填写 | 旧新对照、删除与保留、唯一 owner、必要迁移 | 待填写 |
| 风险门禁与最终复核 | 待填写 | 适用矩阵、非作者结论、最终集成候选核验 | 待填写 |

最终记录卡号、冻结范围、主仓/库输入及包摘要、复核人、适用门禁、主线提交与尚未完成的独立范围。所有必要项通过后才更新 DONE。验证通过、提交、推送、部署运行分别报告；新源码或产物造成证据失效时，补验对应部分后再作结论。

两个样本说明本清单的用途：resources 的参数首尾字符裁剪阻塞行为反例验收，真实模板复现仍不代替产品入口验收；time/wait 的声明与运行时不符、deadline 输入被改写阻塞公开产物与契约验收，旧等待算法和能力边界还需逐项裁决。两项均未取得完整真实主仓链证据，因此不能以原库 75 项通过直接接收或标主仓迁移 DONE。此结论限于[评估中的固定候选](UPSTREAM-INTAKE-ASSESSMENT-2026-10-18.md)，不外推全部上游模块。
