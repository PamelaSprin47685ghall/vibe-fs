# U0-A1-K1：Casebook Fetch 的结算消费者

## 认领与范围

从 `b8d8ab204` 接续总计划和 U0-A1 接手卡，认领 Fetch 的 Refresh/Access mandatory settlement owner。依据 knowledge-reuse[005,011,013] 与 durable-events[024,025]。Capture/Host deletion、Evict、真正 physical fatal child、installed Host 分开留待后续；本包不关闭整个 knowledge-reuse013 或 GAP。

当前 Refresh 将所有 mutation error 返回旧答案＋stale；Access 的 Lifecycle 丢弃 Result.Error 并吞普通异常，随后 Fetch 返回 fresh/refreshed。CasebookStore 已保 operation/case/event/original AppendError，不能把这层证据字符串化后再猜是否已提交。

先补四个正式防御反例：Refresh/Access × committed/实际 CurrentCommit Unknown。合法 producer 当前无自然 semantic cut；使用已登记的 payload decorator 仅将本次请求 payload 改坏，真实 Casebook rule/Integrator/Store 产生 bad fact＋cut-tail。gen257正式 **0 pass、4 fail、0 skip、1 TODO，1/1排空**，0.23s wall/0.11s test；所有物理、原 cause/prepared、旧 capture/baseline 与新handle cold 前提通过，四个失败均在最后正常答案拒绝断言，实际旧结果分别为stale/fresh。原业务红有效，主义务TODO保留。

初实施的Fable签名把未公开构造器的Exception误解析为interface，并有两个参数名不符；check另发现owner内nested match/if。修为显式class/end签名、统一参数名并按claim/deliver拆开真实职责，gen258构建与check通过。这些属于编译/门禁失败，不登记业务红。

扩大验证另加独立OS cold：首先暴露原生BigInt字段经JSON变为字符串的夹具问题；现在显式恢复accessOrder/lastAccessOrder，仍核完整typed Case与全部bytes，不改领域语义。随后原R0的`instanceof Error`不适用于Fable的typed Exception载体：测试迁移为response不存在、公开isIncident为真、拒绝对象与原callback incident严格同一。这比native构造器判断更精确地证明“拒绝普通答案”；不把载体差异记为生产故障。最终有限验收见下文。

## 拟修复边界

- 纯 incident 从原 CasebookAppendFailure 构造，只认本 EventId 的实际 settled Casebook cut，复用 AppendError.semanticCuts 分类；未尝试/无新写或普通 Unknown 空 Cuts 不能 fatal。
- 必填 typed capability 归实例 composition owner，guard 在 callback 前认领一次；无 optional/global/default/fallback。callback 返回仍须拒绝普通答案，callback 抛错须原样传播。
- Access 保普通异常 best-effort，但将既有 Result 交回 Fetch，由 Fetch 在 catch 之外裁决。Refresh 同样先交 owner，再决定普通 stale。
- required owner 由 Boot→Hooks→Tools→Fetch 递传；同 scope single-flight 保持，独立 owner/store/workspace 不得借用其他 work 的 capability。

实施后分别记实际 I/O、独立 cold、受控错误映射、domain callback、composition 接线与真正 report/kill 证据。构建只用 node scripts/build.mjs，冻结输入验证，不改原预算或重跑碰运气。

## 实施与追加的根因回归

Refresh/Access 的原 CasebookAppendFailure 现在交给构造时必需的 CasebookSettlementOwner。纯 incident 只认本 EventId 的已结算 Casebook cut，保原 AppendError、Prepared 与 cause；实例 owner 在 callback 前认领一次，callback 返回仍抛原 incident，callback 抛错原样传播。Access 的普通异常仍 best-effort，但 typed Result 在 catch 外交由 Fetch 裁决。Boot→Hooks→Tools→Fetch 无 optional、默认或全局 fatal 绑定；F44 清单只登记此有限接线。

gen262 的正式011/013为18 pass、2 fail、0 skip、2 TODO：跨工作区同 shelfmark 借到左侧答案，同工作区不同实际 Store 也错误加入 flight。修复把 flight 键定为 workspaceRoot＋shelfmark，entry 保实际 Store＋首执行 Task；同 Store 的两个 required owner 共享首任务，不同 Store 在启动新工作前明确拒绝。受控 Bookkeeper barrier 固定顺序，不用 sleep；没有把 owner 加入键而制造同工作区双执行。

只读复核另发现公开重交入口可把真实 incident 交给另一个 owner 再 callback。gen264正式013为12 pass、4 fail、0 skip、1 TODO，四条均在 foreign owner 拒绝断言失败。Redeliver 只查原实例认领字典，同时核 EventId 与原 incident 引用；未知或外来 incident 拒绝，不认领、不重造、不 callback。初次 Fable 因 raise 推断出泛型返回值而失败，补显式 unit 与签名一致后通过；此为编译失败，不登记业务红。
