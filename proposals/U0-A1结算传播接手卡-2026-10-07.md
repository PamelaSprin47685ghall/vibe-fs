# U0-A1：结算传播的剩余执行边界

这是 U0-A0 后的有限接手卡；不重新实施原六个 AppendError case，也不授予 H0b fresh acceptance。认领前核当前 WHAT 和最新施工收据，不继承临时运行中的数字。

## 1. 先冻结证据层级

- 原生 Store 矩阵、独立 cold reopen、受控消费者映射、实际组合 callback、物理 fatal child、installed Host 分开记账。一个层级的绿不得给另一个层级发证。
- 正常 encoder 不能产生 cut 时，先查 actual integration rule 是否存在自然可达的语义拒绝；不能自行发明 duplicate rule。坏 payload 端口注入可以证明防御接续，标题和收据必须明示它，不能称合法输入自然可达。
- 同一 Error、EventId、Prepared 的真实引用及 ordered cleanup 要继续保留。最终工具文本可以渲染；领域中不得重建同文案的新异常冒充原 cause。

## 2. Sphinx mandatory capability 与实际 cut

1. 从 Commands.create 的必填能力、RuntimeHandle.SettleAppendCutUnknown、Wire/MCP 两原 composition binding 追踪当前完整调用链，记录源码身份。不得让测试自造 second runtime。
2. 先用现有 actual EventStore 端口坏输入观察能力验证 Sphinx fact 的真实 rule cut 和 release fault能否形成；保原 inquiry/command/eventId，bad fact与cut-tail字节、owned release、独立cold均须先成立。
3. 通过实际 Commands 路径调用构造时注入的受控 capability，确认回调在真实结算之后且一次。普通 Unknown（Cuts空）、NotAttempted、NoNewWrite必须零incident；合法start有非零append正控。
4. 重投同一 incident 的拒绝必须观察原 RuntimeHandle 的真实guard；若公开接缝不足，窄Surface只装配和调用原guard，不复制HashSet或settlement算法。
5. 另以真正Wire/MCP binding跑 owned fatal child，保原工具请求、终端报告和一个kill；受控callback返回不构成物理退出证明。没有前提就具体留下未验收，不借JS物理绿。

## 3. Casebook mandatory owner（先定契约，后改调用方）

1. 逐一列出 Capture/Refresh/Access/Evict 的原 producer、Workflow、Lifecycle、Bookkeeper、Fetch 与Host deletion消费者。区分已知失败、Unknown、无新写释放失败和确有settled cuts。
2. 当前 refresh/access 的 stale/吞错与Host deletion pending是待裁决消费点；不要将普通Unknown全改成fatal。先保旧成功、旧案/基线、真实效果和identity retention正控。
3. 按knowledge-reuse013在真实composition构造时注入必需typed capability。incident须携原operation/case/event/AppendError以及确属实际结算的cuts；无optional/global/default/fallback，不在Store直连FatalProcess，不把它字符串化为PhaseConflict。
4. 先取正式业务红再落实调用链；合法builder无自然cut时明示受控坏输入防御前提。access的异常catch不得吞掉已交原owner的fatal incident，refresh不得把cut包装成普通stale。
5. 每条成功/普通拒绝/Unknown空cuts/actualcut各作正式正反；独立cold核Case投影，incident不得另改epoch/freshness。最后分别验actual composition、一次report/kill及真实Host身份保留；当前DropSessionIdentity无操作不能代替registry证据。

## 4. 其它消费者分别认领

- Journal：原生初始化/业务Unknown矩阵已存在；补actual Unknown+Cuts→原fatal child，不重复用受控writer说明它。
- Strength：Store/Durability与Boot→Replay有限证明保持；Delegate的Bound CancelOwner双故障、Replay actualcut、PluginStrengthPorts actual composition各自需要原owner执行及ordered cause证明。
- Handoff：已完成WorkRecord与未提交checkpoint是不同事实；补实际Unknown/NoNewWrite的sync/fork completion矩阵，不将已有WriterClosing正控升级为这些分支。
- GateAcquire：目录拒绝已证；proper-lockfile永久mkdir错误仍走forever retry。先明确busy lock与永久IO错误的真实owner合同和原生可取消观察前提，不调大监督预算或直接杀未知PID取绿。

## 5. 然后才进入 H0b

H0b的存储合同设计可与Casebook等独立消费者义务并行；开放真实effect前须完成其实际依赖的Store结算与Sphinx原owner接续证明，不把所有消费者TODO变成统一前置。冻结canonical原锁下fresh read-set/retention cut→纯准入→append→唯一Current→本次fresh witness。duplicate/no-op和unknown均不能授新spend许可；跨handle/process、Host effect前binding、receipt丢失零重发和installed Host各自验收。017历史fold成本没有真实观察能力前保持未证。

每完成一包，更新总计划、08分册、施工记录的状态/原红绿/实际输入与剩余边界，提交前冻结并执行对应requirement和相关门禁。构建只用node scripts/build.mjs，master普通提交推送，禁止force。
