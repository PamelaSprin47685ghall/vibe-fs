# 工作计划：Blogger cycle 失败与 out-of-sync

状态：计划 only。不在本文件生效期内改生产代码。
范围：`ENFORCER-043` 空 text、`missing CurrentRequest`、无 `blog` 调用防御、RFC nudge 接线边界。

---

## 0. 观察到的症状

1. `enforcer-cycle-failed` / `enforcer-cycle-repair`，`result` 含：
   - `blog cycle merged text is empty after canonicalisation (ENFORCER-043)`
   - （口语缩写）`text is empty after canonicalisation (ENFORCER-043)`
2. 偶发：
   ```json
   {"operation":"enforcer-cycle-failed","session_id":"ses_…","result":"missing CurrentRequest"}
   ```
3. 用户判断：2 常是 1 或其他失败后的次生 out-of-sync；任何时候不应 out-of-sync。
4. 额外要求：防御 Blogger 不调用 `blog`；repair/nudge 按 `SSOT/15` + `RFC/enforcer-nudge.md` 落地（本计划先排期，后实施）。

---

## 1. 根因（有代码证据）

### 1.1 ENFORCER-043：merged text 规范化后为空

发射点：

```text
EnforcerHost.validateCycle
  → EnforcerCycle.mergeCalls
  → EnforcerCycle.isValidCycle   // MergedText.Trim().Length > 0
  → Error "blog cycle merged text is empty after canonicalisation (ENFORCER-043)"
```

成立条件（合取）：

1. 最后一条 assistant 上存在 `status = "completed"` 的 `blog` tool part（`blogCallFromPart` 放行）；
2. 每个 call 经 `EnforcerCodec.decodeCall` 后 `Text = None` 或合并结果 trim 后为空；
3. 因而 cycle 在 continuation 边界被拒绝。

`decodeCall` 对 `text` 的规范化：

```text
Map.tryFind "text"
  → 仅接受 string
  → Trim
  → Length > 0 才 Some
```

因此下列输入都会变成“无有效 text”：

| 输入 | 结果 |
|---|---|
| 缺 `text` | `None` |
| `""` / 纯空白 | `None` |
| 非 string（number/bool/object） | `None` |
| 多 call 全部上述情况 | `MergedText = ""` → ENFORCER-043 |

这不是“随机 codec 坏了”，而是 completed blog call 已进入 merge，但 canonical text 全集为空。

### 1.2 执行边界未按 ENFORCER-061 拦截空 text

`BlogTool.execute`：

```text
let text = args.Text "text"   // 读取后丢弃
// 身份齐备与否都 return "OK"
```

与条款对照：

| 条款 | 要求 | 现状 |
|---|---|---|
| ENFORCER-040 | execute 必须 resolve，固定 `"OK"` 给有效进入 | 无条件 `"OK"` |
| ENFORCER-061 | 有工具调用但 canonical text 全空 → 工具返回可读错误，允许 Host tool-loop repair 一次；或 terminal 后 InteractionRepair；整逻辑请求最多一次 repair | execute 不校验；错误推迟到 continuation 的 `validateCycle` |
| ENFORCER-044 | merge/commit 在 continuation，不在 execute | 遵守；但把本可在 execute 拒绝的空 text 也推迟了 |

结论：空 text 的第一失败点被放在 continuation，此时 tool 已 completed，Host 已进入 tool-loop 下一拍，修复面更窄、状态更易漂。

### 1.3 “repair” 是假接通，制造次生态

`handleContinuation` 在 `validateCycle = Error` 时：

```text
if not RepairSpent then
    markRepairSpent
    injectRepair ← true
    emit enforcer-cycle-repair
else
    failClosedNoPark reason   // emit enforcer-cycle-failed + onFail→Idle + ClearCurrentRequest
```

随后：

```text
if injectRepair then return rawMessages   // 不注入 RepairInstruction
```

证据：

- `RepairInstruction` 常量仍在（`# Protocol repair…Call the blog tool exactly once…`）；
- 生产路径注释写明 0.5.1 故意不注入 repair（曾误伤 pending blog / restart canary）；
- `hasBlogToolPart` 在 empty-calls 分支算完后 `let _ = hasBlogToolPart` 丢弃。

效果：

1. 第一次空 text：只打 `RepairSpent` 标记，不修，CurrentRequest 仍 InFlight，不 Park；
2. Host 带着已 completed 的空 blog 继续；
3. 第二次再空：`failClosedNoPark` → Idle + 清 InFlight；
4. journal 上的 `BloggerRequestMaterialized` open 通常不 abandon；
5. `onFail` 把 `RepairSpent` 重置为 `false`（见 `BloggerRuntime.onFail`），“整逻辑请求最多一次 repair”在失败回收后被抹掉。

### 1.4 `missing CurrentRequest`：权威槽与物理 cycle 脱锁

CurrentRequest 定义（已收口过一次 dual-write）：

```text
CurrentRequest ≡ BloggerRuntimeState.InFlight 的 payload
durable 旁路 ≡ BloggerCycleProjection.OpenByBlogger → tryReloadRequestContext
resolveCycleContext = peek InFlight ∨ (reload open ∧ SetCurrentRequest)
```

`missing CurrentRequest` 仅在：

```text
completed blog calls 非空
∧ validateCycle = Ok（或走 commit 分支前）
∧ resolveCycleContext = None
```

`resolveCycleContext = None` 当且仅当：

1. 非 InFlight（Idle/Parked/Disposed/空 cell）；且
2. 无 open materialization，或 context blob 不可读，或 runtime Disposed。

与 1.3 耦合的脱锁时间线（高概率次生路径）：

```text
① blog completed 但 text 空
② “假 repair” 或第二次 failClosedNoPark → Idle，InFlight 清空
③ open request 仍在  ─── 或 ───  被新 materialize supersede abandon
④ Host 仍在旧物理 turn 的 tool-loop / continuation 上投递旧 ProviderRun 的 completed blog
⑤ resolveCycleContext：
     - open 仍在 → 本应 reload 成功（若仍失败，查 blob/Disposed）
     - open 已被 supersede abandon → None → missing CurrentRequest
```

coordinator 侧 supersede：

```text
BloggerCoordinator.materializeRequest
  staleOpen.RequestId ≠ new → BloggerRequestAbandoned "superseded-by-new-materialize"
```

即：旧 cycle 的物理 tool 结果还在飞，逻辑 open 已被新 material 替换 → 权威上下文与 provider step 不再是同一请求。这就是 out-of-sync。

补充脱锁（无 blog 调用）：

```text
extractCalls = Some(_, [])   // 纯正文 / 无 completed blog
→ 直接 return rawMessages
→ 不 Park、不 repair、不 fail、不 abandon
→ InFlight 长期占用 → 后续 onMainMaterial 恒 Skip（COMPANION-008 busy）
```

这是另一种 out-of-sync：逻辑请求“假活”。

### 1.5 无 `blog` 调用：条款有、生产关

| 条款 | 要求 | 现状 |
|---|---|---|
| ENFORCER-060 | 纯文本 terminal、无有效 blog → 一次 InteractionRepair；再失败放弃；coverage 不推进；Main 不阻塞 | empty-calls 直接 `return rawMessages` |
| ENFORCER-030 | 每请求恰好一次 blog | 无执行期强制 |
| RFC ENFORCER-180 §4 | 实现 repair + Main/Squash 分流 | repair 未接通 |
| RFC nudge overlay | 主会话投影 fake user `# [nudgeKey] …` | 非 0.5.2 Active 合同；纯内核/测试在，生产接线未做 |

用户要求“不调用 blog 也要防御，并按 RFC 做 nudge”。必须拆成两层，避免把 RFC 整包偷运进 Active 合同：

1. 协议修复层（Active SSOT/15）：ENFORCER-060/061 InteractionRepair / tool 可读错误；
2. 工程异议层（RFC/enforcer-nudge）：评分 → throttle → NudgeAnchored/Consumed → Main overlay。

无 blog ≠ 自动发 enforcement nudge。无 blog 先走协议 repair；nudge 只消费已提交的 BloggerMain cycle 报告。

## 2. 非根因（已排除）

| 嫌疑 | 结论 |
|---|---|
| `text`/`evidence` 与 rule FieldName 碰撞 | catalog 无 `text`/`evidence` FieldName |
| plugin schema 非 Zod 导致 args 丢失 | `@opencode-ai/plugin` 的 `tool.schema = z`，`allZod=true`；`text` required、其余 optional 正常 |
| CurrentRequest 双字典 dual-write | 已改为 InFlight payload 单权威；测试锁住 |
| `:? string` 在 Fable 误判 JS string | 编译产物为 `typeof _arg === "string"`，正确 |
| Host `state.input` 非常对象 | processor 在非 record 时包成 `{ value: input }`；若模型把整段当非 object 传入，会变成 `value` 键而非 `text`——属边界情形，列入防御，不是主路径 |

## 3. 目标不变式（修完后必须永远成立）

1. 单一 cycle 权威：任一物理 Blogger provider step 的 commit/repair/fail，只绑定产生该 step 的那份 `BloggerRequestContext`（InFlight 或与之 RequestId 一致的 open materialization）。
2. 禁止半失败：不存在“RepairSpent=true 但不注入 repair”“fail 到 Idle 但 open 仍表示 in-flight cycle 且 Host 仍投递该 cycle 工具结果”的稳定态。
3. 失败可分类、可终止：
   - 无 blog（纯正文 terminal）→ 一次协议 repair → 再失败则 abandon open + Idle；
   - 有 blog 无 text → execute 可读错误或 continuation 一次 repair → 再失败 abandon + Idle；
   - 不得永久 InFlight。
4. Main 永不因 Blogger 失败而阻塞（ENFORCER-050/070 精神）。
5. out-of-sync 是 bug 不是日志：`missing CurrentRequest` 在“有 completed blog”路径上应为不可达，或仅在 crash reconcile 明确分类后出现并带 abandon。

## 4. 修复策略（分阶段，后阶段不破坏前阶段不变式）

### 阶段 A — 先量后改（证据锁死）

目的：用运行时计数证明 1.1–1.4，而不是再靠读代码推理。

1. 临时诊断（可随后删除）在以下点打 CTX-014 白名单字段：
   - `blogCallFromPart`：callId、`input` 的 `typeof`、是否含 `text`、text 长度；
   - `validateCycle` 失败 reason；
   - `resolveCycleContext` 分叉：peek hit / open hit / open miss / reload fail / disposed；
   - `failClosedNoPark` / supersede abandon / `onFail` 前后 runtime tag。
2. 最小复现夹具（`tests-mjs`，Fake Host 轨迹，VERIFY-003 精神）：
   - `blog + text=""` / `text="   "` / 缺 text；
   - `blog` 后假 repair 再空 text；
   - 空 text failClosed 后 main 再 offer（supersede）且旧 continuation 重入；
   - 纯正文无 blog；
   - pending blog（status≠completed）不得当纯正文 repair。
3. 门禁：每个夹具先红一次，证明当前实现违反 §3 不变式。

退出条件：每条次生路径有“输入 → 状态序列 → 日志 reason”对照表。

### 阶段 B — 协议层：空 text / 无 blog（Active SSOT/15）

B1. `BlogTool.execute` 与 ENFORCER-061 对齐（不破坏 ENFORCER-040）

```text
decode raw args（与 continuation 同一 codec）
if not hasValidText:
    return 可读错误字符串（非 "OK"）
    // Host tool-loop 可再给模型一次；不在 execute 里挂起
else:
    return "OK"
```

注意：

- 身份缺失仍不 stall tool-loop（现有 ENFORCER-041 行为可保留），但不得把“空 text”伪装成成功 completed 语义之外的静默；
- execute 错误 vs continuation 校验双保险可以保留，但 第一道必须在 execute。

B2. 接通真实 InteractionRepair（ENFORCER-060/061），消灭假 repair

设计约束（吸收 0.5.1 关掉注入的原因）：

```text
仅当同时成立才注入 RepairInstruction：
  - 本逻辑请求 RepairSpent = false
  - last assistant 不存在 status∈{pending,running} 的 blog part
  - （060）无任何 completed blog    或  （061）有 completed blog 但 validateCycle 因空 text 失败
注入后：
  - RepairSpent = true
  - 保持 InFlight + 同一 CurrentRequest（禁止 clear）
  - 不 Park
  - 不 commit、不推进 coverage
再次失败：
  - abandon open（BloggerRequestAbandoned reason=protocol-repair-exhausted）
  - onFail → Idle
  - ClearCurrentRequest
  - 不 Park
```

`RepairInstruction` 已存在；禁止动态拼 delta/TOML（item 15：stable minimal repair）。

B3. empty-calls 分支重写

```text
pending/running blog → return rawMessages（Host 会再入）
pure prose + RepairSpent=false → 注入 repair（B2）
pure prose + RepairSpent=true → abandon + Idle（同上）
禁止再 let _ = hasBlogToolPart
```

B4. failClosed 与 open materialization 同寿

所有 `failClosedNoPark` 路径：

```text
emit failed
abandon open（若仍 open 且 RequestId 匹配）
onFail → Idle
ClearCurrentRequest
```

禁止“内存 Idle、journal 仍 open、Host 仍投递旧 tool result”的稳定态。

B5. resolveCycleContext 防张冠李戴

```text
reload open 时：
  若 InFlight 已有 ctx 且 RequestId ≠ open.RequestId → 不覆盖，返回已有（或 fail closed 并打诊断）
commit 前：
  ctx.RequestId 必须与 open/receipt 期望一致
旧 ProviderRun 的 completed blog 到达时若 open 已 abandon：
  → 明确 reason（stale-cycle-after-abandon），不报笼统 missing CurrentRequest
  → 不 commit
```

B6. RepairSpent 生命周期

```text
beginRequest / onMaterial(Start|Offer) → RepairSpent=false（新逻辑请求）
成功 commit → false
abandon / 最终 fail → false 且 open 已清
禁止 onFail 在“同一逻辑请求第二次空 text 前”把 RepairSpent 清掉后再次假 repair
```

实现建议：RepairSpent 绑定 `BloggerRequestId`，或 abandon 与 onFail 原子配套，避免“Idle 但还算同一请求”。

退出条件：

- 阶段 A 夹具全绿；
- 不再出现 `missing CurrentRequest`（或仅 stale-cycle 明确 reason）；
- canary：`host-transform-capability`、`companion`、`fallback` 不回退。

### 阶段 C — 状态机审计（out-of-sync 清零）

对 `BloggerRuntimeState` × Host 事件做穷尽表：

| 状态 | material | tool completed | pure prose terminal | park timeout | dispose | crash recover |
|---|---|---|---|---|---|---|
| Idle | Start/materialize | ignore/stale | ignore | n/a | Disposed | open→分类 |
| InFlight | Skip | commit/repair/fail | repair/fail | →Idle+abandon? | Disposed | 不 stomp |
| Parked | PendingOffer+resume | stale? | n/a | n/a | Disposed | RestoredParked |
| Disposed | ignore | ignore | ignore | ignore | — | Unreadable |

补测：

- `tests-mjs/Enforcer/blogger-runtime.test.mjs` 扩决策表；
- crash recovery 与 supersede 交叉：live InFlight 不 stomp（已有）+ abandoned 后 stale tool 不 commit（新增）。

退出条件：表中无空白、无“未定义 → 靠日志碰运气”。

### 阶段 D — RFC nudge（显式非 Active，可开关）

前置硬门禁（ENFORCER-180 第 0 步 7–9 等，STATUS 已部分具备 host-transform canary）：

1. 拼写错误字段到达 codec（C-03 类）；
2. main transform 插入 fake user 后 HOST-010 仍能绑 ProviderRunIdentity；
3. Y compaction 后可重新 prompt。

实施顺序严格按 RFC ENFORCER-180：

```text
Catalog 生成器门禁
→ 纯 codec/throttle 属性测试（已有基础）
→ BlogEntryCommitted 派生报告（0.5.2 若仍剥 scores，需先定：nudge 是否要求 score 回 Active）
→ NudgeAnchored / NudgeConsumed 事实
→ Main overlay 投影 + Seal 包含 + BloggerDelta 排除
→ epoch 切换遗忘
→ Fake Host 轨迹 + OpenCode canary 三轮
```

产品边界决策（实施前必须书面定一条）：

- D-opt-1：nudge 仍留 RFC，本轮只做协议 repair（阶段 B/C），nudge 另开版本；
- D-opt-2：将 RFC 子集升格 Active（改 SSOT + conformance，走例外协议），再接线。

未定前禁止“代码先接、条款后补”。

### 阶段 E — 验证阶梯（VERIFY-001/002）

```text
0 gate:static / architecture-gate（single-writer、repair 注入点唯一）
1 tests-mjs：codec / cycle / runtime 决策表 / repair 一次 / stale cycle
2 资源契约：abandon 后 open=0，InFlight 不泄漏
3 Fake Host 轨迹：§ENFORCER-192 中 pure text、empty text、blog+trailing prose、crash 窗口
4 单 canary：host-transform-capability、companion、manager-companion、fallback
5 不在本计划默认范围；发布时 test:release ×3
```

禁止：加 sleep、放宽断言、repeat-until-pass、假 repair 再留注释“以后再接”。

## 6. 风险与非目标

| 风险 | 缓解 |
|---|---|
| repair 注入再污染 mock 前缀 | 仅 protocol 固定句；scenario 声明或 internal turn；pending blog 不注入 |
| execute 返回非 OK 是否打断 Host | 对照 Host tool-error 路径；错误应进 tool result 并继续 loop |
| abandon 过于积极丢掉可 reconcile crash | abandon 仅协议耗尽/最终 fail；crash window C 仍 recommit |
| 把 RFC nudge 与协议 repair 搅在一起 | 分阶段；nudge 不消费未提交 cycle |
| 触碰 ARCH-003 | 只读 Host；不改 opencode 本体 |

非目标：

- 不改 Main 等待 Blogger；
- 不在 transform 里做 CTX 容量估算；
- 不恢复 `EnforcementCycleCommitted`；
- 不在本计划实施阶段改 SSOT 正文（除非选 D-opt-2 走正式升格）。

## 7. 完成定义

1. 空 text / 无 blog / stale supersede 三条 Fake Host 轨迹绿，且曾红过。
2. 生产路径不再 emit `missing CurrentRequest`（或仅 `stale-cycle-after-abandon` 等精确 reason，且不 commit）。
3. `RepairInstruction` 有真实注入点与一次上限；无“标记 spent 但不修”。
4. open materialization 与 InFlight 同寿：commit / abandon / dispose 三者之外无第四种永久悬空。
5. 相关 canary 绿；`gate:static` 绿。
6. RFC nudge 若做：HOST-010 seal 含 nudge、BloggerDelta 不含、epoch 内字节稳定——否则明确不做并留在 RFC。

---

## 8. 一句话结论

空 text 是第一因（completed blog + canonical text 空）；假 repair + failClosed 不清 open/乱清 InFlight + materialize supersede，使旧 tool-loop 与逻辑请求脱锁，表现为 `missing CurrentRequest`。先修协议权威与一次真 repair，再谈 RFC nudge。
