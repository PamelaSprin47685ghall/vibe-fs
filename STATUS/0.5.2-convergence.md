# 0.5.2 全 SSOT 收敛发行方案

## 一、发行目标

0.5.2 的目标不是“多修几个 PARTIAL”，而是一次性建立以下最终状态：

```text
Active SSOT 中每个条款都有唯一状态
Active 条款全部 CONFORMANT
不存在 PURE_CORE_ONLY
不存在 NOT_IMPLEMENTED
不存在未解释的 PARTIAL
不存在生产零调用点的测试专用代码
不存在第二套旧协议或兼容旁路
不存在状态文档、版本、证据与源码漂移
不存在已解决事项仍留在 Active Blockers
不存在未来设计冒充当前产品规范
```

0.5.1 已经证明当前发布基线是稳定的：`gate:static`、构建、641 项 unit、285 项 harness、18 个 canary 三轮并发均通过。0.5.2 应从这个绿基线出发，逐项收口，不能以“大扫除”为由大范围重写。

# 二、当前真实问题

## 2.1 合规表不是当前真值

当前 `STATUS/conformance.md`：

* 仍绑定 0.5.0 发布前 commit `24bda4f5`；
* 按现有表逐项统计，135 个汇总项中：

  * 104 个 `CONFORMANT`
  * 25 个 `PARTIAL`
  * 3 个 `PURE_CORE_ONLY`
  * 3 个 `NOT_IMPLEMENTED`
* 多处状态已被后续实现和 canary 证据反超；
* 使用范围表达，如 `STRENGTH-001…005`，无法知道单个条款的真实状态；
* 另设“未列入主表的条款”，说明表本身不是完整账本。

因此第一步不能直接根据旧表改代码，而必须重建逐条款账本。

## 2.2 状态文档已有明显漂移

当前仓库同时存在：

* `README.md` 仍写当前版本 `0.5.0-rc.1`；
* `STATUS/README.md` 已写 0.5.1；
* `STATUS/README.md` 的源码文件数量仍是旧值；
* conformance 绑定旧 commit；
* blockers 文件标题写“活跃”，正文又写 Blogger 链已闭合；
* blockers 仍记录“发布前要跑三轮”，但 0.5.1 发布证据已经跑完三轮；
* 部分 blocker 记录的缺口已经被源码修复，却未归档。

这些不是文案小问题，而是仓库失去“哪里是真相”的表现。

## 2.3 生产树中仍有旧入口

当前源码仍保留：

```text
Companion.Submit
CompanionHost.SubmitProjection
CompanionHostBlogger.blog
startMainFromContext 兼容别名
CompanionJournalPort 的 squash-legacy 路径
“legacy records 可缺 EffectiveAgent”之类字段宽松
```

它们已经不是生产权威，只供旧测试或兼容路径使用。继续保留会造成：

* 新实现与旧测试各走一套入口；
* 新不变量无法阻止旧入口复活；
* 后续维护者误把兼容函数重新接回生产；
* conformance 无法证明“只有一个实现”。

0.5.2 必须删掉这些入口，而不是继续标注 `Legacy`。

## 2.4 大量 PARTIAL 实际属于三种不同问题

不能用同一种方式处理。

### A. 真正的生产缺口

主要包括：

* `EXEC-009`：`join` 尚未从 durable `HandleProjection.joinable` 消费；
* `PERSIST-009`：外部副作用的 durable-effect 语义没有统一闭合；
* crash/restart 后部分资源所有权仍由运行期对象补充；
* 某些协议还存在测试入口与生产入口双轨。

### B. 已实现但证据或状态过时

例如：

* `REVIEW-007` 已有真实 Manager Guard canary；
* `ARCH-004` 已有显式 cold-boundary 机制；
* `VERIFY-001/003` 的发布层级已经跑通；
* Blogger 0.5.1 的多个状态已闭合，但 conformance 未完全刷新。

这类不应再改生产代码，只补精确判据和当前证据。

### C. 未来功能冒充当前规范

包括：

* spec/14 Strength 大部分条款；
* spec/15 中未启用的 throttle、nudge 和后续监督链；
* spec/16 Student & Teacher；
* 与它们对应的 `PURE_CORE_ONLY` 生产源码和测试。

这些文件自己仍写着“默认关闭”“等待 Host canary”“首个生产版本”等措辞，说明它们本质是已批准设计，而不是当前发布合同。

# 三、最关键的规范裁决

## 3.1 Active SSOT 只描述已经交付的产品

0.5.2 冻结以下规则：

```text
spec/ = 当前发布产品的强制规范
RFC/  = 已批准但未交付的未来设计
docs/archive/ = 历史决策、迁移方案和旧证据
STATUS/ = 当前实现状态，不定义产品语义
```

SSOT 中不得再出现：

```text
默认关闭
待 Host canary
待灰度
目标版本：首个生产版本
尚未接线
纯领域内核已实现
实施只能在……
```

这些都是状态或路线图语言，不属于当前产品的单一真相。

# 四、建立逐条款机器账本

## 4.1 新增唯一状态源

新增：

```text
STATUS/conformance.toml
```

每个 Active 条款必须单独一项，禁止范围行：

```toml
[[clause]]
id = "EXEC-009"
lifecycle = "active"
status = "conformant"
owner = [
  "src/Wanxiangshu/Journal/LinkageProjection.fs",
  "src/Wanxiangshu/Session/HandleController.fs",
  "src/Wanxiangshu/Infrastructure/OpenCode/Tools/JoinTool.fs",
]
tests = [
  "tests/unit/Execution/handle.test.mjs",
]
canaries = [
  "tests/e2e/tests/manager-full-loop-canary.mjs",
]
required_layer = 4
verified_commit = "<commit>"
evidence = "docs/evidence/0.5.2/exec-009/"
```

允许的 lifecycle：

```text
active
superseded
```

未来设计不进入这个文件，因为已经迁到 `RFC/`。

允许的 release 状态：

```text
conformant
```

开发分支可以临时使用：

```text
implementing
blocked
```

但发布 gate 只允许 Active 条款全部为 `conformant`。

## 4.2 生成 Markdown，不再手写两份

新增：

```text
scripts/conformance-gen.mjs
scripts/conformance-gate.mjs
```

职责：

1. 从 `spec/01…13` 和 Active `spec/15` 提取全部条款。
2. 要求每个条款在 `conformance.toml` 恰好出现一次。
3. 禁止未知条款和范围表达。
4. 检查 owner 文件存在。
5. 检查 test/canary/evidence 路径存在。
6. 检查 `verified_commit` 非空且与当前验证提交一致。
7. 生成 `STATUS/conformance.md`。
8. 手工修改生成文件时 gate 失败。

## 4.3 不强迫每个原则写无意义单测

每条 clause 必须声明需要的最低证据层：

```text
0 = 静态/结构门禁
1 = 纯领域反例测试
2 = adapter/codec 测试
3 = Fake Host/harness
4 = 真实 Host canary
5 = release 三轮证据
```

例如：

* `ARCH-003` 适合第 0 层，不需要假单测；
* `HOST-010` 必须第 4 层；
* `VERIFY-004` 必须第 5 层；
* `BloggerToml` 适合第 1、2 层。

这样可以清除当前“因为没有以条款 ID 命名的单测，所以 PARTIAL”的机械状态。

## spec/01：架构 DNA

### ARCH-001

必须解决“事实序列看起来像 stage”这一长期歧义。

冻结解释：

```text
禁止的是运行时可变程序计数器驱动控制流。
允许的是不可变业务事实以及 Fold 得出的业务状态。
```

对 Orchestrator 检查：

* `CandidateReady`
* `RebasedCandidateReady`
* `ConflictDetected`
* `PublishClaimed`
* `PublishSucceeded`

每个事实必须描述已经发生的业务事件，而不是“下一步应执行第几阶段”。

如果 `JobProgress` 仍含纯控制阶段枚举：

* 删除枚举；
  -改为从事实投影出 capability，例如：

  * `MayReviewCandidate`
  * `MayRebase`
  * `MayPublish`
  * `IsCompleted`

增加 architecture gate：

```text
禁止 CurrentStage / Phase / StepIndex / Generation / Lease
禁止根据 ordinal 决定业务动作
允许 typed business fact 与 derived capability
```

### ARCH-004

已有 cold-boundary 机制，不再重写。

收口动作：

* 将 `cold-boundary.js` 作为唯一边界目录；

  -禁止测试通过嗅探消息变化自动判定 cold；
  -新增生产 boundary 与 TestKit boundary 的双向完整性门禁。

### ARCH-005/006/007/008

* ARCH-005、006、007 补机器判据，不为命名而写假测试。
* ARCH-008 若已被 ARCH-009 完全取代：

## spec/09：Execution、Fork、Join、PTY

### EXEC-009 是本轮最重要的生产改造之一

当前问题：

```text
durable projection 知道哪些 handle 可 join
但 JoinTool 仍主要消费运行期 mailbox
```

目标：

```text
JoinTool
→ 查询 HandleProjection.joinable
→ 按 durable handle 找 completion payload/blob
→ 原子写 HandleRetired
→ 返回最小 LWR wire
```

实施要求：

1. `HandleCompleted` 必须携带或可定位 completion blob。
2. runtime mailbox 只能作为等待通知，不是事实来源。
3. restart 后 mailbox 为空时仍可 join。
4. join 成功与 tombstone 必须构成一次受控消费。
5. commit unknown 时不得返回 completion 后又重复 join。
   6.两个并发 join 只有一个成功。
6. cancel 与 join 竞争时结果确定。
7. retired handle 永久不可恢复。
8. `list`、`join`、parent cancel 使用同一个 projection。
9. 删除 `ForkTypes` 中“legacy record 可缺 managed agent”的宽松语义；0.5.1 记录若字段合法则读，否则明确拒绝。

其余收口：

* EXEC-003、013、014 补明确 contract test。
* PTY onExit-only 保持不变。
* process deadline 不改算法。
  -所有 waiter/disposable 在 parent delete、plugin dispose、timeout 时释放。

## spec/11：Journal 与持久化

### PERSIST-009 必须从“抽象口号”变成实际映射

不要强迫所有领域共用一个巨型 `DurableEffect` union；允许 typed domain facts，但必须满足同一个协议。

建立一张效果映射：

| 外部效果            | Request/Claim              | Accepted/Completed        | Reconcile           |
| --------------- | -------------------------- | ------------------------- | ------------------- |
| Prompt send     | PromptClaimed/Submitted    | PhysicalAccepted          | PROMPT-011          |
| Worktree create | WorktreeCreateRequested    | WorktreeCreated           | Git probe           |
| Session create  | SessionCreateRequested     | SessionCreated            | Host snapshot       |
| Git publish     | PublishClaimed             | PublishSucceeded          | ref/head/tree probe |
| Blogger request | BloggerRequestMaterialized | BlogEntry/SquashCommitted | ProviderRun receipt |

实施规则：

* request fact 必须在效果前；
* effect identity 必须确定性；
* accepted 必须证明物理完成；
  -结果未知时 reconcile，不盲重试；
  -Blob 先写，fact 后写；
  -重复 accepted 幂等；

  -不得借收敛版再次做 journal clean break。

如果某个效果无法满足 Requested-before-effect：

-不得假装 conformant；
-要么引入预分配 identity；
-要么修正 PERSIST-009 的规范边界，并写清物理限制。
