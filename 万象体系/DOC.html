序言

一万头大象，怎样一起跳舞

写程序这件事，长久以来是一个人的手艺：一个工程师，一台电脑，一条思路，从需求走到代码。后来人工智能来了，我们忽然有了一群不知疲倦的数字程序员。它们读代码、查资料、写功能、补测试、做审查；来自不同厂商，用着不同模型，能力不同，习惯不同，而且还在不断进步。

于是问题发生了变化。

过去的问题是：怎样造出一头更聪明的象？

现在的问题是：如果一百个、一千个、一万个智能体一起工作，会发生什么？

万象术最早把这件事比作"一万头大象跳舞"。大象并不笨，问题在于它又有力、又很重。一头象走错一步，只是一步；一万头象同时行动，如果没有道路、红绿灯、账本和分工，聪明本身反而会放大混乱。

软件工程也是一样。一个智能体犯错，通常只是一次局部失误；一百个智能体同时修改、判断、执行、重试，问题就不再是谁更聪明，而是：谁负责什么，哪些事情可以同时发生，哪些事情必须等待，已经发生的事情怎样成为可以追溯的事实，一项工作能不能跨越某一次模型会话继续向前。

万象术最初的问题：不试图制造一个全知全能的智能体，而是研究不同智能体怎样在同一个工程中各尽其长，又共同成事。

但系统继续往下做以后，我们发现更大的问题并不是"怎样多用人工智能"，而是：

怎样不浪费人工智能。

接下来的三条线——万象术、万象稿、万象器——都是这一个问题的不同深度。它们不增加新的魔法，只是把已经付出的智能、算力与硅片，重新摆到真正产生价值的位置上。

序言

站在用户这一边

模型供应商希望模型更好用、更广泛地被调用，这是自然的。但用户面对的是另一笔账：

为了把一件真实的事情做完，我究竟付出了多少钱、多少时间和多少机器资源？

这两个目标并不完全相同。用户常常在五种毫不知情的地方付钱：

浪费触发场景你在为什么付费
组织方式任务真正困难的部分只有十分之一，整条工作链却都运行在最昂贵的模型上为"整个链条同一个价"付费
失忆昨天已经查明的问题，今天又重新搜索、重新阅读、重新推理为同一份认知劳动付第二遍钱
等待本来可以同时进行的工作被排成长队，先完成的要等最慢的分支为别人的尾巴付费
计算组织推理引擎反复搬运本来能够共享的数据，重新整理同一批底层状态为重复组织同一个世界付费
硬件结构真正需要的是内存带宽，却不得不连同大量闲置的通用算力一起采购为用不满的硅片付费

万象从这一点出发，把问题一路往下追，追成三件事：

万象术 · 减少智能使用中的浪费 万象稿 · 减少推理执行中的浪费 万象器 · 减少硬件供给中的浪费

三件事最后算的是同一本账：

完成一项真实任务的总成本。

这份文档的其余部分，就是沿着这条链，从最上面的智能组织，一路走到最底层的硅片。

万象术 · 智能组织

模型不是岗位，模型是算力

万象术里许多看起来有些反常的设计，并不是为了追求一个复杂的架构，而是因为简单办法已经在真实工程中暴露过问题。

我们逐渐形成的第一个判断是：

模型不是岗位，模型是算力。

一项复杂任务里，有些判断值得使用最强的模型。但文件查找、状态整理、简单比对、辅助记录，并不天然需要同样昂贵的能力。如果所有工作都锁死在一个模型上，相当于把不同难度、不同价值的工作用同一种价格结算。

所以在万象术里，一个参与者"是什么"，由它承担的职责决定；这一刻实际使用哪一个模型，是另一件事。模型可以换，职责不应该跟着漂移。

职责（稳定）

工程师 · 项目负责人 · 运维员 · 记录员

职责定义边界与责任归属，不随时间漂移。一个参与者"是什么"，由它承担什么决定。

模型（可换）

困难判断 → 最强模型
辅助工作 → 更廉价模型

同一职责在不同时刻可以落到不同价格、不同能力的模型上，把昂贵的推理留给真正困难的部分。

这件事最终没有神秘指标，只看一条：

同样质量的任务，能不能花更少的钱做完。

当前系统已经把岗位责任与底层模型选择分开，并允许辅助性工作使用更廉价的模型。这不是性能技巧，而是结算方式的改变：让不同难度的工作，停止用同一种价格结账。

万象术 · 智能组织

真正稀缺的是注意力

我们反复见过一种看似简单、实际非常低效的智能体：它先做规划，然后自己调查，自己写代码，自己运行命令，自己解释结果，最后再自己判断工作已经完成。

问题不只是缺少监督。更直接的问题是，它把完全不同的工作塞进了同一个注意力空间。

工作需要的视角
复杂算法局部专注，长时间盯住一个难点
项目管理盯住全局目标与验收条件
执行命令面对真实机器状态，而不是想象
审查主动寻找作者没有看到的东西
历史整理从外部回看整个过程

同一个模型不断在这些任务之间切换，最终昂贵的上下文里充满了大量与眼前推理无关的信息。所以万象术把这些职责拆开：

工程师

专注理解问题与修改代码。

不负责真实命令执行。

项目负责人

负责分解、委托、验收和推进。

不亲自进入代码细节。

运维员

负责真实机器上的运行、进程和测试结果。

不接受并行改写同一现场。

记录员

承担工作历史整理与认知上下文。

不争夺主任务的决策权。

这些边界已经成为万象术比较稳定的软件工程规则，而不是依赖某一种模型的提示技巧。这里最重要的不是"角色更多了"——恰恰相反。是让每一次昂贵的模型调用承担更窄、更明确的责任。

分工的目的不是组织漂亮，而是减少注意力浪费。

万象术 · 智能组织

工程师可以很多，运维员只有一条主线

有些并发越多越好，有些并发越多，世界越难解释。

十个工程师可以在彼此隔离的工作空间里同时研究十种方案。但如果十个运维智能体同时修改同一个运行环境、安装依赖、启动进程、修补测试现场，很快就没人能回答一个基本问题：

眼前这个结果，到底是谁造成的？

所以万象术允许调查和实现大量展开，却让同一条任务主线上的真实执行保持连续。这样做不是为了追求某种抽象的并发哲学，而是为了用户真正关心的两件事：

  • 出了问题以后，能不能查清楚原因；
  • 已经跑过的验证，能不能知道它验证的是哪一份代码。
物理环境如果失去因果关系，前面花在智能上的所有钱都可能白花。因此，同一条持续工作的主线上，运维执行保持唯一的逻辑连续性；即使底层会话发生变化，也不能凭空变出第二个同时有效的操作员。

这不是在限制智能，而是在保护已经花掉的钱：可追溯性一旦丢失，重跑与排查会把并发省下的时间全部吃回去。

万象术 · 智能组织

主任务不写回忆录，旧钱不花两遍

长任务里有两种浪费，一种在任务内部，一种跨任务。

任务内部：不要把秘书工作买成主力推理

模型本来正在解决一个困难问题，却不断被要求回顾前面做了什么、整理历史、压缩上下文、总结错误。这些工作都必要，但它们不一定应该占用当前解决问题的那次思考。

万象术设置了独立的记录角色：记录员是每个托管工作会话旁边的伴随角色，负责记录工作历史与认知上下文。它解决的不是"让人工智能拥有神奇记忆"，而是一个很普通的工程问题：

支持性工作不要持续打断主线工作。

模型越昂贵，这件事越重要。如果一次高价值推理的大量上下文都被日志、回顾和整理占据，用户实际上是在购买很贵的秘书工作。

跨任务：同一份认知劳动被重复购买

比任务内部的历史整理更贵的，是跨任务失忆。一个模型昨天为了理解某个隐蔽问题，读了十几个文件，排除了几条错误路线，终于找到真正原因；过几天来了相似问题，系统又从头开始。

案例库就是针对这件事设计的。它保存一次工程问题留下的可复用经验，并同时记住这个经验当时依赖了哪些真实文件状态。

因此案例库从一开始就不是"真理库"，而是可以失效、可以更新的经验缓存。这是一种很朴素的记忆，但对用户来说，朴素已经足够：

第二次解决类似问题时，少读多少文件，少走多少老路，少调用多少模型。

至于让系统进一步从历史中自动总结长期制度，目前仍属于值得研究的方向，尚不足以作为万象体系的核心价值主张。万象术今天更可靠的部分，是那些已经明确写入系统的固定软件工程纪律：

职责分离 证据边界 独立复核 真实执行 任务交接 机器门禁
万象术 · 智能组织

并发在现场裂变，结果提前回收

复杂工程有一个很难提前回答的问题：到底需要多少并发？在任务最外层，可能只看到一个普通需求；真正读进代码以后，工程师才发现里面有六个彼此独立的问题，可以立刻同时推进。

如果所有并发都必须由最上层提前规划，就意味着最不了解局部问题的人，反而负责决定最细的并行结构。

所以万象术允许工程师在现场发现问题可以拆开时，直接把自己的工作裂成多条并行路线。这些路线最终仍然属于同一个工程责任，不会因为并行多开了几条执行路径，就凭空多出几个互相推诿的责任主体。

并发结构往往是在真正理解问题以后才显现出来的。最外层负责给方向，最接近问题的人负责发现并行机会。

真正困难的不是分出去，而是收回来

一次分出十个子任务并不难，麻烦的是它们不会同时结束：有的很快完成，有的走得很慢，有的发现此路不通。如果系统一定要等十个全部结束再处理任何结果，那么并行工作到了后半程就会逐渐变成等待。

相关委托规则明确把分派、继续、结果收取和状态查看分开处理。这解决的是一个很朴素的用户问题：

已经完成的工作，为什么要因为另一个无关任务还没结束而继续等？

大规模智能体系统的效率，很大一部分就损失在这种尾部等待里。并行省下的时间，常常又还给了等待。

万象术 · 智能组织

跨会话接力与机器门禁

模型在长期工作中有两个相反的弱点：它可能太早觉得自己已经完成；也可能在同一个问题里待得太久，对自己早先的判断越来越依赖，很难重新审视整件事情。

这两种情况本质上都来自同一个限制：把长期任务的连续性寄托在一次模型会话上。

让任务活得比一次会话更久

万象术因此让项目负责人可以接力。前一任退出以后，新一任看到的是当前工作区、已有结果和仍未完成的事情，而不是被迫继承前任全部私人思考过程。

  • 前任完成的工作不会丢；
  • 前任的路径依赖也不需要全部继承。

这样，一项任务可以持续很久，而具体负责判断的模型可以更新。用户购买的应该是一项任务的持续推进，而不是祈祷某一次会话永远保持清醒。

不要让作者自己给自己发金牌

模型写完代码以后，最容易得到的一种评价，就是它自己认为代码很好。这种评价的问题不在于模型一定会撒谎，而在于作者和审查者共享同一套盲点。

所以万象术把评审从实现里拆出来，并且把"模型认为没有问题"和"机器世界允许合入"继续分开：

前者检查语言与算法、结构、简洁性、测试证据、逻辑边界和完整性；后者检查真正的代码状态、分支变化和合入条件。用户真正需要的并不是更多赞美，而是：

一个错误有没有机会被另一个视角发现。

万象术 · 智能组织

给深度推理一副骨架

还有一类问题，不适合直接交给一个模型自由展开。问题本身可能包含很多假设、证据、相互依赖的调查方向；模型可以写出很长的推理，但长并不等于深。

如果没有结构，模型很容易把"说得更多"误认为"知道得更多"。所以这一类问题的要点，是给深度推理一副骨架：

事实什么已经有证据？哪些结论直接建立在可验证的状态上。
证据什么是真正新增的外部证据，而不只是模型的又一次自述。
假设什么只是一个可能解释；它与事实的差距在哪里。
依赖哪些调查方向相互依赖，哪些可以独立推进。
待解决工作还有哪一个关键问题没有回答；哪个新调查真正可能改变结论；哪些只是把已有观点换一种说法。

关注的并不是某个固定流程，而是把复杂探究分成事实、证据、假设、依赖和待解决工作，让新的推理必须真正增加认识，而不是只增加文字。现有设计也明确区分模型提出的判断与真正新增的外部证据。

计价方式的改变

深度推理不应该按"想了多久"计价，而应该按"新增了多少有用认识"计价。

情形判断
继续调查能够显著改变答案值得继续
再调用一次只会把已有内容重说一遍这是用户不应该支付的成本

这也解释了为什么万象术不把"更长上下文、更长思考"当成默认进步：堆叠字数不等于推进认识，而用户只为后者付费。

万象稿 · 推理执行

数据不动，视角动

万象术把更多智能工作组织起来以后，更底层的浪费会自然暴露：多个推理分支阅读相同背景，不同分支拥有大量共同历史，但因为它们站在不同的逻辑位置，运行时往往需要不断重新组织同一批底层数据。

现有推理系统已经能够很好地共享相同前缀。万象稿继续追问：

如果推理变成不断分叉、重新汇合、不同参与者拥有不同阅读顺序的图，一份物理数据还能不能继续共享？

其中最核心的洞见可以浓缩成一句话：

数据不动，视角动。

一份键值缓存写入以后，不因为另一个推理分支希望以不同的逻辑位置理解它，就把整份数据重新搬一遍。万象稿把物理存储位置、写入时的位置和不同读者眼中的虚拟位置分开，在查询侧补偿位置差异，从而让同一份底层数据服务不同的合法视角。

示意性地看，共享前后的差别在于同一份物理缓存被复制的份数：

$$\text{搬运量}_{\text{重建}}=k\cdot C_{\text{phys}}\qquad\text{搬运量}_{\text{共享}}=C_{\text{phys}}+k\cdot \Delta_{\text{view}}$$

上式为量级示意（$C_{\text{phys}}$ 为一份物理缓存，$k$ 为读者数量，$\Delta_{\text{view}}$ 为查询侧补偿的位置差），不是实测数据。

沿着同一个方向，未经激进优化的初步实现已经表现出明显的局部收益。这批结果现在更重要的意义，不是某一个具体倍数，而是说明：

在多分支推理中，相当一部分成本来自重复组织同一个世界，而不是模型本身必须完成的数学计算。

万象稿 · 推理执行

结构低频，数值高频

沿着"共享"这个方向，另一个问题也变得明显：

如果推理图的结构没有变化，为什么每生成一个新词元，都要重新扫描和整理整个历史？

因此，万象稿正在把低频变化的结构与高频变化的数值拆开：把多个读者共同需要的结构尽量共享，把真正随每一步变化的工作压缩到更小范围。

如果这部分工作可以被拿掉，推理系统就有机会从"不断重建上下文"转向"在稳定共享世界上持续计算"。

值得强调的是，万象稿不是独立于推理引擎之外的调度器。它研究的问题发生在推理执行本身，因此必须进入模型执行、缓存管理、注意力计算和后端调度这些真正决定计算量与数据搬运的位置——这也是它直接基于 llama.cpp 源代码工作的原因。

万象器 · 硬件供给

缺的是带宽，为什么还要为闲置算力付钱

继续往下，软件最终会碰到物理世界。对于小批量的大模型生成，特别是超大规模稀疏模型，很多时候计算单元并不是一直在做乘加运算，而是在等待下一批权重从内存到达。

这意味着，用户买一台推理机器时，真正短缺的资源可能不是理论峰值算力，而是：

  • 内存容量——模型与缓存放不放得下；
  • 有效带宽——纸面数字有多少真的到达计算单元；
  • 送达能力——把数据及时送到计算单元手里的通信组织。

问题随之变得很直接：

如果真正短缺的是带宽，为什么一定要把大量暂时用不满的通用算力一起买回来？

这里真正想验证的是一种硬件经济结构：每颗芯片本身都有独立的内存通道。如果系统能够有效地把这些通道组织起来，那么用户购买的就不再只是一颗更昂贵的大芯片，而可以通过更多成熟芯片获得更大的总内存和总带宽。

这就是万象器的出发点——它不从"我要做一颗 AI 芯片"开始，而从"用户到底在为什么付费"开始。

万象器 · 硬件供给

先用现有芯片，重新算一次硬件的账

万象器目前与黑芝麻智能推进合作。第一步不是重新流片，而是利用现有芯片和高速扩展互联，探索多颗芯片共同承担大模型推理。

第一阶段的目标很明确：以黑芝麻现有芯片组成推理原型，在统一模型和统一运行条件下，对标英伟达 DGX Spark，争取以约二分之一到三分之一的硬件成本达到相近的实际推理性能。

第一阶段真正想带走的，不是这台原型机

纸面到有效到底有多少纸面带宽能够变成有效带宽。
通信拐点芯片增加到什么程度以后，通信开始成为主要成本。
忙闲分布哪些计算单元经常忙，哪些计算单元经常等。
交换条件大模型推理到底愿意拿硅面积换什么。

这些数据会直接决定第二阶段是否值得继续向专用芯片推进。

下一代芯片不应该从一张空白纸开始

如果先决定"我要做一颗人工智能芯片"，再寻找它适合什么工作，很容易重新做出一颗越来越复杂的通用芯片。万象器希望反过来：

  • 先让真实模型跑起来；
  • 先让真实互联暴露瓶颈；
  • 先看真实的软件系统最终把时间花在哪里。

然后再决定：片上高速缓存应该多大；需要多少内存控制器；低精度计算应该占多少面积；稀疏专家怎样路由；芯片之间怎样交换数据；哪些通用功能对目标负载价值很低，可以让位给真正稀缺的资源。

第二阶段计划围绕这种真实工作负载，与产业伙伴探索专用推理芯片和机柜级系统，目标指向 Kimi K3 等超大参数模型的商用推理。

万象 · 三层一本账

为什么三件事会走到一起

万象术、万象稿、万象器并不是因为名字相近才放在一起。它们是同一个问题向下追了三层。

层发现的浪费对应的线回答的问题
最上层昂贵的模型被大量用在不值得它做的事情上万象术什么智能工作值得发生
中间层推理运行时在重复整理和搬运本来可以共享的数据万象稿这些推理怎样更少重复
最底层为获得真正稀缺的内存资源，不得不购买大量未被充分利用的通用计算能力万象器剩下不可避免的计算怎样更便宜地落到硬件上

它们共同形成的是一条用户侧的成本链：任务 → 模型调用 → 推理执行 → 数据搬运 → 硬件。只要其中一层存在大量不必要的重复支付，就值得继续优化。

这也是万象真正希望积累的能力：

不是在某一层把一个指标做到极端，而是理解一项真实任务的成本怎样一层一层产生。

三层之间不是并列的产品线

万象术让任务用更少的昂贵模型完成；完成任务的推理分支越多，万象稿要处理的共享问题就越尖锐；而万象稿压缩掉的重复搬运，又直接影响万象器该为什么付费——是算力，还是带宽。

一条线索贯穿：哪一层出现了重复支付，就继续往下追。

万象 · 三层一本账

多、快、好、省

"多、快、好、省"不是宣传语，而是四种不同的浪费。

多 · 规模协调成本

解决的是规模扩大以后协调成本迅速上升的问题。更多智能体、更多推理分支、更多芯片加入以后，系统仍然要能继续工作。

快 · 无意义等待

已经完成的结果不等最慢分支，可以并行的工作不排成长队，没有变化的结构不反复重建。

好 · 自我证明

作者不能因为自己认为完成就自动通过；旧经验不能因为曾经正确就自动成为今天的事实。

省 · 用户账本

把前面所有问题重新放回用户账本：昂贵模型有没有用在刀刃上，旧认识有没有重复购买，推理数据有没有重复搬运，硬件支出有没有真正转化成有效吞吐。

所谓"省"，不是最后再做一次成本优化。它应该从第一行架构开始——这也是为什么三条线从第一天起就长在同一个账本上。

万象由清华大学交叉信息研究院计算机科学实验班校友张昆玮、戴元熙担纲创业。

学校背景能够说明过去，不能证明未来。这家公司真正希望证明的是另一种能力：

看到一个系统问题以后，能不能不断向下追问，直到找到浪费真正发生的位置。

观察到的浪费对应的追问
模型太贵研究怎样组合模型，把昂贵推理留给困难判断
模型注意力被琐事占满拆职责，让每次昂贵调用承担更窄的责任
经验反复丢失让旧认识能够复用，并且随代码变化重新维护
并发一开始无法判断让执行者在现场展开并行，而不是由最外层提前规划

推理运行时反复整理同一份数据重新组织数据：数据不动，视角动
硬件真正缺的是带宽重新计算算力和带宽之间的采购关系

这样一路从智能体，追到推理引擎，再追到芯片。

团队与附录

结语

人工智能过去几年的进步，很大程度上来自"更多"：更大的模型，更多的算力，更长的上下文，更长的思考，更高的并发。下一阶段还会继续需要"更多"。

但当人工智能开始大规模进入真实生产，另一个问题会越来越重要：

已经拥有的智能，究竟有没有被有效使用。

用户不会因为系统调用了更昂贵的模型而获得价值，不会因为生成了更多词元而获得价值，不会因为机器拥有更高的理论峰值而获得价值。用户只在事情真正被做完的时候获得价值。

所以万象最终想优化的不是模型调用次数，也不是单颗芯片的峰值，而是：

每完成一项真实任务，需要付出多少资源。

知道什么时候值得使用最强模型。知道什么时候旧经验已经足够。
知道什么时候应该并行。知道什么时候不应该再继续调查。
知道什么时候应该共享，而不是复制。知道用户真正购买的是计算，还是带宽。

这是我们理解的下一代机器智能基础设施。

智能最终必须懂经济学。

万象皆可用，众智自成事。

团队与附录

附录：技术实现概况

万象体系目前的三个方向分别建立在不同的工程载体上。

万象术 · F# / OpenCode 插件

选择 F#，主要是因为万象术内部存在大量关于身份、权限、任务状态、事件、委托关系与失败处理的复杂语义。相比把这些约束散落在大量条件判断中，强类型和代数数据类型更适合把"什么状态合法、什么状态不应该出现"直接表达在程序结构里。

// 示意：把合法状态写进类型，而不是写进一大堆 if
type Role =
    | Engineer          // 理解问题、修改代码
    | Lead              // 分解、委托、验收、推进
    | Operator          // 真实机器上的运行与进程
    | Recorder          // 工作历史与认知上下文

type TaskState =
    | Dispatched        // 已分派，独立推进
    | Running           // 进行中
    | Collected         // 结果已被取回
    | Verified          // 通过机器门禁
    | Failed of string  // 失败必须带原因

万象术并不是简单包装模型接口。它真正实现的是模型之上的任务组织层：把不同模型组织成承担不同职责、可以长期协作的工作系统。

万象稿 · llama.cpp 源代码

选择从成熟推理引擎内部开始，而不是在外围再包一层服务，是因为万象稿研究的问题发生在推理执行本身：上下文怎样组织，多条推理分支怎样共享已有计算，同一份底层数据怎样服务不同的逻辑视角，以及计算图发生变化时哪些工作实际上不需要重新做。

因此，万象稿需要进入模型执行、缓存管理、注意力计算和后端调度这些真正决定计算量与数据搬运的位置。它不是在研究"当推理本身从一条线变成一张图以后，推理引擎应该怎样变化"之外的任何东西。

万象器 · x64 主机 + 5 × RX 6800（TP5）

当前实验平台以 Vulkan 为主要计算与设备控制基础，重点研究多张独立显卡之间的直接数据交换、集合通信、任务切分，以及通信延迟对逐词元推理的影响。现有工程已经覆盖五张 RX 6800 的真实多卡运行和点对点通信实验。

方向工程载体从这里开始的原因
万象术F# · OpenCode 插件复杂语义直接用类型表达
万象稿llama.cpp 源码问题发生在推理执行本身
万象器TP5 · RX 6800 · Vulkan可反复修改的真实物理实验场

这套平台的意义不在于把 RX 6800 本身做成最终产品，而在于提供一个可以反复修改软件栈、通信方式和计算组织的真实物理实验场。在这里，很多在纸面上容易被忽略的问题会直接暴露出来：通信究竟发生了多少次；一次很小的数据交换为什么可能比计算本身更昂贵。
