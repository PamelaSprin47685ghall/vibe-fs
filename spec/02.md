# spec/02 — 智能体系统与能力

条款 ID 前缀：`AGENT-`

## AGENT-001：Canonical Role 与 Agent Tier

Canonical Role（不变角色）决定工具权限与 system prompt。

Canonical Role 不决定 Companion 资格。 每个 managed work session 都有一个叶子 Companion，与角色无关（COMPANION-001、COMPANION-002）。

```fsharp
type Role =
    | Orchestrator | Manager | Coder | Inspector | DevOps
    | Browser | Meditator | Reviewer | Blogger | Executor
```

Agent Tier 只改变模型绑定：

```fsharp
type AgentTier = Fast | Deep
```

fast-ROLE 与 deep-ROLE 使用完全相同的 system prompt、工具权限和能力矩阵。

## AGENT-002：0.5.0 必须存在的 20 个 Agent

```text
fast-orchestrator     deep-orchestrator
fast-manager          deep-manager
fast-coder            deep-coder
fast-inspector        deep-inspector
fast-devops           deep-devops
fast-browser          deep-browser
fast-meditator        deep-meditator
fast-reviewer         deep-reviewer
fast-blogger          deep-blogger
fast-executor         deep-executor
```

缺少任意一个 → 万象术启动失败。每个 Agent 必须拥有非空且 pair 内互异的 model 字符串。

## AGENT-003：Peer 计算

```fsharp
peer(fast-coder) = deep-coder
peer(deep-coder) = fast-coder
```

Peer 名称必须在启动配置验证阶段证明存在。

## AGENT-004：不再支持的旧名称

以下全部非法：`orchestrator`, `manager`, `build`, `plan`, `coder`, `inspector`, `devops`, `browser`, `meditator`, `reviewer`, `blogger`, `executor`, `fast`, `deep`, `reviewer-fast`, `fast_reviewer`。

不提供 alias、不自动补全。

## AGENT-005：用户必须显式选择

每个新的公开 Authority Root 必须携带准确 Agent（`fast-coder`、`deep-reviewer`）。省略 agent、使用旧名称或 build/plan → `HostContractUnsupported`。

## AGENT-006：能力矩阵

| 角色 | 工具 |
|------|------|
| Orchestrator | `fork-manager`, `join` |
| Manager | `fork-agent`, `join`, `list` |
| Coder | `read`, `write`, `edit`, `glob`, `grep`, `inspector` |
| Inspector | `read`, `glob`, `grep`, `executor` |
| DevOps | `fork-pty`, `executor`, `read`, `glob`, `grep`, `inspector`, `coder`, `join`, `list` |
| Browser | `read`, `glob`, `grep`, network tools |
| Meditator | `read`, `glob`, `grep`, `inspector` |
| Reviewer | `read`, `glob`, `grep`, `inspector`, `verdict` |
| Blogger | `blog` |
| Executor | 无工具 |

## AGENT-007：工具权限双层 fail-closed

第一层：Host-final Agent permission。无权工具不进入 provider-visible schema。
第二层：ToolRegistry execution gate。即使 Host 配置异常，也拒绝越权执行。

两层都读取同一个 `AttemptExecutionProfile.CanonicalRole`。Role 无法确定时模型可见插件工具集为空。删除任何类似"role unresolved 时暂时允许 inspector"的特殊放行。

本条只约束角色工具集合。Host 元权限（例如 `external_directory`、`doom_loop`、`question`）不进入 `ToolPermission` / AGENT-006 矩阵；其覆盖规则见 AGENT-016。

## AGENT-008：内部 Agent 不可见

Blogger、Executor 永远不能出现在任何模型可见的 enum、schema 或工具参数提示中。

## AGENT-009：示踪 Agent 描述

| 暴露面 | 可见 Agent |
|--------|-----------|
| Manager fork-agent schema | fast/deep coder, inspector, devops, browser, meditator, reviewer |
| Orchestrator fork-manager schema | fast-manager, deep-manager |
| Inspector tool | fast-inspector, deep-inspector |
| Coder tool | fast-coder, deep-coder |
| list() | 当前运行中的 handle（不是列举可创建 Agent） |

## AGENT-010：fast/deep 权限完全一致

```text
permissions(fast-coder) = permissions(deep-coder)
permissions(fast-reviewer) = permissions(deep-reviewer)
```

fast/deep 只改变 model 绑定。不得出现 fast 只能读、deep 才能写的情况。

## AGENT-011：Manager 无普通工具

Manager 只有 `fork-agent/join/list`。不能直接读文件、运行终端或操作仓库。这是架构故意约束——Manager 的职责是协调，不是亲自执行。

## AGENT-012：Coder 的 Inspector 是不透明的

Coder 可以看到 `inspector` 工具，但其 prompt 只将 Inspector 描述为不透明的只读调查服务。Coder prompt 不得泄露 Inspector 的 Executor 权限。Coder 不得把 Inspector 当作常规验证代理（编译、测试等）。

## AGENT-013：DevOps 独占 PTY

只有 DevOps 可以创建和操作 PTY 会话。Manager 通过 `fork-agent("fast-devops", prompt)` 委派终端操作。DevOps 的文件修改只能通过同步 `coder` 工具委派，不能直接 `write/edit`。

## AGENT-014：Reviewer 是只读的

Reviewer 只有只读工具 + `verdict`。不能写文件、不能运行命令。

## AGENT-015：Orchestrator 只 fork Manager

Orchestrator 的 `fork-manager` 只接受 `fast-manager` 和 `deep-manager`。不能创建普通子 Agent。

## AGENT-016：Host 元权限 `external_directory` 固定 allow

`external_directory` 是 OpenCode Host 的路径边界元权限，不是角色工具，也不属于 AGENT-006 能力矩阵。

### Host 默认与合并语义

Host `Agent.state` 默认 ruleset 含：

```text
external_directory: { "*": "ask", <白名单目录>: "allow" }
```

Agent 级 permission 与默认 ruleset 的合并方式是 flat concat；运行时 `Permission.evaluate` 取 `findLast` 命中规则。因此：仅写角色工具的 allow/deny 不会取消 Host 的 `external_directory:* = ask`。

### 强制覆盖

每一个 managed agent（AGENT-002 的 20 个名字）的 Host-final permission 对象必须显式包含：

```text
external_directory = "allow"
```

该规则必须排在 Host 默认 `external_directory` 规则之后，使任意外部 path pattern 的求值结果为 `allow`，从而：

1. 访问项目目录外路径时不弹出 `permission.asked` / 用户确认。
2. 不把 `external_directory` 解释为角色能力，不新增 `ToolPermission` case。
3. 不扩大 AGENT-006 工具矩阵，不放行 bash 或其它角色未授权工具。

### 唯一写入点

唯一生产写入点是 `StaticTools.permissionObj`（经 `ManagedAgentConfig.applyOwnedFields` 落到每个 managed agent）。禁止第二处散落覆盖。

### 禁止项

1. 不得省略 `external_directory` 覆盖并依赖用户全局 config 或交互式 always-allow。
2. 不得把 `external_directory` 编入 `Roles.permissions` / `ToolPermission` / AGENT-006 矩阵。
3. 不得用全局 `permission: { external_directory: "allow" }` 顶替 agent 级写入：managed agent 的 Host-final 字段是 AGENT-002 清单上的每个名字。
4. AGENT-007 的 `"*": "deny"` 与角色工具白名单保持不变；本条不放宽 bash、write、edit 等任何角色工具。

### 验证

第 1–2 层测试必须用 Host 的 ruleset 语义（flat merge + `findLast`）证明：在 Host 默认 `external_directory:* = ask` 之后，每个 managed agent 对任意外部 path pattern 求值结果为 `allow`。
