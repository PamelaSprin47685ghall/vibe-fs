# spec/07 — Host 集成合同

条款 ID 前缀：`HOST-`

## HOST-001：事件分层

```text
碎片事件（message.updated / part.delta / session.updated）
    ↓ 最早边界丢弃
粗粒度信号（session.status idle/retry, session.deleted）
    ↓ single-flight
Reconciler 从 SDK 读取完整消息
    ↓
纯策略（completion / ReviewGuard / continuation / abort）
```

## HOST-002：唯一允许进入业务层的信号

只有 `session.status=idle`、`session.status=retry`、`session.deleted` 可以进入 Session 生命周期与 Reconciler 信号通道。

`chat.message` 仅进入 Prompt acknowledgement 通道，不能用于拼装 terminal turn 或驱动普通业务流程。

## HOST-003：Transport 与 Domain Contract 分离

Transport 可以是 plugin event 或 global SSE。Domain contract 永远是 typed HostSignal。业务层不得观察原始 payload。

```fsharp
type HostSignal =
    | SessionIdle of sessionId: SessionId
    | ProviderRetry of {| SessionId; Attempt; UserMessageId: MessageId option |}
    | SessionDeleted of sessionId: SessionId
```

## HOST-004：Reconciler

Single-flight：同一 session 同时最多一次 reconcile 请求。Dirty 标记：idle 信号到达时设 dirty=true。

Unknown 等待协议：一次 idle 建立 Dirty latch。最多 3 次因果重读，仍 Unknown 则保持 Dirty 等下一信号。

```fsharp
type ReconciledTurn =
    { SessionId; UserMessageId; AssistantMessageId
      AgentRole: AgentRole option; Directory: string
      Parts: ProviderVisiblePart array
      Outcome: TurnOutcome }  // Completed / Failed / Aborted
```

## HOST-005：XTrace 分段与 durable cursor

```fsharp
type XTracePart =
    | PromptText of role: SemanticRole * text: string
    | AssistantText of text: string
    | Reasoning of text: string          // 仅 host-visible；hidden reasoning 不抓取、不推断、不伪造
    | ToolCall of name: string * arguments: string
    | ToolResult of text: string
    | MediaOmitted of mediaType: string option

type XTraceItem =
    { Cursor: XTraceCursor          // 生命周期内严格单调，独立于 Host transcript 数组下标
      Provenance: InternalProvenance  // session/run/message/part 归属；renderer 永不输出
      Part: XTracePart }
```

XTrace 是 X 整个生命周期的唯一原始语义轨迹（COMPANION-003）：Host 可见的 prompt、正式正文、reasoning/thinking、tool call/result 与 omission marker，best-effort 累积但不声称包含未暴露的内部思维。不包含 UI delta、usage、cost、timestamp、directory、finish reason、runtime ID。tool call/result 留在 XTrace 供 Y 压缩；LWR 投影禁止输出 raw tool call/result。

Session 可能经历多个 Agent/Fallback 切换，因此 provenance 按 provider run 分段保存，不使用单值 Model。

Host compaction 不删除 XTrace：否则「Y 落后时由 X 补缺口」与「LWR 自包含」在 compaction 后无法同时成立。compaction 只重锚 provider-prefix proof（PrefixCoverage，HOST-006）。

`join().workRecord` = 最终 LWR（COMPANION-003），经 LWR 投影后不含 raw tool。`join().formalRecord` 已废止，不存在。

`TerminalSessionA`、`ARecord`、session-wide A 术语废止（迁移注记：原「A 版」语义由 XTrace + OpeningPromptRaw + TerminalOutputRaw 取代）。

## HOST-006：官方 Compaction 的预防与收容

上下文恢复的唯一合法机制是 spec/12 的失败驱动协议。Host compaction 的结果不得参与产品语义。

该目标分两层实现。 第一层把能关的关掉，第二层收容任何仍然出现的 compaction。两层都必须存在：第一层依赖 Host 的配置键与 Hook 名，会随上游版本漂移；第二层只依赖 transcript 里可识别的事实，是主要防线。

### 预防层：必须关闭，无法证明则启动失败

四种行为必须关闭：

```text
automatic compaction        阈值触发
overflow compaction         溢出触发（预测式与 provider 报错后）
compaction autocontinue     压缩后自动续发
compaction prune            物理删除持久消息行
```

对应三个配置键。 `automatic` 与 `overflow` 共用一个开关：阈值路径与 provider 报错路径都在同一处短路，因此 overflow 没有独立的键。列出第四个无键条目会产生一个探测永远无法验证的设置。

前三种行为由 Host 的自主判断触发，插件对时机无任何控制。`prune` 绕过投影边界直接删消息行，与 COMPANION-009 的「原始 Host transcript 永远不物理删除」直接冲突。

启动时必须证明这些键确已关闭。静态读取配置不足以证明：必须包含一次运行时探测——首个 managed session 完成第一轮请求后，该 session 的 compaction pseudo-run 数量必须为零。第一轮必然远低于任何阈值，此时出现 pseudo-run 只能说明存在不受该配置控制的第二实现。

设置不可用与首轮出现 pseudo-run 同时成立时，报设置不可用：那是根因，pseudo-run 是它的后果。

不满足则 `HostContractUnsupported`，启动失败，不降级运行。理由不是「一次 compaction 会破坏正确性」——收容层保证它不会——而是无法预防的自动 compaction 会让机制空转：每隔几轮就重锚一次，probe 永远攒不够 coverage，而从外部看一切正常。

### 收容层：任何出现的 compaction 一律重锚

manual compaction（用户 `/compact`）在 Host 侧没有配置开关也没有可否决的 Hook，因此无法预防。它是官方支持的用法：用户的显式意图与本方案缩短上下文的目标一致。

收容层同时覆盖第二种情况——预防层被绕过时 Host 自行触发的 compaction。两者不作区分：观察面相同（transcript 里只有一条 pseudo-run，没有「谁触发的」字段），正确处置相同，分类只会长出永不执行的分支。这与 CTX-005 同构。

识别判据是折叠后的单一谓词：`agent = "compaction"`、`mode = "compaction"`、`summary = true` 任一为真。

处置是一次重锚，不是无动作，也不是崩溃：

```text
观察到 compaction pseudo-run
→ 退役 ActivePrefixEpoch（Snapshot → None，EpochId += 1）
→ PrefixCoverage 归零（CoverableTurnCutoff、CoveredPrefixDigest、CoverableFrameCount）
→ RecordCoverage.IngestedThrough 保留（XTrace 坐标，与 Host 编号无关）
→ BlogFrame 全部保留
→ 后续正常轮次在新 Host 编号下重新累积 PrefixCoverage，probe 能力自然恢复
```

Epoch 退役是因为 `CutoffExclusive` 是旧编号下的索引，compaction 后不再指向任何真实前缀。PrefixCoverage 归零而非重新指向摘要之后，是因为 Companion 可能因 busy skip 落后于 Host，声称覆盖会用更窄的 Y 替换更宽的摘要。`RecordCoverage` 不得归零：它是 durable XTrace cursor，清零会让旧 Y frames 与重新读取的 X 内容重复（COMPANION-008）。Frames 保留是因为那些工作确实发生过。Epoch 递增而非原地清空，是因为这是一次真实的冷边界，COMPANION-009 的逐字节稳定以 epoch 为界。

重锚是持久事实 `ContextReanchored`（PERSIST-010），因为它原子地改变两处投影。

重锚不违反 CTX-001、CTX-002：触发它的是已经发生的外部物理事件，不是插件对容量的测量或预测。

### 效果只做 best effort 保证

明确不保证：B 覆盖了 Host 丢弃的内容（busy skip 期间未消化的 turn 真实丢失）；前缀缓存连续（epoch 切换是一次冷边界）；Host 摘要的质量（摘要文本永远不作为 B 读取，不进入 FrozenRecordPrefix）；重锚后立即可 probe（第一个恢复槽可能找不到新 coverage，按 CTX-011 走正常主请求）。

### 不变的部分

Host compaction 结果不得成为 `PrefixEpoch`、`BlogFrame`、`FrozenRecordPrefix`、Authority Root 或 Continuation，不得推进 Fallback cursor。`ContextReanchored` 记录的是插件自己的退役动作，不是把摘要当作事实。

## HOST-007：日志规范

日志只记录诊断：session_id、role、handle_id、operation（fork-agent/join/nudge/project/blog/process/review/publish）、result、error、bytes/duration/tree hash。不写 stage、phase、owner、lease、generation、next_action。日志不是恢复协议。

## HOST-008：Session 关联

```fsharp
type ManagedSessionKind =
    | WorkSession
    | CompanionSession of mainSessionId: SessionId

type SessionAssociation =
    { SessionId: SessionId
      Kind: ManagedSessionKind
      BloggerSessionId: SessionId option
      ParentSessionId: SessionId option
      Role: AgentRole }
```

不变量：

```text
每个 WorkSession 恰好一个 CompanionSession
每个 CompanionSession 恰好属于一个 WorkSession
CompanionSession.BloggerSessionId = None（Y 不递归）
SessionId ≠ BloggerSessionId
```

关联由 Session 种类决定，不由 CanonicalRole、AgentTier、工具权限、当前 Logical Run、Authority Root 或 Fallback Agent 决定（COMPANION-001、COMPANION-002）。

优先存宿主 metadata。重启时复用同一 Blogger（不发 delta 给空白 Y）。

## HOST-010：Transform → ProviderRunIdentity 绑定

`experimental.chat.messages.transform` 的 input 是空对象，不携带任何身份。但 Host 在触发该 Hook 之前已经创建并持久化了本次 provider run 的 assistant message。因此绑定由一次因果读取建立，不由猜测建立。

### 绑定判据

transform 执行期间，从 SDK 读取该 Session 的消息，目标 `ProviderRunIdentity` 是唯一满足全部条件的 assistant message：

```text
role = "assistant"
time.completed 未设置
parentID = transform 输出中最后一条 user message 的 id
id 为该 Session assistant message 中最大者
```

Host 保证：`Plugin.trigger` 对每个 hook `await`，因此 transform 内的异步 SDK 读取合法且 Host 会等待。

### 必须 fail closed 的情形

```text
命中 0 条    → 不写 seal
命中 ≥2 条   → 不写 seal
agent = "compaction" 或 summary = true → 不写 seal（compaction 路径顺序相反）
```

`ProviderInputSeal`（REVIEW-010）不存在时，第二次 PERFECT 只能返回 `PendingIdentity` 或 `Rejected`，绝不 `Confirmed`。不得退回 same-root 或 physical-message 猜测。

### 脆弱性与门禁

本绑定依赖 Host 内部执行顺序，而非公开类型合同。绑定语义不变：seal-bind、唯一未完成 assistant、同一 run。

Host 版本升级门禁 canary 必须以 journal 侧可观测代理断言该顺序，不得要求直接观测 transform 内存读数与 `ToolContext.messageID` 的共时等式。原因（Host 能力限制，ARCH-003；非实现困难）：

```text
transform 侧读取的唯一未完成 assistant id  → 只用于运行期 plan/seal，不落盘
ToolContext.messageID                     → 仅工具 execute 的 ctx 字段，不在 provider wire
两侧同一 run 内                            → 不共存于 journal
```

Host 源码锚点：`prompt.ts` 在 transform 前已创建并持久化 assistant（绑定判据成立），但该 id 不作为独立事实行写入插件 journal；`ToolContext.messageID` 见 plugin `tool.ts`，只在 execute 路径注入。

可观测代理等式（层 4 canary 必须直接断言）：

```text
Reviewer 链：ReviewVerdictRecorded.ProviderRun == ProviderInputSealed.ProviderRun
  （前者 = VerdictTool 的 ToolContext.messageID；后者 = ReviewSeal.bindToRun 绑定的同一 messageID）
X 链：PrefixRebaseCommitted.SolvingProviderRun 唯一非空
  （= 该 run 的 bindableRun / messageID）
```

代理等式失配或为空时 must fail。顺序或身份通路改变时 canary 必须先红。

（rev.2，supersedes rev.1：rev.1 要求 canary 直接断言「transform 时唯一未完成 assistant id ≡ 同 run `ToolContext.messageID`」。该直接等式在 testkit 架构下物理不可观测，见 `STATUS/blockers/README.md` HOST-010 条目。）

## HOST-011：Tool 执行身份的两个半边

Host 在两个不同边界暴露互补的身份，插件必须知道各自缺什么。

| 边界 | assistant message id | tool call id |
|------|---------------------|--------------|
| `ToolContext`（工具 execute 参数） | `messageID` ✅ | `callID` ✅（Host 侧 `Tool.Context` 声明为 `callID?`，经 registry 透传，SDK 发布类型未声明） |
| `tool.execute.before` / `after` | ❌ 不存在 | `callID` ✅ |

因此 `ReviewAttemptIdentity`（REVIEW-004）所需的 `ProviderRunIdentity` + `ToolCallId` 只能同时从 `ToolContext` 取得。

规则：

```text
ProviderRunIdentity := ToolContext.messageID     缺失 → fail closed
ToolCallId          := ToolContext.callID        缺失 → fail closed
```

禁止：用 `tool.execute.after` 的 `callID` 补齐 `ToolContext` 缺失的身份（两者不在同一调用上下文，无法可靠配对）。使用 SDK 未声明且 Host 源码中也不存在的字段（例如 `userMessageID`）——物理用户消息身份只能来自插件自己维护的 `chat.message` 绑定表。

## HOST-012：多实例共享边界

Host 的 `InstanceStore` 按 directory 缓存实例（`../opencode/packages/opencode/src/project/instance-store.ts`
的 `load`：`cache.get(directory)`），每个 project 各实例化一次插件。git worktree（orchestrator
的 manager worktree 是独立 project）因此触发第二个插件实例——实测（Host 1.18.10）同一
插件模块 `server(input)` 调用两次，`input.directory` 分别为主 workspace 与 worktree 路径，
每次调用产生独立的 `PluginRuntimeScope` 与 `ToolRuntimeScope`。

fork→verdict 因果链跨越实例边界：orchestrator（主实例）的 reverify fork 出的 worktree
子会话，其后续请求由 worktree 实例的 transform 与工具处理。任何 per-instance 状态若被这条
链的两端读取，必然不一致——实测 deep-reviewer 的 `VerdictTool` 读不到主实例注册的
`SessionParents`，REVIEW-008 fail closed 拒绝 verdict。

规则：

```text
跨实例共享（模块级单例，所有插件实例同一引用）：
    SessionParents        fork 注册与 VerdictTool/ForkTool 读取
    VerdictSessions       verdict 提交标记与 guard 去重
    SessionDirectories    子会话目录注册与 TreePortFor

每实例独有（物理资源与绑定，不得跨实例借用）：
    AgentJournal          独立 runtimeId 文件（PERSIST-002 writer 锁）
    Companions / Blogger  按会话键的运行时缓存
    OwnedSessions / UserMessageBindings / hook 订阅
```

新增跨实例状态必须同时登记到共享清单与 `PluginRuntimeScope` 的初始化，否则该字段的写入
与读取在第二个实例上静默失配（本条款的设立即来自一次这样的实测失败）。
