# spec/06 — Orchestrator 与恢复

条款 ID 前缀：`ORCH-`

## ORCH-001：工具

Orchestrator 只有 `fork-manager` 和 `join`。不能读写仓库、解决冲突、操作 Git、调普通子角色。

`fork-manager` 只接受 `fast-manager` 和 `deep-manager`。

## ORCH-002：Clean Gate

每次用户消息送入 Orchestrator 前工作区必须 clean。dirty 判定包括：staged change、tracked unstaged change、untracked file、submodule dirty。ignored file 默认不计入。

禁止：自动 stash、自动 commit、猜用户意图。

插件 runtime、spool、lock、worktree 必须放在目标工作树之外。

## ORCH-003：一个 Job 一个 worktree 一个 Manager

一个 ManagerJob 生命周期中：不重新创建 worktree、不更换 Manager、冲突返回同一个 Manager。Manager Agent 必须持久化（`fast-manager` 或 `deep-manager`，不降级为 `Role.Manager`）。

## ORCH-004：主程序

```fsharp
let runManagerJob job =
    // 1. use worktree
    // 2. create Manager
    // 3. run guarded Manager → candidate
    // 4. rebaseReviewPublishLoop(job, candidate)

let rec rebaseReviewPublishLoop job candidate =
    // 1. read current target head T
    // 2. rebase candidate to T
    // 3. post-rebase dual PERFECT on same worktree/Manager
    // 4. acquire short integration gate
    // 5. re-read target head
    //    - still T: ff-only + write Published
    //    - changed: release lock, rebaseReviewPublishLoop again
```

禁止：递归回到创建整个 Job 的入口。冲突递归只能发生在 `rebaseReviewPublishLoop` 内。

注：Integration Gate 只能在发布 CAS 窗口获取（第 4 步），不在 `runManagerJob` 入口提前获取。

## ORCH-005：短 CAS Integration Gate

Integration Gate 只保护 ref mutation，不在 LLM Review 或冲突修复期间持有。

```text
读取目标 head T
→ 在 job worktree rebase 到 T
→ post-rebase 双 PERFECT
→ 获取短 Integration Gate
→ 再读目标 head
    ├─ 仍为 T：ff-only + 写 Published
    └─ 已变化：释放锁，重新 rebase + 重新 review
```

多个 Job 可以并行 rebase 和 review。lock 只保护 ref mutation。target 变化时绝不复用旧 post-rebase witness。

## ORCH-006：持久事实（业务屏障）

```fsharp
ManagerJobCreated =
    { ManagerJobId; ManagerSessionId
      ManagerAgent              // "fast-manager" 或 "deep-manager"
      WorktreeIdentity          // 稳定身份，不是可变路径
      WorktreePath              // 诊断用；恢复必须按 WorktreeIdentity 定位
      TargetRef
      TargetBranchFrozen }      // git symbolic-ref 冻结结果（ORCH-008）

CandidateReady =
    { ManagerJobId; CandidateCommit
      PreRebaseReviewWitnessId }

RebasedCandidateReady =
    { ManagerJobId; RebasedCommit
      TargetHeadSnapshot
      PostRebaseReviewWitnessId }

ConflictDetected =
    { ManagerJobId
      CandidateCommit
      TargetHeadSnapshot
      ConflictFiles
      DiagnosticsDigest }

PublishClaimed = { ManagerJobId; TargetRef; ExpectedHead }
Published = { ManagerJobId; CandidateCommit; ResultingTargetHead }
JobFailed = { ManagerJobId; Reason }
JobAbandoned = { ManagerJobId }
```

Witness ID 引用规则：`PreRebaseReviewWitnessId` 和 `PostRebaseReviewWitnessId` 必须指向已持久化的 `ConfirmedReviewWitness`（REVIEW-006）。事实中只存 ID，但 witness 本身自包含——Fold 不需要外围 Map 补齐身份。

`ConflictDetected` 是恢复必需的事实：没有它，崩溃后无法区分"Manager 正在解决冲突"与"Manager 尚未产出 candidate"，会导致重复 rebase 或丢失冲突上下文。

禁止：`CandidateCreated → 等待 review 或走 publish` 这种无法确定恢复动作的分支。事实中省略 `ManagerAgent`（会导致恢复时降级为 `Role.Manager`，违反 ORCH-003）。Barrier 事实省略 witness ID（会导致 Guard 依赖外围状态，违反 REVIEW-006）。

## ORCH-007：恢复逻辑

启动时 Fold NDJSON 获取每个活跃 ManagerJob 的最后事实，按事实决定唯一恢复动作。

```text
Published    → 清理 worktree，从活跃 Map 删除
JobAbandoned → 清理 worktree，从活跃 Map 删除
JobFailed    → 清理 worktree，明确失败
无事实       → Job 不存在
```

### PublishClaimed 恢复（唯一需要 CAS 判断的分支）

`PublishClaimed { ManagerJobId; TargetRef; ExpectedHead }` 意味着崩溃发生在 CAS 窗口内：ref mutation 可能已发生，也可能没有。

必须按固定顺序求值，第一个匹配的分支生效：

```text
读取 currentHead = GetTargetHead(TargetRef)     // 失败 → fail closed（ORCH-008）
读取 rebasedCommit = 该 Job 最后的 RebasedCandidateReady.RebasedCommit

1. currentHead = rebasedCommit
       → ff 已经完成，只是没写事实
       → 补写 Published { ResultingTargetHead = currentHead }（幂等）

2. currentHead = ExpectedHead
       → ff 从未发生，target 未被他人推进
       → 获取 short Integration Gate，重新读 head 确认仍为 ExpectedHead，ff-only，写 Published

3. 其他（currentHead 既非 rebasedCommit 也非 ExpectedHead）
       → PublishClaim 过期，target 已被他人推进
       → 丢弃 claim 与旧 post-rebase witness
       → 回到 rebaseReviewPublishLoop：重新 rebase 到新 head + 重新双 PERFECT
```

分支 1 必须先于分支 2 求值。若 `ExpectedHead` 恰好等于 `rebasedCommit`（不可能，因为 ff 前 head 必然是 rebase 的 base），顺序仍然安全。

分支 3 绝不复用旧 witness（REVIEW-008：tree/barrier 变化使 witness 失效）。

### 其他事实的恢复

```text
RebasedCandidateReady → 该 Job 已有 post-rebase witness
                        → 直接进入 CAS 窗口：short gate + 读 head
                          ├─ head = TargetHeadSnapshot → ff + Published
                          └─ head 已变 → 重新 rebase + 重新 review

ConflictDetected      → 同一 worktree、同一 Manager 恢复冲突解决（ORCH-003）
                        → 不新建 worktree、不换 Manager

CandidateReady        → 有 pre-rebase witness，未 rebase
                        → 进入 rebaseReviewPublishLoop

ManagerJobCreated     → worktree 存在，Manager 尚未产出 candidate
                        → 从 worktree 恢复同一 Manager 继续工作
```

禁止：恢复时新建 worktree 或更换 Manager。恢复时跳过 post-rebase review。用 worktree 文件系统状态代替事实判断恢复动作。

## ORCH-008：target ref 安全

目标 branch 由 `git symbolic-ref` 在 fork 时冻结。`GetTargetHead` 失败 → fail closed，不得 fallback 到 HEAD。`git merge --ff-only` 检查当前 branch == frozen target branch、当前 target head == expected head。
