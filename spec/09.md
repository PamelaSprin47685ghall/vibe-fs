# spec/09 — 执行模型

条款 ID 前缀：`EXEC-`

## EXEC-001：Fork/Join/List

Manager 控制面：`fork-agent` / `join` / `list`

Orchestrator 控制面：`fork-manager` / `join`

DevOps 额外控制面：`fork-pty`

## EXEC-002：Fork-agent 语义

```json
{
  "agent": "fast-coder | deep-coder | ... | <existingAgentId>",
  "prompt": "string"
}
```

新建 Agent：prompt 非空，agent 为准确角色名。已有 Agent ID + prompt：nudge/continue，fire-and-forget。

Busy existing agent：不创建新 RunId、不安装新 listener、不创建新 completion。nudge 归属于当前 active Run。

## EXEC-003：Fork-pty 语义

```json
{
  "agent": "pty | <ptyId>",
  "prompt": "string",
  "signal": "TERM | KILL | INT | HUP | QUIT | USR1 | USR2 (optional)"
}
```

PTY ID + prompt 非空 = write。PTY ID + prompt 空 = read。PTY ID + signal = 发信号。

## EXEC-004：Join 语义

（rev.2，supersedes rev.1 单结果平铺 wire：`status`/`agent`/`work_record` 三字段对象。rev.2 统一有界批次；中断见 EXEC-017；drain 与排序见 EXEC-018；Orchestrator verdict 批量见 EXEC-019。）

等待并消费可 join 的完成项。单结果也走统一批量形态，不维护第二套单项协议。`formalRecord` 已废止，不存在。

领域结果（agent / PTY / orchestrator 共用形状）：

```fsharp
type NonEmptyBatch<'item> =
    private
    | NonEmptyBatch of head: 'item * tail: 'item list

type JoinWaitOutcome<'item> =
    | ResultsAvailable of NonEmptyBatch<'item>
    | InterruptedByUserMessage
```

`InterruptedByUserMessage` 不属于 `ForkError`（EXEC-017）。批次上限、竞争优先级与稳定排序见 EXEC-018。

### LLM-visible 成功 wire

```toml
status = "completed"
count = N

# <entry-local work_record comments，仅 agent 完成项；SyntheticToml.comment>
[[result]]
ordinal = 1
kind = "agent"
status = "completed"
agent = "deep-coder"
```

不变量：

* 顶层只含 `status = "completed"` 与 `count`（本批 N，`1 ≤ N ≤ MaxJoinBatch`，`MaxJoinBatch = 32`，EXEC-018）
* 每项恰好一条 `[[result]]`，字段：`ordinal`（本批 1-based）、`kind`（`agent` | `pty` | `orchestrator`）、`status`、适用时 `agent`
* agent 完成项的最终 LWR（`includeOpening=false`，EXEC-006）以该项 `[[result]]` 之前的 entry-local 注释块呈现；**禁止** `work_record = ...` 字段（记法见 spec/13 §9.6）
* PTY 保持独立最小 schema（`kind = "pty"` 等，spec/13 §9.6），不塞 agent session 语义
* Orchestrator 项见 EXEC-019
* runtime-only 身份（agent_id、run_id、child_session_id、authority_root、provider_run、directory、digest、freshness、covered_through、tier、fallback_peer）不得进入 LLM-visible join 结果；需要时留在 typed runtime / journal / diagnostic surface

### LLM-visible 失败 wire

真正错误（无结果可返回）时：

```toml
status = "failed"
agent = "deep-coder"

[error]
code = "..."
message = "..."
```

禁止用 `status = "failed"` 或 `error = "aborted"` 表达用户消息中断（EXEC-017）。不要同时输出 `outcome = message` 与 `[error].message`。

### 完成 cell 与消费

每个 RunIdentity 对应 single-assignment completion cell。Terminal/SendFailure/Cancel 竞争 TrySetResult，首个成功者唯一生效。每项 consume 成功后从 joinable 索引删除，并写入永久 `HandleRetired` tombstone（EXEC-009）。批次不伪造全局原子事务；不变量是每个 completion 最多被消费一次（EXEC-018）。

无活跃资源时返回 `NothingToJoin`。

## EXEC-005：List 语义

```json
{ "kind": "all | agent | pty (optional)" }
```

返回当前运行期资源的派生视图，包含 Running、Busy、CompletedAwaitingJoin 三种状态。不包含 Retired。不承担 Agent catalog 功能。

## EXEC-006：Child Run 生命周期

新建 Agent：先监听 terminal，再发送 prompt（极快 terminal 也不丢）。

child 初始上下文 = 创建时物化的父 LWR（`includeOpening=true`：Opening + Y frames + X gap + terminal，COMPANION-003）。gap/terminal 均经 LWR 投影，不含 raw tool call/result。不存在「B else A」分支：Y 从未成功时也是同一物化算法（Opening + 0 frames + 全 X gap 投影），没有旁路语义。

child 的 OpeningPromptRaw 是 fork 原始 assignment 与权威 requirements，不是带 `parent_work_record` 的 synthetic transport envelope——后者是继承 context，不复制进 child 自己的 Opening，否则多代 fork 递归嵌套。

terminal 提取 child 最终 LWR 供 join：`includeOpening=false`（布置者已知任务）；`TerminalOutputRaw` 只取 formal text + host-visible reasoning；completion 只携带该 LWR。不存在独立的 session-wide A 提取，不把末回合 tool call/result 写入 work record，不把 child Opening 回传父模型。

## EXEC-007：Nudge

Fire-and-forget：不建插件队列，不等待当前 run。如果 Host 不支持 busy append，返回 `BusyNudgeUnsupported`。Busy→Idle 竞态以 Host AcceptPrompt 返回的 run/message identity 为唯一归属依据。

## EXEC-008：Parent Background

子 Agent 创建时的不可变快照。始终使用创建时物化的父 LWR（`includeOpening=true`，frozen bytes 冻结于 `ChildRunCreated`）。FrozenRecordPrefix 专用于父 Session X 的前缀缓存保护，不应用于 child background。不存在「无 B 则 session-wide A」分支——同一物化算法覆盖全部状态。

创建失败重试、Host retry、restart recovery 必须读同一个 frozen parent LWR blob，不重新物化，否则同一 child logical run 的背景可能漂移。

## EXEC-009：Handle 生命周期持久化

```fsharp
HandleLinked
HandleCompleted
HandleAbandoned
HandleRetired
```

```fsharp
type HandleLifecycle =
    | Active
    | CompletedAwaitingJoin of HandleCompletion
    | Abandoned of HandleAbandonReason
    | Retired
```

HandleId 创建一次并持久化。重启恢复同一个 ID。

四态语义：

* `Active`：已 link，尚未完成或放弃
* `CompletedAwaitingJoin`：完成 cell 已写入（Terminal / SendFailure / Cancelled），`join` 可消费
* `Abandoned`：持久终态；不可回退为 Active/CompletedAwaitingJoin；不得误报为 Completed；父取消经 `HandleAbandoned` 进入此态（不再经 `CompletedAwaitingJoin(Cancelled)` + retire）
* `Retired`：`join` 消费完成后的 durable tombstone。Retired ID 永远返回 `RetiredHandle`，不得退回到"把输入当成 Agent 名称重新 fork"

`HandleAbandoned` 事实由 `HandleController.recordAbandon` 唯一写入（CAS：首个生效）。`join` 对 Abandoned 必须立即以明确 Abandoned `status` 纳入 `[[result]]` 批次返回（EXEC-004），不得阻塞等待，不得误报 Completed。

**中断 ≠ 终态。** loop-detect 中断、Host abort 后自动续跑（LOOP-006）、ProviderRetry 等 wake **不得**写入 `HandleAbandoned`，也不得用 Aborted 填满 pending completion cell 并向父 Join 广播终态。`HandleAbandonReason` 仅：`ParentCancelled` / `DeadlineExceeded` / `HostSessionGone`。

Agent、PTY、ManagerJob 分别具有 typed handle。父取消必须逐项取消所有 owned physical resources。

## EXEC-011：Process Deadline

```fsharp
let effectiveDeadline request configuredHardLimit =
    min (TimeSpan.FromSeconds(float request.EstimatedRunningSeconds * 3.0),
         configuredHardLimit)
```

LLM estimate 不能突破管理员硬上限。Hard limit 必须有限。Timeout 后 SIGKILL 整个进程树，kill 后等待真实 onExit。不设置第二套互相竞争的业务 timeout。

## EXEC-012：大输出摘要

触发条件：`stdout bytes + stderr bytes > 3 × estimated_output_bytes`

200KB chunked ripple-carry reduce。Map 并发，结果按 chunk index 排序。Executor IDs 由 hash 生成（确定性）。Map/reduce 失败时返回 partial summary + 最后 200KB raw tail。

## EXEC-013：Large Gate

SemaphoreSlim(1,1)。只限制 Large。Medium 无并发限制。success/failure/cancel 都由 use! 释放。

## EXEC-014：Executor 私有 Runtime

每个 parent session 拥有一个私有 Executor runtime。Executor map/reduce completion 不进入 Manager mailbox。

## EXEC-015：PTY 行为

```
- TERM 后默认等待 5 秒再 KILL
- Close = stdin EOF（不是 SIGKILL）
- 每次 read 返回自上次 read 后的 unread delta
- UTF-8 半字符：保留在内部 buffer
- Buffer 上限 > 64KB
- PTY completion 只由 backend onExit 触发
- Signal/Close 不提前完成
- parent abort 后 await process-tree 收敛
```

## EXEC-016：Background Join Guard

拥有 `join` 的角色在 assistant terminal 时，若仍有未消费的后台资源，不得以 Completed 收束；发送 Continuation `JoinGuard`，优先于 Manager Review Guard（REVIEW-007）。

适用范围：`Manager`、`Orchestrator`、`DevOps`。其它角色无 `join` 义务，本条不适用。

### 何谓 outstanding

派生谓词，不是程序计数器：

| 角色 | outstanding |
|------|-------------|
| Manager | 本 session 的 handle 处于 `Active` 或 `CompletedAwaitingJoin`（EXEC-005 listable） |
| DevOps | 同上，或本 session 仍有 live PTY（EXEC-015；PTY 以 runtime 视图为准） |
| Orchestrator | 仍存在 non-terminal `ManagerJob`（ORCH-004 `activeJobs`） |

Executor 私有 runtime 永不进入此谓词（EXEC-014）。

### 行为

```text
TurnCompleted
→ outstanding?
  → yes: 延迟 Completed；发送 JoinGuard Continuation；本 turn 不进入 Review Guard
  → no:  再走 REVIEW-007 / Reviewer Guard 等既有路径
```

JoinGuard：

* Continuation（PROMPT-003）：不建新 Logical Run、不改 profile、不重置 Fallback
* 经 PromptDispatcher（PROMPT-005）；fire-and-forget = Detached（PROMPT-007）
* 同一 session 已有 outstanding JoinGuard claim 时不再重复发送
* 文案 instruction-only（ARCH-010），固定英文：要求先 `join` 收取完成项；需要视图时用 `list`

禁止：

* 在 outstanding 时报告 terminal Completed 让 join/AwaitManager 提前返回
* 用 Host background-subagent 通知语义替代本仓 `join` 义务
* 为 JoinGuard 引入 Stage / Lease / Generation 程序计数器
* 扫描完整 journal 历史判断 outstanding（PERSIST-008：投影 O(1)）
* Executor map/reduce completion 触发本 guard

## EXEC-017：Join 中断不是错误

`JoinWaitOutcome.InterruptedByUserMessage` 表示调度权从正在等待的 `join` 交还给最新 user 消息。它：

* 不是网络失败；
* 不代表子任务失败；
* 不触发重试、AABB 或错误展示；
* **不属于** `ForkError`。

### Wire

```toml
status = "interrupted"
reason = "new_user_message"
action = "handle_latest_user_message"
```

明确禁止：

```toml
status = "failed"
error = "aborted"
```

也禁止把中断编码为 `CANCELLED` 错误对象或任何 `ForkError` 分支。

### 中断范围

tool-call abort（新 user 消息打断当前 join 工具调用）只唤醒**当前** join waiter：

```text
tool-call abort
  → 只 Signal 当前 join 的局部中断源
  ≠ runtime.Cancel()
  ≠ child cancellation
  ≠ mailbox 永久取消
  ≠ HandleAbandoned
```

`runtime.Cancel()` 只保留给真正的生命周期终止（父取消 owned resources、deadline、Host session gone 等，EXEC-009）。中断后 child 继续运行；后续 `join` 仍可消费其 completion。

与 EXEC-009「中断 ≠ 终态」一致：join tool abort 不得写入 `HandleAbandoned`，不得用 Aborted 填满 pending completion cell。

## EXEC-018：Join 批次 drain、竞争优先级与稳定排序

### MaxJoinBatch

```text
MaxJoinBatch = 32
```

单次 `join` 最多返回 32 个已消费完成项。剩余 joinable 继续留在队列，下次 `join` 再取。理由：避免工具结果无限膨胀；避免 work record 挤爆上下文。

### 竞争优先级

`join` 被 user 消息打断时，**先**重新检查当前是否已有可消费结果。已有结果优先返回 `ResultsAvailable`；确实没有结果才返回 `InterruptedByUserMessage`。

动机：child 已完成并持久化后 user 消息恰好到达时，已完成结果不得被无故隐藏。

```fsharp
match tryDrainAvailable () with
| Some results ->
    ResultsAvailable results

| None ->
    let! signal = awaitCompletionOrUserInterrupt ()

    match tryDrainAvailable () with
    | Some results ->
        ResultsAvailable results

    | None when signal = UserInterrupted ->
        InterruptedByUserMessage

    | None ->
        continueWaiting ()
```

durable agent completion：mailbox / journal change 只作 wake signal；真正结果只从 durable projection 读取（ARCH-002）。

### 稳定排序

批次内排序键，严格按序应用：

1. durable completion sequence（若投影存在该字段）；
2. 否则 handle 创建序；
3. `AgentId` / handle 身份稳定 tie-breaker。

明确禁止：

* JS 对象属性枚举顺序；
* Promise 完成竞速顺序；
* 当前系统时间；
* 不稳定 map/hash 顺序。

### 逐项 CAS 消费

每个 handle 仍单独 CAS consume：

```text
读取 joinable
→ consume(handle, expectedVersion)
→ 成功才入批
→ CAS 失败则重新读投影
```

批次不伪造全局原子事务。真正不变量：每个 completion 最多被消费一次；批次只是一组逐项成功消费的结果。CAS 失败或竞态丢项不得用另一 handle 的 completion 顶替填充。

## EXEC-019：Orchestrator verdict 批量 join

Orchestrator 的 `join` 与 agent/PTY 共用 EXEC-004 批次 wire 与 EXEC-017/018 等待语义；本条只固定 verdict mailbox 的排空规则。

1. 第一个 verdict 可用后唤醒；
2. 立即排空已有积压；
3. 单次最多 `MaxJoinBatch`（32）条；
4. 保持发布顺序（FIFO；禁止按字符串化 verdict、map 键序或完成竞速重排）；
5. 超出上限的剩余 verdict 继续入队，下次 `join` 再取。

LLM-visible 项：

```toml
[[result]]
ordinal = 1
kind = "orchestrator"
status = "completed"
outcome = "<verdict 的稳定字符串表示>"
```

禁止单结果旁路（例如顶层仅 `outcome = "..."` 而无 `[[result]]`）。`InterruptedByUserMessage` 与 agent join 同形（EXEC-017）。
