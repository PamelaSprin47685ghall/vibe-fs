一次说清下一请求的 view：`{ prefixUntil, thenMap }`，两个字段都必填。`prefixUntil` 是非负整数锚点编号：编号小于它的内容位于缓存前缀，成本低；编号大于等于它的部分每回合按原价重算。当轮 `thenMap` 对编号小于 `prefixUntil` 的项静默忽略，不修改缓存前缀。提高边界不会恢复此前压缩掉的原文。

上下文整理应当轻重有别，而不是每轮推倒重来。大约八成时候，只清掉约两成已经失去作用的内容：过期猜想、重复输出和已被结论替代的过程，保留眼下仍需核对的原文与证据。少数真正适合收束的关口，例如一段调查已有可靠结论、工作重心已经转移，才做一次较深的整理，争取让约八成旧上下文退场，把仍能影响后续判断的目标、约束、结论、证据出处和未决问题留下来。这是分配整理力度的经验，不是按回合计数的配额，也不是为了凑比例删除有用材料。

已经确认不再需要的内容，应趁它还在可替换区时尽早摘要，不要让它带着原价反复进入后续请求。仍有用且稳定的内容则保留在便宜的缓存前缀里，不必为了显得精简而反复重写。缓存便宜不等于废话值得长留，深度整理也不等于抹掉因果与凭据；先判断什么还会改变下一步行动，再决定保留多少。

`thenMap` 必须逐个覆盖所有编号大于等于 `prefixUntil` 的可见存活锚点。每个值只能是 `null`（保留当前内容）或非空摘要字符串（把该锚点当前代表的整个区间替换为摘要）。不要只列出要替换的编号，保留的编号也必须明确写 `null`。例如 `{ "5": null, "6": "<summary>", "7": null }`。运行时若确实漏项，漏项按 `null` 保留，不抛错；这不是省略表态的理由。空白摘要不是保留，会被拒绝。

存活锚点划分区间。每次替换针对最新完整区间，区间内此前并入的摘要也一起被换掉。真实锚点被替换后消失，其新内容进入左侧最近的存活锚点区间：6 被替换后由 5 代表，下次替换 5 会连原 6 的摘要一起替换。压缩永久生效；`null`、漏项和 `prefixUntil` 都不能恢复原文。

隐含锚点 `0` 永远指向最开头，永远存在，可以替换但不消失；真实锚点从 `1` 开始。1 被替换后进入 0 的区间，之后替换 0 会整段覆盖它。0 也受本轮前缀保护约束；要替换 0，使用 `prefixUntil: 0`。

同一份 view 语义用于编程面、advisor 和交付。advisor 先生成完整 view，再根据宿主掌握的已交付事实取 delta；首次交付完整 view。`prefixUntil` 不是顾问已看过的位置。
