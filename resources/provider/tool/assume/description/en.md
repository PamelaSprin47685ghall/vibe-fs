Pin a judgment that has already been abstracted into the current working assumption, then continue executing.

Abstract first, then call `assume`. In your reasoning, separate the essential structure: which parts are independent, which have real dependencies, which are domain decisions, and which are merely mechanical execution. Once you have a conclusion you intend to act on, put it in `assumption`. It may be as short as one sentence.

`assume` is not verification, does not make the domain decision for you, and does not make a guess true. It is a commitment act: you have finished abstracting with the information currently available, so stop reopening the decision without information gain and execute against it, then verify.

After the call, do not reopen the same choice without new evidence. The information available during abstraction does not increase merely because you hesitate; hesitation produces no new knowledge, only new branches, new errors, and less time. Wavering immediately after abstraction rejects your own abstraction without any new fact that could justify the rejection.

Experienced participants treat the first well-abstracted decision as the default object of execution; a second thought earns the right to overturn it only by carrying a new fact. Otherwise this is not greater caution but a domino chain: abstract → hesitate → change answer → hesitate again → change again → more wrong → more anxious → more wrong. Its usual endpoint is not a better answer, but a worse answer with less time remaining.

Only execution results, verification results, or external input that materially changes the structure should reopen the decision and revise the assumption. Do not call `assume` repeatedly merely to soothe uncertainty.

A successful return does not establish that the assumption is proven. It establishes that the current assumption has been explicitly committed. The next move is execution, then verification: abstract → commit → execute → verify.
