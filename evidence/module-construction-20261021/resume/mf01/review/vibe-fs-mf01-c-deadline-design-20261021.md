# MF01 C: one Host deadline owner, isolated design

This package would prove a deadline mechanism around the real temporary guest and scratch filesystem. It would not prove production shell lifetime, ledger admission, ReadOutput, Callable diagnostics, memory limits or production reception. A and B stay frozen; no implementation or runtime experiment was performed for this design.

## Read contract

Main `JsSandbox.fs:72-109` creates a single deadline reference. The first borrow snapshots `max(0, reference.current - Date.now())`; later concurrent borrows do not snapshot it again. Each lease has its own absolute `borrowNow + duration`. Borrow, partial release and reset recompute `max(now + savedRemaining, all live lease ends)`. An expired lease can stay in the map until released, but its old absolute end cannot dominate a later time. Final release restores `now + savedRemaining`. Its closure is idempotent. Reset with live leases replaces savedRemaining with `max(0, requestedEpoch - now)` and still takes the maximum with those lease ends. Reading RemainingMs does not refresh the base budget.

`ToolWorkflow.fs:692-705` forwards BorrowDeadline and reads RemainingMs from that same reference. `JsCallLoop.fs:1729-1738,1863-1886` acquires the lease once around proof plus execution, releasing it in finally; duration is `2 * min(spec.maxDuration, Host.hardLimit) + 2 * signalGrace`, not just one callback estimate. Construction/spec validation precedes this lease. C will expose the trusted Host borrow operation without pretending it implements the full CallLoop computation or actual shell execution.

Production unpark/abandon reset the same owner to a new base epoch. The real shell/process scopes have their own finite physical deadlines and continue while a model is parked (`process-execution/004`); C does not pause or replace those absent scopes. C parks only the guest watchdog after an actual T observation, as A/B already do. Its lease absolute ends still age while parked; reset on resume supplies the new base budget. Park does not rewrite every lease or pause all clocks.

## Host ownership and linearization

Add one private HostDeadline object per exact GuestOwner. It owns current epoch, first-borrow saved budget, live lease ends, release closures and the one watchdog. No guest copy owns a business deadline. Trusted Host calls borrow/reset/release directly, including while guest code cannot read a message. Ordinary Host capability admission, Callable command submission, Callable result admission and top-level business result admission all consult this same current epoch immediately before admission. A complete buffered frame that arrives after expiry cannot win merely because the timer callback was queued later.

The deadline comparison that admits a capability is its admission point. Once admitted, the original Host operation remains owned until settled; timeout neither replays it nor pretends an accepted write did not occur. A callback/reply may become unknown to its caller after closing, but already accepted Host work is drained by the existing owner. Terminal outcome admission retains the A/B exact phase and single-settlement rules.

Borrow/reset/release re-arm the same timer; timer callbacks recompute current remaining and use bounded timer chunks, avoiding Node's overflow-to-1ms behavior for a large valid epoch. No refresh happens on reads. Before a new borrow, require an active, unexpired business owner; a request to borrow after revocation cannot revive the guest. Repeated release is a no-op after its first application, including after native close. Reset to an expired epoch arms the next timer at zero rather than synchronously committing Closing: repository-programming/028 explicitly permits past reset then future reset in one Host turn before the program's next capability, and that valid sequence must survive. The next timer or business admission rechecks the current epoch and commits expiry if still expired. Once Closing has actually won that admission point, a later reset cannot revive it.

ParkRequested remains deadline-bound until actual T and exact native identity are observed. Publishing Parked checks the current deadline again and then suspends the timer; a late STOP observation is not permission to erase expiry. While Parked, reject new capability/Callable/borrow admission but permit already-owned releases and trusted reset to update stored policy without killing the stopped continuation. Resume consumes the exact site, applies reset through the same deadline object, re-arms before CONT, then follows the existing ack -> Host admission -> activate -> original deferred protocol. No deadline update has to be read by guest. RemainingMs can read the stored absolute policy without changing it; parked state itself does not grant new work.

### Abandon and old leases: approved isolated extension

The current production reset rule keeps old leases in its maximum. Thus a 10s cleanup base can still be extended by a previously issued long lease until its scope releases. B's fixed cleanup watchdog currently has no such leases. C must not accidentally claim both a hard cleanup cap and unchanged live-lease dominance.

Root approved this isolated extension: `enterCleanup(epoch)` on the same HostDeadline irreversibly retires old execution leases and fixes the cleanup epoch. Cleanup capability calls remain allowed. Borrow may return a bounded no-op release but cannot extend the cleanup epoch, and reset cannot extend it. Releases of retired exact lease closures are harmless no-ops. This follows Host cancellation of the original scopes; their already accepted work stays owned and drains separately. It is a new candidate contract to test, not a claim about existing production behavior. Do not add a second cleanup timer with a different authority while calling the system single-owner.

## Remaining risks

The source contract currently uses wall-clock epochs; clock adjustment behavior remains inherited and is not silently replaced with a different monotonic policy. C measures elapsed witness times monotonically but does not claim a wall-clock-jump proof. A Host event-loop stall can delay timer processing, so per-admission deadline checks are necessary; no hard real-time scheduling guarantee is claimed. The membrane derivation needs independent diff review to ensure only business clocks were removed. Startup still needs an external owner. Actual heap enforcement, production Host permission/ledger integration, signal ownership API, full Callable diagnostic behavior and full shell deadline/cancel/drain composition remain open.
