# 为什么采用分域文档体系

旧体系把行为、边界、实现步骤、验证、进度和未来设想压进同一批文件。读者每读一页都要在抽象层级之间跳转；实现者直接从高层目标跳到代码，文档矛盾时临场选一边。注意力被稀释，规范与实现的偏离被“看起来完成了”掩盖。

本体系把知识按问题切开，而不是按文件长度或发布习惯切开。

## 被拒方向

**单文件真理源。** 所有问题指向同一套文档，名义上清晰，实际把“应表现出什么”与“此刻怎么写”混写。冲突时没有越权判据，只有口才。

**按版本复制整套文档。** 每个版本一份完整副本、revision 封印、release manifest 绑定文档版本——把文档治理做成第二套配置系统。滚动基线更便宜：当前 docs HEAD 与当前实现面对齐即为当前系统。

**Proposal 直达代码。** 候选设计未进入正式规范就被实现，会在基线上叠加未裁决变量。出问题后无法区分旧基线缺陷与新设计副作用。

**未实现时提前删除 Proposal / 永久保留 Proposal。** 禁止未经用户同意删除任何未实现的 Proposal。裁决后把知识分发到正式层，只将剩余物理差距写入 Status；不得把 Proposal 正文搬成第二份规范。Git 保存完成历史，长期知识留在正式层。

**独立 Decision 档案。** 再造 `accepted-decision` 状态层，等于用元数据重复表达 `what/` 已承担的“已被裁决”。分发到正式层即可，不需要第三套身份。

**把 resources 抬成永久非文档权威。** `resources/` 是实现面的当前承载方式，可被规范要求改写。规范定义语义；实现选择载体。

## 权衡

| 选择 | 代价 | 收益 |
|------|------|------|
| 七目录分域 | 同一主题可能跨文件 | 每文件只回答一类问题；越级指挥可被规则拒绝 |
| `how` 描述目标实现而非当前快照 | 实现落后时读者需对照 `status/` | 规范不被半完成代码拖成灰文档 |
| 规范面原子更新、实现面可落后 | 需要维护活跃 `status/` | 设计可继续裁决，不必假装代码已追上 |
| 条款 ID 跨目录迁移但不改号 | 编号可不连续 | 测试名与交叉引用不因搬家失效 |
| Clean break 废止未迁移旧规则 | 迁移遗漏即废止 | 禁止“旧路径隐式仍有效” |
| Hotfix 豁免 Proposal（GOV-012） | 线上紧急修补时不先写 proposal | 消除线上排障时的治理摩擦，代码与文档在同 Commit 原子更新 |

## 核心取舍

高层文档不得越级指挥代码。代码对齐目标实现（`how/`）；实现尚未对齐时，差距只进 `status/`，不偷偷改写 `how/` 去迁就现状。

Proposal 不得污染不可信规范面。规范面内部矛盾或未登记的实现差距存在时，可以讨论 proposal，但不得把它写成当前 `what/shape/how/proof`。

Proposal 不是档案。裁决后按 GOV-006 把知识分发到正式规范面，只用最小 Status 跟踪剩余物理差距；实现对齐并通过 proof 后删除该差距。

Hotfix 不得成为破坏文档一致性的借口。Hotfix 豁免的是 Proposal 的前期流程，不豁免文档与代码的同 COMMIT 原子更新。
