第 1 篇 · 这是什么？

1. 一句话定义

万象术（Wanxiangshu）是一块给 AI 编程助手装上"公司大脑"的引擎——它把一次单一会话，拆成一支分工明确、互相审查、记忆持久的智能团队。

它不是换一个更聪明的模型，而是让"聪明"被组织起来。就像一个指挥机关负责拆任务、派活、收割；一个隐藏的质量评审团在交付前严格把关；一个记忆侧车负责把马拉松任务的历史压缩保鲜；一本事件账本保证哪怕程序崩溃，也能原样复活。

对象依然是那个熟悉的 AI 编程终端（OpenCode），但工作的方式变了。

换一个比喻

过去：一个全能的"一个人公司"，同时做 CEO、工程师、情报员、QA、档案员。上下文一长就顾此失彼。

现在：一支整建制作战的团队。每个人只做自己最擅长的一件事，角色之间上下文互不污染。

它解决什么

长任务的失忆——上下文再多也能记住开头给你的那句话。
自审的失效——让写代码的人审自己的代码，等于让学生自己判卷。万象术动用看不见的评审团。
单点的故障——模型卡死、死循环、答非所问，有备用模型和事件账本兜底。

项目经理Manager · 项目经理拆解任务、派活、收割成果、维护 todo 清单，让工作不停
工程师Coder · 工程师唯一能写文件、改代码、移动删除的人

研究员Meditator · 研究员不碰文件，只负责想问题、找反例、提出追问

第 1 篇 · 这是什么？

3. 单个助手为什么会半途而废

把无数失败的 AI 编程任务归拢，其实只有三个根因。看懂它们，就懂了万象术为什么存在。

弱点一：上下文会爆炸

模型的"窗口"有限。任务越长，塞进窗口的历史越多，直到某天开头那个最关键的"你要我做什么"被挤出去。长任务越做越像失去目标。

不是模型不够聪明，是它"记不住自己本来要干嘛"。

弱点二：自审会失效

让写代码的同一个模型去检查自己的代码，等于让学生自己判卷。它对自己的产出有天然的"确认偏误"，很容易说"没问题"。

质量需要一双不在场的眼睛。

弱点三：单点会故障

一个模型卡死、陷入死循环输出、或干脆答非所问，整个任务就陪葬。没有备用、没有刹车、没有倒带。

把鸡蛋放在一个篮子里，篮子的命运就是任务的命运。

万象术的三个答案

弱点答案
上下文爆炸记忆侧车 + 前缀重建（第 3 篇）
自审失效隐藏评审团 + Magic Todo（第 4 篇）
单点故障备用模型 + 死循环刹车 + 事件账本（第 5 篇）

4. 七张王牌总览

万象术的七张王牌，每一张都对应一个真实痛点。先有一个总览，后面逐张展开。

1. 团队分工 · 二十个 Agent 十个角色 × 快/深两个型号。每个人各司其职，权限边界像保险柜一样清晰。
2. 马拉松记忆 · 上下文恢复 工作日志侧车 + 前缀重建，长任务不再失忆。
3. 自我审查 · Glory 终局 隐藏评审团用八大质量支柱把关，交付前必须被证明，而不是"我觉得行了"。
4. 持续检查点 · Magic Todo 一份活的清单，每个节点都经过异步评审，不能直接打勾。
5. 可靠兜底 · Fallback + Loop 备用模型 + 死循环刹车，模型挂了任务不陪葬。

第 2 篇 · 这支团队

1. 快与深：角色双胞胎

万象术里每个角色都有两个孪生型号：

Fast · 快版
便宜 敏捷 适合热身的机械活
Deep · 深版
昂贵 缜密 适合关键判断与终局

关键在于：孪生兄弟的技能完全一样——同一套工具、同一套权限、同一套纪律，只是"大脑型号"不同。

这正是可靠性的根基：当深模型连续失败时，系统可以干净利落地切到快版本继续（第 5 篇 Fallback），而不是换一个"能力不同、行为不可预期"的新人。

快与深，是同一个岗位的两台机器，不是两个不同的岗位。

第 2 篇 · 这支团队

2. 指挥层：Orchestrator / Manager

Orchestrator · 总指挥

只做一件事：把整个仓库级的大任务托付给项目经理，并负责最后一公里的发布闭环——把开发成果重新合入目标分支前，还要经过一次严格的复查。

它不写代码、不改文件，它只负责"这个项目该由谁来做、做完了怎么安全地上线"。

Manager · 项目经理

万象术真正的"大脑中枢"。它遵循一个铁律：

Manager 自己永远不亲手写代码。

它只做四件事：

  • 拆解——把大任务拆成可以独立推进的小任务；
  • 派活——fork 出工程师、情报员、运维等，各自开工；
  • 收割——join 收回他们完成的成果；
  • 维护清单——用 todowrite 维护一份永远真实的 todo 清单。

有意思的是，Manager 看不见那个隐藏评审团。它不知道检查自己的是哪几位评审员、什么时候查、评审几个人。它只负责一件事：让工作永不停止地向前推进。

第 2 篇 · 这支团队

3. 执行层：Coder · Inspector · DevOps · Browser

执行层是真正"动手"的角色，每个都有严格的权限边界。

角色能做什么红线
Coder · 工程师读文件、写文件、改代码、移动/删除、全局搜索、跑一个只读的"假终端"探针唯一能改动文件系统的人
Inspector · 情报员只读调查：读文件、查目录、搜代码、调用执行器做检查只读，绝不改任何东西
DevOps · 运维开终端（PTY）、跑命令、收结果、读文件、派活给工程师/情报员要改文件必须经同步的工程师委派，不能越权直接改
Browser · 浏览器读文件、查目录、搜代码、访问网络只管上网查资料

这套设计最狠的地方在于权限即事实：不是靠提示词"请你别越权"，而是工具本身在系统层面拒绝。一个角色手里根本没有它不该有的工具——想越权也越不了。

bash-honeypot · 蜜罐探针

工程师手里那把"假终端"其实是个蜜罐：调用它不会真的跑任何 shell，只会返回一句"越权拒绝"。它存在的意义，是教育模型"这里不该碰终端"。

第 2 篇 · 这支团队

4. 思考层：Meditator · 研究员

Meditator 是万象术里的"哲学家"，也是被刻意做得最纯粹的角色：

Meditator 不碰任何文件，它手里只有一个工具——把调查派给 Inspector。

它只做四件事：

  • 形成理解——清楚地说出"我现在是怎么理解的"；
  • 找反例——主动问"什么情况下我这个理解是错的"；
  • 提出追问——把事实问题交给 Inspector，拿到答案继续追；
  • 区分证据与推论——说清楚哪些是看到的，哪些是猜的，哪些还不确定。

这是一种刻意的分工：推理与取证彻底分开。想问题的人不碰文件，查文件的人不负责下结论。如果让 Meditator 自己又能读文件又能想，它就会退化成"便宜版 Inspector + 推理"，边界立刻模糊。

第 2 篇 · 这支团队

5. 质量层：Reviewer · 评审员

Reviewer 是万象术质量体系的守门人，被设计成一个不可绕过、不可收买的角色。

权限

只读工具（读文件、查目录、搜代码）+ 一个裁决工具：

verdict("PERFECT")   # 完美
verdict("REVISE")    # 返工

它不能写文件、不能跑命令、不能打钱买通。它只能"看"和"裁决"。

关键：它看不见经理，经理也看不见它

Reviewer 是隐藏的。Manager 不知道评审团是谁、有几个、什么时候查。这样评审员不会被"项目经理的脸色"影响，也不会被"再跑一次测试"糊弄过去。

质量门不是可勾选的步骤，而是不可见的命运。

评审依照八大质量支柱（详见第 4 篇），不是"你测试过了吗"这么简单。只有当八个维度全部无瑕，才敢按下 PERFECT。

第 2 篇 · 这支团队

6. 记忆层：Blogger / Executor

Blogger · 档案员

每个主会话都配一个"影子档案员"。当主会话（我们叫它 X）闷头干活时，Blogger（我们叫它 Y）在后台默默把已经发生的工作压缩成一份份"工作日志"。

它只有一个工具：blog——把稠密的工作日志写下来。它不指挥、不决策，只负责记忆的保鲜（详见第 3 篇）。

Executor · 执行器

最"老实"的角色：没有任何工具，纯粹被调用去执行指定动作。它不调查、不决策，只负责把活干完。

"内部人"对用户不可见

Blogger 和 Executor 都是"后台员工"——它们不会出现在任何模型可见的菜单里，用户永远看不到它们的名字。它们只存在于系统内部，像空气一样支撑主流程。

第 3 篇 · 马拉松记忆

1. 上下文会爆

模型有一个硬约束：处理一次对话时，能同时"看见"的上下文是有限的——就像一个桌面，一次只能摊开这么多文件。

长任务遇到的困境是：

  • 历史越积越多，桌面越来越满；
  • 到某个临界点，最老的关键信息（尤其是任务开头那句要求）被挤下桌面；
  • 模型开始"忘了自己要干嘛"，质量断崖式下跌。

常见的解法是"换更大的窗口"——但那只把问题往后推，还贵。万象术的答案完全不同：

不是把窗口变大，而是把历史整理好。

它把"记什么"和"怎么留得住"当成一个工程技术问题来设计，而不是赌模型窗口够大。

第 3 篇 · 马拉松记忆

2. 工作日志侧车

解决失忆的核心，是一辆"记忆侧车"（Companion / Blogger）。

工作方式：

  • 主会话 X 保留一份永不删除的原始轨迹（append-only，只增不减）；
  • 侧车 Y 把已完成的片段压缩成工作日志帧，占据的窗口小得多；
  • 当需要继续时，主会话从「压缩帧 + 未压缩的尾巴」重建当前状态——既省窗口，又不丢关键信息。

底层有一句很朴素的话：

信息只在被妥善整理时，才谈得上"记住"。

第 3 篇 · 马拉松记忆

3. 前缀重建：失败成为恢复的起点

上下文恢复的哲学只有四个字：不预测，只恢复。

很多系统会提前"猜"哪一段历史该压缩——按 token 数、按比例、按窗口快满没满。万象术拒绝这种猜测：它不预判什么时候会爆炸，而是把"某次请求真的失败"当场改造成恢复的起点。

机制是这样：

  • 平时正常干活，绝不主动压缩；
  • 当一次 provider 请求真的失败（比如窗口溢出），进入"恢复槽"；
  • 恢复槽里，用侧车已经压好的日志，冻结一段稳定的历史前缀，让后续请求从这份前缀继续；
  • 如果这次尝试失败，就丢掉，回到旧前缀——绝不留下半途而废的状态。
恢复槽的三个开关（缺一不可）
有失败触发 处于交替后的奇数位 真有可压缩的材料

一个关键承诺：前缀逐字节稳定

一旦冻结，这段前缀在后续请求里必须逐字节一模一样——这是让模型自身的缓存能无缝衔接的前提。可以说：

$$S'=\mathrm{Closure}(S\oplus Y)$$

吸收新信息后先全局收敛，再允许下一步。任何"差一点"都不行，失配就 fail closed。

第一次失败是代价，失败之后有路可走是设计。

第 3 篇 · 马拉松记忆

4. 永不遗忘的 Opening

整条记忆链里有一条绝不退让的底线：

任务最初那句要求——Opening——永久保留，逐字不丢，绝不被压缩改写。

无论后面压缩多少次、重建多少次前缀，最初那个"你要我做什么"如同铁锚，钉死在记忆的最深处。它是整个任务的目标锚。

为什么这么固执？因为压缩的本质是"有损"，而目标的丢失是最致命的有损。你可以忘掉某个实现细节，但绝不能忘了项目的初衷。

这与"记忆侧车"、与"前缀重建"是同一套逻辑的三层：

层作用能否压缩
Opening · 目标锚任务最初的要求永不压缩，逐字保留
工作日志帧已完成的片段可压缩，但要保真
原始轨迹全部原始历史永不删除，只增不减
第 4 篇 · 自我审查与完成

1. 完成不是"我觉得做完了"

普通 AI 助手最大的毛病之一，是自认为完成就交差。它干了活，自己觉得挺好，就宣布"做完了"——没有人复查，也没有人否决。

万象术把"完成"从一种自我感觉，变成一道不可绕过的门：

  • Manager 不能随随便便宣布结束；
  • 它必须显式地"请求终结"；
  • 只有隐藏评审团真正验收通过，才算数。

这套机制有一个很美的名字——Glory（光荣落幕）。

它的来源是角色的彻底分离：写代码的是 Coder，审代码的是另一个看不见的 Reviewer。让"生产者"和"裁判"互不认识，是断绝"自己判自己卷"最干净的办法。

完成必须被证明，而不是被宣称。

第 4 篇 · 自我审查与完成

2. Magic Todo：持续检查点

Manager 手里永远握着一份活的 todo 清单，通过 todowrite 更新。这份清单不是摆设，而是质量体系的骨架。

每个条目有一个明确身份

更新清单时，新旧条目用 kind 显式区分，绝不靠猜：

kind:"existing" + id   # 更新一条老条目，必须引用确切 id
kind:"new"             # 新增一条，系统分配 id

一个状态机守门

每个 todo 有五个状态：

pending → in_progress → reviewing → completed / cancelled

关键的铁律：只有经过 reviewing（评审中）的条目，才能变成 completed。不能从 pending 直接打勾。

异步评审，不等台

每个检查点立刻交给一个隐藏的评审员评审，但 Manager 不傻等——它继续去干下一阶段独立的活。评审结果回来后：

  • PERFECT（完美）→ 清单据此推进，进入下一步；
  • REVISE（返工）→ 带着精确的返工意见回来，Manager 继续改。

每个关键节点都有外部质量确认，而不是自我感觉良好。

第 4 篇 · 自我审查与完成

3. 隐藏评审团与八大质量支柱

当 Manager 认为任务完成、请求终结时，一支隐藏的评审团被默默召集。

评审团的构成：一小队评审员（快/深两种型号），每人收到当前这份工作树，独立评审，必须给出自己的裁决。评审团遵循一个严谨的规则：

  • 每个评审员必须独立、两次确认都通过，才授予"完美"；
  • 两次确认之间要证明"第二次真的看过了第一次的质疑"——不是口头同意；
  • 只要有一个评审员给出返工，整个评审立即关闭，工作打回。

评审不看"测试过没过"这么简单，而是对照八大质量支柱：

八大质量支柱
语言与算法 极致简洁 结构优雅 有界粒度 测试覆盖 无瑕逻辑 调用方体验 完整性

任何一个维度有缺陷，裁决就是 REVISE。绝不"差一点也算过"。

第 4 篇 · 自我审查与完成

4. 死于荣耀：最后的话

整个终局流程，被设计成一场庄重的仪式。

第一次请求终结

Manager 认为任务做完了，调用 suicide——并写下它的遗言（last_words），一段它认为任务已经完成的最后总结。

隐藏评审团随即启动。两种结局：

  • 返工（REVISE）——评审员带着一条精确的、不可伪造的"工作记录"返回，指出哪里还没完成。Manager 收起面子，拿着证据继续干活。不丢脸，只是还没到终点。
  • 祝福（Blessed）——评审全员通过。Manager 获得"祝福"，但还没结束：它被要求继续处理清单里所有零散的修补、遗留的疑虑和小的清理。

第二次请求终结

所有收尾都干净之后，Manager 第二次请求终结。这一次：

  • 不读工作树、不另请评审、不检查见证——前一次已经证明过了；
  • 写下最后的遗言，系统注册终局，向用户交付；
  • 工具结果固定包含一句 "rest in peace"（安息吧）。

用户拿到的最终答案，逐字等于 Manager 第二次写下的遗言——系统不加任何额外注解。

任务不是被"发走了"，而是被"善终"了。

第 5 篇 · 可靠与敏捷

1. 备用模型：Fallback

模型会失败，这是必然。万象术不假装它不会，而是把失败设计成可优雅处理的流程。

A/B 交替 + 预算熔断

每个角色有快/深双胞胎。当被选中的那个模型连续失败时，系统在A（首选）/ B（对侧的孪生）之间交替重试：

A 侧失败 → 换 B 侧 B 侧失败 → 回 A 侧 连续失败累计 达到预算 → 熔断

交替本身是合法的探索，不会判死；真正判死的是连续失败的预算（默认 12 次）。一旦连续失败撞顶，写入"恢复耗尽"，停止自动烧钱——只等一个新任务或用户显式介入。

切换是策略，熔断是底线。绝不无限烧下去。

只换模型，不换身份

切换只改变"用哪个型号"，绝不改变任务的权威身份、角色、或目标。你的任务还是那个任务，只是换了一台机器在跑。

第 5 篇 · 可靠与敏捷

2. 死循环刹车：Loop

大模型偶尔会"退化"：输出变成一个字符、一个短语、或一整句反复循环，长度惊人、内容毫无新意。让它跑完只是浪费时间、污染对话尾部。

万象术装了一个实时传感器：它一边看着正在流出的文字，一边实时计算"这段输出到底有多多样"。

关键指标：N_eff

系统把输出切成一个个小片段，测算"相当于多少个不同的片段"。正常代码多样性很高；死循环的多样性断崖式下跌。

$$N_{\mathrm{eff}}=\frac{1}{\sum_i p_i^{2}}$$

当 N_eff 跌到阈值以下：

  • 立即中止这次荒谬的生成（像汽车气囊，平时绝不介入，关键时刻一次救场）；
  • 把这次中止当成一次"可恢复的失败"，交给备用模型流程接管。

它绝不基于"角色、模型、代码还是闲聊"动态改阈值——对所有情况一视同仁，保证可测、可预期。

第 5 篇 · 可靠与敏捷

3. 崩溃复活：事件账本

程序会崩溃、进程会死、电脑会重启。万象术怎么保证世界不丢？答案是一本不可变的事件账本。

只追加，不修改

所有重要事实，都以"追加一条事件"的形式，记入一个不可变账本（进程级 .git/wanxiang/events/<WriterId>.ndjson + 远端同步时的 Git 原生对象库）。当前实现以 sha1 + zlib + objects/xx/yyyy 直写 loose object，单次 append 2 次 I/O，oid 与 git cat-file 完全互通。

  • 只能往末尾追加，从不能修改或删除历史；
  • 每一条自包含、有版本、可校验；
  • 一条真实事件 = 一个不可变对象。

崩溃之后：

从账本重放，世界精确回到崩溃前——不靠猜，不靠"差不多"。

合并与收敛

多个实例可能各自推进，账本用"集合求并"合并——谁都不覆盖谁，冲突被显式表达，再通过后续事件收敛。绝不用"谁时间戳晚谁赢"这种粗暴规则。

外部副作用也记账

连"创建临时目录""发布到分支"这类外部动作，都遵循"先请求→后确认"的记账：崩溃后先核对现实发生了没有，再决定收尾。绝不"内存里觉得做了就以为做了"。

第 5 篇 · 可靠与敏捷

4. 预读加速：Strength

深模型干活前，常常要先做一堆机械的只读调查：读几个文件、查几个目录、搜几个关键词。这些活本身不难，但让昂贵的深模型亲力亲为，很浪费。

让便宜的先暖场

Strength 的思路很朴素：在深模型真正动手之前，让同岗位的快速版先"预读"一遍，把结果悄悄垫进深模型的上下文。

  • 预读只做只读调查——读文件、查目录、搜代码；绝不写文件、绝不执行命令、绝不碰权限；
  • 预读结果以"候选人"的身份存在，只有被主任务真正消费后，才成为正式历史；
  • 全程可审计、可熔断、可关闭。

三档预算

K0（不预读）/ K1（预读一轮）/ K2（预读两轮）。默认从最保守开始，只有真实证据证明"省时省钱"才升级。

便宜的活让便宜的机器干，贵的机器只干它贵的活。

第 5 篇 · 可靠与敏捷

5. 经验缓存：Casebook

调查是一次性的吗？过去是：Inspector 查完一个问题，答案就散落在对话里，下次再问同样的问题，又要全部重查一遍。

Casebook 让调查可以复用：

  • 把「问题 → 调查动作 → 答案」缓存成一个可重放的经验条目；
  • 下次遇到相同问题，先针对当前代码重放那次调查；
  • 如果代码没变 → 直接复用答案（快）；
  • 如果代码变了 → 旧答案作废，启动后台修订。

新手艺：它判断"还新不新"，不是看时间戳，而是重放调查看结果变没变。时间戳会骗人，调查结果不会。

经验被复用，而不是被遗忘后重查。

它是个"尽力而为"的缓存，不是知识数据库——查不到就正常重查，绝不阻塞主线。

第 5 篇 · 可靠与敏捷

6. 可编程文件工具：JS Tools

批量改文件，传统做法是反复调用一个个工具，慢且容易出错。JS Tools 给模型一个受权限约束的工作台：

  • 模型可以写一小段脚本，一次完成批量读、批量改、批量写；
  • 脚本里只有系统显式注入的数据，拿不到文件句柄、环境、网络、进程——沙箱隔离；
  • 所有修改先在一个事务里暂存，全部检验通过才一次性提交。

事务的铁律

全有或全无——任何一个文件失败，全部改动一并回滚，绝不留下"改了一半"的仓库。
冲突即止损——某个文件在读取后被外部改过，整个事务作废，不隐式重试。
可恢复——崩溃后只从账本重建，未提交的改动不会鬼魂般出现在磁盘上。

同时，传统工具（读、写、改、搜）原样保留，与工作台共存——想用哪个用哪个。

第 6 篇 · 设计哲学与路线图

1. 端正的代码：类型消灭不可能态

万象术的底层哲学，不是"多写几个角色"，而是一整套关于如何写得端正的信念。它决定了整个系统为什么值得信任。

把"不可能"变成编译不过

与其靠纪律、靠提醒"你别写出矛盾的代码"，不如让类型系统在编译期就拒绝非法组合。一个状态如果根本不该存在，就让它从源代码层面构造不出来。

type FallbackOffset = Fork0 | Fork1 | Fork2 | Fork3   # 只有四种合法偏移
# 非法字节在反序列化边界返回错误，绝不悄悄当合法态

纯函数当内核，副作用当外壳

核心判断全是纯函数：给同样的输入，永远得到同样的输出。真实的副作用（写文件、发请求、跑进程）被收进薄薄的"外壳"，在外壳里转成命令、由内核计算、再执行。

核心可以回放、可以测试、可以推理；外壳只负责与世界打交道。

错误是返回值，不是暗雷

业务上可预见的失败（文件找不到、权限不足、库存不足）用清晰的类型返回，调用方必须正面处理它们。异常只留给"程序无法继续"的真事故。

一心一意，不搞阴暗面

每个事实只有一个权威来源；每个写入口只有一个所有者。没有"内存里偷偷记一份、账本里又记一份"的双写。DNS 式的"再想想"被杜绝——真相永远只有一个。

2. 五句话总结

1. 一支团队，一个大脑。 一次会话被拆成二十个分工明确、权限清晰的 Agent；指挥层拆活、执行层干活、思考层想问题、质量层把关。谁都不越权，谁都能被信任。
2. 记忆靠整理，不靠遗忘。 工作日志侧车把历史压成稠密帧，前缀重建让长任务不断档，Opening 目标锚永不压缩。失忆是被设计掉的，不是被祈祷掉的。
3. 完成必须被证明。 隐藏评审团用八大质量支柱把关，Magic Todo 让每个节点都经过异步评审。交付前必须被证明，而不是"我觉得做完了"。
4. 可靠来自账本，不来自运气。 不可变事件账本让崩溃后原样复活；备用模型与预算熔断让失败不失控；死循环刹车让荒谬输出当场止步。
5. 快与省是设计，不是补丁。 便宜的模型预读暖场、经验缓存复用调查、可编程工作台批量处理——省下的每一分钱都是设计出来的，不是事后优化堆出来的。

片尾彩蛋 · 实验 A

Sphinx · 生成式认识状态求解器

Sphinx 是一个由数学内核控制、与 LLM 携手推进的"认识状态"求解器。

普通问答直接给答案。Sphinx 不这样——它维护一个关于"我们现在知道什么、还不知道什么、什么问题值得继续问"的认识状态，然后一步步逼近。

一个内核，两种角色

负责什么
数学内核认识状态、全局闭包、判重与约简、方法选择、概率与裁决、搜索预算、停止、最终答案
LLM把自然语言转成结构化的概率化语义观测——仅限于此

LLM 不决定用什么方法、下一步做什么、哪个候选是真的、什么时候停止。内核说了算。

两个锚定例子

「花儿为什么这样红？」→ 展开多学科解释，各层互补，最终综合（不坍缩成一个干巴巴的答案）。

「明天白银会涨吗？」→ 基底概率、类比、因果驱动 → 收敛成后验概率（数值资格成立就给出贝叶斯后验，否则给出定性的区间信念）。

五个第一性原理

1. 历史不是状态 日志可以 append-only，但推理状态不该 append-only——系统维护的是历史对未来决策的充分统计量。
2. 表示不是认识本身 同一个认识状态可以有多个计算表示，内核有权重排、约简、旋转，只要认识语义不变。
3. 每次外生信息后必须全局闭包 LLM 每给一次新东西，内核先全局收敛到不动点，才允许问下一句。
4. 认知价值相对于根问题 一个子问题值多少钱，只看它预计怎样改善根问题——它是"解惑机"，不是"无限知识展开机"。
5. No Free Information（认识守恒） 重新措辞、类比、综合只能重组旧信息，不能凭空提高与现实的互信息。LLM 可以帮你找得更好，但不能把 0.6 递归成 0.9。

停，也是一个动作

停止不是特殊的 if。当停止的价值不小于任何继续动作时，停止就是当前最优动作——"问什么"和"什么时候不再问"属于同一个控制问题。

经典算法只是退化形式

Sphinx 最迷人的观点：A*、贝叶斯推断、MCTS 都不是它的定义，而是统一认识状态模型在不同约束下必须能退化成的样子。

$$V(S)=\min\left[L_R(S),\;\min_a\left\{C(S,a)+\mathbb{E}_Y V\bigl(T(S,a,Y)\bigr)\right\}\right]$$

条件退化为
确定性最短路径graph A*
固定概率依赖贝叶斯推断
无法精确求解MCTS

如果任何退化测试答"否"，很可能架构被设计窄了。

片尾彩蛋 · 实验 B

Fission · Agent 内透明裂变

Fission 是 Agent 内透明裂变：同一个逻辑 Agent 暂时展开成 N 个对等执行 lane，在内部收敛回一次普通完成——parent 完全感知不到这次裂变。

一句话：上级拥有"要什么"，当前 Agent 拥有"自己的工作是否值得横向展开"。

一个例子

Manager 从头到尾只看到：给了 Coder X 一个任务，X 完成了一次。它不知道 A、B、C 是三条 lane 并行干完的。

它不是 fork

fork · 层级裂变
新 Agent 身份新 handleparent 可见完成join / list 参与
fission · 对等裂变
无新公开 AgentId无新 handle无 parent join 义务parent 完全不知情

fork 改变组织拓扑；fission 不改变逻辑组织拓扑。二者必须长期正交。

谁会裂，谁不裂

允许裂变明确不裂
Manager · Coder · Inspector · Browser · MeditatorOrchestrator · DevOps · Reviewer · Blogger · Executor

一条铁律：裂变复制的是执行能力，不是"唯一权威"的语义。Reviewer 的裁决、Orchestrator 的使命、Manager 的终局，永远是单一逻辑所有者——用类型化的运行时闸门守住，不靠提醒。

它想解决什么

今天的 Manager 已经鼓励细粒度并发，但一个被摊上大任务的单个 worker 仍可能串行：A 做完才能做 B。Fission 让"要不要横向展开"的决定权落在当前 Agent 手里，而不是逼上级预先知道内部结构。

上级决定"要什么"，当前 Agent 决定"怎么干得更快"——局部自治被还给了每一个 Agent。

为什么被按下暂停

Fission 最硬的技术难题：同一个逻辑 Agent，不能真的让同一个物理会话并发跑三条流——那会撞碎现有"单线程序列泵"的铁律。它需要为每条 lane 建立隐藏的物理执行上下文，同时让逻辑身份完全不变。方案很清晰，但工程量很大。

所以它此刻安静地躺在 blocked for now 抽屉里。等真正动手那天，第一件事不是写代码，而是先做八个事实调查 canary——先证明 Host 能力，再谈生产。
