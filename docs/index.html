第 1 篇 · 这是什么？

1. 一句话定义

万象术（Wanxiangshu）是一块给 AI 编程助手装上"公司大脑"的引擎——它把一次单一会话，拆成一支分工明确、互相审查、记忆持久的智能团队。

它不是换一个更聪明的模型，而是让"聪明"被组织起来。就像一个指挥机关负责拆任务、派活、收割；隐藏 review 负责在合格证据上把关；记忆侧车负责把马拉松任务的历史压缩保鲜；durable event substrate 则保证哪怕进程崩溃，已发生事实仍可重放，普通程序可以从可信世界重新进入，而不是猜测性“复活”旧 continuation。

对象依然是那个熟悉的 AI 编程终端（OpenCode），但工作的方式变了。

换一个比喻

过去：一个全能的"一个人公司"，同时做 CEO、工程师、情报员、QA、档案员。上下文一长就顾此失彼。

现在：一支整建制作战的团队。每个人只做自己最擅长的一件事，角色之间上下文互不污染。

它解决什么

长任务的失忆——上下文再多也能记住开头给你的那句话。
自审的失效——让写代码的人审自己的代码，等于让学生自己判卷。万象术动用看不见的评审团。
单点的故障——模型卡死、死循环、答非所问，有备用模型和事件账本兜底。

3. 单个助手为什么会半途而废

把无数失败的 AI 编程任务归拢，其实只有三个根因。看懂它们，就懂了万象术为什么存在。

弱点一：上下文会爆炸

模型的"窗口"有限。任务越长，塞进窗口的历史越多，直到某天开头那个最关键的"你要我做什么"被挤出去。长任务越做越像失去目标。

不是模型不够聪明，是它"记不住自己本来要干嘛"。

弱点二：自审会失效

让写代码的同一个模型去检查自己的代码，等于让学生自己判卷。它对自己的产出有天然的"确认偏误"，很容易说"没问题"。

质量需要一双不在场的眼睛。

弱点三：单点会故障

一个模型卡死、陷入死循环输出、或干脆答非所问，整个任务就陪葬。没有备用、没有刹车、没有倒带。

把鸡蛋放在一个篮子里，篮子的命运就是任务的命运。

万象术的三个答案

弱点答案
上下文爆炸记忆侧车 + 前缀重建（第 3 篇）
自审失效隐藏评审团 + Magic Todo（第 4 篇）
单点故障备用模型 + 死循环刹车 + 事件账本（第 5 篇）

4. 十个核心机制总览

2026-08-18 的万象术已经不能再用旧版“七张王牌”概括。下面十个机制最能帮助第一次阅读的人建立当前世界模型。它们不是十个互相独立的 feature，而是共同约束身份、权限、记忆、并行、失败、恢复与终局的一整套行为。

1. 团队分工 · 二十个 Agent 十个角色 × 快/深两个型号。每个人各司其职，权限边界像保险柜一样清晰。
2. 马拉松记忆 · 上下文恢复 工作日志侧车 + 前缀重建，长任务不再失忆。
3. 自我审查 · Glory 终局 隐藏评审团用八大质量支柱把关，交付前必须被证明，而不是"我觉得行了"。
4. 持续义务 · Magic Todo / Obligation Ledger 一份事实性的“仍欠世界什么”账本持续更新；它帮助推进与评审，但不再被误写成终局的机械 checklist 门。
5. 可靠兜底 · Fallback + Loop 备用模型 + 死循环刹车，模型挂了任务不陪葬。
6. 崩溃重入 · Durable Facts + /continue 一切事实写入耐久账本；进程死后只依据 durable facts 与可信物理观察重入普通程序。未完成工具不会被插件加载或普通 hook 自动“复活”。
7. 快与省 · Strength / Casebook / JS Tools 便宜的模型预读暖场、经验缓存复用、批处理一次搞定——快是设计，不是补丁。
8. 同一人并行 · Fission 同一个 logical participant 可以展开多个 coequal execution presents；不新造 participant、不新造 parent obligation，最后仍只完成一次。
9. Agent 与物理模型解耦 · Execution Model Routing Fast/Deep 描述的是同一岗位的执行方式，不是固定模型名；真正用哪款模型会结合岗位与当前占用再决定。
10. 信息克制 · Horizon / Projection 内部机器状态不会整包倒进上下文；只有会改变下一步的事实才被翻译成自然语言或结构化结果，展示本身也不会凭空创造授权。
分发闭环 v0.8.2：dist/OpenCode/Plugin/Plugin.js + resources/ 单点闭包；PackageResources 以 import.meta.url 定位资源，不依赖 process.cwd()；files: ["dist/","resources/"] 白名单隔离源码。见 distribution。

5. 这一版和旧 wiki 最大的不同

如果你读过旧版文档，最危险的不是少记了几个新名词，而是用旧的心智模型理解新的行为。这次更新把近几轮设计演进重新翻译成用户视角：哪些能力现在真的存在、你会看到什么、系统在失败时会怎么做、哪些“看起来方便”的自动行为反而被刻意禁止。

下面十条可以当成新版的迁移指南。它们不要求你知道内部模块名；只要记住行为边界，就不会被旧文档带偏。

十个最值得重新认识的变化

旧说法现在你应该这样理解
Fission 还是“以后也许会做”的实验它现在是正式能力：同一个 Agent 可以把自己的工作横向展开成多个并行执行面，最后仍只向上级交付一次。它不是 fork，也不会凭空制造多个“人”。
Fast / Deep 就是两个固定模型它们首先表示同一岗位的两种执行绑定。真正使用哪个物理模型会结合当前负载再决定，所以“换执行绑定”不等于“换身份”，也不一定等于“换到另一款模型”。
崩溃后系统会自动把旧工作原样复活不会。系统保留已经发生的事实，但不会偷偷重跑上次未完成的工具或副作用。想继续旧会话时，用显式 /continue；系统会基于现状重新判断，而不是盲目接着跑。
Manager 只会被“继续推进”提醒一两次每一次新的完整停顿都可以得到新的继续机会。系统只防同一次停顿被重复注入，不会因为早先提醒过就永久沉默。
Todo 就是一张 pending / completed 状态表现在更像“当前欠债清单”：每次提交的是完整的当前义务账户，写清还欠什么、当前在做什么。UI 里的状态只是兼容显示，不是任务真相，也不是终局按钮。
记忆侧车想写几次摘要都行记忆更新被收紧成一轮一个明确观察，避免同一轮被重复计数或模糊合并。对你来说，结果是长任务记忆更可追溯、重建边界更稳定。
Strength 只是“后台预取一点文本”它现在是一条真正的影子调查执行：可以真实做只读预查，但主任务不等待它；只有结果被主任务在正确时机真正接纳后，它才算进入正式历史。
系统靠很多隐藏阶段和状态机“记住下一步”现在更强调从事实重新判断下一步，而不是持久化一个隐藏的“下一步该跑哪段”状态。对用户的意义是：恢复时更少猜测，更少因为内部阶段错位而卡死。
Browser 查到网上有个说法，就等于本地项目需要处理它外部资料必须保留来源、质量与分歧；“网上存在这种可能”不会自动变成你仓库里的事实或待办。
“Blessed” 就等于任务已经结束第一次通过终局审查只是获得 Blessing：仍可继续处理小尾巴。第二次明确结束才进入 rest，最终用户看到的答案就是 Manager 当时写下的最后话。

读新版时最重要的一条原则

不要把内部名字当产品行为。Life、Participant、WorkRecord、Finality 这些词只是帮助解释边界；你真正需要关心的是：谁有权做什么、什么信息会被保留、什么时候系统会等待、什么时候会拒绝、失败后哪些动作绝不会被偷偷重复。

新版文档的目标不是让你学会仓库内部结构，而是让你能准确预测 Wanxiangshu 会怎么行动。

1. 快与深：角色双胞胎

万象术里每个角色都有两个孪生型号：

Fast · 快版
便宜 敏捷 适合热身的机械活
Deep · 深版
昂贵 缜密 适合关键判断与终局

关键在于：Fast/Deep 改变的是 ExecutionBinding，不改变 Role、Persona、authority 或 office entitlement。 同一个岗位必须暴露同构的 capability；tier 不能偷偷给一个角色增加权限。

还要再分开一层：EffectiveAgent 也不等于 physical model。 provider-attempt-recovery 可以在同角色的 A/B execution binding 之间切换；真正发给哪个物理模型，由唯一 execution-model-routing scheduler 在 chat.message 前按 role 与当前 running leases 决定。两个 execution binding 完全可能被路由到同一个 physical model。

Fast/Deep 是同一个 office 的执行绑定；ModelTarget 是另一层物理调度。换机器不等于换人，换人更不等于换权威。

2. 指挥层：Orchestrator / Manager

Orchestrator · 总指挥

只做一件事：把整个仓库级的大任务托付给项目经理，并负责最后一公里的发布闭环——把开发成果重新合入目标分支前，还要经过一次严格的复查。

它不写代码、不改文件，它只负责"这个项目该由谁来做、做完了怎么安全地上线"。

Manager · 项目经理

万象术真正的"大脑中枢"。它遵循一个铁律：

Manager 自己永远不亲手写代码。

它只做四件事：

  • 拆解——把大任务拆成可以独立推进的小任务；
  • 派活——fork 出工程师、情报员、运维等，各自开工；
  • 收割——join 收回他们完成的成果；
  • 维护清单——用 todowrite 维护一份永远真实的 todo 清单。

当前 Role Law 对 Manager 还有两个容易被旧文档漏掉的纪律。第一，ready frontier 要连续填充：不要把并发工作组织成“这一波全部结束，再开下一波”的 wave/barrier；每拿到一个结果就重新计算 ready frontier，有空位就继续发。第二，delegation surface 上的 expected_tool_calls 只是校准提示：显式值替换估计、真实工具调用递减、缺省保留已有估计，但它绝不是执行上限。

Manager 看不见隐藏 review 的编排拓扑。它无需知道 reviewer roster、barrier、witness、cohort 等机器机制；这些不是 Manager 的 checklist。它看到的是足以改变合法下一行动的最小后果。

3. 执行层：Coder · Inspector · DevOps · Browser

执行层是真正"动手"的角色，每个都有严格的权限边界。

角色能做什么红线
Coder · 工程师repository programming、读写改移删、结构化搜索，以及被明确授权的代码变换仓库 mutation 必须走 capability-projected、sandboxed、all-or-nothing 的正式 surface；不能把 query-shell 当执行
Inspector · 情报员本地 repository investigation：read / glob / grep 等真实 observation只读；reasoning 不能冒充 evidence acquisition，历史 hint 不能冒充当前证明
DevOps · 运维真实 command / PTY / signal / completion observationexecution 必须 bounded、可终止；kill 不等于 physical exit，非零退出是结果不是“工具异常”
Browser · 浏览器public-web external investigation，保留 provenance、source quality 与 disagreement不能把公网可达性偷换成本地 repository 事实或自动产生本地 obligation

这套设计最硬的地方在于：Agent 看得见的能力，和系统真正允许它执行的能力必须一致。 请求可以临时收窄权限，但不能把岗位原本没有的权力凭空加出来；Fast/Deep 也不能改变权限。只靠提示词说“不要越权”不算真正的权限边界。

bash-honeypot · 蜜罐探针

旧 wiki 喜欢把某些 surface 写成“假终端教育模型”，当前合同更严格：工具名就是 semantic act。 run 表示真实 act / economic commitment；query-shell 只允许 observation。不能用同一个工具名在不同角色身上偷偷改变含义，也不能把“调用了一个工具”降格为预测。

第 2 篇 · 这支团队

4. 思考层：Inquiry · 研究员

Inquiry 是万象术里把“提出解释”和“获得证据”刻意拆开的角色。旧文档称它 Meditator；当前 canonical Role 名为 Inquiry。

Inquiry 可以形成认识、提出反例与调查问题；真正的 repository observation 仍必须由有相应 authority 的调查角色取得。

它只做四件事：

  • 形成理解——清楚地说出"我现在是怎么理解的"；
  • 找反例——主动问"什么情况下我这个理解是错的"；
  • 提出追问——把事实问题交给 Inspector，拿到答案继续追；
  • 区分证据与推论——说清楚哪些是看到的，哪些是猜的，哪些还不确定。

这是一种刻意的认识论分工：proposal / evidence / uncertainty 必须可区分。 外部信息动作受 capability 与 horizon 约束，停止也属于策略的一部分；“我觉得仓库大概是这样”永远不能被提升成 observation。

第 2 篇 · 这支团队

5. 质量层：Reviewer · 评审员

Reviewer 是万象术质量体系的守门人，被设计成一个不可绕过、不可收买的角色。

权限

只读工具（读文件、查目录、搜代码）+ 一个裁决工具：

judge("PERFECT")   # 当前没有发现足以扣住 acceptance 的实质缺陷
judge("REVISE")    # acceptance 被扣住，因为仍欠一件实质之物

judge 只接受 typed enum PERFECT | REVISE，没有 description 参数；成功回执也不会 echo verdict，避免模型把“裁决”误解成“写入某个可回声状态”。旧工具名 verdict 已无 alias。

关键：它看不见经理，经理也看不见它

Reviewer 是隐藏的。Manager 不知道评审团是谁、有几个、什么时候查。这样评审员不会被"项目经理的脸色"影响，也不会被"再跑一次测试"糊弄过去。

质量门不是可勾选的步骤，而是不可见的命运。

Reviewer 在裁决前要从 Examiner's Ledger 的八个方向完成思考（详见第 4 篇），但 Ledger 不是 checklist，也不是八项打分表。PERFECT 不表示“字面无瑕/全知全能”，而表示当前没有发现足以合理扣住 acceptance 的 material defect；真实 minor workmanship 可以与 PERFECT 共存，但不能因此被隐瞒。

第 2 篇 · 这支团队

6. 记忆层：Blogger / Distiller

Blogger · 档案员

主工作会话会配一辆 Companion 记忆侧车；Blogger 把已经发生的语义历史压成可复用 frame。后台附属会话是否需要自己的 Companion 取决于它承担什么工作，因此不能再笼统写成“每个 session 都有一个影子档案员”。

Blogger 的 cycle 合同现在非常严格：每个 Blogger provider run 恰好一次 chronicle。0 次或两次以上都不是“之后再合并”——而是 invalid cycle，进入有界协议修复。一次有效 cycle 原子地产生一个 BlogObservationCommitted；tip 与 frame 是同一份不可拆 observation。

Distiller · 输出蒸馏

Distiller 不是旧 wiki 所说的“没有工具、纯粹执行指定动作”的 Executor。它的 WHY 是处理过大的真实执行输出：在不发明因果、不把 fragment 冒充整体成功的前提下，把大输出压成有损但诚实、可继续使用的 observation。真实 process completion 仍由 process-execution 的 backend exit 事实定义。

"内部人"对用户不可见

Blogger、Distiller、Companion、Bookkeeper、StrengthReplica 等内部拓扑不能被粗暴投影成 provider-visible 状态 DTO。participant horizon 只允许会改变合法行动的最小事实穿过去；隐藏机制本身不是知识奖励。

第 2 篇 · 这支团队

7. 同一人，多执行面：Fission

Fission 已经不是提案。 它现在是正式能力：同一个 logical participant 可以拥有多个对等执行面，同时保持一份 identity、authority、responsibility 与最终 completion。

Fission 的核心不是“多 fork 几个 Agent”，而是：同一个 Agent 在不分裂身份、权限和责任的前提下，暂时拥有多个对等执行面。 对上级来说，它仍然只是一个下属、一份责任、一次最终完成。

调用面与准入

fission("lane A\nlane B\nlane C")
  • 输入按 newline 做 canonical parse，至少两条 lane，空 lane 非法；除 newline normalization 外保留 prompt bytes；
  • 只允许 physical subsession origin；user-facing/root caller 在 reserve、建 LWR、建 session、interrupt 之前就拒绝；
  • V1 同一 participant 同时只允许一个 active fission group，不允许 recursive fission；
  • 当前允许裂变的岗位是 Manager、Coder、Inspector、Browser、Inquiry；Orchestrator、DevOps、Reviewer、Blogger、Distiller 明确不裂。

物理上必须分 session，逻辑上仍是一个人

同一个 Host SessionId 不能承载多条并发 provider stream，所以每条 lane 都创建 fresh sibling Host session；它们的 Host parent 都等于旧 caller 的 parent，而不是互相嵌套。只有所有 lane 都成功 start 后，旧 present 才被 Fission-owned silent interrupt。这个 admission 是 all-or-none：不能裂出半支队伍后假装成功。

完成怎样不丢、不重

裂变前已经在飞的 child/PTY completion，会 exactly-once broadcast 给所有 lane；裂变后产生的 completion 则 lane-affine。各 lane 输出用 lane index 做 keyed work convergence：同 key/ref/digest 的 replay 幂等，内容冲突 fail closed。只有全部 records / deliveries 都被 accounting 后，才填回原 participant 那一个 completion cell。

崩溃不等于自动重建 Fission

Fission tool crash 不会在 plugin init、普通 hook、普通 session ingress 时自动 reconstruct。durable facts 留下可审计证据；只有显式 /continue 才可以向用户暴露并决定 surviving lanes 的后续。这个边界与整个 crash-reconciliation 的“事实恢复，不恢复旧 continuation”保持一致。

fork 创造新的 participant obligation；fission 只复制当前 participant 的执行面。一个是组织拓扑，一个是同一人的局部并行。

第 3 篇 · 马拉松记忆

1. 上下文会爆

模型有一个硬约束：处理一次对话时，能同时"看见"的上下文是有限的——就像一个桌面，一次只能摊开这么多文件。

长任务遇到的困境是：

  • 历史越积越多，桌面越来越满；
  • 到某个临界点，最老的关键信息（尤其是任务开头那句要求）被挤下桌面；
  • 模型开始"忘了自己要干嘛"，质量断崖式下跌。

常见的解法是"换更大的窗口"——但那只把问题往后推，还贵。万象术的答案完全不同：

不是把窗口变大，而是把历史整理好。

它把"记什么"和"怎么留得住"当成一个工程技术问题来设计，而不是赌模型窗口够大。

第 3 篇 · 马拉松记忆

2. 工作日志侧车

解决失忆的核心，是一辆"记忆侧车"（Companion / Blogger）。

工作方式：

  • 主会话 X 保留一份永不删除的原始轨迹（append-only，只增不减）；
  • 侧车 Y 把已完成的片段压缩成工作日志帧，占据的窗口小得多；
  • 当需要继续时，主会话从「压缩帧 + 未压缩的尾巴」重建当前状态——既省窗口，又不丢关键信息。

不是“定时做摘要”，而是持续追赶同一条 live execution

当前 context-compression 明确禁止把 Blogger catch-up 写成“先冻结一个 drain frontier，追到那里就结束”。只要同一 live execution 还活着，Blogger 在安静时可以 park；后续又出现新的 material，就唤醒同一个 continuation继续追赶。只有 process death 才真正打断这条 process-local continuation；跨进程不会悄悄自动 resume。

同时，Blogger provider run 的协议也从旧版“多次 blog 再 merge”收紧为 exact-one：每个 provider run 必须恰好一次 chronicle。有效 chronicle 原子地产生 observation，历史压缩本身不能凭空创造新的 diagnosis occurrence。

底层有一句很朴素的话：

信息只在被妥善整理时，才谈得上"记住"。

第 3 篇 · 马拉松记忆

3. 前缀重建：失败成为恢复的起点

上下文恢复的哲学只有四个字：不预测，只恢复。

很多系统会提前"猜"哪一段历史该压缩——按 token 数、按比例、按窗口快满没满。万象术拒绝这种猜测：context compression 是 failure-driven 的，不允许因为“看起来快满了”就擅自改历史。 当前输入侧还有明确的 200 KiB delta trigger；它不是一个 output budget，也不允许靠文字分类决定是否压缩。

机制是这样：

  • 平时正常干活，绝不主动压缩；
  • 当一次 provider 请求真的失败且 recovery slot 条件成立，才允许构造 candidate；
  • 恢复槽里，用侧车已经压好的日志，冻结一段稳定的历史前缀，让后续请求从这份前缀继续；
  • candidate 必须比已提交状态严格更新，且只能吸收属于自己 causal range 的 frame；未满足提交条件就不能覆盖旧前缀。
恢复槽仍是证据门，不是 token 预测器
有失败触发 真有可压缩的材料 candidate 严格更新 Opening floor 不被越过

一个关键承诺：前缀逐字节稳定

一旦冻结，这段前缀在后续请求里必须逐字节一模一样——这是让模型自身的缓存能无缝衔接的前提。可以说：

$$S'=\mathrm{Closure}(S\oplus Y)$$

吸收新信息后先全局收敛，再允许下一步。任何"差一点"都不行，失配就 fail closed。

第一次失败是代价，失败之后有路可走是设计。

第 3 篇 · 马拉松记忆

4. 永不遗忘的 Opening

旧 wiki 把 Opening 简化成“任务最初那句要求”。当前 work-record 的定义更精确：Opening 是一个 canonical semantic interval，而不是一条随便挑出来的 user message。

第一次被接受的 planComplete=true BlindPlan checkpoint（T1）的 tool call + result 是 Opening 的构成性边界；在 T1 之前已经发生的 planComplete=false checkpoints 也属于 Opening。

Opening 保留的是这个 XTrace interval 的原始语义，不允许根据“我现在记得的大意”重写。它在 parent→child 的工作委派投影里需要保留；child→parent、review、finality、sync 等不同投影则按 includeOpening 合同明确决定是否携带。换句话说，Opening 属于 work record，不属于某个 receiver 的偏好。

为什么这么固执？因为压缩的本质是有损，最危险的有损不是少了某个日志细节，而是把“最初接受了什么计划、以什么边界开始这段工作”重写成事后叙事。

WorkRecord 由三块构成，且一份 invocation 只 materialize 一次：

层作用能否压缩
Opening?T1 及其之前的构成性工作起点；某些投影可按合同省略原始 XTrace interval，不重构
Chronicle已由语义记忆覆盖的 bounded 工作陈述允许有损，但必须诚实且受 causal range 约束
Recent尚未进入 Chronicle 的当前尾部；formal statement 的最后 assistant text 也在这里保留当前必要语义，不把 raw tool transcript 当报告 DTO

WorkRecord 没有固定的 Summary / Files / Risks 模板，也没有一个额外 Closing report。它是 bounded canonical statement，而不是把 session head 随手总结一遍。

第 4 篇 · 自我审查与完成

1. 完成不是"我觉得做完了"

普通 AI 助手最大的毛病之一，是自认为完成就交差。它干了活，自己觉得挺好，就宣布"做完了"——没有人复查，也没有人否决。

万象术把"完成"从一种自我感觉，变成一道不可绕过的门：

  • Manager 不能随随便便宣布结束；
  • 它必须显式地"请求终结"；
  • 只有隐藏评审团真正验收通过，才算数。

这套机制有一个很美的名字——Glory（光荣落幕）。

它的来源是角色的彻底分离：写代码的是 Coder，审代码的是另一个看不见的 Reviewer。让"生产者"和"裁判"互不认识，是断绝"自己判自己卷"最干净的办法。

完成必须被证明，而不是被宣称。

第 4 篇 · 自我审查与完成

2. Magic Todo：持续检查点

Manager 手里维护一份活的 obligation ledger，todowrite 是它的重要投影面之一。它记录“现在仍欠世界什么”，而不是把任务伪装成一个隐藏的 workflow program counter。

当前 wire：完整 obligation account，不是 patch-list

todowrite(
  planComplete: bool,
  workingOn: string,
  obligations: [{ name: string, work: string }]
)

CurrentObligations = last accepted obligations list

每一次被接受的调用都提交一份完整当前账，并 supersede 上一份 account。name 在同一 obligation 存续期间保持稳定，work 说明“还欠什么”；真的 discharge 了就移除，尚未 earned 的就必须保留。workingOn 只是当前实际 focus，经边界归一化后精确指向某个 obligation name；它不成为 obligation status，也不进入 CurrentObligations。

明确禁止 status 机器

当前规范反而明确禁止 provider-visible pending / in_progress / reviewing / completed 这类 status 枚举来伪装进度。OpenCode Host 的 TodoTable 为兼容 UI 仍可能把 workingOn 对应行投影成 in_progress、其它行投影成 pending，但那只是 compatibility sink，绝不能反向恢复或推断 canonical obligation truth。

Canonical truth 是“现在还欠哪些具体结果”，不是“系统觉得自己处于哪个阶段”。

T1：从诚实规划切到 committed mission debt

每次调用都显式携带 planComplete。本 Life 第一次被接受的 planComplete=true 是不可逆 T1 commitment；之后即使 provider raw input 又写 false，effective commitment 仍保持 true。

  • T1 之前：调查仓库、形成计划、解决不确定性等 planning work 可以诚实出现在 obligations 中，只要它们确实描述“为了完成计划还欠什么”；
  • T1 之后：不能再把“让我再想想下一步”“整理一下清单”伪装成 mission debt。每项 obligation 必须指向用户世界/交付物仍欠的结果、修复或证据。

这个 commitment 也是 WorkRecord Opening 的边界：Pre-T1 checkpoints 都属于尚未关闭的 Opening，T1 的 accepted checkpoint 把计划承诺钉住。

每次正式更新清单，都会产生一份过程评审

Manager 每提交一份新的完整 obligation account，系统都会把它当成一个检查点：上一阶段做得怎样、这份“还欠什么”的账是否诚实，都要由独立 Reviewer 看一眼。

下一次更新清单前，通常要先吸收上一份过程评审；如果 Manager 已经准备进入终局，终局入口会负责把最后一份尚未消费的过程评审收干净。系统不会为了“刷新一下评审状态”而额外制造一条新的 todo 更新，因为那反而会凭空多出一个检查点。

同一个 Manager 生命周期会尽量复用同一位专门的过程 Reviewer；只有能确认它永久失效时才更换。这样前后评审有连续性，但 Reviewer 仍然不成为 Manager 的下属或可见成员。

Todo 不是 Finality 的机械门

Finality 明确不以“所有 Todo 都显示 completed”为结束条件。 当前 obligations 只是终局判断的一部分；系统还会看当前工作树、审查证据、是否仍有未归队的工作等。

实践上，当现实或当前 focus 已经变化，Manager 应先把清单改成真实情况，再继续做下一件实质工作。目的不是频繁刷状态，而是避免团队拿着一份已经失真的债务表继续行动。

Magic Todo 的魔法不在“状态更多”，恰恰在于删除状态幻觉：只记当前欠债、计划是否已经承诺、以及每次账本更新产生的真实 review obligation。

第 4 篇 · 自我审查与完成

3. 隐藏评审团与八大质量支柱

当 Manager 认为任务完成、请求终结时，一支隐藏的评审团被默默召集。

旧 wiki 把终局评审写成“固定一小队快/深 Reviewer，每人做两次确认”。现在更准确的理解是：评审历史会连续积累，但每次终局请求仍要引入新的独立判断。 日常的过程评审和真正的终局评审是两种不同证据，前者不能直接冒充后者。

“Reviewer 说 PERFECT”本身也不够。终局确认还要求证据对应当前工作、当前版本，而且第二次确认必须建立在一次真实的 challenge 之后，而不是同一条回复里重复喊两遍 PERFECT。

  • 进入终局前，最后一份过程评审先被收干净；如果它要求 REVISE，就直接返工，不继续假装“已经进入终局”。
  • REVISE 不只是一个红灯，还必须带回足够具体的工作记录，让 Manager 知道哪里需要重做。
  • 过程评审即使刚给了 PERFECT，终局仍需要自己的新鲜确认；两种 acceptance 不能互相借用。
  • 当前工作树一旦发生实质变化，旧终局确认就只能留作历史，不能继续拿来证明新版本。

评审不看"测试过没过"这么简单，而是对照八大质量支柱：

八大质量支柱
语言与算法 极致简洁 结构优雅 有界粒度 测试覆盖 无瑕逻辑 调用方体验 完整性

八个方向不是机械 checklist。REVISE 必须“买到”实质更好或更真的结果：未满足 material obligation、重要 claim 缺证据、阻断性 correctness/safety/boundary defect 等才正当扣住 acceptance。轻微 typo、纯偏好、表演式谨慎不能因为“更严格看起来更专业”就自动升级成 REVISE；反过来，PERFECT 也不能压住真实的 non-blocking 观察。

过程评审一次明确裁决就可以结束；终局评审才需要“双 PERFECT + 真实 challenge”的更高确认强度。第一次 PERFECT 之后，Reviewer 会收到一次真正的质疑与复核机会；只有在这个 challenge 已经真实返回之后，另一轮独立裁决仍然是 PERFECT，系统才把它当成确认。可信度来自真实先后关系，而不是某段固定文案。

第 4 篇 · 自我审查与完成

4. 死于荣耀：最后的话

整个终局流程，被设计成一场庄重的仪式。

第一次请求终结

Manager 认为任务做完了，调用 suicide——并写下它的遗言（last_words），一段它认为任务已经完成的最后总结。

隐藏评审团随即启动。两种结局：

  • 返工（REVISE）——评审员带着一条精确的、不可伪造的"工作记录"返回，指出哪里还没完成。Manager 收起面子，拿着证据继续干活。不丢脸，只是还没到终点。
  • 祝福（Blessed）——评审全员通过。Manager 获得"祝福"，但还没结束：它被要求继续处理清单里所有零散的修补、遗留的疑虑和小的清理。

第二次请求终结

所有收尾都干净之后，Manager 第二次请求终结。这一次：

  • 不读工作树、不另请评审、不检查见证——前一次已经证明过了；
  • 写下最后的遗言，系统注册终局，向用户交付；
  • 工具结果固定包含一句 "rest in peace"（安息吧）。

用户拿到的最终答案，逐字等于 Manager 第二次写下的遗言——系统不加任何额外注解。

当前 Finality 的关键变化：第一次请求终局之前，系统先把最后一份过程评审收干净；如果它要求返工，就直接把证据交回 Manager。评审通过得到 Blessing 也不会立刻结束任务，而是允许继续处理小尾巴。第二次明确请求结束才进入 rest。整个流程没有“Todo 全打勾就自动过关”的机械按钮。

Manager 停下来时的继续提醒也不再有“这个任务一生只提醒几次”的限制。系统只避免同一次停顿被重复提醒；每一次新的完整停顿都可以获得新的继续机会，因此长任务不会因为早先已经提醒过而永久沉默。

任务不是被"发走了"，而是被"善终"了。

第 5 篇 · 可靠与敏捷

1. 备用模型：Fallback

模型会失败，这是必然。万象术不假装它不会，而是把失败设计成可优雅处理的流程。

A/B 同岗位切换 + 预算熔断

每个岗位都有 Fast/Deep 两个执行绑定。当一次模型尝试被确认失败后，系统会在当前执行绑定 / 同岗位的另一侧之间有界切换：

A 侧失败 → 换 B 侧 B 侧失败 → 回 A 侧 连续失败累计 达到预算 → 熔断

交替本身是合法探索，真正的底线是有限恢复预算。达到预算后就停止自动烧下去，等待新的工作或明确介入；一次成功会清掉连续失败计数，同一个失败也不会被重复记账。

切换是策略，熔断是底线。绝不无限烧下去。

换执行方式，不换身份

Fallback 不改变角色、人格、语言、任务目标或用户授权。真正使用哪一款物理模型仍由独立的负载调度决定，所以 A/B 两侧甚至可能在某些时刻落到同一款模型。

系统也不会把所有异常现象都粗暴计入 fallback：Host 主动中断、旧工具残留、空白回复、Strength 影子调查失败都有各自语义，不能污染主任务的失败账。

第 5 篇 · 可靠与敏捷

2. 死循环刹车：Loop

大模型偶尔会"退化"：输出变成一个字符、一个短语、或一整句反复循环，长度惊人、内容毫无新意。让它跑完只是浪费时间、污染对话尾部。

万象术装了一个实时传感器：它一边看着正在流出的文字，一边实时计算"这段输出到底有多多样"。

关键指标：N_eff

系统把输出切成一个个小片段，测算"相当于多少个不同的片段"。正常代码多样性很高；死循环的多样性断崖式下跌。

$$N_{\mathrm{eff}}=\frac{1}{\sum_i p_i^{2}}$$

当 N_eff 跌到阈值以下：

  • 立即中止这次荒谬的生成（像汽车气囊，平时绝不介入，关键时刻一次救场）；
  • 把这次中止当成一次"可恢复的失败"，交给备用模型流程接管。

它绝不基于"角色、模型、代码还是闲聊"动态改阈值——对所有情况一视同仁，保证可测、可预期。

第 5 篇 · 可靠与敏捷

3. 崩溃恢复：耐久事实 + 显式 /continue

程序会崩溃、进程会死、插件会重新加载。当前设计刻意不再说“世界原样复活”，因为这句话很容易让人误以为旧的未完成动作也会自动接着跑。万象术真正承诺的是：已经发生的重要事实不丢，恢复时只依据这些事实与当前现实重新判断下一步。

只追加，不修改

重要事实进入本地 append-only 事件流：只往后写，不回头改。同步到 Git 是独立动作，不会让每次普通事件记录都变成一次 Git 写入。

  • 只能往末尾追加，从不能修改或删除历史；
  • 每一条自包含、有版本、可校验；
  • 启动时与运行时都用同一套规则解释这些事实，避免“重启前一种世界、重启后一种世界”。

崩溃之后，恢复“事实”，不恢复旧程序计数器

  • 临时内存不算恢复依据；只相信已经持久化的事实与当前能观察到的现实；
  • 某个外部动作结果未知时，先核对现实，不能因为“没看到成功记录”就自动做第二次；
  • 插件启动只负责把系统准备好，不会顺手扫描旧会话并替你续跑；
  • 普通新消息、普通工具调用也不会把上次进程遗留的未完成工具重新执行；
  • 只有用户显式输入 /continue，系统才会整理旧会话的已知事实，并基于现在的世界决定怎么继续。

崩溃恢复的核心不是“续播旧动作”，而是“事实仍在，所以可以从可信世界重新开始”。

合并与收敛

多个实例可能各自推进，账本用"集合求并"合并——谁都不覆盖谁，冲突被显式表达，再通过后续事件收敛。绝不用"谁时间戳晚谁赢"这种粗暴规则。

外部副作用也记账

连"创建临时目录""发布到分支"这类外部动作，都遵循"先请求→后确认"的记账：崩溃后先核对现实发生了没有，再决定收尾。绝不"内存里觉得做了就以为做了"。

第 5 篇 · 可靠与敏捷

4. 预读加速：Strength

深模型干活前，常常要先做一堆机械的只读调查：读几个文件、查几个目录、搜几个关键词。这些活本身不难，但让昂贵的深模型亲力亲为，很浪费。

让便宜的先暖场

Strength 的思路很朴素：只在适合的主任务里，让同岗位的 Fast 一侧做一次可丢弃的只读预查。它不是“所有 Deep 回复前都自动跑一遍”，也不会在 fallback、返工、Reviewer 或其它后台叶子任务上无限套娃。

  • 预读只做只读调查——读文件、查目录、搜代码；绝不写文件、绝不执行命令、绝不碰权限；
  • 它是一条真实的影子会话，继承主任务的岗位、人格与语言，只换成更便宜的执行侧；
  • 预读结果一开始只是候选材料，只有主任务真的走到接纳它的那一轮，才进入正式历史；中途失败或被取消的影子结果不会污染主任务；
  • 全程可审计、可熔断、可关闭。

三档预算

K0 / K1 / K2 表示影子调查最多允许发起 0 / 1 / 2 轮模型请求，不是工具调用次数。K0 或关闭 Strength 时，主任务的行为应该和“系统没有这项能力”一样，不留下隐藏副作用。

DryRun 不是假跑

DryRun 仍会真实启动一条可见的影子会话，并得到自己的结束或超时结果；但主任务不会等待它完成，它的结果也永远不会晋升进正式历史。它更像“观察这套加速机制本身会怎么跑”，而不是偷偷预写答案。

便宜的活让便宜的机器干，贵的机器只干它贵的活。

第 5 篇 · 可靠与敏捷

5. 经验缓存：Casebook

调查是一次性的吗？过去是：Inspector 查完一个问题，答案就散落在对话里，下次再问同样的问题，又要全部重查一遍。

Casebook 让调查可以复用：

  • 把「问题 → 调查动作 → 答案」缓存成一个可重放的经验条目；
  • 下次遇到相同问题，先针对当前代码重放那次调查；
  • 如果没发现相关证据变化 → 返回原来的标准答案，同时明确“未发现变化”；
  • 如果发现变化 → 尝试刷新答案；刷新成功就给新版，刷新失败则仍可返回旧答案，但必须明确它是一份较旧的记录。

新手艺：它判断"有没有 evidence delta"，不是看 timestamp，也不看 commit history。更关键的是，no-delta 只是一条 freshness hint，不是正确性证明；重放结果或内部事件顺序都不能把缓存答案升级成当前事实。

Casebook 可以诚实地“有点旧”，不能不诚实地“假装已验证”。

它是尽力而为的经验缓存，不是知识数据库。维护失败不等于“这份经验从此不可用”；允许诚实地返回旧答案，比假装“已重新验证”更重要。后台缓存会自行收尾，意外删除一个缓存会话也只做清理，不会为了缓存本身启动复杂恢复流程。

第 5 篇 · 可靠与敏捷

6. 可编程文件工具：JS Tools

批量改文件，传统做法是反复调用一个个工具，慢且容易出错。JS Tools 给模型一个受权限约束的工作台：

  • 模型可以写一小段脚本，一次完成批量读、批量改、批量写；
  • 脚本里只有系统显式注入的数据，拿不到文件句柄、环境、网络、进程——沙箱隔离；
  • 所有修改先在一个事务里暂存，全部检验通过才一次性提交。

事务的铁律

全有或全无——任何一个文件失败，全部改动一并回滚，绝不留下"改了一半"的仓库。
冲突即止损——某个文件在读取后被外部改过，整个事务作废，不隐式重试。
崩溃不隐式善后——如果修改进行到一半时进程中断，下一次启动不会偷偷 undo / redo / 重跑脚本 / 补提交；只保留“旧工具中断了”和当前磁盘现状，等新的明确意图处理。

这里的“all-or-nothing”也要按真实文件系统能力理解：它保证正常成功 → 全部新状态；正常失败 → 全部旧状态；崩溃 → 后续只能收敛到可证明的完整终态，不声称普通文件系统能让多个路径在同一个 CPU instant 原子变化。正常可观察失败会做 CAS-style rollback，但第三方已经覆盖的内容绝不被强行写回。

同一条回复里可以并行提出多个 JS / 内置工具调用；系统会按确定性顺序逐个提交，每个调用都有自己的事务边界，后一个看到前一个真正提交后的状态。模型不需要自己造锁，也不能自行调用 commit()/rollback()/snapshot() 控制宿主事务。

传统 read/edit/write/glob/grep/patch 与 JS 工作台可以共存，但权限保持一致：一个岗位没有 Edit 权限，就不能借 JS 的 write() 覆盖旧文件来绕过；没有某项能力时，相关方法干脆不会出现在它的工作台里。

一句话：JS Tools 的价值不是“让模型拥有任意 JavaScript 权力”，而是给它一个受岗位权限约束、无环境/网络/进程暗门、可一次完成复杂文件变换的沙箱工作台。
第 5 篇 · 可靠与敏捷

7. 模型路由：Agent ≠ Model

旧文档很容易让人把“Fast / Deep Agent”理解成“固定绑定到两款模型”。现在更准确的理解是：Agent 是岗位与执行身份，模型只是这一轮真正被派到的物理算力。

为什么要拆开

如果角色名直接等于模型名，系统一旦需要负载均衡、故障切换或容量控制，就会被迫“换模型 = 换身份”。这会污染权限、记忆和恢复语义。

Wanxiangshu 因此把两件事分开：

  • Agent 身份决定岗位、人格、语言、权限与这次工作的连续性；
  • 模型路由根据岗位需求与当前占用，决定这一轮实际落到哪款模型。

同一条消息重试，路由要稳定

同一次真实用户消息如果因为传输或 provider 原因需要重试，系统会尽量保持同一份路由绑定，避免重试过程中突然换模型造成行为漂移。

但当同一个会话收到一条新的用户消息时，那就是新的执行机会；旧占用不会因为“这个 session 还活着”就一直霸占容量。

什么时候归还容量

容量只在真正观察到这条回复已经 terminal 时归还。不是“看起来安静了”、也不是固定等几秒就释放。这样可以避免两条真实执行误以为同一份物理容量都空闲。

Fallback、Strength、模型路由各管一层

机制它解决的问题它不会偷管的事
Fast / Deep同一个岗位的两种执行绑定不直接等于某个固定物理模型
Fallback一次模型尝试失败后换同岗位另一侧继续不改变角色、人格或用户授权
Model Routing结合当前占用决定实际使用哪款模型不改变“这个 Agent 是谁”
Strength是否允许一个便宜的只读影子调查不污染主任务的 fallback 与身份

你可以把它理解成：岗位是“谁来负责”，模型是“这一轮借哪台机器干活”。两者分开，系统才既能稳定又能调度。

第 6 篇 · 设计哲学与语义全景

1. 为什么它的行为尽量“端正”

万象术的设计目标不是让内部代码看起来漂亮，而是让用户能预测系统的行为：什么能发生、什么绝不会偷偷发生、失败之后下一步依据什么决定。你不需要知道实现语言，也能感受到下面这些原则。

不可能的组合，尽量从世界里消失

系统会尽量把互相矛盾的状态做成“根本无法同时成立”，而不是先允许它们出现，再靠提示词或临时修补解释。例如主任务与后台附属任务有明确归属；一个 Agent 的角色、人格与当前执行方式也不会被混成一个模糊字符串。

用户感受到的结果是：换模型不等于换人，换执行方式不等于换权限，后台多开一个辅助会话也不等于多出一个新的责任主体。

事实与“下一步”分开

Wanxiangshu 会持久保存“已经发生了什么”，但刻意避免持久保存一个神秘的“下一步必须去哪里”。这意味着崩溃后系统依据事实重新判断，而不是盲目恢复某个半途的内部阶段。

能重放的是事实；未来动作必须重新从事实中得出。

可预见的失败，要说人话

文件不存在、权限不足、进程非零退出、等待超时、目标已改变、外部动作结果未知——这些都属于可以被理解和处理的结果，不应该一股脑伪装成“系统崩了”。

尤其是进程执行：非零退出仍然是一次真实完成；发送 kill 也不等于进程已经退出。系统会尽量把“我发出了动作”和“世界真的发生了什么”分开报告。

每件事只有一个真相来源

Todo 的当前义务来自最后一次被接受的完整账本；角色权限来自 office/capability；外部副作用是否成功来自真实确认；当前模型占用来自 lease；历史记忆来自语义轨迹。不会因为 UI 里还有一个看起来相似的字段，就让那个字段反过来变成第二份真相。

看到一段文字，不代表它自动获得权威

系统会把内部事实转成模型能理解的自然语言、结构化提示或工具结果，但展示只是展示。一段文本被放进上下文，不会因此变成新的用户授权、不会自动创建待办，也不会把缓存答案升级成“当前已验证事实”。

等待要有因果，不靠“差不多等够了”

需要等进程、评审、子任务或外部事件时，系统更偏向等待一个明确的事件：真正完成、真正退出、真正有新结果。时间可以作为有界逃生口，但不会因为“已经过了几秒”就假装某个外部动作一定完成。

隐藏机制尽量不污染你的上下文

你不需要看到内部 session id、review roster、lease 表、companion 拓扑、恢复游标等机器细节。只有当某个事实会改变你或 Agent 的合法下一步时，它才值得穿过边界。

复杂性可以存在于系统内部，但不应该被包装成“更多状态字段”甩给用户。

第 6 篇 · 设计哲学与语义全景

2. 你看到的是语义，不是机器

Wanxiangshu 内部会同时处理会话、子任务、模型选择、审查、记忆、恢复、工具调用和外部进程。如果把这些内部零件原样倒进模型上下文，Agent 很快就会开始“管理机器”，而不是完成你的任务。

所以系统有一条非常强的原则：内部可以复杂，向外只暴露会改变合法行动的那部分意义。

工具说明不是 tooltip，而是动作合同

当 Agent 看见一个工具时，它应该立刻知道三件事：这个动作真正会做什么、明确不会做什么、成功后世界会发生什么变化。比如 inspect 必须明确“调查但不修代码”；真正执行命令的动作也不能被包装成“只是预测一下结果”。

同一个工具名在任何角色手里都必须保持同一个含义。不能今天的 run 真执行，明天换到另一个角色就变成“模拟执行”。如果权限不同，正确做法是不给这个角色那项能力，而不是偷换词义。

看得到的能力，必须真的能执行

如果 Agent 的工具列表里出现了某个动作，系统运行时就必须真的允许它；反过来，没有权限的动作也不能只是“藏起来但底层还能调”。这让权限边界不依赖模型自觉。

Fast / Deep 两档不会改变岗位本身的权限。Coder 无论快版深版都还是 Coder；Reviewer 无论快版深版都不能突然获得写文件能力。

机器拓扑不会伪装成任务事实

内部可能有 Companion、StrengthReplica、Dedicated Reviewer、Fission lanes、多个 Host session，但这些名字本身对任务没有意义。只有它们产生了一个会改变下一步的后果，例如“这个子任务完成了”“这条 review 要返工”“这个外部事实与旧结论冲突”，才会被投影到 Agent 能看见的世界。

用户消息与“系统继续说一句”不是同一件事

一条物理上看起来像 user message 的输入，不一定就拥有真正的用户 authority。系统会区分真正的人类 Root、内部 continuation、Host 内部消息和来源不明的输入；来源不明时默认拒绝升级成授权。

这也是为什么自动 continuation、Manager encouragement、review challenge 之类机制不会被伪装成“用户又下了一条新命令”。

语言世界稳定，但协议标识不乱翻译

一个 participant life 会生活在稳定的自然语言世界里。英语就是英语，中文就是中文；但工具名、协议字面量、代码标识、路径和机器 identity 不因为语言切换而被翻译成另一个名字。

外部知识先保留“它来自哪里”

Browser 带回来的网页事实不会只剩一句“网上说”。系统会尽量保留来源、质量、相互冲突的观点和不确定性。旧知识、缓存、搜索结果都只是材料，不会因为被写进上下文就自动升级成当前仓库事实。

对用户来说，最重要的不是系统内部有多少组件，而是每一条出现在上下文里的信息都知道自己“凭什么在这里”。

第 6 篇 · 设计哲学与语义全景

3. 用户视角的能力地图

把内部实现名字全部拿掉，Wanxiangshu 可以理解成十三层彼此咬合的用户能力。它们不是菜单里的十三个开关，而是共同决定“这支 AI 团队会怎么工作”的行为边界。

1 · 身份：谁还是谁

一个 Agent 的岗位、人格、当前执行方式与底层物理模型彼此分开。Coder 换成另一种执行绑定，仍然是同一个 Coder；同一个岗位被调度到另一款模型，也不会因此获得新的权限、忘掉原有语言或变成另一名团队成员。

这条边界让 fallback、模型负载均衡、Strength 预读和 Fission 并行都能发生，而不会把“技术切换”伪装成“组织换人”。

2 · 权限：能看见什么，就真的只能做什么

每个岗位的能力由它有资格产生的后果定义。Coder 可以修改仓库；Inspector 负责本地只读取证；DevOps 控制真实进程；Browser 负责公网资料；Reviewer 只读并裁决。工具列表和运行时权限来自同一套边界，不能靠提示词说“请自觉不要越权”。

请求可以临时收窄权限，但不能临时放大岗位权力。Fast / Deep 也不能借 tier 差异偷偷扩权。

3 · 托付：把工作交给别人，不等于把责任甩掉

fork、inspect、repair、commission 等动作会明确“把什么工作交给什么样的人”。子任务有自己的执行空间，但上级仍然拥有原始 responsibility；attachment 只改变执行拓扑，不会自动转移使命。

返回时传递的是一份 bounded work record：足够让接收方理解这段工作做了什么、最近发生了什么，而不是把整个子会话的内部机器状态倾倒回来。

4 · Fission：同一个人可以横向展开

Fission 不创造多个新 Agent，而是让当前 Agent 暂时展开多个对等执行面。它适合“我自己已经知道内部有几块可以同时推进”的场景。

这些执行面使用独立物理会话，避免并发流互相撞坏；但逻辑身份仍只有一个。完成时所有结果先收敛，再向 parent 交付一次。如果中途崩溃，也不会后台偷偷重建 lane，而是把事实留给显式恢复。

5 · 真实执行：命令、进程与输出都讲物理事实

DevOps 的命令不是“让模型猜一下命令会怎样”，而是真实动作。系统区分启动、发送信号、真实退出、超时、取消与非零 exit code；其中非零 exit code 仍是一种正常可观察完成。

输出太大时会经过 Distiller 有损压缩，但压缩必须承认自己只看到了 fragment，不能把“某个片段没报错”冒充“整条命令成功”。

6 · 时间与等待：等的是事件，不是心理预期

系统不会因为“过了几秒应该好了”就当某件事完成。等待进程、review、子任务或外部资源时，优先等待真实事件；deadline 是防止无限卡住的边界，而不是业务真相。

如果等待链真的卡住，系统可以诊断“当前在等谁、谁又在等谁”，但诊断本身不会获得替你做决定的权力。

7 · 长期记忆：原始历史、压缩记忆与最近工作各司其职

原始语义轨迹只追加不删除；Blogger 把已发生的片段压成较小的 Chronicle；WorkRecord 再把 Opening、Chronicle 与 Recent 组合成一份有界工作陈述。

压缩不是按“窗口快满了”随意触发，而是在有真实失败/边界证据时才替换历史。已经发给模型的历史前缀一旦成立，就尽量保持字节稳定，减少模型看见同一过去却不断变形的问题。

8 · Todo：记“还欠什么”，不是记“现在处于第几阶段”

Manager 的 todo 是完整 obligation account。每项都说明还欠的具体工作，workingOn 只指当前 focus。UI 可以为了兼容显示 pending/in_progress，但这些状态不是任务真相。

计划完成前，可以把“调查、形成计划、解决未知”诚实地记成 planning obligations；一旦做出 T1 commitment，清单就应该转成真正的 mission debt：用户世界还欠什么结果、修复或证据。

9 · Review：裁决不是表演式严格

Reviewer 的 PERFECT 不代表“宇宙中再也没有任何可改之处”，而代表当前没有发现足以正当扣住 acceptance 的实质缺陷；REVISE 则必须指出一个修复后能真正买到更好或更真实结果的问题。

八个质量方向帮助 Reviewer 想完整，但不是八格 checklist。一个小 typo 不会因为“严一点总没错”就自动推翻整个 acceptance；反过来，PERFECT 也不能要求 Reviewer 对真实 minor 观察闭嘴。

10 · Finality：Blessing 不是终点

Manager 请求结束时，系统会先清掉仍悬着的过程评审，再进入终局审查。第一次通过只得到 Blessing；它告诉 Manager“你已经挣得 acceptance，但可以继续处理小尾巴”。

第二次明确结束才进入 rest。此时最终交给用户的答案就是 Manager 的 last_words，不再由系统额外包一层“系统总结”。

11 · 失败与恢复：不重复未知副作用

模型失败可以在同一岗位的不同执行绑定之间有界切换；重复输出会被 degeneration guard 主动止损；但任何自动恢复都不能跨越“我们不知道刚才那个外部动作到底发生没发生”的边界。

因此 unknown effect 必须先核对现实；进程崩溃后也不会自动重跑旧工具。显式 /continue 的意义就是把“恢复旧意图”重新交给当前真实世界，而不是让后台代替用户赌一次。

12 · 调查与知识：旧答案可以复用，但不能装成新事实

Inspector 的本地调查要求真实 read/glob/grep observation；Browser 的公网调查保留 provenance 与分歧；Casebook 可以复用过去的问答与观察，但 no-delta 只说明“没发现变化”，不等于“答案已经重新证明”。

更抽象的 Inquiry / epistemic reasoning 则负责区分 proposal、evidence 与 uncertainty。系统允许“我现在还不知道”保持为真正的不确定性，也允许“停止继续调查”成为一个合理动作。

13 · 修改与交付：复杂操作尽量一次成形

批量修改走沙箱化的 repository programming：先在不可变快照上构造结果，再以事务方式提交；文件在中途被别人改了就 fail closed，不偷偷重读后重新执行模型程序。

多个 Git 工作道路合入共享目标时，长时间 review/repair 不占全局锁，真正发布只用很短的原子门；目标分支发生变化就重新确认，而不是覆盖过去。最终安装包则自带运行所需资源，不要求用户把源码树放在某个特殊工作目录里。

把这十三层合起来

你得到的不是“一个会调用很多子 Agent 的聊天机器人”，而是一支有身份、有权力边界、有记忆、有审查、有失败语义、有并行自治、又能在崩溃后保持责任连续的 AI 软件团队。

第 6 篇 · 设计哲学与语义全景

4. 安装、运行与故障边界

这一页只说作为用户真正需要知道的运行边界：Wanxiangshu 以 OpenCode plugin 的方式工作，安装后的行为应该依赖安装包本身，而不是依赖开发者电脑上恰好存在的源码目录。

运行环境

项目当前要求
Wanxiangshu当前版本 0.8.2
Node.js20 或更高
OpenCode plugin API兼容 @opencode-ai/plugin >= 1.17.4

安装包会携带运行代码与语义资源；角色说明、质量规则、语言资源等都按 artifact 自身位置加载，而不是假设你必须从仓库根目录启动。换句话说，工作目录不应该决定角色是谁、工具怎么解释、中文资源能不能找到。

启动时不会偷偷恢复旧工作

Plugin 加载本身只负责准备运行环境，不会因为“发现上次留下了一些事件”就自动调用 Host、扫描旧 session、重跑工具、修改 Git 或修复半截事务。

这是一个刻意的安全边界：启动成功只表示系统准备好了，不表示它替你决定了过去某件未完成工作的下一步。

旧会话需要你明确说“继续”

如果一个旧 session 因进程退出、插件重启或工具中断而停在那里，使用 /continue 才表示“请基于现在的事实重新看看这件事”。系统会把已知 durable facts 与当前物理状态整理成恢复上下文，但不会把旧的未完成调用当作“理应继续执行”。

这尤其重要于写文件、Git 发布、创建外部资源等副作用：如果结果未知，第一步是核对现实，而不是重复做一次。

命令失败不等于插件坏了

真实命令退出码非零、工具返回业务拒绝、等待超时、文件在事务中途被别人修改，这些都可以是正常的“工作结果”。它们会尽量以明确后果返回给 Agent，让 Agent 决定下一步。

真正的基础设施契约破坏则不同：例如系统无法确认一个关键身份、底层能力缺失、持久化边界失效。这种情况下倾向于 fail closed，而不是编一个看似顺畅的业务结果继续。

语言不会在半路漂移

同一个 participant life 会保持稳定的自然语言世界。中文会话不会因为一次内部恢复突然变成英文角色说明；英语也一样。工具名、协议字面量、代码和路径则保持原样，不为了“更像中文”而改名。

你不需要维护内部缓存或恢复文件

Casebook、事件流、WorkRecord、Companion 记忆、模型 lease、review witness 等都属于系统内部。正常使用时不应该要求你手动清理它们来“让系统恢复正常”。当某个内部事实真正影响你的动作时，系统应该把后果翻译出来，而不是让你操作内部数据库。

如果看到“等待”，它应当有一个对象

Wanxiangshu 的等待通常对应一个真实对象：某个 Agent、某个 process、某个 review、某个物理退出或某个 deadline。它不会把无限 sleep 当成正常 workflow。用户真正需要理解的是“系统在等什么”，而不是内部循环跑到了第几次。

好的恢复体验不是“什么都自动做”，而是“自动保存足够事实，同时把需要重新授权的动作留给当前世界”。

5. 五句话总结

1. 一支团队，但身份、权威、执行绑定和物理模型不是一回事。 十个 Role × Fast/Deep 形成 20 个 Agent；capability 由 office 后果定义，physical ModelTarget 再由独立 scheduler 决定。换执行者、换模型都不能偷偷换人或换权。
2. 长任务靠事实、记忆整理和有界工作记录延续，不靠“把旧会话复活”。 原始历史只追加，Blogger 每轮只提交一次明确观察，Opening / Chronicle / Recent 各司其职；进程死后从已知事实重入，显式 /continue 才处理旧会话。
3. 完成必须被合格证据证明，但 review 不是 Manager 的机械 checklist。 Todo 始终保持“仍欠什么”真实；终局会看当前工作与合格审查；Blessing 不是终点，第二次明确结束才真正完成。
4. 并发、投机与恢复都不能稀释责任。 fork 会真的新增下属责任；Fission 只是同一个 Agent 横向展开；Strength 的影子结果没被主任务接纳就不算正式历史；结果未知的外部动作永不自动重放。
5. 端正来自清楚的边界。 一个事实只有一个真相来源，展示不能造权，等待必须有因果，未知副作用不自动重放，内部复杂性不以更多状态字段甩给用户。

如果只记一句：Wanxiangshu 不是“多 Agent 编排器”，而是一套让身份、权限、工作、记忆、失败、审查与并行都保持责任清楚的 AI 软件团队运行方式。

附录 · 概念演进档案

Sphinx → epistemic-reasoning

当前地位：Sphinx、A*、MCTS 等名称不再定义 package identity。现行 normative owner 是 epistemic-reasoning；本页以下内容保留为理解 HOW/history 的设计直觉。

Sphinx 曾被构想成一个由数学内核控制、与 LLM 携手推进的“认识状态”求解器。 后续 requirements 重构把真正不可替代的部分抽出来：proposal 与 evidence 必须分型，不确定性必须保留，信息动作与停止必须由受约束 policy 决定。

普通问答直接给答案。Sphinx 不这样——它维护一个关于"我们现在知道什么、还不知道什么、什么问题值得继续问"的认识状态，然后一步步逼近。

一个内核，两种角色

负责什么
数学内核认识状态、全局闭包、判重与约简、方法选择、概率与裁决、搜索预算、停止、最终答案
LLM把自然语言转成结构化的概率化语义观测——仅限于此

历史 Sphinx 强调“内核说了算”；当前 package 用更抽象的语言表达同一边界：模型可以提出 semantic proposal，但 proposal 不自动成为 evidence，controller 对信息动作与停止负责。

两个锚定例子

「花儿为什么这样红？」→ 展开多学科解释，各层互补，最终综合（不坍缩成一个干巴巴的答案）。

「明天白银会涨吗？」→ 基底概率、类比、因果驱动 → 收敛成后验概率（数值资格成立就给出贝叶斯后验，否则给出定性的区间信念）。

五个第一性原理

1. 历史不是状态 日志可以 append-only，但推理状态不该 append-only——系统维护的是历史对未来决策的充分统计量。
2. 表示不是认识本身 同一个认识状态可以有多个计算表示，内核有权重排、约简、旋转，只要认识语义不变。
3. 每次外生信息后必须全局闭包 LLM 每给一次新东西，内核先全局收敛到不动点，才允许问下一句。
4. 认知价值相对于根问题 一个子问题值多少钱，只看它预计怎样改善根问题——它是"解惑机"，不是"无限知识展开机"。
5. No Free Information（认识守恒） 重新措辞、类比、综合只能重组旧信息，不能凭空提高与现实的互信息。LLM 可以帮你找得更好，但不能把 0.6 递归成 0.9。

停，也是一个动作

停止不是特殊的 if。当停止的价值不小于任何继续动作时，停止就是当前最优动作——"问什么"和"什么时候不再问"属于同一个控制问题。

经典算法是历史校准，不是今天的合同

Sphinx 时代用 A*、贝叶斯推断、MCTS 做“架构不能被设计窄”的退化校准。今天这些算法更适合作为设计历史与理解材料：它们可以帮助解释认识状态模型，但不再要求系统必须以某个统一搜索器实现。

留下来的签名

Evidence 不由措辞创造；proposal 不等于 observation；uncertainty 不能被抹平；停止与继续属于同一个决策问题。 这四件事比“Sphinx”这个名字更稳定，因此它们进入了 epistemic-reasoning。

Fission · 从实验到正式生产合同

当前地位：Fission 已由 intra-participant-parallelism 正式拥有，不再是 blocked proposal。正片第 2 篇给出当前合同；本页保留它从“透明裂变”直觉走向 production semantics 的历史图景。

Fission 是 Agent 内透明裂变：同一个逻辑 Agent 暂时展开成 N 个对等执行 lane，在内部收敛回一次普通完成——parent 完全感知不到这次裂变。

一句话：上级拥有"要什么"，当前 Agent 拥有"自己的工作是否值得横向展开"。

一个例子

Manager 从头到尾只看到：给了 Coder X 一个任务，X 完成了一次。它不知道 A、B、C 是三条 lane 并行干完的。

它不是 fork

fork · 层级裂变
新 Agent 身份新 handleparent 可见完成join / list 参与
fission · 对等裂变
无新公开 AgentId无新 handle无 parent join 义务parent 完全不知情

fork 改变组织拓扑；fission 不改变逻辑组织拓扑。二者必须长期正交。

谁会裂，谁不裂

允许裂变明确不裂
Manager · Coder · Inspector · Browser · InquiryOrchestrator · DevOps · Reviewer · Blogger · Distiller

一条铁律：裂变复制的是 execution present，不复制 participant identity / authority / responsibility。 Manager 本身可以拥有 Fission entitlement，但它的 finality authority 仍只有一个 logical owner；多个 lane 不能各自制造一份“终局”。

它想解决什么

今天的 Manager 已经鼓励细粒度并发，但一个被摊上大任务的单个 worker 仍可能串行：A 做完才能做 B。Fission 让"要不要横向展开"的决定权落在当前 Agent 手里，而不是逼上级预先知道内部结构。

上级决定"要什么"，当前 Agent 决定"怎么干得更快"——局部自治被还给了每一个 Agent。

工程难点后来怎样落地

“同一逻辑 Agent 不能在同一个物理 SessionId 并发跑多条 stream”这个判断保留了下来，解决方案也从提案进入 production：每条 lane 创建 fresh sibling Host session，且 parent(lane)=parent(old caller)；所有 lane start 成功后才 silent-interrupt old present。这样物理并行成立，而逻辑 parent tree 不被改写。

原先只画在图上的“最后合回一次”也变成了可验证合同：pre-fission completion 广播 exactly-once，post-fission completion lane-affine，work record 按 lane index keyed convergence；同 key/ref/digest replay 幂等、冲突 fail closed；全部 accounting 完成后才填原 participant 的唯一 completion cell。
