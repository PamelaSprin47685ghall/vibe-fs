# SSOT/04 — Fallback 与 Circuit Breaker

条款 ID 前缀：`FALLBACK-`

## FALLBACK-001：Fallback 属于 Logical Run

Fallback 不属于 Session 永久状态。A/B 是一对 OpenCode Agent（SelectedAgent / PeerAgent），不是模型槽位。

新 Authority Root 创建新 Fallback cursor：`Offset=0, A=SelectedAgent`。

## FALLBACK-002：Modulo-4 Cursor 与 ConsecutiveFailureCount

```fsharp
type FallbackCursor =
    { Offset: byte                    // 仅 0|1|2|3
      ConsecutiveFailureCount: int }  // 连续失败次数，不超过上限

let side offset =
    match offset with
    | 0uy | 1uy -> SideA           // SelectedAgent
    | 2uy | 3uy -> SideB           // PeerAgent

let advance offset = byte ((int offset + 1) % 4)

let effectiveAgent authority cursor =
    match side cursor.Offset with
    | SideA -> authority.SelectedAgent
    | SideB -> authority.PeerAgent
```

## FALLBACK-003：统一 FallbackController

Host 事件只负责唤醒。只有统一的 FallbackController 能提交 `FallbackCursorAdvanced`。

```text
idle 或 retry 信号
→ single-flight reconcile
→ 从完整 Host snapshot 识别失败的 provider attempt
→ 用 FallbackAttemptIdentity 去重
→ FallbackController 原子推进 cursor
→ 根据 Host 是否会自动继续，决定是否发送 continuation
```

禁止：`ProviderFailureContinuation` 直接写 cursor。`retry` 事件本身直接写 cursor。

```fsharp
type FallbackAttemptIdentity =
    { SessionId
      LogicalRunId
      AuthorityRootUserMessageId
      ProviderRunIdentity }
```

同一 failed attempt 最多推进一次。

## FALLBACK-004：不变量

- 失败：Offset 前进，ConsecutiveFailureCount + 1
- 成功：Offset 保持不变，ConsecutiveFailureCount = 0
- Authority profile 中的 SelectedAgent、PeerAgent、CanonicalRole 永远不变
- Fallback 只改变 `AttemptExecutionProfile.EffectiveAgent`
- Host 自动重试时不额外发送 continuation
- Host 已停止自动重试时，才发送同 Logical Run continuation
- continuation 不产生第二次 cursor advance

## FALLBACK-005：有限 Circuit Breaker

必须区分两件独立的事：

| 概念 | 是否有界 | 规范位置 |
|------|---------|---------|
| Cursor pattern（Offset 的 A/A/B/B 循环） | 无界。Offset 永远 `(n+1) mod 4`，任何失败次数都不会让循环停止或判死 | FALLBACK-002 |
| 自动恢复预算（`ConsecutiveFailureCount` 上限） | 有界。默认 12 | 本条款 |

`AutoRecoveryBudget = 12`（默认，可由管理员配置为其它有限正整数）。

判定点在每次失败推进之后：

```text
失败 attempt
→ Offset := (Offset + 1) mod 4          // 永不停止
→ ConsecutiveFailureCount := n + 1
→ if ConsecutiveFailureCount >= AutoRecoveryBudget
      then 写 FallbackExhausted，不再自动发出新物理请求
      else 允许下一次自动 attempt
```

因此第 12 次连续失败发生在 `Offset=3`（SideB），推进后 `Offset=0`，`ConsecutiveFailureCount=12`，随即写 `FallbackExhausted`。不存在自动的第 13 次 attempt。 Cursor 停在 `Offset=0` 只是记录，不代表还会自动请求。

`FallbackExhausted` 后返回明确终局失败。恢复只有两条路径：新的 Authority Root（PROMPT-002），或用户显式恢复动作。两者都创建新的 cursor（`Offset=0, ConsecutiveFailureCount=0`）。

成功时 `ConsecutiveFailureCount := 0` 且 `Offset` 不变（FALLBACK-004）。因此长 Logical Run 中零散失败不会累积耗尽预算。

本条款不定义任何 wall-clock deadline。 万象术不存在 provider-failure wall-clock 协议：预算只按连续失败计数，不按时间。

## FALLBACK-006：完整序列示例

```text
SelectedAgent=fast-coder, PeerAgent=deep-coder
AutoRecoveryBudget=12

attempt 1  在 Offset 0 → fast-coder   失败 → Offset 1, count 1
attempt 2  在 Offset 1 → fast-coder   失败 → Offset 2, count 2
attempt 3  在 Offset 2 → deep-coder   失败 → Offset 3, count 3
attempt 4  在 Offset 3 → deep-coder   失败 → Offset 0, count 4
attempt 5  在 Offset 0 → fast-coder   失败 → Offset 1, count 5
...
attempt 12 在 Offset 3 → deep-coder   失败 → Offset 0, count 12
→ count 达到 AutoRecoveryBudget → 写 FallbackExhausted
→ 无自动 attempt 13
```

成功中断的例子：

```text
attempt 1  在 Offset 0 → fast-coder   失败 → Offset 1, count 1
attempt 2  在 Offset 1 → fast-coder   成功 → Offset 1, count 0
```

Offset 停在 1：下一次失败仍从 SideA 的第二格继续前进，不回到 0。成功不重置 Offset。

## FALLBACK-007：持久事实

```fsharp
FallbackCursorAdvanced =
    { LogicalRunId; AuthorityRootUserMessageId
      ProviderRunIdentity
      PreviousOffset; NextOffset
      ConsecutiveFailureCount }

FallbackExhausted =
    { LogicalRunId; AuthorityRootUserMessageId
      FinalConsecutiveFailureCount; FinalOffset }
```

Fold 验证（不满足任一条则拒绝该 envelope，fail closed）：

```text
NextOffset = (PreviousOffset + 1) mod 4
ConsecutiveFailureCount = 前一个 FallbackCursorAdvanced 的 count + 1
                          （无前值时 = 1）
ConsecutiveFailureCount <= AutoRecoveryBudget
```

成功不写任何事实。 `ConsecutiveFailureCount = 0` 是 Fold 从"存在成功的 provider attempt"派生的，不是持久事件。成功由 Host snapshot 证明（HOST-004 ReconciledTurn.Outcome = Completed），因此 cursor 的 count 归零不需要额外 journal 写入口——这保持了 FALLBACK-003 的单一写入口约束。

`FallbackExhausted` 之后同一 `(LogicalRunId, AuthorityRootUserMessageId)` 不再接受 `FallbackCursorAdvanced`。Fold 遇到则拒绝。

## FALLBACK-008：空/XML-only terminal

空/XML-only 不进入 A/B 计数，最多触发一次 interaction repair continuation。

## FALLBACK-009：Host 能力门禁

若 Host 自身在某个次数停止 retry，必须用 `ProviderRetryAttempt` continuation 延续同一 Logical Run。continuation 使用同一 AuthorityRoot，不建新 completion，不重置 cursor。不得伪称无限 AABB 已实现。

## FALLBACK-010：Host Attempt 计数与 ConsecutiveFailureCount 不是同一个量

`HostSignal.ProviderRetry` 携带的 `Attempt`（HOST-003）是 Host 自己的重试计数：由 OpenCode 决定语义、可能从 0 或 1 起算、可能在 Host 内部重置、可能在同一次万象术 attempt 中出现多次。

`FallbackCursor.ConsecutiveFailureCount`（FALLBACK-002）是 万象术的领域计数：只由 FallbackController 在确认失败的 `ProviderRunIdentity` 上推进，由 `FallbackAttemptIdentity` 去重（FALLBACK-003）。

禁止：

```text
把 HostSignal.ProviderRetry.Attempt 写入 ConsecutiveFailureCount
用 Attempt 值判断是否到达 AutoRecoveryBudget
用 Attempt 值推导 Offset
用 Attempt 值决定是否发送 continuation
```

`Attempt` 唯一合法用途是诊断日志（HOST-007）与唤醒（FALLBACK-003：Host 事件只负责唤醒）。Host 是否会自动继续，只能由 reconcile 后的完整 snapshot 判断，不能由 `Attempt` 数值推断。
