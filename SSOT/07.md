# SSOT/07 — Host 集成合同

条款 ID 前缀：`HOST-`

## HOST-001：事件分层

```text
碎片事件（message.updated / part.delta / session.updated）
    ↓ 最早边界丢弃
粗粒度信号（session.status idle/retry, session.deleted）
    ↓ single-flight
Reconciler 从 SDK 读取完整消息
    ↓
纯策略（completion / ReviewGuard / continuation / abort）
```

## HOST-002：唯一允许进入业务层的信号

只有 `session.status=idle`、`session.status=retry`、`session.deleted` 可以进入 Session 生命周期与 Reconciler 信号通道。

`chat.message` 仅进入 Prompt acknowledgement 通道，不能用于拼装 terminal turn 或驱动普通业务流程。

## HOST-003：Transport 与 Domain Contract 分离

Transport 可以是 plugin event 或 global SSE。Domain contract 永远是 typed HostSignal。业务层不得观察原始 payload。

```fsharp
type HostSignal =
    | SessionIdle of sessionId: SessionId
    | ProviderRetry of {| SessionId; Attempt; UserMessageId: MessageId option |}
    | SessionDeleted of sessionId: SessionId
```

## HOST-004：Reconciler

Single-flight：同一 session 同时最多一次 reconcile 请求。Dirty 标记：idle 信号到达时设 dirty=true。

Unknown 等待协议：一次 idle 建立 Dirty latch。最多 3 次因果重读，仍 Unknown 则保持 Dirty 等下一信号。

```fsharp
type ReconciledTurn =
    { SessionId; UserMessageId; AssistantMessageId
      AgentRole: AgentRole option; Directory: string
      Parts: ProviderVisiblePart array
      Outcome: TurnOutcome }  // Completed / Failed / Aborted
```

## HOST-005：A 版（session-wide formal assistant 累积）

```fsharp
type FormalAssistantPart =
    | Text of string
    | Reasoning of {| Text: string; ProviderKind: string option |}

type FormalAssistantSegment =
    { ProviderRunId: string
      EffectiveAgent: string
      ProviderId: string option
      ModelId: string option
      Parts: FormalAssistantPart list
      Outcome: TurnOutcome }

type ARecord =
    { Segments: FormalAssistantSegment list }
```

A(X) best-effort 累积 Host 可见的正式正文与 reasoning/thinking，但不声称包含未暴露的内部思维。不包含 tool raw output、UI delta、usage、cost、timestamp。Session 可能经历多个 Agent/Fallback 切换，因此按 provider run 分段保存，不使用单值 Model。

`join().formalRecord` = session-wide A。`join().workRecord` = Companion LatestB。

## HOST-006：官方 Compaction 的预防与收容

上下文恢复的唯一合法机制是 SSOT/12 的失败驱动协议。Host compaction 的结果不得参与产品语义。

该目标分两层实现。 第一层把能关的关掉，第二层收容任何仍然出现的 compaction。两层都必须存在：第一层依赖 Host 的配置键与 Hook 名，会随上游版本漂移；第二层只依赖 transcript 里可识别的事实，是主要防线。

### 预防层：必须关闭，无法证明则启动失败

```text
automatic compaction        阈值触发
overflow compaction         溢出触发（预测式与 provider 报错后）
compaction autocontinue     压缩后自动续发
compaction prune            物理删除持久消息行
```

前三项由 Host 的自主判断触发，插件对时机无任何控制。`prune` 绕过投影边界直接删消息行，与 COMPANION-009 的「原始 Host transcript 永远不物理删除」直接冲突。

启动时必须证明这四项确已关闭。静态读取配置不足以证明：必须包含一次运行时探测——首个 managed session 完成第一轮请求后，该 session 的 compaction pseudo-run 数量必须为零。第一轮必然远低于任何阈值，此时出现 pseudo-run 只能说明存在不受该配置控制的第二实现。

不满足则 `HostContractUnsupported`，启动失败，不降级运行。理由不是「一次 compaction 会破坏正确性」——收容层保证它不会——而是无法预防的自动 compaction 会让机制空转：每隔几轮就重锚一次，probe 永远攒不够 coverage，而从外部看一切正常。

### 收容层：任何出现的 compaction 一律重锚

manual compaction（用户 `/compact`）在 Host 侧没有配置开关也没有可否决的 Hook，因此无法预防。它是官方支持的用法：用户的显式意图与本方案缩短上下文的目标一致。

收容层同时覆盖第二种情况——预防层被绕过时 Host 自行触发的 compaction。两者不作区分：观察面相同（transcript 里只有一条 pseudo-run，没有「谁触发的」字段），正确处置相同，分类只会长出永不执行的分支。这与 CTX-005 同构。

识别判据是折叠后的单一谓词：`agent = "compaction"`、`mode = "compaction"`、`summary = true` 任一为真。

处置是一次重锚，不是无动作，也不是崩溃：

```text
观察到 compaction pseudo-run
→ 退役 ActivePrefixEpoch（Snapshot → None，EpochId += 1）
→ Companion coverage 归零（IngestCursor、CoverableTurnCutoff、CoveredPrefixDigest）
→ BlogFrame 全部保留
→ 后续正常轮次重新累积 coverage，probe 能力自然恢复
```

Epoch 退役是因为 `CutoffExclusive` 是旧编号下的索引，compaction 后不再指向任何真实前缀。Coverage 归零而非重新指向摘要之后，是因为 Companion 可能因 busy skip 落后于 Host，声称覆盖会用更窄的 B 替换更宽的摘要。Frames 保留是因为那些工作确实发生过，作废的只是索引映射。Epoch 递增而非原地清空，是因为这是一次真实的冷边界，COMPANION-009 的逐字节稳定以 epoch 为界。

重锚是持久事实 `ContextReanchored`（PERSIST-010），因为它原子地改变两处投影。

重锚不违反 CTX-001、CTX-002：触发它的是已经发生的外部物理事件，不是插件对容量的测量或预测。

### 效果只做 best effort 保证

明确不保证：B 覆盖了 Host 丢弃的内容（busy skip 期间未消化的 turn 真实丢失）；前缀缓存连续（epoch 切换是一次冷边界）；Host 摘要的质量（摘要文本永远不作为 B 读取，不进入 FrozenB）；重锚后立即可 probe（第一个恢复槽可能找不到新 coverage，按 CTX-011 走正常主请求）。

### 不变的部分

Host compaction 结果不得成为 `PrefixEpoch`、`BlogFrame`、`FrozenB`、Authority Root 或 Continuation，不得推进 Fallback cursor。`ContextReanchored` 记录的是插件自己的退役动作，不是把摘要当作事实。

源码证据与 SSOT 例外协议记录：`STATUS/blocker-HOST-006.md`、`STATUS/evidence/host-context-recovery.md`。

## HOST-007：日志规范

日志只记录诊断：session_id、role、handle_id、operation（fork-agent/join/nudge/project/blog/process/review/publish）、result、error、bytes/duration/tree hash。不写 stage、phase、owner、lease、generation、next_action。日志不是恢复协议。

## HOST-008：Session 关联

```fsharp
type ManagedSessionKind =
    | WorkSession
    | CompanionSession of mainSessionId: SessionId

type SessionAssociation =
    { SessionId: SessionId
      Kind: ManagedSessionKind
      BloggerSessionId: SessionId option
      ParentSessionId: SessionId option
      Role: AgentRole }
```

不变量：

```text
每个 WorkSession 恰好一个 CompanionSession
每个 CompanionSession 恰好属于一个 WorkSession
CompanionSession.BloggerSessionId = None（Y 不递归）
SessionId ≠ BloggerSessionId
```

关联由 Session 种类决定，不由 CanonicalRole、AgentTier、工具权限、当前 Logical Run、Authority Root 或 Fallback Agent 决定（COMPANION-001、COMPANION-002）。

优先存宿主 metadata。重启时复用同一 Blogger（不发 delta 给空白 Y）。

## HOST-010：Transform → ProviderRunIdentity 绑定

`experimental.chat.messages.transform` 的 input 是空对象，不携带任何身份。但 Host 在触发该 Hook 之前已经创建并持久化了本次 provider run 的 assistant message。因此绑定由一次因果读取建立，不由猜测建立。

### 绑定判据

transform 执行期间，从 SDK 读取该 Session 的消息，目标 `ProviderRunIdentity` 是唯一满足全部条件的 assistant message：

```text
role = "assistant"
time.completed 未设置
parentID = transform 输出中最后一条 user message 的 id
id 为该 Session assistant message 中最大者
```

Host 保证：`Plugin.trigger` 对每个 hook `await`，因此 transform 内的异步 SDK 读取合法且 Host 会等待。

### 必须 fail closed 的情形

```text
命中 0 条    → 不写 seal
命中 ≥2 条   → 不写 seal
agent = "compaction" 或 summary = true → 不写 seal（compaction 路径顺序相反）
```

`ProviderInputSeal`（REVIEW-010）不存在时，第二次 PERFECT 只能返回 `PendingIdentity` 或 `Rejected`，绝不 `Confirmed`。不得退回 same-root 或 physical-message 猜测。

### 脆弱性与门禁

本绑定依赖 Host 内部执行顺序，而非公开类型合同。必须存在一条 canary 直接断言该顺序：transform 时读到的唯一未完成 assistant message id，等于随后同一 run 内 verdict 工具收到的 `ToolContext.messageID`。

该 canary 是 Host 版本升级门禁。顺序改变时它必须先红；确认无替代路径后才触发 SSOT 例外协议。

证据：`STATUS/evidence/host-transform-run-binding.md`。

## HOST-011：Tool 执行身份的两个半边

Host 在两个不同边界暴露互补的身份，插件必须知道各自缺什么。

| 边界 | assistant message id | tool call id |
|------|---------------------|--------------|
| `ToolContext`（工具 execute 参数） | `messageID` ✅ | `callID` ✅（Host 侧 `Tool.Context` 声明为 `callID?`，经 registry 透传，SDK 发布类型未声明） |
| `tool.execute.before` / `after` | ❌ 不存在 | `callID` ✅ |

因此 `ReviewAttemptIdentity`（REVIEW-004）所需的 `ProviderRunIdentity` + `ToolCallId` 只能同时从 `ToolContext` 取得。

规则：

```text
ProviderRunIdentity := ToolContext.messageID     缺失 → fail closed
ToolCallId          := ToolContext.callID        缺失 → fail closed
```

禁止：用 `tool.execute.after` 的 `callID` 补齐 `ToolContext` 缺失的身份（两者不在同一调用上下文，无法可靠配对）。使用 SDK 未声明且 Host 源码中也不存在的字段（例如 `userMessageID`）——物理用户消息身份只能来自插件自己维护的 `chat.message` 绑定表。
