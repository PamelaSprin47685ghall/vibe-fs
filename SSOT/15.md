# 一、执行摘要

Blogger 是 Work Session 的 Companion 叶子 Agent，负责生成工作日志。0.5.1 已交付的 Blogger 工具化语义要求 Blogger 调用 `blog` 工具提交工作日志，不再以 assistant 正文输出。

Blogger 必须调用：

```text
blog(
    text = "...",
    evidence = "..."
)
```

其中：

* `text` 是唯一 required 字段；
* `evidence` 是单个 optional 字符串；
* 每个请求的协议要求恰好调用一次 `blog`（ENFORCER-030）；
* Provider 违约发出多个有效调用时，Host 按 PartOrdinal 防御性归并为一个 entry（ENFORCER-042），并记录 protocol-violation diagnostic；
* 归并时 `text` 按 tool-call 顺序拼接，`evidence` 按顺序去重后拼接；
* `blog` 工具每次立即返回固定字符串 `"OK"`；
* 工具执行本身不挂起；
* Host 发起 tool-loop continuation 后，Blogger transform 才进入挂起状态；
* 下一批可供 Blogger 消化的主 Session delta 到达时，解析该挂起 transform；
* Main Session 永远不等待 Blogger。

本设计保留现有 Companion 的 Journal Frames、coverage、BlogSquash、prefix probe、fallback 和 compaction 恢复模型。物理 Blogger transcript 仍然不能作为有效 B 历史；有效 Frames 继续只由 Journal fold 派生。

> 规则评分、throttle 与主模型 nudge overlay 见 `RFC/enforcer-nudge.md`。

# 二、目标与非目标

## ENFORCER-001：目标

Blogger 工具化必须实现：

1. Blogger 工作日志工具化。
2. 同一 Blogger provider step 内多个 `blog` 调用的确定性合并。
3. `0..9` 统一置信度评分占位 schema（字段可带，但当前只记录 `text`/`evidence`）。
4. 缺失评分字段等价于零。
5. 字段名拼写容错。
6. PrefixEpoch 内逐字节稳定。
7. PrefixEpoch 切换后自然遗忘。
8. 崩溃、重启、fallback、BlogSquash、Host compaction 下的确定性恢复。
9. 全链路纯函数测试、Fake Host 轨迹和 OpenCode canary。

> nudge overlay、throttle 与完整规则目录见 `RFC/enforcer-nudge.md`。

## ENFORCER-002：非目标

本功能不负责：

* 证明 Blogger 判断一定正确；
* 强制主模型服从警告；
* 阻塞主模型等待监督结果；
* 代替正式 Reviewer；
* 改写或撤销主模型已经执行的操作；
* 估算上下文余量；
* 主动触发 compaction；
* 根据模型大小减少规则目录；
* 为 fast-blogger 和 deep-blogger 提供不同规则；
* 在 epoch 之间保留警告；
* 从警告文本推导领域事实；
* 将 nudge 伪装成 system instruction；
* 修改 OpenCode 本体。

主模型有权判断某条反馈是否适用；Enforcer 的职责是及时提供工程异议，不承担最终裁决。

# 三、核心术语

## ENFORCER-003：Blogger Cycle

一次 Blogger provider step，从一个 provider input 开始，到该 step 中所有 `blog` 工具调用及其工具结果全部完成为止。

一个物理 Blogger turn 可以包含多个 Blogger Cycle：

```text
provider step
→ blog call(s)
→ tool result(s) "OK"
→ continuation transform
→ provider step
→ blog call(s)
→ ...
```

Blogger turn 可以长期不 terminal；挂起的是 continuation transform，不是工具执行。

## ENFORCER-004：Blogger Cycle 结果

一个 BloggerMain Cycle 合并后产生一组 `CanonicalBlogCall`：

```fsharp
type CanonicalBlogCall =
    { ProviderRunIdentity: ProviderRunIdentity
      ToolCallId: ToolCallId
      PartOrdinal: int
      Text: string option
      Evidence: string option }
```

0.5.1 只记录 `text` 与 `evidence`。评分报告、规则字段与 nudge overlay 见 `RFC/enforcer-nudge.md`，不属于当前产品合同。

# 四、Agent 与工具能力修改

## ENFORCER-010：Blogger 工具权限

Blogger 的工具权限由“无工具”修改为：

```text
Blogger → blog
```

其他角色不得看到或执行 `blog`。

执行门必须同时验证：

```text
CanonicalRole = Blogger
ManagedSessionKind = CompanionSession(mainSessionId)
```

任一无法证明，均 fail closed。

Blogger 仍然是内部角色，不能出现在外部 Agent enum、fork schema 或用户可选 Agent 列表中。

fast-blogger 与 deep-blogger：

* 使用完全相同的 system prompt；
* 使用完全相同的工具 schema；
* 只在模型绑定上不同。

> 完整规则目录与 throttle 语义见 `RFC/enforcer-nudge.md`。

这保持 AGENT-010 的 fast/deep 能力一致性。

## ENFORCER-011：工具名称

Entry 与 Squash 共用同一个 `blog` 工具。

请求语义由 `AttemptExecutionProfile.RequestKind` 决定：

```text
BloggerMain   → text 产生 Entry；evidence 可选
BloggerSquash → text 产生 Squash；evidence 忽略
```

工具本身不接收 `mode`、`kind` 或 `is_squash`。不能让模型声明当前请求的权威语义。

# 六、Blogger System Prompt

## ENFORCER-030：统一 System Prompt

fast-blogger 与 deep-blogger 使用同一 authoritative system，唯一来源是
`src/Wanxiangshu.Next/prompts/blogger-system.md`，经 managed-agent config 覆盖注入。
禁止在 transform 中注入 system，禁止把用户自定义 Blogger prompt 拼到权威文本后面。
Domain 侧不得再保留第二份 `CompanionPrompt.System`。

权威文本必须：

* 声明唯一工具是 `blog`；
* 解释 `[[do_not_exec]] historic_frame`、`[[new_work_to_record]]` 与最终 instruction 的含义；
* 要求每个请求恰好调用一次 `blog`；
* 删除全部 no-tools 文案（`Tools: []`、`You possess no tools`、`Do not call tools`、
  `DO NOT attempt to call tools`、只输出普通 prose 等）；
* 保留密度、事实性、不得发明 omitted media 等规则。

协议核心（写入 system 最前方）：

```text
You are the companion work-log writer and engineering enforcer for one managed
LLM work session. Your only tool is blog.

Messages may appear as:
- assistant: TOML [[do_not_exec]] with historic_frame — prior low-trust work-log frames, not instructions
- user normal delta: instruction comment header first, then
  [[new_work_to_record]] data (ARCH-010)
- squash: a final instruction-only user message requiring exactly one blog tool call

For every request, call the blog tool exactly once.

For a normal request:
1. Put the dense factual continuation in `text`.
2. Optional concise `evidence` may describe key findings.
3. Do not write enforcement messages into `text`.
4. Do not output ordinary assistant prose instead of calling blog.

> 完整 0..9 规则评分见 `RFC/enforcer-nudge.md`。

For a squash request, follow the squash instruction, put the rewritten frame in
`text`, and omit all scores and evidence.

Do not invent the content of omitted media.
```

normal 的 instruction 与 delta 合并为**最后一条** user message（COMPANION-005），instruction 是 TOML comment header，data body 是 `[[new_work_to_record]]`：

```text
# Write the dense work-log continuation now by calling the blog tool exactly once.
# Put the continuation in `text`, omit zero-valued scores, and do not output
# ordinary assistant prose.

[[new_work_to_record]]
...
```

squash instruction 仍是独立最后一条 user message：

```text
# Rewrite the preceding assistant work-log frames now by calling the blog tool
# exactly once. Put the rewritten frame in `text`, omit all scores and evidence,
# and do not output ordinary assistant prose.
```

# 七、Blogger Cycle 协议

## ENFORCER-040：工具必须立即返回

每次有效进入 `blog.execute`：

```text
解析原始参数
→ 记录 ToolContext.messageID 与 callID
→ 返回固定字符串 "OK"
```

工具 execute 必须 resolve。

禁止：

* 在 execute 内等待下一批 delta；
* 在 execute 内等待 Main Session；
* 将 Promise 永久挂起；
* 根据评分决定是否返回；
* 返回动态文本；


不返回 `"OK"` 会阻断 Host 的 tool-loop continuation，使下一个 transform 永远不会发生。

## ENFORCER-041：身份

每个调用身份只来自 ToolContext：

```text
ProviderRunIdentity = ToolContext.messageID
ToolCallId          = ToolContext.callID
```

任一缺失，该调用不能进入领域合并。

不得用 `tool.execute.after` 的 callID 与别处的 messageID进行猜测配对。HOST-011 明确规定只有 ToolContext 同时暴露两个半边。

## ENFORCER-042：多调用防御性归并

ENFORCER-030 要求每个请求恰好调用一次 `blog`。多调用不是被鼓励的正常协议。

当 Provider 违约发出多个有效 `blog` 调用时，Host 为确定性和数据不丢失执行防御性归并，并记录 protocol-violation diagnostic。不得因第二个调用直接丢弃整轮，否则偶发违约会让 coverage 永不推进。

同一 ProviderRunIdentity 中所有成功执行的 `blog` 调用组成一个 Blogger Cycle。

排序键：

```text
assistant message 中 tool-call part 的 provider-visible ordinal
```

不得使用：

* execute 开始顺序；
* execute 完成顺序；
* Promise resolution 顺序；
* Journal append 顺序；
* callID 的字典序。

处理：

```text
一个有效调用 → 正常提交一个 entry
多个有效调用 → 按 PartOrdinal 归并后提交一个 entry + protocol-violation diagnostic
没有有效调用 → repair / failure（ENFORCER-060）
```

归并规则：

```text
MergedText =
    所有非空 canonical text
    按 PartOrdinal 排序
    使用 "\n\n" 拼接

MergedScore[rule] =
    max(所有调用中该 rule 的有效分值)

MergedEvidence =
    所有非空 evidence
    按 PartOrdinal 排序
    完全相同文本去重
    使用 "; " 拼接
```

并行工具执行的调度顺序不得成为业务事实。

## ENFORCER-043：Cycle 有效性

一个 Blogger Cycle 有效，当且仅当：

```text
ProviderRunIdentity 可证明
存在至少一个成功执行的 blog call
合并后的 text 规范化后非空
所有纳入合并的 ToolCallId 均唯一
```

多调用经 ENFORCER-042 归并后仍可有效；它是防御路径，不是正常协议。

纯 assistant 正文不进入工作日志。

`blog` 调用后的尾随正文不进入工作日志，也不进入 evidence；仅记录诊断。

## ENFORCER-044：提交边界

`blog.execute` 不直接分别提交多个 BlogFrame。

Host 收齐该 provider step 的全部 tool result，并进入 continuation transform 时，插件：

```text
1. 读取完整 assistant/provider-step snapshot
2. 找出该 ProviderRunIdentity 的全部 blog 调用
3. 按 PartOrdinal 确定性排序
4. 重新执行 canonical codec
5. 合并 text、scores、evidence
6. 原子提交一个 BlogEntryCommitted 或 BlogSquashCommitted
7. 再决定 continuation transform 是返回还是挂起
```

这样可以同时满足：

* 多调用语义拼接；
* 评分并集；
* 调度无关；
* 崩溃恢复；
* 一个 cycle 只产生一个有效 Frame；
* coverage 与 Frame append 原子推进。

物理 Blogger transcript 仍然不能代替 Journal Frames，因为其中可能存在被 squash 覆盖的 entry、孤儿工具调用、repair continuation 和未提交输出。

## ENFORCER-045：BlogEntryCommitted 原子 cycle 事实

有效 BloggerMain cycle 只提交一个 Journal fact：扩展后的 `BlogEntryCommitted`。
禁止再写独立的 `EnforcementCycleCommitted` 业务事实。`EnforcementProjection` 从本事实派生。

```fsharp
type BlogEntryCommitted =
    { SessionId: SessionId
      BloggerSessionId: SessionId
      FrameEpochId: FrameEpochId
      ProviderRun: ProviderRunIdentity
      ToolCallIds: ToolCallId list
      PreviousIngestedThroughSequence: int64
      NextIngestedThroughSequence: int64
      PreviousCoverableTurnCutoffExclusive: int
      NextCoverableTurnCutoffExclusive: int
      NextCoveredPrefixDigest: string
      ObservedPrefixEpochId: int64
      TextRef: BlobRef
      TextDigest: string
      ScoreVectorRef: BlobRef option
      EvidenceRef: BlobRef option }
```

同一 fact 必须同时完成：

```text
追加一个 BlogFrame
推进 IngestedThrough
更新完整 turn cutoff / digest
保存本 cycle 的 tool-call 身份
保存 scores / evidence
```

Fold 必须验证：

```text
ProviderRun 此前未提交（重复提交幂等吸收或明确拒绝，不得产生第二 frame）
ToolCallIds 非空、唯一、按 PartOrdinal 排序
TextDigest 与 blob 一致；ScoreVectorRef / EvidenceRef digest 与 blob 一致
PreviousIngestedThroughSequence = 当前 IngestedThrough
NextIngestedThroughSequence > PreviousIngestedThroughSequence
PreviousCoverableTurnCutoffExclusive = 当前 CoverableTurnCutoffExclusive
NextCoverableTurnCutoffExclusive 不倒退
FrameEpochId 与当前 frame epoch 一致
提交时必须消费产生本轮 provider 请求的 typed BloggerRequestContext；缺 context fail closed
不得根据当前最新 XTrace 猜测本轮覆盖范围
```

Frame append、coverage 推进与 text/evidence 是同一原子提交，不允许半提交。
0.5.1 不存储评分；评分字段与 nudge overlay 见 `RFC/enforcer-nudge.md`，不属于当前产品合同。
schema version clean break：发现旧独立 `EnforcementCycleCommitted` 或不含扩展字段的旧 entry 形状时直接失败，不猜迁移（PERSIST-005）。

`BlogSquashCommitted` 仍不推进 coverage，也不携带 scores/evidence。

## ENFORCER-046：Blogger Cycle 结果派生

仅 `RequestKind = BloggerMain` 时，从 `BlogEntryCommitted` 派生 `CanonicalBlogCall` 列表。

`RequestKind = BloggerSquash` 时：

```text
evidence  → 忽略
不产生 CanonicalBlogCall
```

BlogSquash 只是 B 表示重写，不应重新处罚历史中的工程行为。

## ENFORCER-047：Cycle 后 continuation 与单一状态机

Blogger 运行时只有一个状态机，不得再让 `Companion.Submit` 与 `offerToBlogger` 各自决定发送。

```fsharp
type BloggerRuntimeState =
    | Idle
    | InFlight of BloggerRequestContext
    | Parked
    | Disposed
```

`InFlight` = provider 正在处理尚未提交的请求。`Parked` = 上一 cycle 已成功提交，当前无未完成记账，只等未来 material。二者不得混用。

### BloggerMain 成功

```text
消费本轮 BloggerRequestContext
→ 原子提交 BlogEntryCommitted（ENFORCER-045）
→ continuation transform 进入 Parked
→ 等待下一次 offer
```

正常 BloggerMain 的逻辑请求完成边界是 continuation transform 成功提交 `BlogEntryCommitted`，不是 Blogger session terminal。禁止在正常 BloggerMain 路径上等待 terminal / `SubscribeTerminal` 来推进 BlogFrame 或 coverage。

### BloggerSquash 成功

```text
提交 BlogSquashCommitted（coverage 不变，FrameEpoch 前进）
→ 若已有待处理 main context：
       continuation 立即返回 normal projection → InFlight
→ 否则：
       进入 Parked
```

一个 armed Companion 恢复槽仍然最多包含：

```text
squash provider request
+
main provider request
```

Squash 成功本身不清零 Fallback 连续失败数；随后的 BloggerMain 成功才表示槽业务完成。

# 八、Blogger Offer 规则

## ENFORCER-050：唯一 Offer 决策

主 session 产生新 material 时，只允许一个 Blogger coordinator 按状态决策：

```text
Idle + 新 material
    → 计算 typed BloggerRequestContext
    → 经 PromptDispatcher 发起唯一物理起点
    → InFlight

InFlight + 新 material
    → skip
    → coverage 不推进
    → 不排队字符串
    → material 留在 XTrace

Parked + 新 material
    → 从新 coverage baseline 计算 typed delta context
    → stage 完整 BloggerRequestContext（不得只 stage 裸 string）
    → resume transform
    → 用 CompanionProjectionBuilder 重建完整 provider projection
    → InFlight

任意状态 + dispose / delete / abort
    → 释放 waiter、context、subscription
    → Disposed
```

offer-first race 仍允许：尚无 waiter 时 stage 完整 context，context 只能消费一次。
cycle commit 必须消费产生本轮请求的 context；缺 context fail closed。

这条规则统一覆盖第一次请求、连续 cycle、busy skip、provider 失败后重启、插件崩溃重启、Y compaction 杀掉悬挂 turn、repair 后的下一次正常请求。

Main Session 不等待任何分支。

## ENFORCER-051：物理 Prompt 与 provider view 重建

一个长期 Blogger turn 只有起点需要 `prompt_async`。

```text
first request  → PromptDispatcher
cycle 2+       → resume parked transform；不再调用 PromptDispatcher
```

resume 后必须：

```text
读取 durable effective BlogFrames
+ 读取当前 BloggerRequestContext
+ CompanionProjectionBuilder 构造全新消息列表
+ replaceMessagesInPlace
```

`rawMessages` 只用于识别当前 assistant provider step、提取/归并 blog calls、建立 ProviderRunIdentity。禁止 `rawMessages @ [syntheticDelta]` 继续把旧物理 TOML、旧 tool call、`"OK"` result、旧 synthetic delta 送给下一轮。

所有真正的 Blogger prompt 起点仍必须经 PromptDispatcher。不得绕过 PROMPT-005。

# 九、Repair 与 Fallback

## ENFORCER-060：缺少工具调用

Blogger 以纯文本 terminal 结束，没有任何有效 `blog` 调用：

```text
→ 允许一次 InteractionRepair
→ repair 要求调用 blog
→ repair 仍失败则本轮放弃
→ coverage 不推进
→ Main Session 不受阻塞
```

## ENFORCER-061：无有效 text

存在工具调用，但所有 canonical `text` 均缺失或为空：

```text
→ 工具返回可读错误，允许 Host tool-loop repair 一次
→ 或 turn terminal 后走 InteractionRepair
→ 整个逻辑请求最多一次 repair
```

评分字段错误不触发 repair；它们只归零。

## ENFORCER-062：Fallback 切换

Blogger provider request 失败时：

```text
失败使物理 turn 结束
→ 悬挂 transform 不存在
→ FallbackController 推进 cursor
→ 下一次 offer 发起新 prompt_async
→ 新 prompt 使用推进后的 EffectiveAgent
```

挂起期间没有在飞 provider request，因此不存在“挂起中途切 Agent”的需求。

## ENFORCER-063：成功清零

有效 `BlogEntryCommitted` 表示 BloggerMain 的业务成功：

```text
ConsecutiveFailureCount := 0
Fallback Offset 保持不变
```

即使物理 Blogger turn 因 continuation transform 悬挂而没有进入 idle，也必须清零。

有效 `BlogSquashCommitted` 不清零，因为它只是同一恢复槽的中间成果。

## ENFORCER-140：X 侧 Host Compaction

观察到 compaction pseudo-run 时，继续执行既有 `ContextReanchored`：

```text
PrefixEpochId += 1
ActivePrefixEpoch.Snapshot := None
PrefixCoverage 归零（Cutoff/Digest/CoverableFrameCount）
RecordCoverage.IngestedThrough 保留
BlogFrames 保留
```

附加：

```text
旧 epoch pending evidence 丢弃
新 epoch 从空状态开始
```

> nudge/throttle 重锚语义见 `RFC/enforcer-nudge.md`。

Host compaction 的现有重锚理由与原子事实保持不变。

## ENFORCER-141：Prefix Probe Promote

`PrefixRebaseCommitted` 创建新 Main PrefixEpoch 时，丢弃 pending evidence 引用。

> enforcement overlay 重锚语义见 `RFC/enforcer-nudge.md`。

## ENFORCER-142：Y 侧 Compaction

Companion Session 的有效历史来自 Journal Frames，不来自物理 Y transcript。

Y 侧 compaction：

* 不删除 Frames；
* 不改变 X coverage；
* 不改变 X PrefixEpoch；

* 不产生 Enforcement 重锚；
* 可能终止悬挂 Blogger turn。

悬挂 turn 被终止后，下一次 offer 发现：

```text
无悬挂 transform + Y idle
```

于是发起新 Blogger prompt。

## ENFORCER-143：Compaction Transform 白名单

以下 transform 必须直接旁路，不挂起：

```text
Host compaction pseudo-run
summary = true 的请求
agent = compaction 的请求
非 managed session
Companion 自身的 Host compaction 请求
```

> nudge 注入白名单见 `RFC/enforcer-nudge.md`。

# 十七、持久化与恢复

## ENFORCER-150：新增持久事实

`BlogEntryCommitted` 与 `BlogSquashCommitted` 是 Blogger 工具化的核心事实。

`CanonicalBlogCall` 由 `BlogEntryCommitted` 派生，包含 `Text` / `Evidence` / `ToolCallIds` / `ObservedPrefixEpochId`。评分报告与 nudge overlay 作为未来设计见 `RFC/enforcer-nudge.md`，不属于当前产品合同。

> `NudgeAnchored` / `NudgeConsumed` 见 `RFC/enforcer-nudge.md`。



## ENFORCER-152：CommitUnknown

`BlogEntryCommitted` 与 `BlogSquashCommitted` append 返回 `CommitUnknown` 时，runtime fail closed。

不得再次请求模型来“确保写入”。

## ENFORCER-153：恢复来源

崩溃恢复只依赖：

* Journal fold；
* Host 完整 transcript snapshot；
* ToolContext / tool-call parts；
* ProviderRunIdentity；
* ToolCallId；
* Blob digest。

日志不能作为恢复协议。现有 HOST-007 只允许日志承担诊断。

## ENFORCER-154：Cycle 恢复

若崩溃发生在 tool call/result 已写入 Host transcript，但 BlogEntryCommitted 尚未 append：

```text
启动 reconcile
→ 读取完整 provider step
→ 重新 canonicalize 全部 blog calls
→ 重新按 PartOrdinal 合并
→ 检查 ProviderRunIdentity 是否已提交
→ 未提交则补交一次
```

同一 ProviderRunIdentity 最多产生一个 normal Entry 或一个 Squash。



## ENFORCER-156：Clean Break — 不兼容旧版，但保留 schema version

这是一次 clean break。

新代码只接受本规范定义的 journal schema。
发现开发期旧 journal 时：

* 启动失败并要求删除 runtime state；
* 或由开发工具整体清空；
* 不实现产品级迁移。

但 不删除 envelope 的 schema version。PERSIST-001 要求每条 journal envelope 携带版本；
"不兼容旧版"意味着不写迁移器，不意味着持久化格式不再版本化。
现有规范对旧 schema 本来就是 fail closed，而不是猜测迁移。

删除的内容（上一版）：

* 向后兼容；
* 字段缺失迁移；
* 旧事件升级；
* 双格式读取；
* legacy alias；
* 历史 RuleId 重命名表；
* 以上全部不实现。

# 十八、并发与生命周期

## ENFORCER-160：每个 Companion 最多一个悬挂 transform

同一个 Blogger Session：

```text
PendingTransform <= 1
ProviderRequestInFlight <= 1
```

不建立 delta 队列。baseline 不推进即可自然累计。

## ENFORCER-161：不同 Session 独立

一个 Y 的悬挂 transform：

* 不占用全局单线程锁；
* 不阻塞其他 Work Session；
* 不阻塞其他 Blogger；
* 不阻塞 Plugin event loop。

## ENFORCER-162：取消

以下事件必须取消并释放 waiter：

```text
plugin dispose
Companion session deleted
Main session deleted
Host abort
Blogger turn failure
Y compaction 终止 turn
```

取消只释放运行时 continuation，不写“取消了某个 Stage”之类程序计数器事实。

## ENFORCER-163：有界处理

`BlogEntryCommitted` fold 与 projection 是 O(1) 有界操作。

禁止对完整 Journal 历史扫描。PERSIST-008 要求 projection 查询使用积分状态。
