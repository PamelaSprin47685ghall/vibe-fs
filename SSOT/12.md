# SSOT/12 — 失败驱动的上下文恢复

条款 ID 前缀：`CTX-`

本文件规定万象术如何应对上下文耗尽。核心裁决：不预测，只恢复。 系统不观察容量、不估算余量、不分类失败；正常请求总是先直接执行，只有真实 provider attempt 失败后的恢复槽（CTX-006）才尝试上下文替换或压缩。

Companion 的结构、投影与身份在 SSOT/08。Session 种类与关联不变量在 HOST-008。槽的算术与 armed 判据在 FALLBACK-011、FALLBACK-012。事实的 fold 规则在 PERSIST-010。

## CTX-001：不观察上下文容量

万象术不得读取、查询、推导或缓存任何模型的上下文窗口大小。

禁止出现以下概念，无论名称如何拼写：

```text
contextWindow      maxContextTokens   remainingTokens
promptTokenEstimate contextRatio      headroom
nearLimit          shouldCompact      ensureCapacity
```

禁止依赖 tokenizer。禁止维护模型上下文表。禁止字节到 token 的换算。

管理员配置、模型元数据和 provider 返回值均不得改变本规则。

唯一允许的字节计量是 CTX-003 的输入合同，以及与文件大小、进程输出预算有关的既有合法计数（EXEC-011）。

## CTX-002：不主动预测溢出

Work Session 与 Companion Session 都不在请求前判断是否「接近上限」。

禁止：

```text
投影长度超过上下文的某个比例
剩余空间小于输出预算
Y frames 字节数超过阈值
累计 token 达到某个比例
按模型型号选择压缩点
```

正常请求总是先直接执行。真实失败是唯一恢复触发信号。

因此第一次真实溢出必然表现为一次失败。这是方案主动接受的代价，不是缺陷。

本条禁止的是插件对容量的测量与预测，不是对已发生事件的反应。 HOST-006 的重锚由 transcript 里出现的 compaction pseudo-run 触发——那是一个已经完成的外部物理事件，读它不等于估算余量。区分判据：触发输入是「还剩多少空间」则违反本条，是「发生了什么」则不违反。

## CTX-003：最低上下文环境合同

万象术支持的任意 LLM 必须满足：

> 在扣除固定 system prompt、工具 schema 和 provider 固定封装后，至少可以接收 200 KiB 的 provider-visible 动态输入。

```fsharp
module ContextContract =
    let BloggerDeltaLimitBytes = 200 * 1024
```

该常量是输入合同，不是上下文估算：不与模型窗口比较，不计算比例，不随模型变化，不触发主动 squash。它只约束单次送往 Companion 的 TOML delta 大小。

限制作用于完成 TOML 渲染后的 UTF-8 字节数，不是渲染前字符串长度，也不是字符数。

delta 的 source 是 XTrace 中尚未被 `RecordCoverage` 覆盖的 suffix（COMPANION-007）。reasoning 保留：decision-relevant host-visible reasoning 进入 delta；hidden reasoning 不抓取、不推断。

## CTX-004：输出预算属于 provider

假设所有受支持 LLM 均由 provider 强制实施有效输出预算。插件不计算 squash 输出应占多少 token，也不检查输出是否满足某个压缩比例。

插件只检查通用语义有效性：

```text
isValidTerminal = 非空 且 不是 XML-only terminal
```

该谓词是唯一的内容级校验，属主唯一（FALLBACK-008）。它检查成功产物的有效性，不检查 provider 错误，与供应商无关。

输出没有缩短到足够程度时，后续请求可能继续失败，并自然进入下一轮恢复槽。插件不预判。

## CTX-005：失败不分类

业务控制流只观察完整 Host snapshot（HOST-004）的 `Outcome`：

```text
Completed | Failed | Aborted
```

不得根据错误文字区分上下文溢出、网络故障、限流、服务端错误、模型内部错误或请求格式错误。

系统对所有 `Failed` / `Aborted` attempt 执行同一恢复协议，不判断、不证明、不记录失败根因。

「溢出」只允许出现在诊断日志和人类解释中，不得进入 Journal 字段、Fallback 判定、probe 判定、squash 判定或 projection 选择。

禁止维护任何 provider 错误模式表。provider 更换后，恢复代码不需要修改。

Host 提供的错误类型名同样不得用于分类。 `HOST-006` 的预防层使溢出以 `finish = "error"` 加 `status = idle` 的形式落地，reconcile 从完整 snapshot 读到的就是 `Failed`——这正是本条要求的形态。读取 Host 侧的 `ContextOverflowError` 这一名字来推断根因，与读错误文字等价，同样禁止。

同理，Host compaction 的来源不分类。 用户手动 `/compact` 与 Host 意外触发走完全相同的处置（HOST-006 收容层）：观察面相同、正确处置相同，分类只会长出永不执行的分支。`ContextReanchored` 因此只携带「哪条消息证明它发生了」，不携带「它为什么发生」。

## CTX-006：恢复槽的两种动作

恢复槽必须同时满足三个条件，缺一不可：

```text
armed        本槽由本次序列内紧邻的真实失败推进而来（FALLBACK-012）
primed       Offset 为奇数，即 A′ / B′（FALLBACK-012）
hasMaterial  确有可用材料：比已提交 epoch 更新的候选（CTX-011），
             或至少一个可 squash 的 frame（CTX-012）
```

满足三者的槽按 Session 种类执行不同的恢复动作：

| Session | 恢复动作 | 额外 LLM 调用 |
|---------|---------|--------------|
| Work Session（X） | 用已提交的 Companion 工作日志替换原始历史前缀（prefix probe） | 无 |
| Companion Session（Y） | 对现有 BlogFrame 前半段发起 squash 请求 | 有，一次 |

两者语义不同：

| 行为 | X prefix probe | Y frame squash |
|------|---------------|----------------|
| 是否额外调用 LLM | 否 | 是 |
| 是否先永久提交 | 否 | 有效后立即提交 |
| 主请求失败后是否保留 | 否 | 是 |
| 失败后是否回滚 | 不需要，从未提交 | 不回滚 |
| 作用对象 | X 原始历史 | Y BlogFrame |

恢复槽是「有机会恢复的槽」，不是「必然压缩的槽」。 armed 且 primed 但无可用材料时直接发出正常主请求，不构造空 probe（CTX-011）——这是正常状态，不是错误。

## CTX-007：Attempt 三结局按 RequestKind 分派

每个 attempt 只有三种结局，全部来自 reconcile 快照的 `Outcome` 与 `isValidTerminal`，不解析 provider 错误文本。动作按 `RequestKind`（PROMPT-008）区分：

| RequestKind | 结果 | 动作 |
|-------------|------|------|
| `BloggerSquash` | Completed + valid | 提交 squash；Offset、count 均不变；继续主请求 |
| `BloggerSquash` | Failed / Aborted | 当前槽失败；Offset+1，count+1；不发主请求 |
| `BloggerMain` | Completed + valid | 提交 entry；count 清零；Offset 不动；槽结束 |
| `WorkMain` + probe | Completed + valid | 提交 X 结果并 promote probe；count 清零；槽结束 |
| 任意主请求 | Failed / Aborted | 当前槽失败；Offset+1，count+1 |
| 任意生成请求 | Completed + invalid | 最多一次 repair（FALLBACK-008）；仍无效则放弃本轮生产物，不推进 cursor |

repair attempt 必须携带原 attempt 的相同候选身份（`ProbeId` 或 covered frame descriptor），否则不得用其结果提交事实。

## CTX-008：恢复槽的失败计数

`ConsecutiveFailureCount` 统计失败的恢复槽，不统计物理 attempt 数（FALLBACK-010、FALLBACK-011）。

一个 armed Companion 槽最多有两个物理 request（squash + main），但只产生至多一次 `FallbackCursorAdvanced`，其 `ProviderRunIdentity` 指向使该槽终止失败的那个 attempt。

squash 成功不清零 count：它不是 Logical Run 的业务完成。

## CTX-009：X 不发压缩请求

Work Session 不得为缩短自身上下文而发起任何摘要、压缩或重构 LLM 请求。

X 的恢复操作只能是：

> 使用已由 Companion 成功提交、并能证明覆盖 X 历史前缀的工作日志，替换对应的 X 原始前缀。

该替换是本地 projection 变换，不增加网络往返。

「零延迟压缩」准确指 X 不产生额外的压缩模型调用。 正常主请求本身仍有 provider 延迟，不得宣称本方案提高每轮 KV-cache 命中率——新 response 首次被搬到历史 frame 位置时可能需要重新 prefill。真实收益是删除历史 delta，使 Companion 上下文的长期增长从 Σ(delta)+Σ(response) 降为 Σ(response)。

## CTX-010：X 前缀替换是 attempt-local probe

在恢复槽（CTX-006）中使用 Companion 工作日志替换原始前缀时，不立即修改 `ActivePrefixEpoch`。候选替换只对当前 provider attempt 有效。

```fsharp
type PrefixProbe =
    { ProbeId: string
      BasedOnEpochId: int64
      Candidate: PrefixSnapshot }

type XProjectionChoice =
    | UseCommittedEpoch of ActivePrefixEpoch
    | UsePrefixProbe of PrefixProbe
```

`PrefixProbe` 不是 Session 当前状态，必须作为不可变 `AttemptExecutionProfile` 的一部分（PROMPT-008），不得从 mutable session cache 临时读取。

```text
probe attempt 成功 → 候选永久提升为 ActivePrefixEpoch
probe attempt 失败 → 候选丢弃，后续非 probe 槽使用旧 ActivePrefixEpoch
```

不得采用「先提交，再回滚」。 因此不存在 `PrefixProbeRolledBack`、`PrefixProbeCleared`、`PrefixProbeRejected`、`RestoreOldEpoch`——失败的 probe 从未成为领域事实（PERSIST-010）。

probe 成功只是经验判据，不是失败根因的逻辑证明。 瞬时网络故障可能恰好在 probe 请求时消失，造成一次不必要但合法的有损 rebase。这是方案主动接受的取舍。

反之，probe 失败也不代表另一侧 Agent 用同一候选会失败：`A′` 失败后的 `B′` 允许重新构造并使用等价候选。`A′` 失败只说明「SelectedAgent + 该候选」未解决问题。

Probe projection 形状：

```text
[system: X 固定 system prompt]
[user: synthetic companion memory（低信任标记，COMPANION-010）]
[raw X messages after Candidate.CutoffExclusive]
[current physical user message，最后]
>>> assistant
```

原始 Host transcript 永远不物理删除。被覆盖的历史只是不再进入后续 provider projection。

Host compaction 是这一保证的唯一例外来源，且不在插件控制内。 它写入一条 summary 消息，随后 Host 在读取时过滤掉摘要之前的历史，使 `CutoffExclusive` 所用的编号作废。处置见 HOST-006 的收容层：退役 epoch、归零 PrefixCoverage、保留 Frames 与 RecordCoverage，probe 能力在后续轮次自然恢复。若 `compaction.prune` 被开启，消息行会被真正删除，那已超出恢复范围——因此它进入 HOST-006 的必须关闭清单。

## CTX-011：覆盖游标与候选选择

Companion 的消化位置不能只有 message index，因为大消息可能按 part 拆成多个 chunk。

```fsharp
type SemanticCursor =
    { TurnIndex: int
      PartIndex: int }

type RecordCoverage =
    { IngestedThrough: SemanticCursor }          // 决定 LWR gap 起点；可落在 turn 中间

type PrefixCoverage =
    { HostEpochId: int64
      CutoffExclusive: int
      CoveredPrefixDigest: string
      CoverableFrameCount: int }
```

`RecordCoverage.IngestedThrough` 是实际已消化到的 part；`PrefixCoverage.CutoffExclusive` 是已完整消化的最后一个 semantic turn 边界；`CoveredPrefixDigest` 是 X 在该边界的 canonical digest。两种 coverage 是不同类型（COMPANION-003），禁止互算。

LWR gap 从 `RecordCoverage.IngestedThrough` 开始；probe 只使用 `PrefixCoverage` 与对应的 `CoverableRecordPrefix`（Opening + 可证明覆盖完整 turn 的 Y frame prefix），不得使用超前于 cutoff 的 frames，不得使用 RawGap。不得用只消化了一半的 turn 替换 X 前缀。

候选选择：

```text
1. candidateCutoff = min(CutoffExclusive, 本次请求开始前的最大安全 cutoff)

2. snapshot identity 至少含 CutoffExclusive、CoveredPrefixDigest、FrozenRecordPrefixDigest
   cutoff < committed cutoff        → 禁止，覆盖范围不得倒退
   cutoff > committed cutoff        → 允许
   cutoff 相同、FrozenRecordPrefixDigest 不同 → 允许（squash 让 B 更紧凑）
   两者均相同                        → 无新候选

3. candidateCutoff 必须位于完整 semantic turn 边界

4. 从当前 X semantic projection 重算 hash(messages[0..candidateCutoff])

5. 结果必须等于 Companion 保存的 CoveredPrefixDigest；不等则 fail closed，不构造 probe

6. 将 CoverableRecordPrefix 精确物化为 frozen blob（Opening + coverable Y frame prefix；RawGap 不参与）

7. 计算 Candidate SealRoot 与 synthetic ID（COMPANION-013）

8. 将 PrefixProbe 写入本次 AttemptExecutionProfile

9. 使用 probe projection 发出当前槽主请求
```

没有新候选时：不创建空 probe，不重复提交同一 epoch，不等待 Companion，不强制同步，不发压缩请求。直接使用 committed epoch 发出正常主请求。

## CTX-012：提交语义

### X probe promote

只有完整 Host snapshot 满足 `Outcome = Completed` 且 `isValidTerminal` 才可 promote，产生唯一事实 `PrefixRebaseCommitted`（PERSIST-010）。

以下均不得 promote：`prompt_async` 返回、`accepted-*` receipt、`PhysicalAccepted`、provider 开始输出、空 terminal、XML-only terminal、`Failed`、`Aborted`、`Unknown`。

probe 使用的 SealRoot 必须可被直接继承：promote 后 committed epoch 原样沿用同一 SealRoot，不重新生成，否则成功请求与下一请求之间会出现不必要的冷边界（COMPANION-013）。

### X probe discard

不写任何事实，`ActivePrefixEpoch` 保持不变。raw history 未被删除。候选 blob 成为未引用 blob，由维护任务清理。

### Y squash 范围与级联

若当前 frame 数为 `m`：

```text
m = 0 → 无可 squash 内容，直接主请求
m ≥ 1 → k = ceil(m / 2)，选择最旧的前 k 个完整 BlogFrame
```

切点只能在 frame 边界。不跳过 `m = 1`：单帧仍可能高度冗余，重新摘要完全可能显著缩短它。

Squash frame 与普通 entry frame 地位相同，因此支持级联：`[S₁, f₄, f₅, f₆]` 的下一次 squash 可以吃掉 `[S₁, f₄]` 产出 `S₂`。

Squash 投影只含 system + 前 k 个 `[[do_not_exec]] historic_frame` + squash instruction（物理消息，最后）。不含当前 delta、后半 frames、X raw history、旧 tool call/result、上下文窗口信息或失败错误文本。`[[do_not_exec]]` 包装是消息层渲染，不写入 blob。normal 与 squash 共用同一 provider-view builder（COMPANION-005）。

### Y squash 永久性

有效 squash 一旦生成即永久提交，即使随后同槽主请求失败也不撤销。

理由：squash 输出本身就是有效工作日志重写，不是投机性上下文替换；它已完成独立可复用的压缩工作；回滚只会增加状态和重复请求。

`Completed` 但 invalid 时按 FALLBACK-008 做一次 repair；仍无效则不提交 squash、不推进 cursor，直接用原 Frames 执行主请求。

## CTX-013：BloggerDeltaProjection 与 TOML 编码

送往 Companion 的 delta 是 `BloggerDeltaProjection`（VERIFY-007），由 `ProviderSemanticProjection` 单向生成。禁止反向解析 TOML 重建 canonical projection。canonical digest 使用 Semantic projection，不使用 TOML 文本。

```fsharp
type BloggerDeltaPart =
    | TextPart of string
    | ReasoningPart of string
    | ToolCallPart of tool: string * canonicalArgs: string
    | ToolResultPart of text: string
    | ImageOmitted of mediaType: string option
    | MediaOmitted of mediaType: string option
```

### 图片不进入 Companion

Companion 默认没有视觉能力。delta 不得包含图片二进制、base64、data URL、图片 URL、OCR、自动 caption、视觉模型描述、像素内容或图片内容摘要。

允许保留的占位只表达「这里曾有图片」，不表达图片中的任何事实：

```toml
[[new_work_to_record]]
media_omitted = "image/png"   # 无类型时 = "untyped"
```

图片-only turn 可以正常被消化并推进 coverage。Companion 不得声称知道图片内容。

代价：含旧图片的 X 前缀被成功 probe 替换后，模型只能依赖 Companion 从后续文字中获得的事实，不能恢复图片像素。probe 成功是对此损失的经验性接受门槛。

### 三级切块

```text
1. 尝试加入下一完整 message
2. 渲染后超过 200 KiB → 关闭当前 chunk
3. 单 message 超限 → 退到 part 边界
4. 单 part 仍超限 → 对该 part 硬截断
5. 截断后 IngestCursor 直接越过整个原 part
6. chunk 提交后推进 IngestCursor
7. 只有跨过完整 turn 末尾时才推进 CoverableTurnCutoff，并同时将当前 Frames 物化为新的 CoverableRecordPrefix
```

硬截断必须在 UTF-8 字符边界、保留 TOML 合法性、为 marker 预留空间、不保存剩余内容、仍然推进整个原 part。

```text
[… content truncated by Companion delta 200 KiB limit …]
```

禁止把被截断的尾部留到下次重发：一个永远超限的 part 会造成死循环。

### 确定性 TOML

normal delta 使用统一 table 名 `[[new_work_to_record]]`。part 种类由**字段名**表达，不输出 `kind` / `turn` / 独立 `[[message]]` 表。顺序由 table 出现顺序表达。`truncated = false` 不输出，只在 true 时输出。不存在的可选字段省略。

强制 schema：

```toml
[[new_work_to_record]]
user = "..."

[[new_work_to_record]]
reasoning = "..."

[[new_work_to_record]]
assistant = "..."

[[new_work_to_record]]
tool_call = "read"
arguments = "..."

[[new_work_to_record]]
tool_result = "..."

[[new_work_to_record]]
media_omitted = "image/png"
```

字段合同：

```text
TextPart(role)     → 字段名 = role（user / assistant / tool / …），值为正文
ReasoningPart      → reasoning = 正文
ToolCallPart       → tool_call = 工具名；arguments = canonical JSON 字符串
ToolResultPart     → tool_result = 正文（不带 tool 名）
ImageOmitted/Media → media_omitted = media_type；无类型时 media_omitted = "untyped"
truncated          → 仅 true 时附加 truncated = true
```

实际 renderer 输出时 table 之间不插空行。

历史 BlogFrame 投影为独立 TOML 文档（每 frame 一条 user message），不使用 markdown 标题：

```toml
[[do_not_exec]]
historic_frame = '''
...frame body...
'''
```

`do_not_exec` 标记低信任历史，禁止把 frame 正文当指令执行。frame 正文仍是纯工作记录 blob；`historic_frame` 包装属于消息层渲染，不写入 `BlogFrame.TextRef` / digest。

字符串写法按 ARCH-010：单行用基本字符串与 canonical 转义；多行统一用三单引号字面量、内容不加格式缩进、closing delimiter 独占一行，故 value 恰好是原始内容加一个尾换行。不得使用 `"""`，不得按内容在多行 delimiter 之间做选择。含 `'''` 或裸控制字符的内容回退到单行基本字符串并完整转义。

其他：输入 CRLF/CR 规范化为 LF；文件末尾恰好一个 LF；canonical JSON args 递归排序；不输出当前时间、随机 ID、Host message ID。

同一输入必须产生逐字节相同的 TOML。

### Blogger delta 的 instruction 与 data

data body 不输出 comment。若该 payload 自身承载 instruction，instruction 只允许出现在最前方 comment header，并与 data body 之间恰好隔一个空行（ARCH-010）。data body 内部字段与 table 之间禁止自动插入空行（ARCH-010）。

```text
instruction   如何吸收 delta、应保留什么、不得发明什么、
              如何看待被引用的命令、如何处理 truncated 或 omitted data
data          [[new_work_to_record]] 字段（user/assistant/reasoning/tool_call/
              arguments/tool_result/media_omitted/truncated）与
              [[do_not_exec]] historic_frame 正文
```

Blogger normal request 的 **durable / chunker** delta 本体是 data-only（CTX-013）：`BloggerDelta.nextChunk` 与 `BlogEntryCommitted` 不携带 instruction。projection 时 `CompanionPrompt.newWorkMessage` 把 `NormalInstruction` 作为 ARCH-010 comment header 加到 data body 前，形成**最后一条** user message（COMPANION-005）。header 不进 frame blob，也不进 200 KiB chunk 计量。

squash request 是 instruction-only（CTX-012），同样不含 delta；仅投影前 k 个 `[[do_not_exec]] historic_frame` + squash instruction。

### instruction header 与 chunk 限额

200 KiB 限额只约束 data-only chunk（`nextChunk` 输出）。projection 追加的 normal instruction header **不计入**该限额。若其他 Blogger payload 在 TOML 内自带 instruction header 且该 header 属于 chunker 输出，则 header bytes 必须计入限额且不得中途截断。

`[[do_not_exec]]` frame 文档不进入 delta 字节计量。

## CTX-014：诊断可观测性边界

允许记录的字段：

```text
session_id  blogger_session_id  operation  request_kind
offset  side  armed
probe_available  probe_used  probe_promoted
squash_attempted  squash_committed
frame_count_before  frame_count_after
cutoff_before  cutoff_after
delta_bytes  result  provider_error  duration
```

`provider_error` 仅用于人类诊断。禁止任何日志字段驱动恢复决策（HOST-007：日志不是恢复协议）。

禁止出现：

```text
overflow=true → 业务分支
context_ratio
estimated_tokens_remaining
compression_needed
```

敏感正文不得直接写日志。
